## 2. 背景

在时序数据库（Time-Series Database, TSDB）的应用场景中，获取某个时间序列的最新状态（即最后一条记录或特定列的最新值）是一个极高频的操作。例如，在物联网监控大屏、实时告警系统以及设备状态追踪中，用户往往需要频繁执行 `last` 或 `last_row` 函数查询，以获取设备的实时读数。
当前 TDengine 的存储引擎在处理此类查询时，虽然已经针对时序数据进行了优化，但在高并发或海量数据写入的场景下，频繁地从磁盘或内存的 MemTable 中检索最新数据仍然会消耗显著的 I/O 资源和 CPU 计算能力，导致查询延迟增加，影响实时业务的响应速度。
为了进一步提升系统性能，降低查询延迟，本设计方案旨在为存储引擎引入针对 `last` 和 `last_row` 结果的专用缓存机制。通过在内存中维护每个时间序列的最新数据快照，并随写入实时更新，系统可以直接从缓存中返回查询结果，从而避免昂贵的底层存储扫描操作。预期该优化将显著提升最新值查询的吞吐量（QPS），并大幅降低查询响应时间（Latency）。

## 3. 定义

| **术语** | **定义** |
| --- | --- |
| **Last Cache** | 针对时序数据表最新状态的缓存机制，专门用于加速 `last` 和 `last_row` 函数的查询。 |
| **MemTable** | 内存表，TDengine 存储引擎中用于暂存新写入数据的内存结构，数据在落盘前存储于此。 |
| **Last/Last_row** | TDengine 中的聚合函数。`last` 返回某列的最新非空值，`last_row` 返回时间戳最大的那一行数据。 |
| **VNode** | 虚拟节点（Virtual Node），TDengine 中存储和计算的基本单元，负责管理一部分表的数据。 |
| **VGroup** | 虚拟组（Virtual Group），由一个或多个 VNode 组成，用于保证数据的高可用性。 |
| **WAL** | Write Ahead Log，预写日志，用于保证数据在系统崩溃后的持久性和一致性。 |
| **TSDB** | Time-Series Database，时序数据库，专门用于存储和处理随时间变化的数据的数据库系统。 |
| **QPS** | Queries Per Second，每秒查询率，衡量系统吞吐量的指标。 |
| **Latency** | 延迟，指从发送请求到接收到响应所需的时间，衡量系统响应速度的指标。 |
| **OOM** | Out of Memory，内存溢出，指系统内存不足以满足分配请求的状态。 |
| **Warm-up** | 预热，指系统启动后，将数据加载到缓存中以达到最佳性能状态的过程。 |

## 4. 行为说明

### 4.1 缓存配置

TDengine TSDB 的时序数据缓存是通过数据库的配置参数进行控制的。用户可以通过创建或修改数据库时指定缓存参数，以满足不同的性能需求。

#### 4.1.1 缓存参数配置

用户在创建数据库时可通过下表中的参数控制数时序数据缓存的相关属性：

| 参数名 | 类型 | 取值范围 | 默认值 | 描述 |
| --- | --- | --- | --- | --- |
| CACHEMODEL | string | NONE|LAST_ROW|LAST_VALUE|BOTH | NONE | 缓存模型类型。 |
| CACHESIZE | int | [1, 65536] | 1 | 缓存大小，单位为 MB。 |

下面是一个创建数据库时指定缓存参数的示例：
```sql
CREATE DATABASE mydb
  CACHEMODEL='BOTH'
  CACHESIZE=16;
```

参数说明：
- `CACHEMODEL`：指定缓存的类型。
  - `NONE` 表示不启用缓存。
  - `LAST_ROW` 表示仅缓存每张表的最后（时间戳最大）一条行数据结果。开启此选项后，`last_row` 查询将直接从缓存中获取结果，而无需扫描底层存储，从而显著提升查询性能。
  - `LAST_VALUE` 表示仅缓存每张表每一列的最近的非 `NULL` 值结果。开启此选项后，`last` 查询将直接从缓存中获取结果，避免了对底层存储的扫描操作，提高了查询效率。
  - `BOTH` 表示同时缓存 `last_row` 和 `last` 两者的结果。
- `CACHESIZE`：指定每个 `VNode` 中缓存的总大小，单位为 MB。

#### 4.1.2 缓存参数修改

用户可以通过 `ALTER DATABASE` 语句修改已有数据库的缓存参数。例如：
```sql
ALTER DATABASE mydb
  SET CACHEMODEL='LAST_ROW',
      CACHESIZE=32;
```

注：`CACHE_MODEL` 参数切换可能导致 last/last_row 缓存的重建，可能会引起短暂的性能波动以及查询结果的不准确，不建议频繁切换。

### 4.2 缓存更新逻辑

缓存的更新主要发生在数据写入阶段。当新数据写入到 VNode 时，系统会检查当前数据库的 `CACHEMODEL` 配置，并根据配置决定是否更新缓存。
1. **写入触发**：当客户端向 TDengine 写入数据时，数据首先进入 WAL（Write Ahead Log）和 MemTable。在此过程中，存储引擎会同步尝试更新 Last Cache。
2. **时间戳比较**： 对于每一行新写入的数据，系统会将其时间戳与缓存中对应表已有的时间戳进行比较：
  - Last Row 更新：如果新写入数据的时间戳大于或等于缓存中记录的该表最大时间戳，则更新 `last_row` 缓存为当前新行数据。
  - Last Value 更新：对于每一列，如果新写入数据非 NULL 且时间戳大于或等于该列缓存值的对应时间戳，则更新该列的 `last` 缓存值。
1. **乱序数据处理**： 如果写入的数据是乱序的（即时间戳小于当前缓存中的时间戳），缓存更新逻辑会根据具体情况处理：
  - 对于 `last_row`，通常忽略旧数据，保持缓存中最新的行不变。
  - 对于 `last` value，如果新写入的数据填补了之前的 NULL 值且时间戳逻辑允许（具体依赖于实现细节，通常只关注最新时间点），则可能触发更新，但在高性能模式下，通常只维护时间戳严格递增的更新以保证写入性能。
1. **数据删除处理**： 当数据被删除时（例如通过 `DELETE` 语句），如果删除的数据包含在缓存中，系统需要检查并更新缓存：
  - 对于 `last_row`，如果删除的行是缓存中的最后一行，则需要清理缓存或重新扫描以找到新的最后一行进行更新。
  - 对于 `last` value，如果删除的值是缓存中的最新值，则需要清理该列缓存，或重新扫描以找到新的最新非 NULL 值进行更新。
1. **持久化与恢复**： 虽然 Last Cache 主要驻留在内存中，但在系统重启时，需要从 WAL 或数据文件中重建缓存，以确保缓存数据的一致性。

### 4.3 查询优化

当应用程序执行查询操作时，查询优化器会分析 SQL 语句以确定是否可以利用 Last Cache 加速查询。
1. **查询路由**：
  - 如果查询语句仅包含 `last_row` 函数（例如 `SELECT last_row(*) FROM table`），且数据库配置了 `CACHEMODEL='LAST_ROW'` 或 `'BOTH'`，查询引擎将尝试直接从缓存中读取结果。
  - 如果查询语句仅包含 `last` 函数（例如 `SELECT last(col1), last(col2) FROM table`），且数据库配置了 `CACHEMODEL='LAST_VALUE'` 或 `'BOTH'`，查询引擎将尝试直接从缓存中读取结果。
1. **缓存命中**：
  - 若缓存中存在对应表或列的数据，系统将直接返回内存中的缓存值。
  - 此过程完全绕过了对底层数据文件（Data Files）和 MemTable 的扫描，极大地减少了 CPU 消耗和磁盘 I/O，从而实现微秒级的查询响应。
1. **缓存未命中与回退**：
  - 如果缓存尚未建立（例如系统刚启动且未预热），或者查询涉及缓存中未包含的数据（例如请求了未缓存的列），查询引擎将自动回退到标准的存储引擎查询路径。
  - 此时，系统会照常扫描 MemTable 和磁盘文件以获取正确结果，确保查询结果的准确性。

## 5. 性能

引入 Last Cache 机制后，预期在以下方面产生显著的性能提升：

| **性能指标** | **预期变化** | **详细说明** |
| --- | --- | --- |
| **查询延迟 (Latency)** | **显著降低** | 由于直接从内存缓存中读取数据，避免了磁盘 I/O 和复杂的 MemTable 扫描，查询响应时间预期将从毫秒级（甚至更高）降低至微秒级。在高并发场景下，能显著提升用户体验。 |
| **系统吞吐量 (QPS)** | **大幅提升** | 查询处理路径大幅缩短，单个查询消耗的 CPU 和内存资源显著减少。系统可在相同硬件资源下处理更多并发请求，从而提升整体吞吐量。 |
| **资源消耗** | **显著减少** | I/O 减少：减少了对底层数据文件的读取，降低磁盘 I/O 压力。 CPU 降低：减少了数据解压、解码和聚合计算的 CPU 开销。 |
| **系统启动性能** | **略有增加** | 在系统启动或 VNode 加载阶段，为了构建 Last Cache，系统需扫描 WAL 或部分数据文件。这会产生额外开销，可能导致节点启动时间或预热（Warm-up）时间略有增加。 |
| **系统退出性能** | **无显著影响** | 系统退出时仅需释放内存资源，对退出性能无显著负面影响。 |

**性能权衡（Trade-off）**：
- **内存占用**：开启缓存会占用额外的内存空间（由 `CACHESIZE` 控制）。在内存资源紧张的环境下，需要合理配置缓存大小，避免影响系统整体稳定性。
- **写入开销**：虽然缓存更新是在内存中进行的，极其迅速，但理论上会增加微小的写入路径开销（用于更新缓存结构）。然而，相比于查询性能的巨大提升，这一开销通常可以忽略不计。

## 6. 安全

本特性主要涉及内存中的数据缓存，不涉及新的网络接口或外部交互协议，因此主要关注数据访问控制和内存安全。
1. **数据访问控制（Confidentiality）**：
   - Last Cache 中的数据完全遵循 TDengine 现有的用户权限体系。
   - 当用户执行 `last` 或 `last_row` 查询时，系统会首先进行标准的权限验证（Authentication & Authorization）。只有拥有对应表读取权限的用户，才能从缓存中获取数据。
   - 缓存机制对用户是透明的，不会绕过任何现有的安全检查。
2. **数据完整性（Integrity）**：
   - 缓存数据来源于经过验证的写入流程（WAL 和 MemTable），确保缓存内容与底层存储的一致性。
   - 在并发写入场景下，通过内部锁机制或原子操作保证缓存更新的原子性，防止出现脏读或数据损坏。
3. **可用性（Availability）**：
   - **内存保护**：通过 `CACHESIZE` 参数严格限制缓存占用的最大内存，防止因缓存无限增长导致系统 OOM（Out of Memory）崩溃，从而保障数据库服务的稳定性。
   - **故障恢复**：若节点发生故障重启，缓存将从持久化的 WAL 或数据文件中重建，确保服务恢复后数据的准确性和可用性。
4. **内存数据安全**：
   - 缓存数据驻留在服务器内存中。对于对数据敏感性极高的场景，建议确保存储服务器的物理安全及操作系统层面的访问控制，防止通过内存 dump 等手段窃取数据。

## 7. 兼容性

本特性为新增的性能优化功能，完全向后兼容。
1. **功能兼容性**：
   - 默认情况下，`CACHEMODEL` 为 `NONE`，即不开启缓存。此时系统的行为与旧版本完全一致，不会对现有业务产生任何影响。
   - 开启缓存后，`last` 和 `last_row` 函数的语义和返回结果保持不变，仅查询性能发生变化。
2. **数据兼容性**：
   - 本特性不改变底层数据文件的存储格式。
   - 升级到支持本特性的版本后，旧版本写入的数据依然可以正常读取和查询。
3. **客户端兼容性**：
   - 客户端无需修改任何代码或驱动即可受益于此优化（前提是服务端开启了配置）。
   - 现有的 SQL 查询语句无需做任何调整。
因此，本特性对旧有行为无破坏性更改。

## 8. 运维

### 8.1 监控指标

为了确保 Last Cache 正常运行并评估其效果，系统应提供相关的监控指标。建议通过 TDengine 的系统监控机制（如 `log_metrics` 或系统表）输出以下关键指标：
1. **Cache Memory Usage**：当前 Last Cache 实际占用的内存大小。运维人员需关注此指标是否接近配置的 `CACHESIZE` 上限。
2. **Cache Hit Rate**：缓存命中率。计算公式为 `Hits / (Hits + Misses)`。高命中率表明缓存配置有效；低命中率可能意味着 `CACHESIZE` 过小或查询模式不匹配。
3. **Cache Hits/Misses**：具体的命中次数和未命中次数计数，用于量化缓存对查询负载的分担情况。

### 8.2 缓存容量评估与调整

修改数据库参数的命令虽然简单，但核心难点在于准确判断是否需要修改以及如何修改。运维人员可以通过以下步骤判断当前数据库的 `CACHESIZE` 是否满足需求：
1. **查看配置容量 (**`**cachesize**`**)**： 通过查询系统信息架构表，可以获取当前数据库配置的缓存大小上限（单位为 MB）。
```sql
SELECT name, cachesize FROM information_schema.ins_databases;
```

1. **查看实际负载 (**`**cacheload**`**)**： 通过查看特定数据库的 VGroup 信息，可以获取当前实际使用的缓存大小（单位为字节）。
```sql
SHOW <db_name>.vgroups;
```

输出结果中的 `cacheload` 列即为当前缓存的实际负载。
1. **判断与调整策略**：
   - **不足**：如果 `cacheload` 的数值非常接近 `cachesize`（需注意单位换算），则表明缓存空间可能不足，导致部分最新数据无法被缓存，从而影响查询性能。此时应考虑增加 `cachesize`。
   - **充足**：如果 `cacheload` 明显小于 `cachesize`，则说明当前缓存空间是够用的。
   - **调整建议**：具体修改值应根据系统整体可用内存情况决定。如果内存充裕且 `cacheload` 接近上限，可以尝试将 `cachesize` 加倍或提高数倍，以确保所有活跃时间序列的最新值都能驻留在内存中。

### 8.3 日志管理

系统日志（`taosd.log`）中应包含关于 Last Cache 的关键事件，以便于问题排查：
1. **启动/初始化**：记录缓存模块初始化成功及预分配的内存大小。
2. **配置变更**：当通过 `ALTER DATABASE` 修改缓存参数时，记录变更前后的参数值及生效状态。
3. **警告/错误**：
   - 内存分配失败（OOM 风险）。
   - 缓存更新过程中的异常情况。

### 8.4 运维操作建议

1. **模型优化**：定期审查业务查询模式。如果业务场景发生变化（例如不再频繁查询 `last_row`），可将 `CACHEMODEL` 调整为 `LAST_VALUE` 或 `NONE` 以节省内存资源。
2. **故障排查**：若怀疑查询结果异常（如缓存数据陈旧或不一致），可临时将 `CACHEMODEL` 设置为 `NONE` 禁用缓存，对比直接扫描存储引擎的查询结果。若结果不一致，应收集相关日志并联系技术支持进行排查。

## 9. 使用场景

本特性主要适用于对实时性要求极高、且频繁查询最新状态的业务场景。以下是典型的使用案例：

### 9.1 物联网设备实时监控大屏

在工业物联网（IIoT）或智能家居场景中，监控大屏通常需要展示成千上万个设备的实时状态（如当前温度、压力、运行状态等）。
1. **场景描述**：大屏每隔几秒刷新一次，对所有设备执行 `SELECT last_row(*) FROM devices GROUP BY device_id`。
2. **优化效果**：开启 `LAST_ROW` 缓存后，系统无需扫描海量历史数据，直接从内存返回每个设备的最新一条记录，确保大屏刷新流畅，无卡顿。

### 9.2 实时告警系统

告警系统需要持续监测特定指标是否超过阈值。
1. **场景描述**：告警引擎每秒轮询关键指标的最新值，例如 `SELECT last(voltage) FROM power_grid WHERE voltage > 220`。
2. **优化效果**：开启 `LAST_VALUE` 缓存后，告警检测的延迟大幅降低，能够更迅速地捕捉异常状态并触发告警，提升系统的响应速度和安全性。

### 9.3 车辆/物流轨迹追踪

在车联网或物流追踪系统中，需要实时获取车辆或货物的最新位置。
1. **场景描述**：用户在地图上查看车队位置，系统查询所有车辆的最新 GPS 坐标 `SELECT last(latitude), last(longitude) FROM vehicles GROUP BY vin`。
2. **优化效果**：利用缓存机制，即使车辆历史轨迹数据量巨大，获取当前位置的操作也能在微秒级完成，提供丝滑的用户体验。

### 9.4 金融行情快照

在金融交易场景中，获取最新的股票或期货价格是高频刚需。
1. **场景描述**：交易终端需要展示自选股的最新成交价 `SELECT last(price) FROM stocks WHERE symbol IN (...)`。
2. **优化效果**：通过缓存最新价格，系统能够支撑极高的并发查询请求（QPS），确保交易员看到的数据尽可能接近实时。

### 9.5 设备状态即时诊断

运维人员在排查故障时，往往需要查看设备当前的完整运行参数。
1. **场景描述**：运维人员针对特定故障设备执行 `SELECT last_row(*) FROM device_logs WHERE device_id = 'D1001'`。
2. **优化效果**：即使该设备积累了数亿条日志，缓存也能保证立即返回该设备的最后一条完整状态，帮助运维人员快速定位问题。

### 9.6 边缘计算节点资源受限场景

在边缘网关或嵌入式设备上运行 TDengine 时，CPU 和 I/O 资源非常有限。
1. **场景描述**：边缘应用需要频繁获取传感器最新值进行本地逻辑判断。
2. **优化效果**：开启缓存可以显著减少对 SD 卡或低速闪存的读写操作，降低 CPU 负载，从而在低功耗硬件上实现高性能的实时数据处理。

## 10. 约束和限制

1. **内存限制**：
  - Last Cache 完全依赖内存存储。如果配置的 `CACHESIZE` 不足，缓存将无法覆盖所有时间序列的最新数据，导致部分查询回退到磁盘扫描模式，性能无法达到最优。
  - 在 32 位系统或内存受限的环境中，需谨慎设置缓存大小，避免引发 OOM。
1. **数据一致性延迟**：
  - 虽然缓存更新在内存中是实时的，但在极端高并发写入或系统负载极高的情况下，查询结果可能存在微小的可见性延迟（通常在微秒级），但这符合最终一致性模型。
1. **不支持复杂过滤条件的加速**：
  - Last Cache 仅针对纯粹的 `last` 或 `last_row` 聚合查询（可带 `GROUP BY`）。如果查询语句中包含复杂的 `WHERE` 过滤条件（除了针对主键或时间戳的简单过滤），缓存机制可能无法直接命中，仍需扫描底层数据。
1. **冷启动预热**：
  - 系统重启后，缓存需要从 WAL 或数据文件中重建。在此期间（预热阶段），查询性能可能暂时低于峰值水平。
1. **乱序数据更新限制**：
  - 对于严重乱序的历史数据写入（即写入时间戳远小于当前缓存时间戳的数据），缓存通常不会更新（因为缓存只维护“最新”状态）。这意味着如果用户依赖乱序写入来修正历史上的“最新值”，缓存中的数据可能不会立即反映这一修正，直到缓存失效或重启。

## 11. 常见错误和排查

本特性主要涉及内部性能优化，用户直接交互较少，但在配置和资源管理方面可能遇到以下问题：

### 11.1. 常见错误提示

| **错误码/错误信息** | **可能原因** | **排查与解决方法** |
| --- | --- | --- |
| `**TSDB_CODE_OUT_OF_MEMORY**` | 配置的 `CACHESIZE` 过大，超过了物理内存限制或系统配置的内存配额。 | 1. 检查 `taosd.log` 中的内存分配错误日志。 2. 调小 `CACHESIZE` 参数。 3. 检查服务器物理内存使用情况。 |
| `**Database not configured for cache**` | 尝试在未开启缓存的数据库上强制使用缓存特性（如果存在此类调试指令）。 | 1. 确认数据库配置：`SHOW CREATE DATABASE <db_name>`。 2. 使用 `ALTER DATABASE` 开启缓存模型。 |
| **查询结果与预期不符（旧数据）** | 1. 缓存未及时更新（极罕见）。 2. 写入了乱序数据（时间戳小于当前缓存值）。 | 1. 确认写入数据的时间戳是否确实大于当前最新值。 2. 尝试重启 VNode 或将 `CACHEMODEL` 设为 `NONE` 后对比查询结果。 |

### 11.2. 故障排查指南

1. **缓存未生效（查询依然慢）**
   - **现象**：配置了 `CACHEMODEL`，但 `last`/`last_row` 查询延迟没有明显下降。
   - **排查步骤**：
      - 检查查询语句是否符合优化条件（仅包含 `last`/`last_row`，无复杂 `WHERE` 过滤）。
      - 检查 `CACHESIZE` 是否过小。使用 `SHOW <db_name>.vgroups` 查看 `cacheload` 是否已达到 `cachesize` 上限。如果已满，说明缓存发生驱逐或无法写入新数据，导致命中率下降。
      - 检查系统日志，确认缓存模块是否初始化成功。
2. **内存占用过高**
   - **现象**：`taosd` 进程内存占用持续飙升。
   - **排查步骤**：
      - 检查所有数据库的 `CACHESIZE` 总和是否合理。
      - 使用监控工具查看 `Cache Memory Usage` 指标。
      - 如果确认是缓存占用过多，需通过 `ALTER DATABASE` 减小 `CACHESIZE`。
3. **数据不一致**
   - **现象**：`last` 查询返回的结果与全表扫描结果不一致。
   - **排查步骤**：
      - 这是严重错误。首先临时关闭缓存（`ALTER DATABASE ... SET CACHEMODEL='NONE'`）以恢复业务准确性。
      - 保留现场日志（`taosd.log`），特别是关于 WAL replay 或 cache update 的错误信息。
      - 联系技术支持进行深入分析。

## 13. 安装和卸载

本特性作为 TDengine 存储引擎的内部优化功能，集成在标准的 TDengine Server 安装包中。
1. **安装要求**：
   - **无需额外组件**：本特性不需要安装任何额外的插件、库文件或第三方组件。
   - **版本检查**：安装脚本应确保用户安装的是包含此特性的 TDengine 版本（具体版本号需参考发布说明）。
   - **配置文件保留**：如果是覆盖安装或升级安装，安装脚本应默认保留用户原有的 `taos.cfg` 配置文件，以免丢失用户自定义的全局参数设置。虽然本特性主要通过 SQL 配置，但保持环境一致性对用户体验至关重要。
2. **卸载要求**：
   - **清理残留**：标准的卸载脚本（如 `rmtaos`）应能彻底清除程序文件。
   - **数据兼容性提示**：由于本特性不改变底层数据格式，卸载后若回退到旧版本（降级），只要旧版本支持读取当前的数据文件格式，理论上数据是兼容的。但卸载脚本通常不负责数据迁移，建议在卸载或降级前提示用户备份数据。
3. **升级/迁移注意事项**：
   - **平滑升级**：用户从旧版本升级到支持本特性的版本时，安装过程应平滑无感。升级完成后，用户即可通过 `ALTER DATABASE` 或 `CREATE DATABASE` 启用缓存功能，无需执行额外的数据迁移脚本。
   - **默认行为**：升级后，现有数据库的 `CACHEMODEL` 默认为 `NONE`，确保升级操作不会改变既有业务的行为和资源消耗，除非用户显式开启。
总结：本特性对安装和卸载过程无特殊的新增要求，遵循 TDengine 标准的安装/卸载流程即可。
