## 2. 引言

### 2.1 术语与缩写名词

**SMA: **Small Materialized Aggregates, 即物化的聚集或者预聚集。包含了一个数据块的预聚集的结果，通常包含最小值、最大值、和、NULL值等信息。
**TSMA: **Time-range Small Materialized Aggregates, 即基于时间范围的预聚集。包含了按照时间段范围切分的数据的预聚集结果，也包含诸如最小值、最大值、和、NULL值信息。与 SMA 的区别是包含的数据是按照时间段划分，不是按照数据块为单位生成聚合结果。
**RSMA**: Roll-up Small Materialized Aggregates，基于时间段的预聚集。只保留聚集后的结果作为降采样的时间序列数据，同时删除原始的时序数据。RSMA使用的预聚集只支持采用特定聚集函数对该时间段内数据进行了预聚集，不支持针对原始时序数据的乱序处理和时序数据更改操作。该时间段内时序数据写入完成即启动聚集计算过程。

## 3. 需求目标

在大数据量场景下, 经常需要查询某段时间内的汇总结果, 当历史数据变多或者时间范围变大时, 查询时间也会相应增加。通过预聚集的方式可以将计算结果提前计算并持久化完成, 后续查询可以直接读取聚集结果, 而不需要扫描原始数据, 如当前Block内的SMA信息。
Block内的SMA信息粒度较小, 若查询时间范围是日,月甚至年时, Block的数量将会很多, 因此TSMA支持用户指定时间窗口进行预聚集. 通过对固定时间窗口内的数据进行预计算， 并将计算结果存储下来， 查询时可以直接调用查询预计算结果以提高查询性能。
在某些应用场景下，由于原始时序数据规模过于庞大，边缘端无法存储采集的原始数据，同时无法将记录的时序数据全部传输会数据中心，为此需要在边缘侧及时存储降采样后的数据，预聚集模块针对这种应用场景，自动存储降采样后的数据。由于降采样后的数据规模仅为原始数据的十分之一或百分之一，可大幅减少磁盘空间占用；查询时直接扫描降采样数据，响应速度更快。降采样后的数据可以保留较长时间。
预聚集提供的功能，不直接面向客户，与索引功能类似，用于提升查询响应时间和查询性能。

## 4. 功能需求

预聚集功能需求如下表所示：

| 序号 | **功能类别** | **功能名称** | 功能描述 |
| --- | --- | --- | --- |
| 1 | 支持创建TSMA | 1.1 创建TSMA时支持指定函数列表 | 支持在创建TSMA时指定为那些列计算哪些聚集函数. 支持的函数至少包含: `min`, `max`, `sum`, `first`, `last`, `avg`, `count`. |
|  |  | 1.2 创建TSMA时支持指定聚集的窗口大小 | 在创建TSMA时支持指定窗口大小创建, 并按照指定窗口大小进行计算, 支持常用的窗口大小如小时, 天, 月, 年等. |
|  |  | 1.3 支持基于较小窗口创建较大窗口的TSMA, 即递归创建 | 若已经建好了一条TSMA, 那么可以基于此TSMA创建一条聚合窗口更大的TSMA, 在可用的情况下使用此TSMA的输出进行计算. |
|  |  | 1.4 需要支持在超级表和普通表上创建, 可不支持子表 |  |
|  |  | 1.5 支持配置参数: 最大可创建的TSMA个数. | 超出最大配置个数创建时明确报错. 递归创建的算多条TSMA. |
| 2 | 支持删除TSMA | 2.1 删除TSMA时, 删除元数据和计算结果信息. |  |
| 3 | 支持查看TSMA信息 | 3.1 支持SHOW TSMAs, SHOW CREATE TSMA语句查看tsma信息. | 信息包括TSMA名字, db名字, 创建的函数列表, 窗口大小等 |
|  |  | 3.2 支持在information_schema.ins_tsma表中查询tsma信息 |  |
| 4 | TSMA结果计算 | 4.1 创建TSMA时支持对历史数据计算 | 若表中已经存在大量历史数据, 则历史数据也需要计算 |
|  |  | 4.2 能够处理过期数据和删除数据 | 支持在写入过期数据和删除数据时更新计算结果 |
| 5. | TSMA查询 | 5.1 支持查询内部自动选择最优的查询策略. | 若查询中可以使用TSMA的计算结果, 则自动使用, 无需用户干预. 若无可用的TSMA, 则自动扫表计算. 如查询的函数并没有在定义的TSMA中包含. 若多条TSMA可用, 则应当选择窗口最大的TSMA计算. |
|  |  | 5.2 客户端支持配置参数强制不使用TSMA. | 当配置该参数时, 即便有可用的TSMA, 也不使用, 而是扫表计算. |
| 6. | 创建/删除RSMA | 6.1 创建RSMA，删除已存在的 RSMA | 在系统中创建RSMA，或删除已经创建并运行中的 RSMA |
| 7. | 查看RSMA | 7.1 检查系统中已经存在的 RSMA | 读取并显示系统中已经创建并运行中的全部 RSMA 信息 |
|  | 更改 RSMA | 7.2 更改 RSMA 创建信息 | 重新设置未指定 聚合函数的列，设置新的聚合函数用于生成降采样的结果。 |
| 8. | 查询有RSMA 关联的超级表 | 查询具有关联RSMA 的超级表 | 查询引擎识别并读取相应的数据，执行查询并返回结果 |

## 5. 性能需求

在大部分场景下使用TSMA的计算结果查询时, 性能显著优于扫表计算结果。
使用 RSMA 计算的场景下，查询性能显著优于针对原始表的查询。
如超级表meters, 包含10万张子表, 每张表内大约10万行, 数据采集间隔大约2s, 那么每张表包含大约13个小时的数据. 创建TSMA, 函数包括: `avg(c1), max(c2)`, INTERVAL为 1h, 那么每张表被聚集之后剩下大约13行数据. 查询sql如: `select avg(c1), max(c2) from meters`, 要求在使用TSMA查询时性能优于直接查询原始表数据的性能。

## 6. 安全需求

授权用户才在所属的数据库中创建、删除 TSMA/RSMA。针对目标表具备访问权限的用户才能够对指定（超级）表创建相应 TSMA 或 RSMA。
用户针对 TSMA/RSMA 创建、删除操作需要记录审计日志，以满足安全审计和核查的需求。
TSMA/RSMA 创建完成后形成的数据，存储在数据库中，其格式和内容受存储组件的保护。
此外，TSMA/RSMA 的安全控制与TDengine现有其他安全机制协同工作。TSMA 运行期间依托于系统提供的安全传输通道确保网络与传输安全，在从服务端传输到客户端的过程中，应与普通查询数据采用相同的加密信道进行保护，防止数据在传输中被窃听。RSMA 运行期间在虚拟节点所在的物理机运行，不涉及跨节点的网络安全传输需求。

## 7. 第三方依赖需求

无，本模块不依赖任何第三方的库或源代码。

## 8. 其他需求

### 8.1 接口需求

1. 支持不使用TSMA查询配置参数.
2. 支持在 sql语句中采用 `hint` 方式指示不使用TSMA查询.
3. TSMA 不提供开发接口给任何第三方使用，无其他类型的接口。

### 8.2 运维需求

1. 日志记录: 系统创建记录到日志中, 供运维人员排查.
2. 可观察TSMA所使用流计算的计算进度信息。
3. 可观察 RSMA 在集群系统中的状态信息。

### 8.3 测试需求

1. 功能测试: 验证功能的正确性, 包括创建删除, 计算, 查询等.
2. 性能测试: 验证计算结果的查询性能与未使用TSMA查询的性能对比， 验证自动调用 RSMA 之后性能优化情况。
