## 2. 引言

### 2.1 术语与缩写名词

1. **结构化查询语言（Structured Query Language，SQL）：**是一种用于管理和操作关系型数据库的标准编程语言。 它允许用户存储、更新、删除、搜索和检索数据库中的数据。 SQL 被广泛应用于各种数据中心应用程序中，是 ISO 和 ANSI 等标准化机构认可的国际标准。
2. **SQL-92**：《Information Systems - Database Language - SQL (includes ANSI X3.168-1989) (formerly ANSI X3.135-1992(R1998))》，ANSI 在 1992 年发布的数据库 SQL 语言标准。
3. **投影查询**：是选择特定列的操作，返回的结果集中只包含指定的列。
4. **分布式查询**：分布式查询是指因为数据源位于不同节点上导致需要多个节点配合完成的查询。
5. **选择函数**：选择函数是指根据语义在输入集合中选择一行或多行结果返回。用户可以同时指定输出其他列，因此可以方便地知道被选出的值是源于哪个数据行。
6. **视图**：是一个存储在数据库中的查询语句，视图本身不包含数据，只有在从视图读取数据时才动态执行视图所指定的查询语句。
7. **TSBS 测试**：是一个时序数据处理（数据库）系统的性能基准测试平台，提供了 IoT、DevOps 两个典型应用场景。它由 Timescale 开源并负责维护，作为一个性能基准测试平台，TSBS 具有便捷、易用、扩展灵活等特点，涵盖了时序数据的生成、写入（加载）、多种类别的典型查询等功能，并能够自动汇总最终结果。

### 2.2 相关文档资料

1. PostgreSQL 语法： https://www.postgresql.org/docs/17/sql-select.html
2. MySQL 语法： https://dev.mysql.com/doc/refman/8.0/en/select.html

### 2.3 优先级要求

时序数据查询是时序数据库的核心功能，因此本需求优先级较高。但其中少部分功能优先级可以适当降低，例如视图、JSON 运算符等。

### 2.4 版本要求

1. 企业版：才具有视图、权限功能模块。
2. 开源版：具备除了安全会话管理、身份认证、传输数据加密功能功能外所有查询功能

## 3. 需求目标

### 3.1 背景

作为一款自主研发的时序数据库产品，TDengine的核心设计目标是为用户提供高效便捷的时序数据查询与分析能力。面对时序数据来源的多样性（如工业传感器、物联网设备、业务系统日志等）以及数据类型与结构的差异性，同时考虑到用户群体在分析需求和应用场景上的广泛性（包括实时监控、趋势预测、异常检测等），作为通用型时序数据库系统，核心设计理念聚焦于识别并抽象化这些差异性需求中的共性特征，将其转化为可产品化的标准功能模块。

### 3.2 目标

1. 兼具安全性、可靠性、高性能的分布式查询框架，包括合理划分的框架模块、高性能的交互、完备的优化策略、精细的资源控制、多样化的算子等。
2. 提供存在于关系数据库中同时适用于时序数据库的查询语法、函数。
3. 遵循 SQL-92 语法标准，根据时序数据特点进行 SQL 语法的扩展，提供诸如标签操作、时间窗口聚合、ASOF 连接查询、时序数据专有函数等。
4. 适配用户权限控制和数据安全传输机制，确保查询处理流程中数据的安全性，禁止并记录用户无权限的查询访问数据的行为。
5. 完备的操作审计和日志机制，对关键操作记录完备的信息，便于行为追踪和审计。

## 6. 安全需求

1. 身份验证与授权：整合时序数据库的身份认证机制，以确认发起查询的用户或服务身份。身份确认后，授权模块（基于角色的访问控制 RBAC ）根据预定义的策略检查用户权限，确保其仅能执行被允许的查询类型（SELECT, SHOW）以及访问特定的数据库对象（表、视图、列）。
2. 最小权限原则：数据库查询引擎及其关联的服务账户必须严格遵循最小权限原则。引擎在操作系统层面或数据库内部，应仅被授予执行其基本功能所需的最低限度权限。例如，不应拥有不必要的管理权限（如`ROOT`角色），以限制在引擎本身被攻破时，攻击者能够横向移动或对整个基础设施造成损害的范围。
3. 传输过程数据加密：客户端与数据库查询引擎之间的通信必须使用强加密协议，如TLS 1.3，防止在网络窃听中数据被截获。
4. 安全会话管理：查询引擎提供安全会话管理机制，设置合理的会话超时时间，并确保所有会话Cookie设置了`Secure`和`HttpOnly`标志。必须具备会话失效（Session Invalidation）机制，以便在用户注销或检测到异常活动时立即终止会话。
5. 日志记录、监控与审计追踪：查询引擎记录详尽的审计日志（Audit  Logs），涵盖所有数据库连接尝试、敏感数据访问以及潜在的安全异常事件，以便及时发现并响应潜在的入侵行为（如异常大量的查询、非工作时间访问）。
6. 安全错误处理与信息泄露预防：以安全的方式处理和呈现错误信息。向最终用户返回的错误消息应当是通用的、非描述性的（例如：“发生内部错误”），不包含敏感的系统内部信息、数据库连接字符串、服务器路径或底层架构细节，以防止攻击者利用这些信息进行指纹识别或进一步的攻击。
7. 资源限制与拒绝服务保护：为防止恶意用户或有缺陷的查询导致服务不可用，查询引擎实施精细的资源管理和限速，包括单个查询的执行时间（Query Timeouts）、内存消耗控制、以及并发连接数。降低潜在的拒绝服务（DoS）或分布式拒绝服务（DDoS）攻击成功的概率，确保系统稳定性。

## 7. 弹性伸缩需求

1. 计算与存储分离： 提供高效地弹性伸缩的能力。查询引擎能够独立于 TDengine 中的虚拟节点（数据节点）本身进行扩展。在增加或减少计算资源时不涉及大量的数据迁移或数据重组，从而显著减少性能损耗和网络带宽需求。
2. 支持无状态查询节点（Qnode）： 查询引擎的计算节点应为无状态计算节点。这样可以快速、高效地添加或移除节点，无需复杂的会话管理或状态同步过程。
3. 快速扩容：查询节点弹性伸缩操作需要在尽可能短的时间内完成，以快速响应工作负载变化，并将对业务连续性的影响（例如延迟峰值）降到最低，最好能将性能损耗控制在可接受范围内。
4. 查询负载均衡（Load Balancing）：查询调度器能够根据当前各个节点的负载状况（包括数据倾斜情况），将新查询请求或数据片段动态、均匀地分配到健康的节点上。
5. 业务透明与无感（Business Transparency）： 扩容和缩容过程应完全对上层应用透明。在伸缩操作期间，业务查询不应中断，实现“无感”伸缩。
6. 故障恢复与容错性（Fault Tolerance and Recovery）： 伸缩操作/滚动升级过程中（如节点加入或离开集群），查询引擎具备健壮的故障恢复机制，确保即使在qnode/dnode/vnode节点故障时也能继续提供服务。

## 8. 第三方依赖需求

查询引擎的功能代码自主研发为主，尽量降低对第三方（开源）库的依赖。查询引擎依赖的第三方库包括：cjson、geos、lemon，这三个依赖库在查询引擎内部提供JSON转换、地理信息对象操纵、SQL 语法解析的功能。
明确依赖的第三方软件在查询引擎中的功能定位，限制其适用范围。
对于外部依赖的软件，在授权许可变更、安全漏洞等方面带来的查询引擎运行安全风险，需要有积极、快速、完备的应对策略和方案。

## 9. 其他需求

1. 兼容性需求
   - 所有功能兼容 2.x 版本（除非原有行为不合理）
   - 支持 SQL-92 查询语法
2. 接口需求
   - 对外通过连接器提供各语言查询接口，内部配置可以根据需要进行增加或废弃
3. 运维需求
   - 需要提供日志、监控等手段来满足运维需求
4. 易用性需求
   - 提供详细的文档说明，指导用户如何通过 SQL 使用各种查询功能
   - 对于配置项提供默认配置，降低用户的使用门槛
5. 测试需求（不含测试例）
   - 测试各项功能是否正确的满足了需求
   - 测试性能是否达标
