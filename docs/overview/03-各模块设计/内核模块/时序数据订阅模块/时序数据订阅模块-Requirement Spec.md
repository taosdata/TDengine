## 2. 引言

### 2.1 术语与缩写名词

1. **TDengine**：一种高性能、支持分布式架构的时间序列数据库。
2. **生产者（Producer）**：消息队列中用于生产数据。
3. **订阅主题（Topic）**：消息队列中同一类型数据的集合。
4. **消费者（Consumer）**：消息队列服务中接收消费数据。
5. **Kafka: **开源的分布式消息队列中间件。
6. **MQTT Broker**：接收客户端发布的消息，根据主题对消息进行过滤，并分发给订阅者
7. **MQTT Publisher**：发布者向 MQTT Broker 发送消息
8. **MQTT Subscriber**：订阅者从 MQTT Broker 接收消息
9. **MQTT Topic**：消息主题，用于标识消息的类型或内容，客户端可以发布或订阅一个或多个主题
10. **MQTT QoS**：发送者与接收者之间消息传递的保证级别（并非发布者和订阅者之间）
11. **MQTT 遗嘱消息**：WillMessage，在客户端连接时指定的消息，它将在客户端断开连接时自动发布到代理服务器
12. **MQTT 保留消息**：RetainHandling，当一个客户端向一个主题发布消息时，该消息可以被设置为保留消息。这意味着该消息将被保留在代理服务器上，并在新的订阅者连接到主题时被发送给它们。
13. **MQTT 共享订阅**：MQTT 5.0 引入了共享订阅特性，它使得 MQTT 服务端可以在使用特定订阅的客户端之间均衡地分配消息负载
14. **MQTT 消息持久化**：Mosquitto、EMQ 等 Broker 会缓存一些历史消息，订阅者可以获取历史消息
15. **MQTT 会话状态**
   - 持久化会话：消费者重新上线时，消费离线消息，支持清理会话标志
   - 非持久化会话：消费重新上线时，消费当前消息

### 2.2 相关文档资料

kafka 用户手册：https://kafka.apache.org/documentation/

### 2.3 优先级要求

时序数据订阅属于时序数据库系统的基础主键，从功能优先级上来说具有较高的优先级。
通过采用订阅系统，能够降低**应用系统与数据库系统**之间、**应用系统和应用系统**之间的耦合，降低数据库查询的压力和应用系统的复杂程度具有重要的价值。

### 2.4 版本要求

时序数据订阅功能均开源。社区版和企业版功能一致。

## 3. 需求目标

随着系统业务规模的持续扩展，各功能模块间的异步通信与系统解耦需求日益显著，亟需引入高效可靠的消息队列机制，确保整体架构的稳定运行与弹性伸缩。为有效地满足应用实时获取 TDengine 数据写入动态的业务场景，或支持以事件驱动模式实现数据顺序化处理的技术需求，TDengine 原生提供了与 Kafka 等主流消息队列产品功能对标的数据订阅与消费接口方案。
TDengine 内置的数据订阅服务能力使得开发者无需额外集成独立消息队列中间件，既简化了整体架构设计，又显著降低了运维复杂度与资源成本。本功能充分地体现了物联网（IoT）大数据平台建设中对技术栈整合与系统效能优化的深度思考。
TDengine 的 MQTT 订阅（tmqtt）提供类 MQTT Broker 服务器的功能，从 TDengine 已创建的主题订阅数据，不支持 MQTT 消息发布。支持基础身份验证；支持 QoS 0/1 两种质量策略；支持 MQTT 5.0 协议, 支持 TCP 协议。支持 MQTT 协议的共享消费组功能，允许多个消费者共同分担消息消费任务；支持从数据的起始位置开始推送，也支持从最新的数据位置开始推送；支持记录已推送数据的位置，以便在服务重启后，能够从上次停止的位置继续推送数据。

## 4. 功能需求

| 序号 | **功能类别** | **功能名称** | 功能描述 |
| --- | --- | --- | --- |
| 数据写入 | 支持多种开发语言的客户端接入，能将各类业务消息快速写入队列。并且先写入的先被消费出来，满足队列 FIFO 特性。 |
| 数据存储 | 消息队列应支持写入数据库的消息持久化，确保在系统重启后消息不会丢失，存储时长可配置。 |
| 查询主题 | 创建基于查询的订阅主题（Topic），此时，订阅主题是单个查询的结果。 |
| 超级表主题 | 创建超级表类型的订阅主题。此时订阅主题是用于创建订阅主题的超级表包含的全部数据，并可通过配置选项控制是否返回超级表元数据。 |
| 数据库主题 | 创建（全）数据库类型的订阅主题。此时，订阅主题是目标数据库内全部数据，可通过配置选项控制是否返回数据库元数据。 |
| 创建/查看/删除主题 | 通过 SQL 语句操纵订阅主题，包括订阅主题的创建、查看、删除等 |
| 消费者 | 管理消费者的功能，包括并不限于消费者的创建、关闭，查看等 |
| 消费者组 | 多租户消息分发模式 - 同一消费者组内成员以协作方式共同处理指定订阅主题的数据流 - 确保消息在组内被唯一处理 - 支持动态扩缩容，实现资源的弹性分配 分组隔离与独立消费 - 不同消费者组独立维护各自的消费进度 - 各消费组享有独立的offset管理和消息确认机制 资源生命周期管理 - 系统管理员可对闲置或完成使命的消费组执行删除操作 - 删除操作将同步清理相关的元数据、偏移量记录及权限配置 |
| 消费进度 | 动态设置消费者初始消费进度，可选项包括：latest/earliest/none。 消费过程中动态调整消费进度 检索当前消费者的消费进度 |
| 消息确认 | 消费者在处理消息的时候，应能够向消息队列自动发送或手动发送确认消息（commit 操作）。 确认消息的发送可以同步方式或异步方式。 可以查看消息确认的位置（commit 操作）。 |
| 5 | Consumer | 消息回放 | 按照数据写入数据库系统的顺序和时间间隔，向消费者反馈数据。从而实现完备精准的数据写入回放流程 |
| 6 | Partition | 数据分区 | 每个订阅主题的数据能够按照所属虚拟节点分布情况进行数据的分片，并按照消费者组中消费者的数量，动态平衡同一个消费者组中不同消费者获得的数据 |
| 7 | Replication | 数据副本 | 可运行在数据库单副本、两副本、三副本的场景下，并能够无缝兼容多副本系统中的主副本动态切换的场景。 |
| 8 | bnode | MQTT订阅节点 | 支持从 TDengine 中获取订阅的数据，bnode能够将结果使用 MQTT协议推送到用户端。 |
| 9 | mnd-bnode | 管理新类型节点 | 管理节点能够注册和管理 bnode 节点 |

## 5. 性能需求

在服务端有数据能够持续返回的情况下，服务端虚拟节点（virtual node）能够在 5ms 内返回结果
在不同写入模式，包括：单条写入、批量写入、轮询写入等模式下，每个虚拟节点向订阅消费者返回数据的吞吐量不低于 20,000 Tuples/Sec
对于 MQTT 5.0 协议消息推送，支持批量化的消息推送。

## 6. 安全需求

1. **提供用户认证机制：**确保只有合法用户能访问系统。
2. **全流程的数据传输保护**‌：启用 SSL/TLS 加密所有客户端与系统间的通信，可通过确认机制确保消息成功发送。
3. **用户来源访问控制**‌：使用规则限制不受信任 IP 的访问，可强制要求强密码策略和权限管理。
4. **行为监控**‌：实时记录用户的订阅行为和活动日志，便于以后的日志审查。

## 7. 其他需求

1. **系统兼容性需求**
平台应具备多语言客户端支持能力，允许采用不同编程语言的技术栈实现系统集成，确保跨语言环境下的数据交互与结果返回的一致性和准确性。
1. **消息接口需求**
提供面向生产者与消费者的完整接口方案，涵盖消息投递、主题订阅、消费确认等核心操作接口，需明确定义各接口的输入输出参数结构及数据格式规范。
1. **服务可靠性需求**
系统架构须满足高可用性标准，支持集群化部署模式，具备数据多副本冗余机制，确保在单一节点发生故障时，服务整体仍可持续稳定运行。
