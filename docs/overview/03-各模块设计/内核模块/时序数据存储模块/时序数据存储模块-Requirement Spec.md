## 2. 引言

随着物联网、工业监控及金融分析等领域对时序数据处理需求的激增，时序数据库作为专门用于存储和管理时间序列数据的数据库系统，变得愈发重要。时序数据存储引擎作为时序数据库的核心组件，其设计的优劣直接决定了数据库在处理海量时序数据时的效能、稳定性与扩展性。
为了确保该存储引擎能够满足日益复杂的工业物联网、运维监控、金融量化等场景下的严苛要求，并指导其后续的设计、开发与测试工作，特制定本需求规格文档。本文档将系统性地、全面地阐述对时序数据存储引擎的各方面要求，旨在构建一个功能强大、性能卓越、安全可靠且易于维护的存储系统。

### 2.1 术语与缩写名词

| 术语 | 全称 | 解释 |
| --- | --- | --- |
| TS Data | Time Series Data | 时间序列数据，通常由物联网设备产生，包含时间戳和多个字段值 |
| META Data | Meta Data | 元数据，描述时间序列数据的结构信息及属性的数据 |
| None 值 | 未指定值 | 未明确赋值的值，未指定值不会覆盖前值 |
| Null 值 | 空值 | 明确赋值为空的值，相较于 None 值而言，Null 值会覆盖前值 |
| 稀疏数据 | 稀疏数据 | 大部分值为 None 值或 Null 值的数据 |
| 密集数据 | 密集数据 | 大部分值为非 None 值或非 Null 值的数据 |
| 少表高频 | 少表高频 | 采集点基数不大，但采集频率很高的时序场景。时序数据主要来自于高频采集 |
| 多表低频 | 多表低频 | 采集点基数大，但采集频率不高的时序场景。时序数据主要来自于测点的高基数 |
| 乱序数据 | 乱序数据 | 到达系统的数据点的时间戳，比已经存储的某些数据点的时间戳更早的数据 |

### 2.3 优先级要求

1. 高优先级：数据持久化 (WAL)、高并发写入支持、基本的时间范围查询、LSM Tree 核心存储结构
2. 中优先级：数据压缩算法 (Gorilla/Delta)、批量写入优化、TTL 数据过期清理、标签索引过滤。
3. 低优先级：多级存储冷热分离、高级聚合函数、可视化插件支持、多语言 SDK 完善、复杂权限控制。

### 2.4 版本要求

1. 企业版：访问控制、数据加密、审计与合规
2. 社区版：其他需求

## 3. 需求目标

**极致的写入性能**：针对时序数据高并发写入的特点，利用时序场景数据特点设计实现存储引擎，优化写入路径，支持每秒千万级数据点的持续写入，满足大规模物联网设备的数据采集需求。
1. **数据更新与删除支持**：虽然时序数据通常以追加为主，但需支持特定场景下的数据修正（更新）与过期/错误数据的主动删除功能，以满足合规性与数据治理需求。
2. **高效的查询能力**：提供毫秒级的时间范围查询、降采样聚合查询及多维标签过滤查询，确保在海量数据背景下的实时分析响应速度。
3. **高压缩比存储**：采用列式存储与针对时序数据优化的压缩算法（如 Delta-of-Delta, Gorilla 等），显著降低磁盘空间占用，节约存储成本。
4. **数据持久性与安全性**：通过 WAL（Write Ahead Log）机制确保数据不丢失，支持故障快速恢复，保证数据的完整性与一致性。
5. **灵活的数据生命周期管理**：支持多级存储（内存、SSD、HDD、对象存储）与自动数据过期清理（TTL），根据数据热度自动迁移，平衡性能与成本。
6. **分布式部署与高可用性**：支持多节点部署，具备故障自动切换与数据复制功能，确保系统在节点故障时仍能稳定运行。
7. **易用的管理与监控**：提供完善的运维工具与监控接口，支持实时性能指标监控、日志分析及告警机制，简化运维工作。
8. **安全性保障**：实现数据加密存储与传输，支持访问控制与权限管理，确保数据安全与隐私保护。
9. **自主可控**：核心技术具备自主知识产权，对第三方库进行自主可控审查。支持国产化软硬件环境适配，保障系统在关键基础设施领域的长期安全与可控。

## 4. 功能需求

描述功能性要求，在可能的情况下，使用图表、流程图等可视化工具来辅助描述。如果是大的或复杂的功能，将功能性需求先粗分再细分。下表中的 Feature A, Function A.1 等符号应当被替换成有含义的名称。

| 序号 | **功能类别** | **功能名称** | 功能描述 |
| --- | --- | --- | --- |
| 4.1 | 多维数据模型 | 支持“度量（Metric）+ 标签（Tags）+ 时间戳（Timestamp）+ 字段（Fields）”的数据模型。 1. 标签（Tags）：支持键值对形式的索引列，用于快速筛选和分组时间序列。 1. 字段（Fields）：支持多列数值或非数值数据，单条记录可包含多个指标值。 |
| 4.2 | 数据类型支持 | 支持丰富的数据类型，包括但不限于整型（Int32/Int64）、浮点型（Float/Double）、布尔型（Boolean）、字符串（String/Binary）以及时间戳类型。 |
| 4.3 | 纳秒级精度 | 时间戳需支持从秒级到纳秒级的多种精度，满足高频交易或精密仪器监控的需求。 |
| 4.4 | 高并发写入 | 支持多线程，能够处理突发的高流量写入请求而不阻塞。 |
| 4.5 | 乱序写入处理 | 具备处理时间戳乱序数据的能力，允许写入延迟到达的历史数据，并能正确合并与排序。 |
| 4.6 | 批量写入接口 | 提供批量写入 API，减少网络交互开销与磁盘 I/O 次数，提升整体吞吐量。 |
| 4.7 | 时间范围查询 | 支持指定开始时间与结束时间的范围查询，快速检索特定时间段内的数据。 |
| 4.8 | 标签过滤查询 | 支持基于 Tag 的精确匹配、模糊匹配及组合条件过滤，快速定位目标时间序列。 |
| 4.9 | 降采样与聚合 | 内置常用的聚合函数（如 SUM, COUNT, AVG, MIN, MAX, FIRST, LAST 等），支持按时间窗口（如每 5 分钟）进行降采样查询。 |
| 4.10 | 最新值查询 | 提供高效获取指定时间序列最新数据点（Last Value）的接口，适用于实时监控大屏。 |
| 4.11 | B+ Tree 存储结构 | 采用 B+ Tree 或类似的写优化结构，存储元数据信息及其索引。 |
| 4.12 | LSM Tree 存储结构 | 采用 LSM Tree 或类似的写优化结构，将随机写转换为顺序写，提升写入性能。 |
| 4.13 | 多级压缩策略 | 1. 行级/列级压缩：针对不同数据类型采用特定的压缩算法（如 Gorilla 算法压缩浮点数，Delta 编码压缩时间戳）。 1. 通用压缩：支持 Snappy, Zstd, LZ4 等通用压缩算法对数据块进行二次压缩。 |
| 4.14 | WAL 数据保护 | 写入数据先落盘至 WAL，确保系统崩溃后内存中未刷盘的数据可恢复。 |
| 4.15 | TTL 自动过期 | 支持按表或按数据库设置数据保留策略（Retention Policy），自动清理超期数据，释放存储空间。 |
| 4.16 | 共享存储支持 | 支持将数据存储到共享存储系统（如 S3 对象存储），实现存储计算分离架构，提高存储可扩展性和成本效益。数据文件在本地保留一定时间后自动上传到共享存储，支持从共享存储直接读取数据。 |
| 4.17 | 多级存储冷热分离 | 支持多级存储策略，根据数据热度自动将数据在不同存储介质（内存、SSD、HDD、对象存储）间迁移。热数据保留在高性能存储介质以保证查询性能，冷数据自动迁移到低成本存储以节约成本。 |
| 4.18 | 数据删除 | 支持按时间范围或标签条件删除数据，满足 GDPR 等合规性要求。 |
| 4.19 | 数据更新 | 支持对已写入数据的更新操作（通常通过写入新版本数据覆盖旧版本实现），用于修正错误数据。 |
| 4.20 | Compaction 管理 | 支持自动及手动的 Compaction 操作，合并小文件，清理已删除或覆盖的数据，优化读取性能。 |

## 5. 性能需求

| 序号 | **功能类别** | **功能名称** | 功能描述 |
| --- | --- | --- | --- |
| 5.1 | 写入吞吐 | 单机环境下（参考配置：16 Core, 64GB RAM, NVMe SSD），支持每秒写入数据点数（Points/sec）不低于 1,000,000（100万）。在批量写入场景下，目标吞吐量应达到 10,000,000（1000万）Points/sec。 |
| 5.2 | 查询吞吐 | 支持每秒处理不低于 5,000 QPS（Queries Per Second）的简单查询请求。 |
| 5.3 | 写入延迟 | 单次写入请求（Batch Size < 100）的平均响应时间应小于 10ms，P99 响应时间小于 50ms。 |
| 5.4 | 实时查询延迟 | 针对最近 1 小时数据的简单范围查询，平均响应时间小于 20ms。 |
| 5.5 | 历史聚合延迟 | 针对 1 亿数据点的聚合查询（如 SUM, AVG），响应时间应控制在 2 秒以内。 |
| 5.6 | 存储压缩率 | 对于典型的时序数据（如浮点数监控指标），存储压缩比应达到 10:1 以上，即 1TB 原始数据占用磁盘空间不超过 100GB。 |
| 5.7 | 内存控制 | 系统应具备严格的内存管理机制，支持配置最大内存使用量，防止因内存泄漏或过度使用导致系统崩溃（OOM）。 |
| 5.8 | CPU 利用率 | 在空闲状态下，CPU 使用率应低于 5%；在满负荷写入时，CPU 资源应能被充分利用，且无明显锁竞争瓶颈。 |

## 6. 安全可控需求

| 序号 | **功能类别** | **功能名称** | 功能描述 |
| --- | --- | --- | --- |
| 6.1 | 用户认证 | 支持基于用户名/密码的认证机制，并预留集成 LDAP、OAuth2 等第三方认证服务的接口。 |
| 6.2 | 权限管理 | 实现细粒度的权限控制（RBAC），支持按数据库、表甚至列级别的读写权限划分，确保不同角色的用户仅能访问授权数据。 |
| 6.3 | 网络访问限制 | 支持配置 IP 白名单，限制仅允许特定网段或 IP 地址的客户端连接数据库服务。 |
| 6.4 | 传输加密 | 支持 TLS/SSL 协议，确保客户端与服务端之间的数据传输通道加密，防止数据在网络传输过程中被窃听或篡改。 |
| 6.5 | 静态存储加密 | 支持对落盘的数据文件（SSTable）和日志文件（WAL）进行透明加密（TDE），支持集成外部密钥管理系统（KMS）进行密钥轮转与管理。 |
| 6.6 | 操作审计 | 记录关键操作日志（如 DDL 变更、权限修改、批量删除等），包括操作时间、操作用户、源 IP 及具体指令，便于事后追溯与安全审计。 |
| 6.7 | 数据完整性校验 | 在数据存储层实现 Checksum 校验机制，定期或在读取时验证数据块的完整性，防止因磁盘静默错误或恶意篡改导致的数据损坏。 |
| 6.8 | 核心技术自主 | 存储引擎核心代码（LSM Tree 实现、WAL 机制、压缩算法集成等）需具备完全自主知识产权，不依赖闭源或有商业限制的第三方组件。 |
| 6.9 | 第三方库审查 | 引入的所有第三方开源库必须经过安全审查，确保无高危漏洞，且开源协议（如 MIT, Apache 2.0）符合商业分发要求，避免传染性协议。 |
| 6.10 | 国产化适配 | 优先适配国产主流操作系统（如麒麟、统信 UOS）及国产 CPU（如鲲鹏、飞腾、海光），确保在信创环境下的功能完整与性能达标。 |
| 6.11 | **供应链安全性** | 依赖包漏洞扫描 | 在 CI/CD 流水线中集成依赖包漏洞扫描工具，定期检测并修复已知漏洞，确保软件供应链安全。 |
