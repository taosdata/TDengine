## 2. 引言

benchmark 是数据库性能测试基准工具，TDengine 也需要一款 benchmark 工具，能够对写入、查询及订阅等功能进行全面的性能基准测试，输出性能指标。

### 2.1 术语与缩写名词

- **命令行参数**：指通过命令行输入的长参及短参
- **Json 参数**：指从 json 配置文件中配置的参数
- **WebSocket**：是一种在单个TCP连接上进行全双工通信的协议。它基于TCP协议，通过HTTP/1.1协议的101状态码进行握手，从而建立连接。WebSocket允许服务器和客户端之间进行实时双向通信，客户端和服务器之间的数据交换变得更加简单和高效。
- **RESTFUL**:**  **指一种基于 HTTP 协议的 web 服务架构风格，也被称为 RESTful 架构。REST（Representational State Transfer）是一种用于设计网络应用程序的架构风格，它使用客户端和服务器之间的 HTTP 协议进行通信。
- **SQL写入**:  指把多个类似 insert into ... 语法拼写在一起，形成一个大的 SQL 语句的方式
- **Native **:  指直接调用引擎提供的 libtaos.so 客户端库接口的行为
- **SML 写入**: Schemaless 无模式写入，一种快速的自动建表写入方式

### 2.2 相关文档资料

1. WEBSOCKET 文档：[RFC 6455](https://datatracker.ietf.org/doc/html/rfc6455)
2. HTTP 协议标准  [RFC 7231](https://datatracker.ietf.org/doc/html/rfc7231)

### 2.3 优先级要求

引擎集成测试开始前完成

### 2.4 版本要求

与 TDengine 3.0 版本一致

## 3. 需求目标

提供一款 TDengine 性能 benchmark 测试工具，满足以下功能：
1. 提供测试不同写入接口的性能指标
2. 提供测试不同查询接口的性能指标
3. 提供测试订阅及消费的性能指标

## 4. 功能需求

以下列出工具要实现的主要功能：

| 序号 | **功能类别** | **功能名称** | 功能描述 |
| --- | --- | --- | --- |
| 1 | 连接方式 |  |  |
| 1.1 |  | 原生连接 | 可以选择原生连接方式 |
| 1.2 |  | WebSocket 连接 | 可以选择WebSocket 连接方式 |
| 2 | 写入性能 |  |  |
| 2.1 |  | SQL 写入 | 拼 SQL 方式写入性能测试 |
| 2.2 |  | STMT 写入 | STMT 方式 写入性能测试 |
| 2.3 |  | sml(line) | Schemaless 的 line 协议方式性能测试 |
| 2.4 |  | sml(json) | Schemaless 的 json 协议方式性能测试 |
| 2.5 |  | sml(telnet) | Schemaless 的 telnet 协议方式性能测试 |
| 2.6 |  | 写入模式：批写入 | 指一张子表全部写完再写下一张子表的模式 |
| 2.7 |  | 写入模式：交叉(interlace)写入 | 指一轮把每张子表都写完指定行数后再写下一轮的方式 |
| 2.8 |  | 统计写入耗时 | 从数据开始写入至完成的总耗时，单位为秒 |
| 2.9 |  | 统计写入数据量 | 写入数据的总行数，单位为 rows |
| 2.10 |  | 统计写入吞吐量 | 指每秒写入的数据总行数，单位为 rows/s |
| 2.11 |  | 统计写入请求延时 | 写入请求的 min max avg p90 p95 p99 分布情况 |
| 3 | 查询性能 |  |  |
| 3.1 |  | 超级表查询 | 以超级表为单位进行查询方式，会对每个子表发起查询 |
| 3.2 |  | 给定 SQL 查询 | 任意给定一组 SQL 语句依次执行查询的方式 |
| 3.3 |  | 统计总查询耗时 | 开始发起查询至所有查询完成的总耗时，单位为秒 |
| 3.4 |  | 统计总查询次数 | 完成的查询请求次数，单位为：次 |
| 3.5 |  | 统计总QPS | 每秒完成的查询个数，单位为： 次/秒 |
| 3.6 |  | 统计查询延时分布 | 查询请求的 min max avg p90 p95 p99 |
| 4 | 订阅性能 |  |  |
| 4.1 |  | 订阅 topic 名 | 可以设置订阅的 topic 名称 |
| 4.2 |  | 订阅 HOST | 可以设置订阅主机位置 |
| 4.3 |  | 订阅 PORT | 可以设置订阅主机端口号 |
| 4.4 |  | 用户名 | 可以设置订阅主机连接用户名 |
| 4.5 |  | 密码 | 可以设置订阅主机连接验证密码 |
| 4.6 |  | 消费线程数 | 可以设置消费线程数 |
| 4.7 |  | 消费组 ID | 可以设置消费组 ID |
| 4.8 |  | 消费组模式 | 指消费组消费消息模式，分共享消费和独立消费两种模式 |
| 4.9 |  | 创建模式 | 创建消费者的方式，分顺序创建和并发创建两种 |
| 4.10 |  | 消息最大延时 | 在接收消费消息时等待的最大延时，超过此值无消息即会返回 |
| 4.11 |  | 客户端ID | 可以设置消费者的客户端 ID 号 |
| 4.12 |  | 自动提交 | 可设置是否自动还是手动提交消费消息 |
| 4.13 |  | 订阅 TOPIC 列表 | 可以创建及订阅多个 TOPIC , 可以设置 TOPIC 名称及 SQL 语句 |
| 4.14 |  | 统计线程消费消息块个数 | 输出每个线程收到消息块个数 |
| 4.15 |  | 统计线程消费消息行数 | 输出每个线程收到消息行数 |
| 4.16 |  | 统计整体消费消息块个数 | 输出总计收到消息块个数 |
| 4.17 |  | 统计整体消费消息的行数 | 输出总计收到消息行数 |

## 6. 其他需求

- 兼容性需求
   - 兼容原有命令行
   - 兼容原有 json 配置文件
- 接口需求
支持命令行 + 配置文件两种对外接口，命令行优先
- 运维需求
长时间运行状态下无内存泄露
- 易用性需求
命令行参数名称简洁表意，json 配置文件要求分层清晰，命名简单易懂
- 测试需求（不含测试例）
   对主要功能要有测试用例覆盖
   能够提供调试模式方便进行测试及查找问题
