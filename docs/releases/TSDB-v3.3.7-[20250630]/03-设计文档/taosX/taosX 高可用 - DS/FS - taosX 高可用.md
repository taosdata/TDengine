# FS - taosX 高可用

## 1. 背景

taosX 是 TDengine 企业版的一个核心组件，为用户提供另代码数据接入的能力。目前 taosX 以单节点方式运行，存在单点故障风险。随着 taosX 功能和使用场景的不断扩展，单节点服务方式无法满足更高性能和通量的数据接入需求。
本文档中，我们将单节点的taosX ETL服务扩展为分布式高可用服务，目标是在任意节点宕机后（即使只剩一个）仍然能够提供服务。
功能列表概要如下：
- 支持使用共享存储或 PostgreSQL/MySQL 作为集群数据存储。
- 用户可以继续使用 Explorer 进行 ETL 任务管理。
- 第一阶段目标：
  - 任务均衡分布：多个任务可在不同的执行节点上分别执行。
  - 任务级别的多节点高可用：在单个节点故障后，此节点上的任务将被分配到其他节点上继续执行。
- 第二阶段目标：
  - 子任务并发执行：一个数据接入任务，可以通过分片机制在多个节点并发执行。
  - 集群管理：taosx 命令行集成集群管理命令，可对集群任务进行查看和状态监控，并能对故障状态进行运维操作。

## 3. 定义

- **ETL**：抽取（Extract）、转换（Transform）、加载（Load）的数据处理过程。
- **高可用**：系统在大部分时间内可运行，即使在部分节点发生故障时。
- **RAFT 协议**：一种分布式一致性算法，用于在多个节点之间达成共识。**RAFT 协议用于 taosX 元数据（任务、Agent 等）创建、更新和删除**操作，保持元数据在集群各节点间的数据一致性。RAFT 目前只是方案中的一种，因为 taosX 的元数据来源单一，所以可能优先考虑弱一致性协议或其他对等协议。
- **服务降级**：在系统资源不足或出现故障时，降低服务质量，保证核心功能可用。对于 taosX 服务，服务降级可能发生在主节点宕机，且无法满足 RAFT 协议要求的节点数量时；此时 taosX 服务降级，仅支持已有任务的运行和可用性。
- `swarm`：本文档中指 taosx 集群，用于 taosx 集群管理子命令。

## 4. 行为说明

### 4.1 集群管理

#### 4.1.1 创建集群

在 taosx 服务启动后，在第一个节点上创建集群，作为管理节点（Manager）：
```bash
taosx swarm init
```

成功后，可以在其他节点进行 join 操作加入集群：
```bash
taosx swarm join <HOST>[:<PORT>]
```

加入集群后，新加入的节点为 Worker。
- Manager: 管理者可进行集群数据接入任务的管理和执行。
- Worker：仅可进行任务执行，包括数据采集和数据写入。Worker 和 Manager 节点上的数据是一致的（使用共享存储或外置存储）。

#### 4.1.2 查看当前节点

```bash
taosx swarm ls
```

结果如下：

| id | endpoint | role | status | tasks | join_time | uptime |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | host:6055 | manager | ready | 2 | 2025-04-14T14:04:00+08:00 | 2h |

- `id` 表示节点 ID，集群创建后节点 ID 保持不变。
- `status` 节点状态包含如下：
  - `unknown`：节点未连接到集群。
  - `ready`：节点已准备好执行任务。
  - `running`：节点有任务正在执行，括号内表示：节点执行的任务数。
  - `down`：节点下线。

#### 4.1.3 下线（上线）节点

当节点处于运行状态时，可使用 `down` 命令下线该节点。下线节点会停止所有正在执行的任务，并将 taosx 节点标记为 `down`。
处于 `down` 状态的节点，可使用 `up` 命令上线（ `ready`），恢复任务调度。节点恢复后不会发生 rebalance，仅新增任务会被调度到该节点。
```bash
taosx swarm down <id>
taosx swarm up <id>
```

#### 4.1.4 删除节点

需要永久删除节点时（如果节点正在运行中，应先下线该节点）使用如下命令移除节点：
```bash
taosx swarm rm <ID>
```

### 4.2 工作方式

#### 4.2.1 任务调度

- 第一阶段目标：
  #### 任务负载均衡
  多个任务执行时，可以自动分配到所有工作节点上。主要行为如下：
  - 一个任务启动后，自动选择一个较低负载的节点执行。
  - 当执行任务的节点宕机时，管理节点将该任务调度到其他可用节点。
- 第二阶段目标：
  #### 分片机制（Sharding）
  一个任务可以根据分片机制分割为多个子任务，在多个节点上并发执行。
  - Kafka/MQTT/TMQ 自动根据所配置的最大并发数分割子任务，此时每个子任务是一个独立数据订阅入库任务，在多个节点上并发地执行（河北电力多节点应用场景可以使用此机制进行全局管理）。
  - TDengine 数据迁移（查询同步）、关系型数据库数据迁移任务，可以使用预置的分片条件，根据表名或时间分片后，动态创建数据查询写入子任务，在多节点上并发执行。
  此时，父任务将作为子任务的管理器，负责子任务的协调执行、Metrics 收集等工作。.

#### 4.2.2 节点宕机处理

当出现宕机时：
- 当 manager 节点宕机时，自动从剩余的 worker 节点中选择一个作为 manager（分布式抢占方式）。宕机节点的任务将由新的 manager 分发到可用的 worker 中执行。
- 当 worker 节点宕机时，该节点的任务将切换到其他可用节点上执行。
