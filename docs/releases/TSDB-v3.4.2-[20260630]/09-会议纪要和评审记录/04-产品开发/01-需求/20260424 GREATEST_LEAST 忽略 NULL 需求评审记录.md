## 2. 评审记录

评审团队对需求文档（GREATEST/LEAST 忽略 NULL 相关）进行了全面审查，认为所有设计合理，具体评审意见如下：

### 2.1 功能

- 需求精准定位了时序数据场景中传感器掉线、采集延迟、数据缺失导致列值 NULL 频繁出现的核心痛点，明确了通过新增客户端配置项 `ignoreNullInGreatest` 让用户可控地跳过 NULL 参数进行比较的目标，业务价值清晰。

- 配置项设计简洁合理，取值范围为 0/1，默认值 0 保持与 MySQL 一致的现有行为（遇 NULL 返回 NULL），配置为 1 时忽略 NULL 仅对非 NULL 值比较，全 NULL 时仍返回 NULL，边界语义明确无歧义。

- 与现有配置项 `compareAsStrInGreatest` 的交互关系设计清晰，两者正交互不影响，`ignoreNullInGreatest` 仅控制 NULL 参数处理，不改变非 NULL 值之间的比较规则，避免了配置项组合导致的语义混乱。

- 行为示例覆盖默认模式、忽略 NULL 模式、全 NULL、常量与列混合等典型场景，便于开发、测试和用户理解；测试需求涵盖八项测试场景，包括两个配置项交互验证和性能回归，覆盖充分。

### 2.2 性能

- 当 `ignoreNullInGreatest = 0`（默认）时，性能与现有实现完全一致，无额外开销；忽略 NULL 模式下新增的跳过逻辑为简单条件判断，不应引入可观测的性能退化，设计合理。

### 2.3 安全

- 无特殊安全需求，配置项遵循现有客户端配置的权限管理机制，不涉及认证、授权或加密变更，符合安全规范。

### 2.4 兼容性

- 兼容性设计稳妥：默认值 0 确保升级后现有行为不变，不影响已有业务；纯客户端行为，不涉及客户端-服务端通信协议变更；配置项命名与现有 `compareAsStrInGreatest` 风格一致，降低学习成本，保障平滑升级。

## 3. 评审结论

需求文档整体设计合理、逻辑清晰，可用于指导后续开发工作。
