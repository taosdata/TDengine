## 2. 评审记录

评审团队对需求文档（时区与查询改造、时区与流计算改造、时区与自然时间单位用户手册三篇文档）进行了全面审查，认为整体设计合理，具体评审意见如下：

### 2.1 功能

- 需求精准定位了时区语义分散、连接级时区未全面生效、IANA 时区不支持、一周起始日硬编码、自然时间单位不完整等核心痛点，目标清晰，分 v3.4.2（查询侧）和 v3.4.3（流计算侧）两期交付，节奏合理。

- 五层时区优先级体系（L1 SQL 级 → L2 连接级 → L3 客户端全局 → L4 服务端全局 → L5 系统默认）设计完整，各场景回退链定义清晰；评审中发现写入场景的回退链应为 L2→L3→L5 而非 L2→L4→L5，普通列读取的当前状态至少为 L3→L5 而非仅 L5，已由潘魏在文档中修正。

- `TIMEZONE()` 函数增强为同时返回连接级、客户端、服务端三个时区，便于用户排查时区配置问题，设计实用。该改进由张心治在评审中提出并采纳。

- 查询侧 `INTERVAL` 支持 `w`/`n`/`q`/`y` 自然时间单位、`TIMETRUNCATE` 支持月/季/年截断，窗口边界按本地挂钟对齐，DST 切换日和闰年/变长月处理规则清晰；但需注意目前查询和流计算中已支持周（`w`）、月（`n`）、年（`y`），仅季度（`q`）为新增单位，文档背景描述需相应调整。该点由张心治在评审中指出。

- 流计算侧时区固化架构设计合理，所有触发类型（PERIOD/SLIDING/INTERVAL/SESSION/STATE/EVENT/COUNT）创建时统一固化 timezone 和 firstDayOfWeek 到流元数据，运行时不再依赖全局配置，解决了跨国部署场景下流任务时区不可控的问题。

- 流计算 SLIDING 触发新增自然月/季/年单位、INTERVAL 触发补齐 `n`/`q`/`y`，与查询侧 INTERVAL 规则保持一致，设计统一；评审中邝金清指出 INTERVAL 触发已支持 `d`/`w`，仅需新增 `n`/`q`/`y`，文档已修正。

- 流任务时区指定语法，邝金清建议将独立的 `TIMEZONE` 子句改为 `STREAM_OPTIONS(CONFIG(timezone = '...', firstDayOfWeek = N))` 形式，可读性更强且便于后续扩展更多配置参数，已在文档中完成修改。

- 用户手册以版本号标注（无标记/v3.4.2/v3.4.3）区分功能交付状态，结构清晰，同时涵盖查询侧和流计算侧的完整语义，可作为用户使用的统一参考。

### 2.2 性能

- 所有默认行为不变，未使用新语法的用户无任何行为变化；`TIMETRUNCATE` 第三参数传 `0`/`1` 保持旧语义，不引入额外性能开销。

- 自然时间单位窗口切分需要在本地时间坐标系计算后换回 UTC，DST 区域存在一定计算开销，但属于必要语义正确性保障，性能影响可控。

- 流任务时区固化后运行时直接从流元数据读取，无需每次回退查询全局配置，在高并发流计算场景下避免了不必要的配置查询开销。

### 2.3 安全

- 时区设置仅影响时间展示和窗口对齐行为，不涉及认证、加密和权限控制，安全风险低。

- 错误处理设计完备：无效时区字符串、`firstDayOfWeek` 超出范围、`TIMETRUNCATE` 第三参数类型错误均有明确错误码和错误信息，不会导致系统异常。

### 2.4 兼容性

- 向后兼容设计稳妥：所有默认行为不变（时区回退链不变、`firstDayOfWeek` 默认 1=周一），`TIMETRUNCATE` 第三参数传 `0`/`1` 保持旧语义，不使用新语法的用户无任何行为变化。

- 流计算侧 `STREAM_OPTIONS(CONFIG(...))` 为新增语法，不影响已有流任务；已有流任务未固化时区的升级处理需在实现阶段明确迁移策略。

- 用户手册以版本号标注区分功能可用性，避免用户在低版本使用高版本功能时产生困惑。

## 3. 评审结论

需求文档整体设计合理、逻辑清晰，可用于指导后续开发工作。
