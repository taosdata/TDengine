## 2. 评审记录

评审团队对设计文档（GREATEST / LEAST 函数忽略 NULL FS）进行了全面审查，认为整体设计对齐主流 SQL 生态多列求极值能力、语义清晰、可落地性强，具体评审意见如下：
1. 设计目标清晰精准，核心痛点定位明确，紧扣时序数据场景中列值为 NULL（传感器掉线、采集延迟、数据缺失）非常常见导致遇 NULL 即返回 NULL 的 MySQL 兼容行为不利于多列求极值实际使用的核心痛点，明确核心目标为新增客户端配置项 `ignoreNullInGreatest` 允许用户选择在比较中跳过 NULL 参数，在保持默认 MySQL 兼容行为的前提下提供灵活的 NULL 处理策略，目标聚焦、指引明确。
2. 功能设计全面细致，可落地性强，覆盖核心业务场景：核心语义定义准确，`ignoreNullInGreatest` 默认值 `0` 保持历史行为不变、设为 `1` 时跳过 NULL 仅在非 NULL 值中比较、全 NULL 仍返回 NULL 三级语义清晰无歧义；参数规则完整，支持 ≥ 2 个参数、数值与字符串类型、常量列引用及任意标量表达式混合；返回类型推导覆盖 NULL 字面量类型、全同类型、全数值提升、全字符串长度取最长、混合类型受 `compareAsStrInGreatest` 控制五种情况，`ignoreNullInGreatest=1` 时 NULL 字面量被剔除按剩余参数推导的特殊处理精准；两项配置正交互不影响的设计使组合语义可预测；适用范围覆盖 SELECT/WHERE/GROUP BY/ORDER BY/子查询/流式查询六种上下文；边界场景表覆盖 15 种输入组合预期行为（含两项配置同时开启场景），错误处理覆盖参数个数不足、不可比较类型、行数不匹配三类报错，设计闭环完整。
3. 设计文档结构规范，版本与修订记录清晰：明确修订记录（0.1 初稿 Stephen、1.0 发布 Simon Guan），8 个章节从背景、定义、行为说明（含核心语义、适用范围、参数规则、返回类型推导、NULL 处理、配置项、边界场景）、性能、安全、兼容性、运维到文档分层呈现，术语定义准确（GREATEST/LEAST、比较类型、NULL 传播），逻辑清晰、无歧义，符合 TDengine 设计文档规范要求。
4. 安全性、兼容性与性能考虑周全，风险可控：安全方面明确不读写元数据无权限新增、字符串比较按字节序不引入用户区域设置敏感性、不向外暴露内部错误码细节；兼容性设计稳妥，`ignoreNullInGreatest` 默认值 `0` 保证升级到 v3.4.2 后行为与历史版本完全一致对现有业务零影响，纯客户端配置变更无协议变更无数据格式变更，`compareAsStrInGreatest=0` 时混合类型语义对齐 PostgreSQL 数值优先策略；性能方面默认路径与现有实现一致无额外开销，`ignoreNullInGreatest=1` 路径仅在 NULL 检测分支增加跳过逻辑开销可忽略，标量函数可下推到 vnode 不阻塞算子流水线。

## 3. 评审结论

设计文档整体设计合理、逻辑清晰，功能覆盖全面，`ignoreNullInGreatest` 配置项语义、NULL 处理三级行为、返回类型推导规则、与 `compareAsStrInGreatest` 正交性、边界场景等核心设计规范严谨，使用场景贴合时序数据多列求极值中 NULL 频繁出现的实际业务需求，性能、安全、兼容性设计符合系统规范，精准解决了遇 NULL 即返回 NULL 导致多列求极值不可用的核心痛点。
