## 2. 评审记录

评审团队对设计文档（三员权限+强制访问控制 FS）进行了全面审查，认为整体设计在首轮评审（2026-02-11）基础上经过多轮迭代优化，安全模型严谨、可落地性强，具体评审意见如下：
1. 设计目标清晰精准，核心痛点定位明确，紧扣 root 超级用户绕过所有权限检查导致无法实现真正权力制衡、消除单点安全风险、建立不可抵赖审计闭环的实际安全痛点，通过强制三权分立（SoD mandatory）永久禁用 root 实现三员权力制衡，通过强制访问控制（MAC）基于 Bell-LaPadula 模型的禁止上读（NRU）和禁止下写（NWD）规则实现跨等级数据安全隔离，两大安全机制目标明确、互为补充，为高安全等级场景提供了完整的访问控制体系。
2. 功能设计全面细致，可落地性强，覆盖核心业务场景：SoD 支持命令行参数和 SQL 命令两种启用方式，启用前校验三角色独立持有、启用后 root 永久禁用且不可逆，SoD mandatory(initial) 过渡模式设计周全；MAC 采用显式激活模式（ALTER CLUSTER 'MAC' 'mandatory'）且不可停用，用户安全等级设计为 [min_level, max_level] 区间解决等级调整过程中读写冲突的实际难题，元数据安全等级覆盖 user/db/stb/子表/普通表/view/topic/stream 等全类型对象并明确继承规则，SECURITY_LEVEL DDL 操作规则分权限控制、等级压制、MAC 状态域、默认值、访问控制规则、一致性约束六个维度系统规范，角色安全等级约束（min+max 双端 floor）和 PRIV_SECURITY_LEVEL_ALTER 受信主体豁免机制设计精巧，MAC 激活预检全量扫描并列出所有违规项及修复 SQL，测试用例 F1-T1~T10 和 F2-T1~T28b 覆盖正常、异常、边界场景。
3. 设计文档结构规范，版本与修订记录清晰：明确修订记录从 0.1 到 1.0 共 9 个版本，每次修订详细记录变更内容（MAC 显式激活、SSecurityPolicyObj 独立存储、MAC 与 RBAC 交互语义、预检查机制、角色等级约束重构、PRIV_SECURITY_POLICY_ALTER 直持约束），术语定义完整准确涵盖三权分立、强制三权分立、超级用户、主体、客体、安全等级、NRU、NWD、DAC、MAC 等核心概念，安全等级五级定义（公开/内部/秘密/机密/绝密）清晰无歧义，章节从背景、定义、行为说明、性能、安全、兼容性、运维、使用场景分层呈现，逻辑清晰。
4. 安全性、兼容性与性能考虑周全，风险可控：安全设计覆盖 SoD 状态随用户对象下发防篡改、vnode.json 配合配置文件加密防安全等级篡改、REVOKE 角色写入审计告警确保不可抵赖；兼容性设计支持从低版本停机升级至 3.4.1.0+，升级后 root 自动 [0,4]、其他用户按角色 floor 约束赋值、db/stb 安全等级置 0 防止普通用户读写中断，MAC 未激活时所有 MAC 检查零开销跳过不影响现有行为；性能方面 MAC 激活后 security_level [0,4] 用户命中 Layer 1 快速路径无需查询元数据，紧急恢复方案（所有用户设为 [0,4]）对性能无影响且保留完整审计记录，操作类型不同增加幅度控制在 20%-100% 范围内。

## 3. 评审结论

设计文档整体设计合理、逻辑清晰，功能覆盖全面，强制三权分立（SoD mandatory）和强制访问控制（MAC）双机制设计严谨，SoD 命令行与 SQL 双启用路径、MAC 显式激活与预检查、用户安全等级区间设计、角色双端 floor 约束、受信主体豁免、DDL 六维操作规范等核心设计规范完备，性能、安全、兼容性设计符合系统规范，精准解决了超级用户单点安全风险、权力制衡缺失、跨等级数据隔离不足的核心安全痛点。
