## 2. 评审记录

### 2.1 架构安全性

- 联邦查询沿用现有 TSDB 查询管线（Parser -> Catalog -> Planner -> Executor），不新增节点类型，架构侵入性低。
- 兜底策略（零下推方案）设计合理：所有 TDengine SQL 功能在零下推路径下均可正确执行，下推失败不影响正确性。
- External Connector 采用 SPI 插件模式，不同数据库类型独立实现，隔离性好。
- **不足**：Connector 模块同时运行在客户端和服务端，分布式部署下凭据分发路径复杂。

### 2.2 身份认证与授权

- 外部源访问使用独立的 USER/PASSWORD 认证，与 TDengine 内部权限体系解耦。
- **不足**：凭据在 mnode 持久化时的加密方案不明确（FS 提及'加密存储'但 DS 结构体无加密标记）。
- **不足**：OPTIONS 中的 TLS 私钥未纳入 sysInfo=true 保护。

### 2.3 密码学设计

- TLS 支持设计合理：通用选项 tls_enabled/tls_ca_cert/tls_client_cert/tls_client_key 覆盖了单向和双向 TLS 场景。
- 证书采用 PEM 文本内容传入（而非文件路径），由 mnode 加密存储并分发，避免了节点间证书文件部署问题。
- **不足**：加密存储的具体实现（主密钥、加密算法）未在设计文档中明确。

### 2.4 数据流与隐私保护

- 密码在 SHOW/DESCRIBE 时脱敏显示，系统表 password 列脱敏处理。
- **不足**：SQL 审计日志中密码明文记录，未提及脱敏措施。
- **不足**：远端错误信息（remote_code、remote_message）可能泄露外部源内部细节。

### 2.5 输入验证与防御

- Parser 是唯一的合法性门槛，所有语义不合法的查询在此阶段拦截。
- 类型映射规则详细，不可映射的类型在 Parser 阶段即报错拒绝。
- **不足**：External Connector SQL 生成时字面量值的处理方式不明确，存在注入风险。
- **不足**：外部表名/列名的标识符转义规则未明确。

### 2.6 第三方依赖

- 依赖 MySQL Connector-C、libpq、Apache Arrow Flight 等官方客户端库，选型合理。
- 连接池由 Connector 模块内部管理，相同 source_name 并发查询共享连接池。
- **不足**：连接池资源限制策略未明确（每源最大连接数、排队超时）。

## 3. 评审结论

**条件通过。**

设计整体架构合理，兜底策略完善。但凭据保护和 SQL 注入防护两个高危问题必须在编码阶段落实。
