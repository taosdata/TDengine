## 2. 评审记录

评审团队对设计文档（状态窗口支持多列状态键 FS）进行了全面审查，认为整体设计在保持现有单列语义不变的基础上自然扩展到多列、逻辑严谨、可落地性强，具体评审意见如下：
1. 设计目标清晰精准，核心痛点定位明确，紧扣工业与物联网场景中设备状态由多个离散字段共同决定（如 run_state 与 mode）、告警状态由 level 与 source 联合定义、流式任务需要在多字段任一变化时切窗并触发通知等实际业务痛点，明确核心目标为将现有状态窗口的单列状态键扩展为支持多列状态键的有序列表，在查询和流计算两条路径统一支持多维度状态切窗，目标聚焦、指引明确。
2. 功能设计全面细致，可落地性强，覆盖核心业务场景：SQL 语法设计兼顾历史兼容与新增能力，单列保留括号内位置参数的历史写法、多列仅允许子句形式配置 EXTEND/ZEROTH_STATE 从而彻底消除解析歧义，两种形式不得混用规则清晰；状态键比较规则简洁明确——任一列变化即切窗、NULL 列不参与比较且不更新对应槽位；NULL 处理设计是本文档最核心的复杂度来源，全 NULL 行沿用单列一致路径、部分 NULL 连续行构成候选段按累积状态逐行判定是否延续、候选段作为整体按前/后兼容性与 EXTEND 模式共同决策归属且不可丢弃，四种兼容性组合 × 三种 EXTEND 模式的决策表覆盖完整并配以基础四类、边界位置、多行候选段三组 12 个示例，语义清晰无歧义；ZEROTH_STATE 多列配置要求参数个数与状态键一致、NO_ZEROTH 占位设计灵活、过滤语义为"所有受约束列同时命中零状态才过滤"合理精准；流计算触发从单槽位扩展为有序多槽位、触发事件语义与查询路径切窗规则保持一致、通知 JSON 多列场景改为数组字段且元素顺序与 SQL 参数顺序一致；错误处理覆盖多列括号内非法配置、单列混用、参数个数不匹配、类型不支持、tag 列等 9 种报错场景，EXPLAIN 输出已更新为列列表形式，设计闭环完整。
3. 设计文档结构规范，版本与修订记录清晰：修订记录完整（1.0 初稿、1.1 补充流计算触发、1.2 SQL 语法兼容历史括号内 EXTEND/ZEROTH_STATE、1.3 重写 NULL 比较语义、1.4 归属决策单元由单行改为候选段），14 个章节从背景、定义、行为说明（含 SQL 语法、比较规则、输入限制、NULL 处理、EXTEND、ZEROTH_STATE、TRUE_FOR、查询示例、流计算、通知内容、EXPLAIN、错误处理）、性能、安全、兼容性、运维、使用场景、约束限制、常见错误排查到可观测性分层呈现，术语定义准确完整（状态窗口、状态键、多列状态键、切窗、有效记录、上一有效状态键、部分 NULL 候选段、EXTEND、ZEROTH_STATE、NO_ZEROTH），逻辑清晰、无歧义，符合 TDengine 设计文档规范要求。
4. 安全性、兼容性与性能考虑周全，风险可控：安全方面明确保证状态键顺序在不同节点间稳定一致避免错误切窗、通知数组顺序与 SQL 定义顺序一致避免消费者误读、非法 SQL 返回明确错误避免进入不确定执行路径；兼容性设计稳妥，单列历史写法（括号内位置参数）完全兼容、单列子句写法完全兼容、单列流通知 JSON 格式不变、多列为纯新增路径不影响现有行为，流触发器部署消息采用兼容演进解码端仍可读取旧单槽位格式、旧流定义无需重建；性能分析客观，单行比较从 O(1) 增加为 O(n) 对常见 2-4 列场景影响可控，明确指出多列状态窗口当前走通用路径在部分优化场景下可能略慢于单列窗口并标记为遗留 TODO，高频切窗场景额外开销主要来自逐列比较和通知 JSON 构造已有预期。

## 3. 评审结论

设计文档整体设计合理、逻辑清晰，功能覆盖全面，SQL 语法兼容设计、多列切窗规则、NULL 候选段归属决策、ZEROTH_STATE 多列过滤语义、流计算触发与通知 JSON 等核心设计规范严谨，使用场景贴合工业设备多维状态分析、告警压缩、生产状态切换等实际业务需求，性能、安全、兼容性设计符合系统规范，精准解决了状态窗口只能描述单一状态维度导致多字段联合状态分析依赖客户端后处理的核心痛点。
