## 2. 评审记录

评审团队对设计文档（拷贝模式数据修复 FS）进行了全面审查，认为整体设计贴合大数据量损坏场景下停机快速恢复的实际运维需求、逻辑严谨、可落地性强，具体评审意见如下：
1. 设计目标清晰精准，核心痛点定位明确，紧扣多副本集群中损坏数据量巨大时 restore 命令按行级解析和 Raft 快照重放性能无法满足客户要求、交付人员手动拷贝文件效率低下且易出错的实际运维痛点，明确核心目标为通过 `taosd -r --mode copy` 命令直接实现文件级拷贝修复，跳过编解码开销预期恢复速度提升一个数量级以上，目标聚焦、指引明确。
2. 功能设计全面细致，可落地性强，覆盖核心业务场景：命令行语法支持本地模式和远程 SCP 模式两种数据源，`--vnode`/`--all-vnodes source`/`--all-vnodes local` 三种 vnode 选择策略覆盖精确修复、完整克隆和交集修复场景；执行流程八步清晰（参数校验→TFS 配置加载→源端解析→连通性检查→vnode 列表确定→逐 vnode 拷贝→vnodes.json 更新→汇总报告），磁盘 ID 重映射规则按 tier 映射/折叠/单盘三种情况分别定义无歧义；出错处理覆盖配置缺失、SSH 连接失败、源端 vnode 不存在、单文件拷贝失败、磁盘空间不足、进程被 kill 六种错误场景，退出码 0-4 语义明确，进程被中断后可安全重新执行（步骤 6c 自动清除不完整数据）；三个使用示例（单盘本地、多级存储指定 vnode、远程 SCP）覆盖典型运维场景，便于交付和运维人员理解使用。
3. 设计文档结构规范，版本与修订记录清晰：明确修订记录（0.1 初稿 张博民），术语定义完整准确涵盖 TFS、磁盘 ID 重映射、主磁盘、SCP 四个核心概念，从背景、定义、行为说明、性能、安全、兼容性、运维、使用场景、约束限制、可观测性到参考文档分层呈现，关联 v3.4.1 数据修复工具 RS 和 FS 文档引用清晰，约束和限制分约束（仅 Linux、不支持容器、双端停机、版本一致、SSH 密钥认证）和限制（不支持增量拷贝、不并行、不做 CRC 校验）两类明确记录，逻辑清晰无歧义。
4. 安全性、兼容性与性能考虑周全，风险可控：安全设计覆盖 SSH 仅支持密钥认证（BatchMode=yes 非交互式执行）、命令注入防护（路径特殊字符严格转义 + isCommandAllowed 白名单机制 + 修复结束后恢复原白名单）、源数据只读访问、最小权限原则（建议专用只读 SSH 账户），安全措施全面；兼容性设计稳妥，`--mode copy` 为新增模式不影响现有 `--mode force` 行为，不修改任何配置参数/SQL 命令/API 接口，修复后数据格式与正常运行完全一致，vnodes.json 采用原子写入（临时文件 + rename）；性能方面明确不启用传输压缩（TSDB 数据已压缩、WAL/meta 体积小），修复在进入正常服务模式前执行并退出不影响正常运行，文件级拷贝跳过编解码开销性能优势显著。

## 3. 评审结论

设计文档整体设计合理、逻辑清晰，功能覆盖全面，命令行语法与 vnode 选择策略、八步执行流程、磁盘 ID 重映射规则、出错处理与退出码、SSH 安全防护与命令注入白名单机制等核心设计规范严谨，使用场景贴合大数据量损坏场景下停机快速恢复的实际运维需求，性能、安全、兼容性设计符合系统规范，精准解决了 restore 命令恢复性能不足、手动文件拷贝效率低下且易出错的核心运维痛点。
