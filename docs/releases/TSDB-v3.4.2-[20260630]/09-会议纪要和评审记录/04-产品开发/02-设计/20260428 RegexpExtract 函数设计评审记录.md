## 2. 评审记录

评审团队对设计文档（REGEXP_EXTRACT 函数 FS）进行了全面审查，认为整体设计对齐主流 SQL 生态字符串处理能力、语义清晰、可落地性强，具体评审意见如下：
1. 设计目标清晰精准，核心痛点定位明确，紧扣 TSDB 缺少正则子串提取能力导致日志字段子串提取依赖客户端后处理、基于正则匹配的派生列需要额外应用层处理、与 Hive/Spark 生态 SQL 迁移成本较高三大实际痛点，明确核心目标为引入与主流 SQL 引擎兼容的 REGEXP_EXTRACT(str, pattern[, group_idx]) 标量函数，增强字符串处理能力，目标聚焦、指引明确。
2. 功能设计全面细致，可落地性强，覆盖核心业务场景：核心语义定义准确，group_idx 默认值 1（第一个捕获组）、group_idx=0 返回完整匹配、超出捕获组数返回 NULL 不报错的行为清晰无歧义；参数规则完整，pattern 须为编译期常量（线程本地缓存编译复用不逐行重新编译）、group_idx 须为 0 到 512 之间整数常量、NULL 参数传播 NULL 到输出；返回值语义覆盖 11 种场景（匹配成功各组、未参与捕获组、NULL 输入、无匹配、超出组数、空串匹配），捕获组匹配空串返回空字符串而非 NULL 的边界处理精准；与现有 MATCH/NMATCH 的关系明确（布尔过滤 vs 子串提取，正交互补）；正则规范采用 POSIX ERE 与 TSDB 现有正则保持一致；跨引擎语义差异对比表（Hive/Spark/Trino/本实现）清晰展示设计选择依据；使用场景覆盖 IP 提取、协议名提取、错误类型提取、完整匹配、WHERE 过滤、嵌套子查询六类典型用法，便于用户理解使用。
3. 设计文档结构规范，版本与修订记录清晰：明确修订记录（0.1 初稿 Stephen），12 个章节从背景、定义、行为说明、性能、安全、兼容性、运维、使用场景、约束限制、常见错误排查到可观测性分层呈现，边界场景表覆盖 15 种输入组合预期行为，常见错误排查表覆盖 8 种错误场景并给出处理建议，逻辑清晰、无歧义，符合 TDengine 设计文档规范要求。
4. 安全性、兼容性与性能考虑周全，风险可控：安全方面明确 ReDoS 风险（恶意正则触发指数级回溯导致 CPU 长时间占用）并给出缓解措施（依赖 readTimeout 和查询级超时配置），REGEXP_EXTRACT 仅需 SELECT 权限无需单独授权；兼容性设计稳妥，REGEXP_EXTRACT 为全新函数不影响已有查询行为，无历史数据格式变更无需升级迁移，旧版本降级后报解析错误符合预期；性能方面 pattern 为常量在线程本地缓存首次编译复用不逐行重新编译开销可控，回溯型 ERE 引擎在嵌套量词下 CPU 开销风险已明确建议加锚点限制回溯范围。

## 3. 评审结论

设计文档整体设计合理、逻辑清晰，功能覆盖全面，REGEXP_EXTRACT 核心语义、参数规则、返回值语义、边界场景、正则规范、跨引擎对比等核心设计规范严谨，使用场景贴合主流 SQL 生态字符串处理需求，性能、安全、兼容性设计符合系统规范，精准解决了 TSDB 缺少正则子串提取能力导致日志解析和数据清洗依赖客户端后处理的核心痛点。
