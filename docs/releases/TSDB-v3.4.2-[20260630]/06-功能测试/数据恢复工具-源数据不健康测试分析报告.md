## 概述

本测试文件针对 `taosd -r --mode copy` (vnode copy-mode repair) 的四个异常/边界场景编写用例，验证修复工具在接收到"不健康"的源数据时，能否正确拒绝或报错，而非静默产生错误结果导致数据丢失。

| 场景 | 方法名 | 核心问题 | 当前状态 |
|------|--------|----------|----------|
| B | `test_corrupted_source_file_detected` | 源文件内容损坏（大小正确） | **BUG** — 工具未检测，直接拷贝损坏数据 |
| C' | `test_partial_current_json_causes_data_loss` | 源 current.json 部分缺失 fid | **BUG** — 工具以不完整列表为准，丢弃未列出的 file set |
| D | `test_stale_source_causes_data_loss` | 源数据比本地旧 | **BUG** — 工具用旧数据覆盖新数据 |
| E | `test_missing_dnode_in_nodeinfo` | 源 vnode.json 的 nodeInfo 不含目标节点 | **已正确处理** — 工具返回 rc=4 |

## 场景 B：源文件内容损坏但大小正确

### 问题现象

修复工具在拷贝 TSDB 文件后，仅校验 `目标文件大小 == 源文件大小`，不做任何内容完整性校验（如 checksum、magic number）。如果源 `.stt`/`.data`/`.head`/`.sma` 文件已全零损坏但大小不变，修复工具会以 rc=0 成功返回，将垃圾数据完整复制到目标 vnode。

### 复现步骤

1. 创建 3 副本数据库，写入 2500 行数据并 flush
2. 对源节点 vnode 数据做快照备份
3. 在快照中将所有 TSDB 数据文件（`*.head`、`*.data`、`*.sma`、`*.stt`）用全零覆盖，保持文件大小不变
4. 停止目标节点，清除其 tsdb 目录
5. 使用被损坏的快照作为源，执行 `taosd -r --mode copy`
6. **不启动 taosd**（避免集群同步修复掩盖问题），直接检查目标 vnode 的 tsdb 文件

### 验证逻辑

- 若 repair 返回非零 → **PASS**（工具检测到损坏并拒绝）
- 若 repair 返回 0 → 检查目标 tsdb 文件前 4096 字节是否全为 `\x00`
  - 发现全零文件 → **FAIL**：`CORRUPTION PROPAGATED: repair succeeded (rc=0) and copied N zero-filled file(s) to target without any integrity check`
  - 无全零文件 → PASS（意外情况，源已损坏但目标干净）

### 示例

```
# 源快照中的文件（已损坏）:
/sim/dnode1/data/vnode/vnode2/tsdb/v2f2059ver1.stt   (524288 bytes, 全为 0x00)
/sim/dnode1/data/vnode/vnode3/tsdb/v3f2059ver1.stt   (524288 bytes, 全为 0x00)

# 执行修复:
$ taosd -c /sim/dnode3/cfg -r --mode copy \
    --source-cfg /sim/dnode3/cfg_corrupt_src/taos.cfg \
    --node-type vnode --vnode 2,3

# 工具输出 (当前行为):
[INFO] vnode2: copy file v2f2059ver1.stt, size=524288 ... OK
[INFO] vnode3: copy file v3f2059ver1.stt, size=524288 ... OK
[INFO] repair completed successfully
exit code: 0                    ← 仅校验大小，未检测内容全零

# 修复后目标节点的文件:
/sim/dnode3/data/vnode/vnode2/tsdb/v2f2059ver1.stt   (524288 bytes, 全为 0x00) ← 损坏数据被原样复制!

# hexdump 验证:
$ hexdump -C /sim/dnode3/.../v2f2059ver1.stt | head -3
00000000  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |................|
*
00080000
```

### 预期修复方向

工具应在拷贝前/后对源 TSDB 文件执行基础完整性校验（如验证文件头 magic number 或计算 checksum），检测到损坏时返回非零退出码并拒绝操作。

## 场景 C：source current.json 部分缺失 fid 条目

### 问题现象

修复工具将源 `current.json` 中的 file set 列表作为"真相"。若源 `current.json` 因截断写入或部分损坏，仅列出部分 fid，则修复后目标 vnode 的 `current.json` 也只包含这些不完整的 fid。未列出的 file set 被永久丢弃 — 既不从源拷贝，也不从本地保留。

### 复现步骤

1. 创建 3 副本数据库，设置 `duration 1d`（缩短文件周期以产生多个 fid）
2. 分 3 批写入数据，每批写入不同天（`now-5d`、`now-3d`、`now-1d`），每批后 flush，产生 3+ 个 file set
3. 执行 `compact database` 确保 fid 完全物化
4. 对源节点做快照
5. 编辑快照中各 vnode 的 `tsdb/current.json`：`fset` 数组只保留第 1 个元素，删除其余 fid 条目
6. 停止目标节点，清除 tsdb 数据
7. 使用篡改后的快照执行 `taosd -r --mode copy`
8. 启动 taosd，查询总行数

### 验证逻辑

- 若 repair 返回非零 → **PASS**（工具检测到 current.json 不一致）
- 若 repair 返回 0 → 查询 `select count(*) from stb`
  - 行数 < 预期 → **FAIL**：`DATA LOSS DETECTED: partial current.json caused N rows to be lost!`
  - 行数 == 预期 → PASS（集群同步恢复了数据，bug 被掩盖）

### 示例

```
# 源 vnode2 磁盘上实际存在 3 个 file set:
/partial_source/vnode/vnode2/tsdb/v2f20588ver1.stt   (存在)
/partial_source/vnode/vnode2/tsdb/v2f20589ver1.stt   (存在)
/partial_source/vnode/vnode2/tsdb/v2f20590ver1.stt   (存在)

# 但篡改后的 current.json 只列出 1 个 fid:
$ cat /partial_source/vnode/vnode2/tsdb/current.json
{
  "fmtv": 1,
  "fset": [
    {"fid": 20588, "head": {...}, "data": {...}, "sma": {...}, "stt lvl": [...]}
    // fid 20589 和 20590 被删除了!
  ]
}

# 执行修复:
$ taosd -c /sim/dnode3/cfg -r --mode copy \
    --source-cfg /sim/dnode3/cfg_partial_src/taos.cfg \
    --node-type vnode --vnode 2,3

# 工具输出 (当前行为):
[INFO] vnode2: source has 1 file set(s), target has 0
[INFO] vnode2: copy 1 file set(s) from source
[INFO] vnode2: current.json generated (1 file set(s))    ← 只写入了 1 个 fid!
exit code: 0

# 修复后目标 current.json:
$ cat /sim/dnode3/data/vnode/vnode2/tsdb/current.json
{"fmtv":1, "fset":[{"fid":20588, ...}]}               ← 丢失了 fid 20589, 20590 的数据!

# 数据丢失:
修复前: select count(*) → 2700 行 (3 个 fid 各含 900 行)
修复后: select count(*) → 900 行  (只剩 fid 20588 的数据)
丢失:   1800 行 (67% 数据永久丢失)
```

### 预期修复方向

工具应：
- 校验源 `current.json` 中列出的 fid 与磁盘上实际存在的 TSDB 文件是否匹配
- 发现 fid 缺失时发出明确 WARNING 或 FATAL_ERROR
- 或保留本地存在但源未提及的 file set（它们可能是本地更新的数据）

## 场景 D：源数据比本地数据旧（stale source）

### 问题现象

修复工具无条件用源数据覆盖目标。如果源是一个过时的快照（缺少最新写入的 file set），修复后目标 vnode 丢失了新写入的数据 — 因为源的 `current.json` 不含新 fid，修复工具按源列表重建目标后新数据不存在。

### 复现步骤

1. 创建 3 副本数据库，写入 Phase 1 数据（2500 行）并 flush
2. 对源节点 vnode 数据做快照（此时快照包含 Phase 1）
3. 继续写入 Phase 2 数据（再 2500 行）并 flush — 快照现在是过时的
4. 确认总行数 = 5000
5. 创建指向过时快照的 `taos.cfg`
6. 停止目标节点，清除 tsdb 数据
7. 使用过时快照执行 `taosd -r --mode copy`
8. 启动 taosd，查询总行数

### 验证逻辑

- 若 repair 返回非零 → **PASS**（工具检测到源数据过旧并拒绝）
- 若 repair 返回 0 → 查询 `select count(*) from stb`
  - 行数 < 5000（Phase 2 数据丢失） → **FAIL**：`DATA LOSS DETECTED: stale source repair dropped data! Expected count>=5000, got N. Phase 2 rows: expected 2500, got 0.`
  - 行数 == 5000 → PASS（集群同步恢复了数据，bug 被掩盖）

### 示例

```
# 时间线:
  T1: 写入 Phase 1 (2500行)，flush → 源快照在此时生成
  T2: 写入 Phase 2 (2500行)，flush → 目标节点上已有 5000 行

# 源快照 (T1 时刻) 的 current.json:
$ cat /stale_source/vnode/vnode2/tsdb/current.json
{
  "fmtv": 1,
  "fset": [
    {"fid": 2059, ...}              ← 只有 Phase 1 的 file set
  ]
}

# 目标节点 (T2 时刻) 实际 current.json:
$ cat /sim/dnode3/data/vnode/vnode2/tsdb/current.json
{
  "fmtv": 1,
  "fset": [
    {"fid": 2059, ...},             ← Phase 1
    {"fid": 2060, ...}              ← Phase 2 (源快照中不存在!)
  ]
}

# 执行修复 (用过时的 T1 快照覆盖 T2 的目标):
$ taosd -c /sim/dnode3/cfg -r --mode copy \
    --source-cfg /sim/dnode3/cfg_stale_src/taos.cfg \
    --node-type vnode --vnode 2,3

# 工具输出 (当前行为):
[INFO] vnode2: source has 1 file set(s)
[INFO] vnode2: copy completed
exit code: 0                        ← 无条件用旧数据覆盖

# 数据丢失:
修复前: select count(*) → 5000 行
修复后: select count(*) → 2500 行   ← Phase 2 数据全部丢失!
        select count(*) where s like 'p2_%' → 0 行
```

### 预期修复方向

工具应：
- 比较源与本地 `current.json` 的 fid 列表，若本地有源中不存在的 fid，说明源是过时的
- 拒绝操作或将本地独有 fid 保留，防止数据回退

## 场景 E：源 vnode.json 的 nodeInfo 不包含目标 dnodeId

### 问题现象

当源 vnode.json 的 `syncCfg.nodeInfo[]` 中不包含目标节点的 dnodeId 时（如源来自另一个 replica group 或集群拓扑已变更），修复工具应拒绝操作 — 否则修复后的 vnode 的 sync 身份会错误。

### 复现步骤

1. 创建 3 副本数据库，写入数据并 flush
2. 对源节点做快照
3. 编辑快照中各 vnode 的 `vnode.json`：从 `syncCfg.nodeInfo[]` 中移除包含目标 dnodeId 的条目
4. 停止目标节点，清除 tsdb 数据
5. 使用篡改后的快照执行 `taosd -r --mode copy`

### 验证逻辑

- 若 repair 返回非零 → **PASS**（当前实际行为：rc=4，日志报 `dnodeId N not found in syncCfg.nodeInfo`）
- 若 repair 返回 0 → 检查目标 `vnode.json` 中 `myIndex` 是否指向正确的 nodeId
  - myIndex 指向错误节点 → **FAIL**：`SYNC IDENTITY BUG`
  - myIndex 正确 → PASS（意外，但可接受）

### 示例

```
# 正常的 vnode.json (3 副本集群, dnode1/2/3):
$ cat /sim/dnode1/data/vnode/vnode2/vnode.json
{
  "config": {
    "syncCfg.myIndex": 0,
    "syncCfg.nodeInfo": [
      {"nodeId": 1, "nodeFqdn": "localhost", "nodePort": 6030},
      {"nodeId": 2, "nodeFqdn": "localhost", "nodePort": 6130},
      {"nodeId": 3, "nodeFqdn": "localhost", "nodePort": 6230}
    ]
  }
}

# 篡改后的源 vnode.json (移除目标 dnode3):
$ cat /tampered_source/vnode/vnode2/vnode.json
{
  "config": {
    "syncCfg.myIndex": 0,
    "syncCfg.nodeInfo": [
      {"nodeId": 1, "nodeFqdn": "localhost", "nodePort": 6030},
      {"nodeId": 2, "nodeFqdn": "localhost", "nodePort": 6130}
      // nodeId=3 被移除了!
    ]
  }
}

# 执行修复 (目标是 dnode3):
$ taosd -c /sim/dnode3/cfg -r --mode copy \
    --source-cfg /sim/dnode3/cfg_tampered_src/taos.cfg \
    --node-type vnode --vnode 2,3

# 工具输出 (当前行为 — 已正确处理):
[ERROR] vnode2: dnodeId 3 not found in syncCfg.nodeInfo
[ERROR] repair failed for vnode2
exit code: 4                        ← 正确拒绝!
```

### 当前结果

**已正确处理**。修复工具返回 rc=4 并在日志中输出明确的错误信息，拒绝执行操作。

## 注意事项

1. **3 副本集群同步效应**：在 3 副本环境中，即使修复工具搞坏了目标节点的数据，taosd 启动后其余 2 个副本会自动通过 Raft 同步修复。这会掩盖修复工具的 bug。测试 B 通过在启动前直接检查磁盘文件绕过此问题；测试 D 和 C' 目前受此影响，在 3 副本环境下可能被掩盖。

2. **TSDB 文件类型**：小数据量场景只产生 `.stt` 文件，不产生 `.head`/`.data`/`.sma`。测试 B 搜索所有四种扩展名以确保能找到可损坏的文件。

3. **多 fid 条件**：默认 `fileDuration` 约 10 天，需设置 `duration 1d` 并跨多天写入数据才能产生多个 fid，否则所有数据共享同一个 file set。
