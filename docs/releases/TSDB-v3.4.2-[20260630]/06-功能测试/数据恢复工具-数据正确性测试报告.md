## 测试目的

验证 `taosd -r --mode copy` 在大数据量场景下的数据修复正确性。特别关注：

1. 数据文件（tsdb/）和预写日志（wal/）同时被销毁后，能否通过 copy-mode 从备份完整恢复数据
2. 修复后全部聚合查询结果与修复前完全一致，无数据丢失或错乱

## 重点测试：大数据量准确性验证

### 测试参数

| 参数 | 值 |
|------|-----|
| 子表数量 | 50 |
| 每表行数 | 200,000 |
| 总数据行数 | **10,000,000** |
| 批次大小 | 5,000 行/次 |
| Vgroup 数量 | 4 |
| 数据总磁盘占用 | ~272 MB |
| 列结构 | `ts timestamp, current float, voltage int, phase float` |

### 测试流程

```
1. 创建数据库 (4 vgroups)
   ↓
2. 写入 10,000,000 行数据 (50表 × 200K行)
   ↓
3. 执行 flush database，确保数据落盘到 tsdb 文件
   ↓
4. 执行 10 条聚合查询，记录基线结果 (baseline)
   ↓
5. 备份全部 vnode 数据目录 → data_backup/
   ↓
6. 停止 taosd
   ↓
7. 销毁所有 vnode 的 tsdb/ 和 wal/ 目录 (模拟数据完全丢失)
   ↓
8. 执行 copy-mode 修复:
   taosd -c <cfg> -r --mode copy --node-type vnode
         --source-cfg <backup_cfg> --vnode 2,3,4,5
   ↓
9. 重启 taosd
   ↓
10. 重新执行相同 10 条查询，逐一与基线比对
```

### 破坏方式（强化验证）

```
销毁内容: tsdb/ + wal/  (不仅仅是 tsdb)
```

| 目录 | 作用 | 销毁后果 |
|------|------|----------|
| `tsdb/` | 时序数据存储文件 | 数据文件丢失 |
| `wal/` | Write-Ahead Log | 无法通过 WAL 回放恢复 |

> **关键点**：同时销毁 tsdb 和 wal 后，数据**只能**通过 copy-mode repair 从备份恢复，
> 排除了 WAL 自动回放恢复的可能性，真正验证了 repair 工具的修复能力。

### 修复详情（每个 vnode）

repair 工具对每个 vnode 执行以下操作：
- 从备份源复制 tsdb 数据文件
- 生成 `current.json` (9 file sets per vnode)
- 更新 `vnode.json` 中 `syncCfg.myIndex` 为 0
- 更新 `raft_config.json` 中 `myIndex` 为 0
- 删除 `raft_store.json` (重置选举状态)
- 清理备份临时目录

## 结论

1. **功能正确性**: `taosd -r --mode copy` 在 10,000,000 行数据量下修复功能完全正确
2. **数据完整性**: 修复后全部聚合查询结果与修复前基线完全一致，无数据丢失
3. **破坏恢复能力**: 即使 tsdb 和 wal 同时被销毁（无法通过 WAL 自恢复），repair 工具仍能从备份完整恢复数据
4. **性能表现**: 4 个 vnode (每个约 9 个 file set, 总计 ~272MB) 修复耗时约 1 秒
5. **稳定性**: 从 1K 到 10M 行，多轮测试均稳定通过，未出现任何数据不一致

**测试结论: PASS ✅**
