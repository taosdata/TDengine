# TD-22830 控制 WAL 文件保留大小测试报告

## 一、测试概述

     WAL 文件保留大小及时长在之前的版本中不但受 WAL_RETENTION_PERIOD 及 WAL_RETENTION_SIZE 两参数的影响，而且还受是否有订阅影响，比较混乱，而且容易出问题。本次对WAL 功能进行了统一约定，仅由上面两个参数控制，不再受订阅影响，简化了程序逻辑。详见：
[WAL 配置参数及行为定义](https://taosdata.feishu.cn/wiki/wikcnyGzP8iwc0XyE1ExSZnJCU1) 
     本测试对以上约定的行为进行验证，符合预期为通过。

### 3.2 测试方案

####   1、参数  WAL_RETENTION_PERIOD

    WAL 保留数据的时长，只能通过订阅进行消费来读取到最早的数据进行衡量，开始的时间为 NOW ，结束的时间为NOW + WAL_RETENTION_PERIOD 
  1）设置 WAL 的参数 WAL_RETENTION_PERIOD 为 1 days， WAL_RETENTION_SIZE 为 -1（不限制）
2）创建超级表 st
3)  创建子表  t1  
4)  创建订阅 select * from st
5)  写入数据，时间为 1 days 内的 100条，1 days 外的 20 条
        6）创建消费订阅程序
        7）预期为 1 days 内的 100条可以收到订阅消费， 1days 外的 20 天收到不了（已经过期）
      以上步骤再循环测试 最小 period 和最大period 

####      2、参数 WAL_RETENTION_SIZE

    WAL 保留数据的大小，只能通过到所在vnode 目录下的 wal 中读取现有文件的大小 
  1）设置 WAL 的参数 WAL_RETENTION_PERIOD 为 -1 （无限制）， WAL_RETENTION_SIZE 为 指定的值 100M
2）创建超级表 st
3)  创建100个子表  t1  ... t100
4)  连续大批量写入数据，每次写入完后检查WAL大小是否在预期内（100M）
        5) 写入到 100W 条记录，预期为 WAL 文件大小始终不超过 100M  

####      3、1+2 的混合模式

   测试1 或 2 哪个条件先到先触发哪个的验证
1） 设置  WAL_RETENTION_PERIOD 为 1 day ， WAL_RETENTION_SIZE 为 指定的值 100M
2)   先验证让时间起作用，写入 1W 条 1-days 内的，100 条 1-days 外的，预期是 100条 1-days 外的无法消费到
3）再验证让大小起作用，写入 120 W条 1 -days 内的，预期是订阅消费不到 120w 条（假设120w占用 120WAL），只能拿到 100W 条记录为符合预期
4）最后验证 1 和 2 都设置为无限制，验证写入时间 100 days ， 大小 1G ，预期是数据都能消费到

#### **      4、参数 WAL_SEGMENT_SIZE **

   上面的验证步骤中加入 WAL_SEGMENT_SIZE 的参数设置，有运行过程中检测 wal 单个文件在此范围内为符合预期。

#### **5、原来有订阅存在的升级场景验证**

**     **按说明文档，如果原来有订阅并且 WAL_RETENTION 为 0 的情况下会按以前的行为进行消费，需要验证

### **3.3  CI 自动化验证 **

方案一 单独测试 WAL_RETENTION_PERIOD 生效的正确性
1、CASE 跑的时长 3 分钟
2、WAL_RETENTION_PERIOD 配置为 30秒，即 30 秒后的 WAL 应该被删除
3、WAL_RETENTION_SIZE 配置为 0， 没有限制
4、 5 节点 3 mnode  3 副本
5、1个超级表，1W 子表，每个子表写入 10W 行数据
6、创建一个订阅，但不去消费
7、检测程序 sleep 30 秒后 每隔 10 秒检测一次各 VNODE 是否有超过 设置的 WAL_RETENTION_PERIOD 时间应该删除但没有被删除的文件

## 四、测试报告

#### **1、验证功能列表**

| 内容 | 结果 |
| --- | --- |
| WAL_RETENTION_PERIOD  选项生效 | 通过( walRetention.py case 验证) |
| WAL_RETENTION_SIZE       选项生效 | 通过( walRetention.py case 验证) |
| 升级兼容性，  WAL_RETENTION_PERIOD 为零时，预期行为是升级到新版本 WAL 中文件仍然保持不变，预期是和原来一致，不删除 | 通过 |
| 升级兼容性， 升级后写入一些数据，无消费， flush database 后，观察 WAL 文件是否有被删除，预期是无消费 WAL 永远不会删除 | 通过 |
| 升级兼容性，创建消费者，把所有数据都消费完，预期为在 snapVer 之前的文件都应删除 | 通过 |
| 升级兼容性，消费进行中的时候，要消费的下一个文件被删除验证，预期为跳过下一个被删除的文件，继续消费，程序不崩溃 | 通过 |
| 内部规则验证，引擎内部默认会保留 256个版本号的 WAL 文件，每个 WAL 文件最大不超过 5M ，这样计算即使每个版本一个 WAL 文件（实际是一个WAL 文件中会包括多个版本号）的最大情况计算， WAL 保留的大小最大是 256 * 5M = 1280M , 约 1G 大小多一些，如果没有单独设置更大的 WAL 保留大小选项，预期 WAL 文件不会超过 1280M 大小 | 通过( walRetention.py case 验证) |
| 同时有订阅消费情况下 WAL 的保留大小行为，预期是 WAL 保留文件大小只受 WAL 两个保留选项及 WAL 内部保留的 256个版本的规则限制，不受订阅及消费的影响 | 通过( walRetention.py case 验证) |
| 只开启 WAL_RETENTION_PERIOD 选项， WAL_RETENTION_SIZE 为默认的场景验证，预期是过期时间达到后触发删除规则 | 通过( walRetention.py case 验证) |
| 只开启 WAL_RETENTION_SIZE 选项，WAL_RETENSION_PERIOD 为默认场景下的验证，预期是只有文件大小达到后触发删除规则 | 通过( walRetention.py case 验证) |
| 同时开启 WAL_RETENTION_PERIOD 和 WAL_RETENTION_SIZE 两选项，预期是哪个条件先达到哪个先触发删除规则 | 通过( walRetention.py case 验证) |
| 长时间大流量高压力场景验证，预期是和小流量短时间验证结果一致 | 通过( walRetention.py case 验证) |
| 集群 + 多副本模式下的验证，预期为和单节点单副本结果一致 | 通过( walRetention.py case 验证) |
