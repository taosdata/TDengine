# 3.3.0.0 问题及复盘

## 1. 发版延期和原因

本节总结导致发版延期的直接原因，在发版前还有一组问题未解决，这些必须解决的问题被标记为 [blocking issue](https://jira.taosdata.com:18080/issues/?jql=labels%20in%20(blocking)%2520ORDER%2520BY%2520updated%2520DESC)，在 5.1 前绝大多数已经解决，但有两个严重问题在 5/1 后解决发版，[TD-29981](https://jira.taosdata.com:18080/browse/TD-29981) ，[TD-29983](https://jira.taosdata.com:18080/browse/TD-29983)
主要原因是兼容性用例中未打开 last 缓存，不然可以在代码合入时就能够发现，可以提前至少一到两周发现问题，不会如此被动。
相应的复盘及补救措施：[5. ci 中的兼容性测试用例](https://taosdata.feishu.cn/wiki/wikcnaV1m87w3xt10gePMQ2jNSf)

## 2. 遗留问题和原因

在正式发布 3.3.0.0 后仍然有一些遗留问题或功能延期，对其中原因做了归类

### 2.1 优先级调整和资源不足导致延期

1. taosX Data in Oracle 延期 （由于 Pi data transformation 产生的资源问题导致优先级调整）
2. OPC 点位动态更新  延期 （由于 OPC 客户支持产生的资源问题）
3. Explorer 支持复合主键和列压缩  延期（由于员工家中重大变故请长假产生的资源问题）

### 2.2 对性能问题重视不够或时间不足

#### 2.2.1 [双副本的性能问题](https://jira.taosdata.com:18080/browse/TD-29879)

1. 更新 vgroup leader 状态重复发起事务，极端情况下有可能造成这些事务永远处理不完
2. 更新 vgroup leader 没有合并事务，发起大量相同类型的事务
这两个性能问题在设计和编码时就应该有相应的意识，开发人员当时没有意识到。在测试阶段发现了，但开发和测试对问题的严重性都不够重视，过程中有一定拖延，导致形成决策时已经临近发版，本来是有充足的时间解决的。

#### 2.2.2 [复合主键导致的查询性能](https://jira.taosdata.com:18080/browse/TD-29745)

TSBS 的测试结果，QA 在 4/24 确认了查询性能下降 14~24%，但开发忙于修复其它基本的功能问题以及合入代码等，无暇顾及性能优化，导致现在还未完全解决。

#### 2.2.3 TSMA 的性能和资源占用问题

TSMA 依赖流计算，流计算的 checkpoint 还有优化空间，目前 TSMA 使用中要限制数量以及窗口数量（单个窗口中的数据量不能过小），否则会产生很高的资源占用。TSMA 的问题最终都发现出来了，其自身直接相关的问题基本都解决了，但与流有关的以及一些影响较弱的问题尚未解决。[TSMA 遗留问题](https://jira.taosdata.com:18080/issues/?jql=labels%20%3D%20tsma%20and%20type%20%3D%20RD-defect%20and%20status%20not%20in%20(%20CANCELED%20%2CTesting%20%2CDONE)%2520%2520)

### 2.3 测试不够充分和深入

#### 2.3.1 引擎

1. last 缓存问题：修复了发版前的 last 问题后，发版后又发现了新的与 last 有关的问题
   - [TS-4794](https://jira.taosdata.com:18080/browse/TS-4794)
   - [TD-29985](https://jira.taosdata.com:18080/browse/TD-29995)
2. 阿里云 S3 不工作：受限于测试环境，仅测试了腾讯云和 mimio 模拟环境
3. 双副本的查询性能问题，详见 [[酒泉项目]2节点单副本升级双副本验证](https://taosdata.feishu.cn/wiki/N1s3wOtkhiTbnjkuvUWcbK5vnVe)

#### 2.3.2 taosX

1. 数据迁移在 WebSocket 下的性能问题，原因较多，[详见](https://jira.taosdata.com:18080/browse/TD-30066) 
   - 引擎在以订阅接口提供元数据信息时性能差 （内部测试中已经发现，但未解决）
   - 相对于原生连接，WebSocket 接口的写入和读取性能差距较大 （内部测试因为资源问题和责任边界一直未进行系统测试，Wade 承担主要责任）
   - taosX 在服务模式下不支持原生连接（此为几个版本前做出的产品决策，如 WebSocket 性能提升到位，则此问题可以忽略）
2. 数据迁移在命令行模式下 crash，此问题原因复杂
   - 产品决策上从 1.4.0 已经放弃继续发展命令行模式，也和交付组强调过，但交付组习惯性地使用命令行在客户现场进行数据迁移
   - 测试组根据产品决策，只测试 websocket 和服务模式，两者共同产生了此问题。
   - 决策：产品侧尽快解决 WebSocket 的性能问题，但交付组在客户现场应放弃使用命令行模式（因为其不具备断点续传、任务自动恢复、可观测性等重要能力）
3. MySQL/PostgreSql 的数据接入
   - 功能本身没有问题
   - 主要原因是界面上的示例和报错不够清晰，测试没有提出这些问题

#### 2.3.3 复合

1. 双活的异常场景（测试用例设计中未覆盖后端单一组件失败的场景，未覆盖连接参数无效的异常场景或覆盖不足，对双活的健壮性未进行压力测试）
2. 文档问题（杂项）：文档是在发版前匆忙赶出，没有经过细致 Review，资源和时间问题
   - 描述不清楚
   - 错误消息不准确
   - 缺少最佳实践

## 3. 原因剖析

1. 客观原因：
   - 3.3.0.0 的任务安排过于庞大，引擎侧有七八个非常大的特性（Join，复合主键，TSMA），taosX 一侧的内容细项也很多。3.3.0.0 如果按常规节奏应该拆成两个版本
   - 客户支持较多：1） OPC 的企业版客户支持；2）Pi data transformation 支持 Jeff 的 PoC，经过了快速在开发分支上开发新的功能进行 demo、出现意想不到的问题再回退到旧分支、最后再花较大力气整合两个分支；3）taosX 的本地客户支持（客户支持较重是产品力不足的结果，但和较重的开发周期迭加在一起会导致两个目标，即客户成功和产品开发，都完成得不好）
2. 主观原因：
   - 测试用例设计不充分，特别是异常场景覆盖不足
   - 测试组不够较真，对清晰的示例、输入提示和错误消息没有较真
   - 旧有的兼容测试用例有功能遗漏项但无人知晓，直到这次有问题才发现，如果此次未发现，以后早晚会出现。
   - 开发人员对性能问题的敏感度和重视不够
   - 部分特性的开发转测试质量较差，下游测试阶段修复基本问题的时间占比很高

## 4. 教训和计划

1. 放缓产品 roadmap 的节奏，让开发和测试更扎实一些，也有一定的 buffer 承接客户支持。版本规划过大这个原因至少对延期的几项功能和性能问题上是有直接影响的。
2. 测试用例的设计上要加强，犯过的错不再犯，加强对异常场景的测试用例设计；引入交付组 Review 关键特性的测试用例设计。这是有一定主观性的，即使时间充足，未必就不会犯这个错误。
3. 开发自测仍然要加强，提升质量，提高下游的效率。有客观时间和主观重视程度两方面的因素，有些 feature 的复杂度也很高，但提测质量就不错，如 Join。但有些 Feature 即使不复杂，提测质量也不行，table merge scan 一个简单的优化做了两个月，结果还是一堆问题且性能提升只是聊胜于无的水平，就是开发人员的主观重视和投入不够。
4. 引擎测试组增加混沌测试机制，这是一直以来的短板，有些客户现场的问题其触发原因非常复杂，我们在家里通过各种常规测试手段确实测试不出来，需要提升测试手段，增加系统运行的随机性和不确定性。
5. 应用测试组增加各项功能的压力测试和复杂数据模型，覆盖 WebSocket 的性能（同比，以及与原生连接的对比），目前的状态是长时间的压力测试不够、数据模型复杂度不够、WebSocket 未覆盖。

## 5. 待讨论事项-产品开发优先级

   - 3.0->3.0 数据迁移和同步的稳定性
   - 导入 CSV 的产品行为和性能的优化 
4. 工具
   - taosBenchmark 根据配置生成 CSV 文件（取代写入引擎）
   - taosBenchmark 的 slice 模式支持定向 VGroup 写入
