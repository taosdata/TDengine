# 重复时间戳的简易方案

## 1. 技术方案

原始数据
- 第一列：交易时间。精确到毫秒 int64。
- 第二列：序列号。每天开盘后，序列号从 1 开始计数，所有股票共用这一个序列号。一个交易所每天大概有上亿条交易记录，因此序列号是 int64。
交易时间和序列号合在一起，可以唯一标志出一条交易记录。假设与如下两条记录，时间戳相同，但是交易序号不同
```plaintext
ts                        sequence       ……
===============================================
2023-10-23 00:00:00.000    999999        ……
2023-10-23 00:00:00.000   1000003        ……
```

### 1.1 方案一：时间精度补充

提供时间精度补充函数（ap)， 在 insert 语句中使用，将输入时间戳补充 6 位十进制有序数值
```sql {wrap}
taos> create database db precision 'ns';
taos> create table st (ts timestamp, seq bigint, ……) tags ……
taos> create table t1 using st ……

taos> insert into table1 values
    (ap('2023-10-23 00:00:00.000',  999999 % 1000000), 999999)
    (ap('2023-10-23 00:00:00:000', 1000003 % 1000000), 1001003);
    
taos> select ts, seq from table1 ;
             ts                |         seq        |
======================================================
 2023-10-23 00:00:00.000000003 |            1000003 |
 2023-10-23 00:00:00.000999999 |             999999 |
    
taos> select to_char(to_timestamp(ts, 'YYYY-MM-DD HH:MI:SS.MS'), 'YYYY-MM-DD HH:MI:SS.MS') ts_ms, i from table1; 
             ms          |        seq        |
===============================================
 2023-10-23 00:00:00.000 |           1000003 |
 2023-10-23 00:00:00.000 |           999999  |
 
 #如果觉得 to_char 和 to_timestamp 使用麻烦，也可以实现降低精度函数，在 select 语句中使用
```

- 实现思路
  - 客户端中每个子表都有缓存，内容是表的 schema。
  - 缓存内容中增加 last_ts，write_seq
  - 在 insert 语句中
    - 输入时间戳 == last_ts 时，将 write_seq 补充到当前时间戳，write_seq ++
    - 输入当前时间戳 != last_ts，将 write_seq 重置为 0，将 last_ts 重置为当前时间戳
- 优点
  - 仅在客户端做微小的修改，服务端完全不动
  - 结合 to_timestamp、to_char 函数，能够解决查询返回的时间精度问题 （[支持时间转换函数](https://taosdata.feishu.cn/wiki/Onoqwn2lQi3BWtkCVFichW1rn6c) ）
- 缺点
  - **存在乱序。因为需要对数据取模，交易记录出现无法避免的乱序**
  - 未从机制上解决重复时间戳问题
  - 改变了用户常规使用行为

### 1.2 方案二：将 64 位时间戳拆分为时间和序列号

第一列的时间戳是 64 位无符号整数，将前 48 位表示毫秒，后 16 位表示序列号。在金融应用时，表的第一列为毫秒精度时间戳，第二列为 16 位无符号的序列号。
```sql {wrap}
taos> create database db precision 'ms';
taos> create table st (ts timestamp, pseudo_seq smallint, seq bigint, ……) tags ……
taos> create table t1 using st ……

taos> insert into table1 values
    ('2023-10-23 00:00:00.000',  999999 % (2^16), 999999)
    ('2023-10-23 00:00:00:000', 1001003 % (2^16), 1001003);
    
taos> select ts, pseudo_seq, seq from table1 ;
             ts          | pseudo_seq |    seq   | 
==============================================================
 2023-10-23 00:00:00.000 |      16959 |   999999 |
 2023-10-23 00:00:00.000 |      17963 |  1001003 |
 
```

- 实现思路
  - 写入数据时，将第一列和第二列通过位运算拼接在一起，成为 64 位数值
  - 查询数据时，将存储在数据文件的 64 位数值，拆分成第一列时间戳和第二列序号
- 优点
  - 仅在服务端做少量修改，修改范围都在 tsdbWrite 和 tsdbRead
- 缺点
  - 序列号为 65536 （最大 2^20），长度不足以表示每天几亿的记录，只能取模，仍然存在乱序
  - 用户需要增加一个无用的列（pseudo_seq），同样改变了用户常规使用行为

### 1.3 方案三：将时间戳修改为 128 位

在方案二基础上，将第一列长度修改为 128 位，如此可以涵盖 64 位时间戳和 64 位序列号。
```sql {wrap}
taos> create database db precision 'ms';
taos> create table st (ts timestamp, seq bigint, ……) tags ……
taos> create table t1 using st ……

taos> insert into table1 values
    ('2023-10-23 00:00:00.000',  999999)
    ('2023-10-23 00:00:00:000', 1001003);
    
taos> select ts, pseudo_seq, seq from table1 ;
             ts          |      seq     | 
==============================================================
 2023-10-23 00:00:00.000 |      999999  |
 2023-10-23 00:00:00.0000|      1001003 |
 
```

- 优点
  - 由 64 位表示序列号，可以完整满足金融应用
  - 用户完全无感知，不改变其行为，seq 列本来就是要存储的
- 缺点
  - 第一列从 64 位改为 128 位，变化较大，但改动量仍然可控

### 1.4 方案四：复合主键

方案一到三，主键仍为一列，只是让其含义更加丰富，在逻辑上赋予了两列的含义。采用复合主键之后，第二列原则上可以为任意列。
- 优点
  - 彻底解决问题
- 缺点
  - 工作量很大，之前评估过需要半年
