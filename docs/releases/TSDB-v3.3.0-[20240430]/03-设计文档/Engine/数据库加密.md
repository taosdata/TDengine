## 3. 定义

- 透明加密: 数据库内数据的加密和解密，对数据库的访问程序是完全无感知的，应用系统不需要做任何修改和编译，就能够直接应用到加密库上
- SM4： 一种分组密码算法，由我国国家密码管理局在2012年发布，常用于无线互联网加密等领域。

## 4. 行为说明

### 4.1 配置密钥

#### 4.1.1 离线设置

为每个节点配置密钥。通过以下命令完成：
```bash
taosd -y {encryptKey}
```

该命令会检查密钥长度，如果超过16 bytes，则报错密钥过长。密钥可包含大小写字母，数字，所有特殊字符。
该命令会将用户输入的密钥，结合所在节点的机器码，做加密处理，处理后会在dnode目录中，生成2个配置文件：
encryptCode.cfg
checkCode.bin

encryptCode.cfg中包含加密处理过的用户输入的密钥。checkCode.bin中包含使用用户输入的密钥对一串预设内容进行加密后的密文，这个密文用于后续校验用，参看4.8节。

对用户密钥进行加密处理的过程，相当于使用当前机器的机器码作为密钥，通过一个不公开的加密算法进行加密。对密钥加密的过程是密钥公开但算法封闭的加密方式。

#### 4.1.2 在线设置

当集群所有节点都在线时，可以使用如下taos shell SQL命令
```bash
create encrypt_key 'value'
```

该命令会检查密钥长度，如果超过16 bytes，则报错密钥过长。密钥可包含大小写字母，数字，所有特殊字符。
该命令会为所有在线的节点生成密钥文件，过程与4.1.1节相同。
使用在线设置的方式要求所有已经加入集群的节点都没有使用过离线方式生成密钥，否则在线方式会失败，在线设置密钥成功的同时也自动加载和使用了密钥，即设置成功后密钥状态为 loaded （详见后面的状态说明）。

### 4.2 密钥一致性检查

taosd 启动后，定期上报检查自己的密钥与 mnode 所在节点的密钥是否相同，如果不相同则该节点显示为 offline，dnode 强制退出，在日志中打印 “inconsistent encryption key”。对于已经初始化并（通过离线或在线方式）成功设置了各节点密钥的集群，新加入节点必须用离线方式生成一致的密钥然后再添加到集群中。

### 4.3 创建加密数据库

通过新增建库参数 ENCRYPT_ALGORITHM 来启用对数据库的加密。
```bash
CREATE DATABASE [IF NOT EXISTS] db_name [database_options]
 
database_options:
    database_option ...
 
database_option: {
   ENCRYPT_ALGORITHM {'none' | 'sm4'}
}


```

ENCRYPT_ALGORITHM: 指定数据采用的加密算法。默认是none，即不采用加密。sm4 表示采用 sm4 加密算法。目前只支持 sm4 加密算法，如果输入其它不支持的加密算法则会报错并建库失败。当输入的 ENCRYPT_ALGORITHM 错误时，报错为 "Invalid option encrypt_algorithm: ${inputValue}"。如果一个或多个在线 dnode 未正确设置密钥，则报错为 "The cluster has not been set properly for database encryption".
ENCRYPT_ALGORITHM 参数会将该数据库的所涉及的所有 vnode 都设置成加密，并将这个加密设置写入到vnode.json配置文件中。

### 4.4 修改数据库

对已存在的库，不支持修改 ENCRYPT_ALGORITHM 参数，包括将未加密数据库改为加密，或者将加密数据库改为未加密。当ENCRYPT_ALGORITHM 参数变化时，alter db报错信息为encryption is not allowed to be changed after database is created。

### 4.5 查看数据库加密配置

系统表 ins_databases 中新增一列 "entryption_algorithm" 以保存各数据库的加密配置，查询该表可查看数据库的加密配置。
```bash
select name, encrypt_algorithm from ins_databases;
              name              | encrypt_algorithm |
=====================================================
 power1                         | none              |
 power                          | sm4               |
```

新添加 encrypt_algorithm 列，加密数据显示采用的加密算法，未加密数据显示为 none。

### 4.6 检验密钥

在 taosd 的启动时和创建 vnode 时（也就是创建数据库时）会检验节点配置的密钥。

#### 4.6.1 启动检验过程

##### 4.6.1.1 获取密钥

读取encryptCode.cfg，如果存在该文件，则对文件中的code进行解析。使用机器码作为密钥，从code中解密出密钥，如果机器码发生变化，则解析密钥失败。当机器码发生变化时，taosd 启动失败，在日志中打印，”failed to get encryption key since machine code was changed"。

##### 4.6.1.2 打开 vnode

在完成获取密钥的过程后（即4.5.1.1节中的描述的过程），taosd在接下来的启动过程中将打开vnode，在打开vnode的过程中，从vnode.json配置中获取该vnode是否是加密的vnode，如果是加密的vnode，则检查在之前的启动过程中是否成功获取到密钥，如果未获取到密钥，则打印无效密钥，并且打开vnode失败。

如果vnode打开失败，使用show vgroups命令，会看到vnode处于offline状态。

#### 4.6.2 创建vnode的检验过程

创建vnode时（也即创建数据库的过程中），会检查taosd在之前的启动过程中，是否成功获取到用户密钥，如果未获取到密钥，则给mnode返回错误。mnode收到vnode返回的错误，会创建db失败。

### 4.7 查看节点密钥状态

添加如下命令来查看节点密钥状态，其中 ins_encryptions 为新增系统表，其包含两个字段：dnode_id 和 key_status。
```bash
show encryptions;

select * from information_schema.ins_encryptions;
  dnode_id   |           key_status           |
===============================================
           1 | loaded                     |
           2 | unset                    |
           3 | unknown                        |
```

key_status 有三种取值：
- 当节点未设置密钥时（即4.1节描述的过程），状态列显示 unset。
- 当密钥被检验成功并且加载后(即4.5.1节描述的过程)，状态列显示 loaded.
- 当密钥被设置，但是没有被加载时，状态显示为 set，此状态出现在先启动了 taosd 而后用离线方式设置密钥的情况

### 4.8 更新密钥配置

当节点的硬件配置发生变更时，节点的机器码也会发生变更，这时会导致加密数据库的vnode 节点无法工作，需要更新密钥配置，即 4.1 节描述的过程中生成 encryptCode.cfg 文件。
更新密钥配置使用与4.1节中同样的命令
```bash
taosd -y  {encryptKey}
```

更新密钥配置，需要先停止taosd，并且使用完全相同的密钥，也即密钥在数据库创建后不能修改。
更新密钥的过程，与4.1节中的过程的不同之处在于，会先读取 checkCode.bin 文件，通过检验 checkCode.bin 中的内容确认，确认密钥没有被更改过。这个检查通过后，与4.1中的过程一样，会生成新的 encryptCode.cfg 和 checkCode.bin 文件。

### 4.9 加密效果

#### 4.9.1 对文件的影响

- vnode_wal
Wal模块只加密 wal 的 body 部分，不加密 wal 的 head 部分。所以加密后，head 部分的长度，保持不变，head内的数据也保持不变。加密后的 body 会有长度的变化，变化的方式是向 16 bytes 长度及其倍数对齐。head 中的 bodyLen 长度保持不变，仍然记录加密前的长度。
- tsdb
按照 tsdb 的页做加密。tsdb 的页的大小为 pageSize * 1024，这个值是 16 的整数倍。所以tsdb加密前和加密后，每个页的长度保持不变，所以被加密的data和stt文件的大小也保持不变。
- tdb
按照 tdb 的页做加密。tdb 的页的大小为 pageSize * 1024，这个值是 16 的整数倍。所以tsdb 加密前和加密后，每个页的长度保持不变，所以被加密的 tdb 文件的大小也保持不变。
wal head 文件中不会包含客户的数据，故不对 head 文件进行加密，不影响加密效果。

#### 4.9.2 效果检验

- Vnode wal的测试
创建一个带有字符类型的表，并且向其中插入一定量的数据。

在未配置加密时，通过hexdump -C工具打开vnode/vnode*/wal/*.log,可以看到明文信息，比如插入的数据的字符串。

在配置加密后，再通过hexdump -C工具打开vnode/vnode*/wal/*.log,无法看到有含义的明文信息，比如插入的数据的字符串。会出现稀疏并且均匀分布式的可读字符。
- Vnode tsdb的测试
创建一个带有字符类型的表，并且向其中插入一定量的数据。

在未配置加密时，通过hexdump -C工具打开data/vnode/vnode2/tsdb/*.data data/vnode/vnode2/tsdb/*.stt,可以看到明文信息，比如插入的数据的字符串。

在配置加密后，再通过hexdump -C工具打开data/vnode/vnode2/tsdb/*.data data/vnode/vnode2/tsdb/*.stt,无法看到有含义的明文信息，比如插入的数据的字符串。会出现稀疏并且均匀分布式的可读字符。

- tdb的测试
在未配置加密时，通过hexdump -C工具打开data/vnode/vnode2/meta/*.tdb ,可以看到明文信息，比如插入的表名。

在配置加密后，再通过hexdump -C工具打开data/vnode/vnode2/meta/*.tdb,无法看到有含义的明文信息，比如表明。会出现稀疏并且均匀分布式的可读字符。

## 5. 性能

对写入、查询的性能都有影响。
写入 wal、写入meta 以及落盘到 tsdb，都会走加密过程。启动时读取未落盘的仍然在 wal中的数据、首次从 tsdb 读取到的数据以及首次从meta读取数据时，都会走解密过程。

## 6. 兼容性

添加了 ENCRYPT_ALGORITHM 参数，导致 mnode 的 Db 对象的版本升级 sver=2，退回到旧版本将出现数据不兼容问题。即该版本不支持回退。

## 8. 使用场景

### 8.1 场景1：离线生成密钥

步骤1：部署节点， 在每个节点上执行 taosd -y {encrypteKey}
步骤2：启动 firstEp
步骤2：为其它节点执行 create dnode
步骤3：启动其它节点taosd

### 8.2 场景2：在线生成密钥

步骤1：把所有节点加入集群并启动整个集群
步骤4=2：启动 taos shell， 在taos shell 中执行  create encryptKey {key}

### 8.3 场景3：增加节点

步骤1：用在线或离线方式部署好集群并设置了加官网密钥
步骤2：在新增节点上生成密钥  taosd -y
步骤2：create dnode
步骤3：启动该节点 taosd

### 8.4 异常场景

1. 离线生成的密钥时，如果存在密钥不一致的情况， 则密钥不一致的dnode 无法加入集群，该dnode显示为offline状态，日志中输出 ”dnode is offline since invalid encryption key"
2. 离线生成密钥的方式下，如果部分节点有密钥部分节点没有，则集群无法完整启动，即无密钥的节点，显示为 offline 状态，日志中输出 ”dnode is offline since no encryption key exists"
3. 先初始化集群，然后用在线方式在所有节点生成密钥，后加入集群的节点必须离线生成密钥，且密钥与在线生成的时候的密钥一致，否则该节点状态显示为offline。

## 9. 约束和限制

约束：无
限制：
- 本次实现中，不支持修改数据库的加密配置，包括将未加密数据库改为加密，或者将加密数据库改为未加密。
- 当数据库创建后，不支持变更密钥
- 本次实现中，未对 last 缓存的持久化文件进行加密

## 15. 附录

1. 将如下函数放在o文件中：
```bash
int32_t generateEncryptCode(char* key, char* machineid, char* encryptCode);
```

generateEncryptCode函数将输入的密钥连同机器码一起作为被加密内容，使用机器码作为密钥进行加密，加密后的内容作为encryptCode返回。

1. 在企业版的o文件中添加如下解析函数：
```bash
int32_t checkAndGetCryptKey(char* encryptCode, char* machineid, char* key);
```

checkAndGetCryptKey 函数根据机器码，解析 encryptCode，解析出被用户密钥和机器码，并且获取当前节点的机器码，与解析出的机器码进行比较，密钥通过char* key参数返回，返回错误定义：
- 如果解析成功放回0
- 如果因机器改变无法解析出密钥则返回-1
- 其他解析失败则返回-2。

1. 密钥一致性检查机制
在dnode的心跳中，包含该节点的密钥信息，mnode收到心跳后，检查该节点的密钥与自己的密钥是否一致，如果不一致，则将该节点设置为offline，并且将密钥不信息返回给dnode。

1. Show encryptions
将密钥状态通过心跳将密钥状态上报到dnode的数据结构中，show encryption从dnode数据结构中读取每个节点的密钥状态。
