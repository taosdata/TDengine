## 2. 测试目标

本次测试的主要目标：本次不涉及功能性变化，主要进行开启缓存时 last/last_row 性能的测试。

## 3. 参考文档

## 4. 测试结论

通过对查询缓存的优化，显著的提升了 last/last_row 的性能。
具体表现如下：
1. 数据模型：100w子表，每个子表100条数据
2. 查询语句：
   - 查询某张子表的 last/last_row。
   - 批量查询某一张超级表下的子表 last/last_row,并使用 tbname in 进行过滤。
   - 批量查询某一张超级表下的子表 last/last_row,并使用 tag in 进行过滤。
3. 性能对比：
   - 查询某张子表的 last/last_row，性能提升 26%。
   - 批量查询某一张超级表下的子表 last/last_row,并使用 tbname in 或 tag in 进行过滤，先前的版本会直接耗尽系统资源导致查询失败，优化后各种场景的 单位时间内返回 last/last_row 查询结果的设备数量 均远超过 1w，满足客户需求。
功能符合预期，测试通过。

## 5. 已知问题和限制

使用 tag in 走优化分支需要如下的条件：
1. **用来过滤的 tag 存在索引，第一个 tag 列默认存在索引。**
2. **不可以使用 or 。**
3. **类型要求：**
  **Tag == varchar 并且 value == varchar**
  **Tag == 有符号数 并且 value == 有符号数 并且 Tag 的类型 >= value 的类型**
  例如： tag bigint value int 那么就可以，如果 tag 是int value 是 bigint 则不可以。还需要格外注意 channel_id in (1) 可以使用索引，但是 channel_id in ('1') 不可以使用索引，因为value 会被识别为 varchar 。

### 6.4 测试流程

1. 环境部署​：在独立的纯净测试环境中，分别部署优化前与优化后的 TDengine 版本，确保测试环境一致。
2. 元数据准备​：依次创建测试所需的数据库、超级表及子表结构。
3. 查询性能对比测试​：
   - 在优化前版本中执行指定查询语句，记录 单位时间内返回 last/last_row 查询结果的设备数量。
   - 在优化后版本中执行相同查询语句，记录 单位时间内返回 last/last_row 查询结果的设备数量。
   - 反复执行查询 10 次，排除偶发差异
4. 结果验证​：对比两次查询的结果集，确保数据准确性一致，排除优化引入的逻辑差异。

## 8. 纳入发版前流程

为确保 last/last_row 性能在迭代中出现回退，本次测试用例将纳入发版前验证体系。具体实施可以参考 jira :
TD-38157

1. 需要打开数据库的缓存开关。
2. 数据建模：包含正常的表，以及宽表（varchar(128k)）。
3. 数据查询类型：
   - tbname in 一次查询查过1000张子表的 last/last_row。
   - tag in 一次查询超过 1000 张子表的 last/last_row。
   - 最终输出 devices / s 的性能指标(单位时间内返回 last/last_row 查询结果的设备数量*每次查询的设备数)。
