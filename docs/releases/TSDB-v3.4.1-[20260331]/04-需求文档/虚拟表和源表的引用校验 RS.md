## 2. 引言

### 2.1 术语与缩写名词

| 源表 | 被虚拟表引用的物理表，包含超级表、普通子表，是虚拟表数据与标签的原始来源 |
| --- | --- |
| 虚拟表（VTABLE） | 基于源表创建的逻辑表，自身不存储实际数据，查询时动态从源表获取数据/标签值，表结构与标签可通过源表引用定义 |
| ins_virtual_tables_referencing | 新增的系统信息表，用于存储源表（库、表、列）与虚拟表（库、表、列）的引用关系，支持灵活的条件查询 |
| 虚拟超级表 | 虚拟表的一种类型，对应物理超级表，其引用关系查询需遍历所有数据库 |
| 虚拟子表 | 虚拟表的一种类型，对应物理子表，其引用关系查询无需遍历整个数据库，性能较高 |
| meta（元数据） | 包含表结构、列信息、标签信息、引用关系等核心数据，源表meta变更需同步影响关联虚拟表 |

高（解决源表meta变更与虚拟表联动问题，保障业务查询连续性、减少重复配置，适配实际运维与业务场景需求，需优先推进）

### 2.4 版本要求

## 3. 需求目标

实现源表meta自动同步更新到虚拟表，明确源表（结构、列、标签）变更对关联虚拟表的影响规则；新增系统表ins_virtual_tables_referencing存储源表与虚拟表的引用关系；支持虚拟表标签值直接引用源表子表的标签值，简化配置；提供虚拟表可用性验证、源表引用关系查询的快捷命令；保障源表变更时虚拟表查询的完整性与安全性，减少业务配置冗余，为源表meta自动更新到虚拟表功能的开发落地提供明确指导，适配运维与业务核心需求。

## 4. 功能需求

为解决源表meta变更后虚拟表无法同步适配、虚拟表标签配置繁琐、源表与虚拟表引用关系难以查询等问题，明确源表与虚拟表的联动规则、新增系统表及快捷命令，具体功能需求如下，覆盖源表变更行为、虚拟表标签引用、可用性验证、引用查询等核心场景：

### 4.1 系统表ins_virtual_tables_referencing新增

新增系统信息表ins_virtual_tables_referencing，用于存储源表与虚拟表的引用关系，支持条件查询，其schema定义如下：

| 字段 | 含义 | 类型 | 单位 | 备注 |
| --- | --- | --- | --- | --- |
| virtual_db_name | 虚拟表DB名称 | Varchar | - | - |
| virtual_stable_name | 虚拟超级表名称 | Varchar | - | - |
| virtual_table_name | 虚拟表表名称 | Varchar | - | - |
| virtual_column_name | 虚拟表列名称 | Varchar | - | - |
| src_db_name | 源表DB名称 | Varchar | - | - |
| src_table_name | 源表表名称 | Varchar | - | - |
| src_column_name | 源表列名称 | Varchar | - | - |
| type | 源表类型 | Varchar | - | 取值仅为virtual/physical |
| err_code | 错误码 | INT | - | 0为无异常，其他值为存在异常 |
| err_msg | 错误信息 | Varchar | - | - |

### 4.2 源表变更对虚拟表的影响

当源表发生增加列、删除列、修改列、删除表等变更时，需明确对关联虚拟表的影响，报错信息需清晰明确，具体行为如下：

#### 4.2.1 增加源表的列

行为：不影响虚拟表的任何行为，虚拟表查询、创建等操作正常执行，新增列不自动同步到虚拟表。

#### 4.2.2 删除源表的列

行为：若被删除的列被虚拟表引用，查询该虚拟表时，涉及该列的操作直接报错，报错信息需清晰明确，告知用户源表列已删除及关联虚拟表列信息。

#### 4.2.3 修改源表的列

仅普通表支持修改列名称，超级表列名称不支持修改；列类型不支持修改，字符类列可修改长度，具体行为如下：

##### 4.2.3.1 修改源表列的类型和长度

行为：不支持修改源表列的类型；字符类型（varbinary/binary/nchar/geometry）仅可修改长度，且只能改大、不能改小；修改后的长度不能超过虚拟表对应列的定义长度，若超过则直接报错，报错信息需清晰明确。

##### 4.2.3.2 修改源表列的名称

行为：仅普通表支持修改列名称；若虚拟表引用了该普通表的列，修改列名称后，查询虚拟表对应列时直接报错，报错信息需清晰明确。

#### 4.2.4 删除源表

行为：若被删除的源表被虚拟表引用，查询该虚拟表时直接报错，报错信息需清晰明确，告知用户源表已删除及关联虚拟表信息。

### 4.3 虚拟表标签值引用源表的标签值

支持虚拟子表的标签值直接引用源表子表的标签值，明确相关SQL语法、约束及示例，具体要求如下：

#### 4.3.1 SQL语法

创建虚拟表时，支持标签值引用源表子表的标签值，语法如下：
```plaintext {wrap}
CREATE VTABLE [IF NOT EXISTS] [db_name].vtb_name 
    (create_defination[ ,create_defination] ...) 
    USING [db_name.]stb_name 
    [(tag_name [, tag_name] ...)] 
 TAGS (tag_value [, tag_value] ...)
其中，create_defination和tag_value的定义如下：
create_defination: [stb_col_name FROM] table_name.col_name
tag_value: const_value | [stb_tag_name from] table_name.col_name
```

#### 4.3.2 约束条件

虚拟子表引用源表标签值时，table_name必须为源表子表，col_name必须为源表的TAG列，否则创建虚拟表时报错。

#### 4.3.3 示例SQL

基础准备SQL：
```sql {wrap}
create stable sptable (ts timestamp, c1  int) tags(t1 int);
create table childTable using sptable tags(1);
```

1. 虚拟子表自定义TAG值：
```plaintext {wrap}
create vtable vtablename (c1 from childTable.c1) using svt tags(1);
```

1. 虚拟子表引用源表子表的TAG值：
```plaintext {wrap}
create vtable vtablename_ref (c1 from childTable.c1) using svt tags(t1 from childTable.t1);
```

### 4.4 虚拟表可用性验证

提供虚拟表可用性验证命令，用于检查虚拟表引用列的可用性，明确语法、行为、限制及性能要求：

#### 4.4.1 SQL语法

SHOW VTABLE VALIDATE FOR [db_name.]tableName

#### 4.4.2 行为说明

执行该命令后，验证指定tableName的引用列（ref col）可用性，输出结果与系统表ins_virtual_tables_referencing的schema一致，包含错误码和错误信息。

#### 4.4.3 约束限制

tableName只能是虚拟子表、普通虚拟表、虚拟超级表，若为其他表类型（如物理表、物理超级表），执行命令时直接报错，报错信息清晰明确。

#### 4.4.4 性能要求

若tableName为虚拟子表或普通虚拟表，查询性能较高，无需遍历整个数据库；若为虚拟超级表，需遍历所有数据库，性能取决于数据库数量及元数据量。

### 4.5 源表引用关系查询（快捷命令）

提供快捷命令查询源表（或源表列）被哪些虚拟表引用，同时支持通过系统表进行灵活查询，明确语法、行为、限制及性能要求：

#### 4.5.1 SQL语法（快捷命令）

SHOW REFERENCES FOR [DB_NAME].TB_NAME

#### 4.5.2 行为说明

该命令用于查询指定源表被哪些虚拟表引用，输出结果为多行4列，分别为virtual_db_name、virtual_stable_name、virtual_table_name、virtual_col_name；该命令等价于对系统表ins_virtual_tables_referencing的条件查询，等价SQL如下：
select virtual_db_name, virtual_stable_name, virtual_table_name, virtual_col_name from information_schema.ins_virtual_tables_referencing where src_table_name='TB_NAME'

#### 4.5.3 约束限制

TB_NAME只能是物理表（源表），若为虚拟表，执行命令时直接报错，报错信息清晰明确。

#### 4.5.4 性能要求

该命令为重量级查询，需遍历所有VNODE的元数据，筛选虚拟表并匹配引用关系，查询性能主要取决于集群中元数据的整体大小，元数据量越大，查询耗时越长。

### 4.6 约束和限制

- 源表列修改限制：仅普通表可修改列名称，超级表列名称不可修改；源表列类型不可修改，字符类列长度仅可改大、不可改小，且不超过虚拟表对应列长度。
- 虚拟表标签引用限制：仅可引用源表子表的TAG列，不可引用超级表或普通表的非TAG列。
- 命令使用限制：SHOW VTABLE VALIDATE仅支持虚拟表类型，SHOW REFERENCES仅支持物理表类型，超出范围直接报错。
- 系统表限制：ins_virtual_tables_referencing仅支持查询操作，不支持插入、更新、删除，保障引用关系元数据安全。

### 4.7 使用场景

增强后的功能需适配以下典型业务场景，确保功能实用性和业务适配性：

#### 4.7.1 场景1：源表结构动态调整，业务查询无感知

业务需求：智能电表业务中，运维人员因需求变更需删除源表meter_001的power列，该列被业务侧虚拟表v_meter_biz引用，需保证业务查询不中断。
解决方案：通过本特性，删除源表power列后，查询虚拟表v_meter_biz时仅power列返回NULL，其他列数据正常，业务查询无需修改代码，保障业务连续性。

#### 4.7.2 场景2：多业务复用源表标签值，减少重复配置

业务需求：某园区多个业务系统需获取智能电表的meter_id和area标签值，若每个系统单独配置虚拟表标签，易出现配置不一致问题。
解决方案：通过虚拟表标签引用源表子表标签的能力，所有业务系统的虚拟表均可直接引用meter_001.meter_id、meter_001.area，实现标签值统一复用，源表标签值变更时，虚拟表自动同步。

#### 4.7.3 场景3：源表生命周期管理，快速排查引用关系

业务需求：运维人员需清理过期智能电表源表meter_999，需确认该表是否被虚拟表引用，避免误删导致业务异常。
解决方案：执行SHOW REFERENCES FOR meter_999，快速查询该源表被哪些虚拟表引用，通知业务侧调整虚拟表后，安全下线源表。

## 5. 性能需求

- 虚拟表常规查询性能：基于源表数据/标签的虚拟表常规查询，性能与直接查询源表基本一致，无额外较大性能损耗。
- 引用关系查询性能：SHOW REFERENCES命令及系统表ins_virtual_tables_referencing查询为重量级查询，性能取决于集群中元数据总量，元数据量越大，查询耗时越长，需优化遍历逻辑，降低集群资源占用。
- 虚拟表可用性验证性能：虚拟子表、普通虚拟表的验证性能较高，无需遍历整个数据库；虚拟超级表验证需遍历所有数据库，性能取决于数据库数量及元数据量。

## 6. 安全需求

- 数据完整性：源表结构变更时，虚拟表仅对应引用列返回NULL，不导致整个查询报错，保证查询操作的完整性，避免业务查询中断。
- 权限管控：虚拟表的创建、查询与源表权限体系保持一致，无额外权限配置；仅拥有源表查询权限的用户，可创建并查询关联的虚拟表，防止未授权访问源表数据。
- 元数据安全：系统表ins_virtual_tables_referencing仅支持查询操作，不支持插入、更新、删除操作，保障源表与虚拟表引用关系的元数据不被篡改。
- 数据隔离：虚拟表为逻辑表，自身不存储任何实际数据，所有数据均动态从源表获取，避免数据冗余；同时虚拟表仅可访问源表中被引用的列/标签，保障源表数据机密性。

## 7. 兼容性需求

完全兼容现有版本，新增的系统表、SQL语法（CREATE VTABLE扩展、SHOW VTABLE VALIDATE、SHOW REFERENCES）不影响现有虚拟表、源表的正常创建、查询及其他操作，现有业务场景无需修改代码即可正常运行。

## 8. 其他需求

- 文档需求：需要修改官网文档，新增虚拟表的完整使用说明，包括创建语法、标签值引用规则、源表变更影响、引用关系查询等内容；补充系统表ins_virtual_tables_referencing的schema定义与查询示例，以及SHOW VTABLE VALIDATE、SHOW REFERENCES命令的使用方法。
- 常见错误和排查：无特殊内容，按4.2、4.4、4.5相关报错说明执行即可，确保报错信息清晰可排查。
- 运维需求：源表日常维护（结构调整、表清理）时，需提前通过SHOW REFERENCES或系统表查询引用关系；源表字符/二进制类列长度修改需遵循相关规则；集群元数据量较大时，避免频繁执行引用关系查询操作。
- 可观测性、安装和卸载：均不涉及特殊需求，遵循TDengine常规规范。
