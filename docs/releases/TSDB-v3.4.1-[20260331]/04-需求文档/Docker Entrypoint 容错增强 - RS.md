## 2. 引言

### 2.1 术语与缩写名词

- **Sync Component**: 数据同步组件,主要指 taosx、taoskeeper 等负责数据同步和监控的服务进程
- **Health Check**: 健康检查,定期检测服务进程状态的机制
- **Progress Persistence**: 进度持久化,将同步进度保存到持久化存储的机制
- **Fault Tolerance**: 容错能力,系统在组件失败后自动恢复的能力
- **Watchdog**: 看门狗进程,监控子进程健康状态并在异常时重启的守护进程

### 2.2 相关文档资料

- 当前 Docker entrypoint 实现:
  - `packaging/docker/entrypoint.sh` (TDgpt 容器入口)
  - `packaging/docker/bin/entrypoint.sh` (TDengine 标准入口)
  - `packaging/docker/bin/startup.sh` (TDengine 启动脚本)
- TDengine Docker 部署文档: [官方文档](https://docs.taosdata.com/deployment/docker/)
- TaosX 数据同步文档

### 2.3 优先级要求

**优先级**: P1 (高优先级)

- 设备长时间离线后重新上线时同步组件无法正确处理断点续传

## 3. 需求目标

### 3.1 背景

当前 Docker 容器的 entrypoint 脚本存在以下问题:
1. **无自动重启机制**: 同步组件(taosx、taoskeeper 等)进程异常退出后不会自动重启,导致服务中断
2. **无健康监控**: 没有主动健康检查机制,无法及时发现进程僵死或响应超时
3. **进度持久化缺失**: 容器重启后同步进度丢失,需要从头开始同步
4. **容错能力不足**: 设备长时间离线后重新上线,同步组件无法优雅处理断点续传
这些问题在以下场景中影响严重:
- IoT 边缘设备部署,网络不稳定
- 云端批量部署,单个容器故障影响整体服务可用性
- 数据迁移场景,同步进度丢失导致数据重复或丢失

### 3.2 目标

重构 Docker entrypoint 脚本,实现以下目标:
1. **自动重启**: 同步组件异常退出后自动重启,保证服务持续可用
2. **健康监控**: 实现进程级和业务级健康检查,及时发现并处理异常
3. **进度持久化**: 同步进度持久化到数据卷,容器重启后可断点续传
4. **容错增强**: 优雅处理设备离线/上线场景,避免数据丢失或重复同步

## 4. 功能需求

| 序号 | 功能类别 | 功能名称 | 功能描述 |
| --- | --- | --- | --- |
| 1 | 进程管理 | 自动重启机制 | 检测同步组件进程退出,自动重启,支持配置重启策略(立即/延迟/退避算法) |
| 2 | 进程管理 | 重启次数限制 | 设置最大重启次数阈值,防止无限重启,超过阈值后进入失败状态并告警 |
| 3 | 进程管理 | 优雅停止 | 收到 SIGTERM 信号时,向子进程发送停止信号,等待优雅退出(超时后强制 SIGKILL) |
| 4 | 健康检查 | 进程存活检查 | 定期检查进程 PID 是否存在,进程状态是否为运行中 |
| 5 | 健康检查 | 端口监听检查 | 检查服务端口是否正常监听(taosx: 6050, taoskeeper: 6043 等) |
| 6 | 健康检查 | 业务健康检查 | 调用健康检查接口(如 /health, /metrics),验证服务响应正常 |
| 7 | 健康检查 | 超时重启 | 健康检查连续失败达到阈值后触发重启 |
| 8 | 进度持久化 | 状态文件管理 | 同步组件定期将进度写入状态文件(JSON/TOML 格式) |
| 9 | 进度持久化 | 数据卷挂载 | 状态文件存储在持久化数据卷中(/var/lib/taos/sync-state/) |
| 10 | 进度持久化 | 启动恢复 | 容器启动时读取状态文件,同步组件从上次进度继续执行 |
| 11 | 容错处理 | 断点续传 | 支持设备离线后重新上线时从断点继续同步,避免全量重传 |
| 12 | 容错处理 | 离线数据缓存 | 设备离线期间数据缓存到本地,上线后批量同步 |
| 13 | 容错处理 | 时钟同步检测 | 检测设备时钟跳变,避免时间戳错乱导致的同步异常 |
| 14 | 日志与监控 | 结构化日志 | 输出 JSON 格式日志,包含时间戳、进程名、事件类型、详情 |
| 15 | 日志与监控 | 事件记录 | 记录启动/停止/重启/健康检查失败等关键事件 |
| 16 | 日志与监控 | 性能指标 | 输出进程 CPU/内存使用率、重启次数、健康检查延迟等指标 |
| 17 | 配置管理 | 环境变量配置 | 支持通过环境变量配置重启策略、健康检查间隔、最大重启次数等 |
| 18 | 配置管理 | 配置文件支持 | 可选:支持从配置文件加载参数(YAML/TOML) |

## 5. 性能需求

| 指标 | 要求 | 说明 |
| --- | --- | --- |
| 健康检查开销 | CPU < 1%, 内存 < 10MB | 看门狗进程资源消耗需极低,避免影响主业务 |
| 重启延迟 | < 5s | 进程异常退出到重启成功的时间间隔 |
| 状态文件写入频率 | 5-60s 可配置 | 平衡数据一致性和磁盘 I/O 开销 |
| 日志输出量 | < 100KB/min | 正常运行时日志量应保持较低 |
| 容器启动时间 | 增量 < 2s | 相比当前 entrypoint,新增逻辑导致的启动延迟应控制在 2s 内 |

## 6. 安全需求

1. **权限隔离**: 看门狗进程不应以 root 权限运行,同步组件应使用最小权限原则
2. **敏感信息保护**: 日志和状态文件中不应包含明文密码或 token
3. **信号处理安全**: 正确处理 SIGTERM/SIGKILL/SIGHUP 等信号,避免数据损坏
4. **文件权限**: 状态文件应设置适当权限(600 或 640),防止未授权访问

## 7. 其他需求

### 7.1 兼容性需求

- **向后兼容**: 新 entrypoint 需兼容现有 Docker Compose 配置和环境变量
- **多架构支持**: 支持 x86_64、aarch64 架构
- **操作系统**: 支持 Alpine、Ubuntu、CentOS 等主流基础镜像
- **容器运行时**: 兼容 Docker、Podman、Kubernetes CRI

### 7.2 接口需求

- **信号接口**: 正确响应 `docker stop` (SIGTERM) 和 `docker kill` (SIGKILL)
- **健康检查接口**: 支持 Docker HEALTHCHECK 指令
- **配置接口**: 通过环境变量暴露可配置参数:
  - `SYNC_RESTART_POLICY`: always | on-failure | unless-stopped
  - `SYNC_MAX_RETRIES`: 最大重启次数,默认 10
  - `SYNC_HEALTH_CHECK_INTERVAL`: 健康检查间隔(秒),默认 30
  - `SYNC_HEALTH_CHECK_TIMEOUT`: 健康检查超时(秒),默认 5
  - `SYNC_HEALTH_CHECK_RETRIES`: 连续失败次数阈值,默认 3

### 7.3 运维需求

- **可观测性**: 提供清晰的日志输出,支持 Docker logs 查看
- **诊断工具**: 提供命令查看当前同步状态和健康状况
- **故障排查**: 文档中包含常见问题排查指南
- **升级平滑**: 从旧版本升级时自动迁移状态文件格式(如有变化)

### 7.4 易用性需求

- **零配置启动**: 默认参数应满足大多数场景,无需额外配置
- **配置验证**: 启动时验证配置参数有效性,给出明确错误提示
- **文档完善**: 提供配置说明、使用示例、故障排查文档

### 7.5 测试需求(不含测试例)

- **单元测试**: 看门狗逻辑、健康检查函数、状态文件读写
- **集成测试**: 
  - 进程异常退出自动重启
  - 容器重启后进度恢复
  - 优雅停止流程
  - 超过最大重启次数后的行为
- **压力测试**: 高频重启场景下的稳定性
- **场景测试**: 
  - 网络断开/恢复
  - 设备长时间离线后上线
  - 时钟跳变场景
