## 3. 需求目标

TSDB 在长期运行过程中，受非正常断电、磁盘故障、并发访问冲突、软件缺陷等因素影响，可能出现 vnode、mnode、dnode、snode 等相关数据文件损坏的情况，导致节点无法启动、数据丢失或查询异常。目前缺乏专门的自动化数据修复工具，运维人员需手动执行复杂的命令、拷贝文件进行修复，效率低且易出错，尤其对于海量时序数据场景，手动修复风险极高。
本需求的目标是
1. 设计并开发 TSDB 数据修复工具（基于 taosd -r 命令扩展），支持通过命令行指定修复类型。
2. 实现 vnode 相关数据文件（WAL、TSDB、TDB）的修复功能，覆盖单副本、多副本两种场景，最大限度恢复未损坏数据，备份已损坏数据，降低数据丢失风险。
3. 暂不开发 mnode、dnode、snode 的相关数据文件修复功能
4. 暂不开发 vnode 中除 WAL、TSDB、TDB 之外的数据文件修复功能，例如 BSE 文件。
5. 工具需具备易用性、可靠性，命令行交互清晰，输出详细修复日志，便于运维人员排查问题，掌握修复进度。
6. 修复工具发布版本为 3.4.1。

## 4. 功能需求

### 4.1 命令行设计

工具基于现有 taosd -r 命令（元数据重建命令）扩展，不新增独立执行程序。执行 taosd -r 即可启动修复模式，通过额外参数指定修复的节点类型、文件类型、修复模式，实现精准修复，避免误操作。

#### 4.1.1 命令格式

```python
taosd -r [--node-type NODE_TYPE] [--file-type FILE_TYPE] ……
```

#### 4.1.2 参数说明

| 参数 | 参数说明 | 可选值 | 是否必选 |
| --- | --- | --- | --- |
| --node-type | 指定需要修复的节点类型，明确修复范围 | vnode、mnode、dnode、snode | 是 |
| --file-type | 指定需要修复的节点对应数据文件类型，需与 --node-type 参数对应匹配 | 1. vnode：wal、tsdb、tdb； 1. mnode：wal、data 1. dnode：config； 1. snode：checkpoint | 是 |
| --vnode-id | 指定需要修复的 vnode ID，支持同时修复多个 vnode，多个 ID 用英文逗号分隔 | 数字，如 2,3 | --node-type=vnode 时必选 |
| --backup-path | 指定损坏文件的备份路径，用于存储修复前的原始损坏文件，便于修复失败后回滚 | 默认值为 /vnode/vnode2/back-yyyymmddhhmmss 输入none，表示不备份损坏文件 | 否 |
| --mode | 指定修复模式，不同模式对应不同修复场景和逻辑 | force：强制修复模式 replica：副本恢复模式 copy：文件拷贝模式 | 是 |
| --replica-node | 副本节点的 SSH 连接信息及数据目录，用于文件拷贝模式下的完好数据获取 | 格式：IP:数据目录，如 192.168.1.24:/root/dataDir | --mode=copy 时必选 |
| --help | 查看工具帮助信息 | 无 | 否 |

#### 4.1.3 命令示例

1. 查看修复工具帮助
```plaintext {wrap}
taosd -r --help
```

1. 修复单副本 vnode 的 TDB 文件
```plaintext {wrap}
taosd -r --node-type vnode --file-type tdb --vnode-id 1234 --backup-path /backup/vnode_tdb --force 1
```

1. 修复单副本 vnode 的 WAL 文件
```plaintext {wrap}
taosd -r --node-type vnode --file-type wal --vnode-id 1234 --force 1
```

1. 修复多个单副本 vnode 的 TSDB 文件
```plaintext {wrap}
taosd -r --node-type vnode --file-type tsdb --vnode-id 2,3 --backup-path
```

1. 修复多副本 vnode（从副本节点拷贝数据）
```plaintext {wrap}
taosd -r --node-type vnode --file-type tsdb --vnode-id 1234 --force 0
```

### 4.2 强制修复模式

适用场景：vnode 为单副本部署（无其他备份节点），其 WAL、TSDB、TDB 文件出现损坏，无法正常启动或运行，需通过解析本地数据文件恢复可用数据。

#### 4.2.1 WAL 修复

核心目标：尽可能多地拯救 WAL 日志中的有效数据，确保修复后的日志可正常重放，步骤如下：
1. 读取 WAL 日志文件和索引文件，识别损坏片段
2. 解析未损坏的日志条目，提取有效写入记录
3. 标记并删除无法解析的损坏日志条目，避免损坏条目影响日志重放
4. 根据修复后的有效日志条目，重建 WAL 日志索引文件，确保索引与日志条目一一对应
5. 修复完成后，自动校验日志可重放性，确保 vnode 启动时可通过该日志恢复数据。

#### 4.2.2 TSDB 修复

核心目标：尽可能多地拯救 TSDB 文件中的时序数据，重建损坏的文件结构，确保修复后的 TSDB 文件可正常被vnode 识别和查询，
1. 逐个解析 TSDB 相关文件（.data/.head/.sma等），校验每个数据块的完整性，标记损坏数据块
2. 提取并恢复未损坏的数据块，确保数据块中的时序数据（时间戳、测量值等）完整无误
3. 删除无法修复的损坏数据块，记录损坏数据块的位置和大小
4. 根据恢复后的有效数据块，重建相应的 .data、.head、.sma 等文件，恢复文件原有结构和索引

#### 4.2.3 TDB 修复

核心目标：尽可能多地拯救 TDB 文件中的 vnode 元数据，结合 WAL 日志和 TSDB 文件反向推导缺失元数据
1. 解析 TDB 元数据文件，包括表结构、标签信息、索引信息等；
2. 重新解析目标 vnode 的 WAL 日志和 TSDB 文件，反向推导缺失或损坏的元数据，补充完善元数据信息
3. 若部分元数据损坏严重无法推导，标记缺失的元数据项，在日志中提示用户

#### 4.2.4 修复后

1. 将修复前的原始损坏文件，按指定路径（--backup-path）进行备份
2. 在备份文件夹中生成修复记录文件（例如 repair.log），详细记录损坏条目位置、数量、修复步骤及修复结果，便于后续排查
3. 在控制台上打印本次修复的摘要信息，例如修复的 vnode ID、文件类型、修复时长、恢复数据量、损坏数据量，让运维人员快速掌握修复情况
4. 在修复过程中，每隔数秒打印过程信息，让运维人员了解修复的进度

### 4.3 副本恢复模式（本期不开发）

适用场景：vnode 为多副本（属于同一 VGroup，存在其他完好的副本节点），当前节点的 vnode 数据文件损坏，可通过复制其他副本节点的完好数据文件实现修复，数据完整性更有保障。
核心修复逻辑：
1. 修复启动后，自动将当前损坏 vnode 的 WAL、TSDB、TD B等核心文件设置为不可用状态，避免 vnode 启动时扫描损坏文件导致启动失败
2. 将当前损坏 vnode 的版本号和任期设置为 VGroup 中的最低值，触发 TSDB 集群的全量同步机制
3. 集群自动从完好副本节点拷贝所有数据文件

### 4.4 文件拷贝模式（本期不开发）

适用场景：在多副本 vnode 部署场景中，满足以下条件时，可使用文件拷贝模式，实现数据快速修复，避免副本恢复模式的同步耗时
1. vnode 数据文件过大（如超过 100GB），副本恢复模式同步耗时过长，需快速恢复服务
2. 其他副本节点可临时停机，避免文件拷贝过程中副本节点数据发生变化，导致拷贝文件不完整
3. 数据库配置了复杂的多级存储，手工拷贝文件极易出错，需工具自动完成拷贝和权限配置
核心逻辑：
1. 通过 --replica-node 参数指定的 SSH 信息，连接副本节点，读取目标 vnode 的数据文件
2. 将副本节点上目标 vnode 的所有数据文件完整拷贝到当前节点对应目录，覆盖损坏文件
3. 拷贝完成后，自动设置文件的权限和所有者，与当前节点 vnode 文件的权限、所有者保持一致

## 5. 性能需求

1. 强制修复模式：修复过程仅读取并处理指定的 vnode 数据文件，不扫描、不回放无关 vnode 的数据，避免占用额外系统资源
2. 副本同步模式：修复性能依赖于数据库多副本同步模块
3. 文件拷贝模式：拷贝速度取决于网络带宽和数据量，工具不限制拷贝速度，最大限度利用网络资源

## 6. 安全需求

1. 发生文件修改前，预先备份发生修改的原始数据
2. 修复过程中若检测到异常（如磁盘空间不足、文件读取失败），自动停止修复操作，记录异常信息和当前修复进度，避免数据混乱

## 7. 其他需求

### 7.1 测试需求

1. 环境准备：生成一份 FQDN 为 localhost 的三节点 TDengine 集群，配置多级存储，写入跨越多个文件组的时序数据，完成数据压缩后，对集群数据进行完整备份，待用（作为原始正常数据）。
2. 损坏模拟：解压备份的原始数据，通过程序修改特定文件位置的数据，模拟真实损坏场景，涵盖以下类型：
  - WAL 文件：修改日志条目内容、删除部分日志片段，模拟日志损坏；
  - TSDB 文件：破坏数据块校验和、删除部分数据块，模拟时序数据文件损坏；
  - TDB 文件：修改元数据内容、删除部分元数据片段，模拟元数据文件损坏。
1. 功能测试：针对每种损坏场景，采用对应的修复命令（节点类型、文件类型、修复模式）执行修复，确认命令可正常启动、修复过程无异常，修复后 dnode 可正常启动，数据可正常查询，未损坏数据无丢失。
2. 验证验收：修复完成后，对比修复后的数据与原始正常数据，校验数据完整性；同时验证修复日志、损坏文件备份的完整性，确保修复过程可追溯、修复结果符合预期。

### 7.2 异常情况处理

工具需支持常见异常场景的自动处理，避免异常导致修复失败或数据二次损坏，具体异常及处理逻辑如下：
1. 参数异常：用户输入无效参数（如不存在的节点类型、不匹配的文件类型、格式错误的 vnode ID）。
2. 文件缺失：指定修复的文件不存在（如输入错误 vnode ID、文件被误删除）。
3. 磁盘空间不足：修复过程中检测到磁盘空间不足，立即停止修复，提示磁盘空间不足及所需最小空间，避免数据混乱。
4. 副本不可用：拷贝模式下指定的副本节点不可达、或副本节点 taosd 服务正在运行。
5. 修复失败：因文件损坏过于严重（如 TDB 文件完全损坏、无可用数据可恢复），工具提示修复失败，详细说明失败原因，同时保留损坏文件备份和修复日志，便于用户排查问题或尝试其他手工修复方式。
