## 2. 引言

### 2.1 术语与缩写名词

- **XOR**：异或运算（Exclusive OR），一种位运算操作
- **Base64**：一种基于 64 个可打印字符来表示二进制数据的编码方法
- **REST API**：表述性状态传递（Representational State Transfer）应用程序接口
- **传输层混淆**：对传输数据进行可逆的简单变换，使其不易被直接读取
- **taos-explorer**：TDengine 的 Web 管理界面

## 3. 需求目标

### 3.1 背景

当前 taos-explorer 的 `/api/-/rest/sql` endpoint 使用明文传输 SQL 语句。在实际使用中，存在以下问题：
1. **日志泄露风险**：企业内部的 HTTP 代理、网关、负载均衡器等中间件可能会记录完整的 HTTP 请求日志，包括请求体中的 SQL 语句，导致敏感的业务逻辑和数据查询条件被记录
2. **审计合规要求**：某些行业（如金融、医疗）的合规要求禁止在日志中明文记录敏感查询语句
3. **开发测试环境**：在未部署 HTTPS 的开发测试环境中，SQL 语句完全明文传输

### 3.2 目标

提供一个轻量级的 SQL 传输混淆机制，满足以下目标：
1. **防止日志明文记录**：通过 XOR 混淆，使中间件日志无法直接读取 SQL 内容
2. **向后兼容**：不影响现有客户端的使用，新旧客户端可以共存
3. **轻量级实现**：性能开销可忽略，不增加系统复杂度
4. **易于集成**：提供多语言客户端示例，方便用户快速集成
**非目标**：
- 不提供真正的加密安全保护（XOR 不是安全的加密算法）
- 不替代 HTTPS（仍需要在生产环境使用 HTTPS）

## 4. 功能需求

| 序号 | 功能类别 | 功能名称 | 功能描述 |
| --- | --- | --- | --- |
| 1 | API 增强 | HTTP Header 支持 | 在 `/api/-/rest/sql` endpoint 支持可选的 `X-Enable-Xor` header，用于控制是否启用 XOR 加密 |
| 2 | 加密传输 | XOR 加密算法 | 实现 XOR 加密/解密逻辑，使用固定密钥对 SQL 文本进行循环 XOR 运算 |
| 3 | 编码转换 | Base64 编解码 | 对 XOR 加密后的二进制数据进行 Base64 编码，确保可以在 HTTP 请求体中传输 |
| 4 | 错误处理 | 解密错误处理 | 当 Base64 解码失败、UTF-8 解码失败或解密后 SQL 为空时，返回明确的错误码和错误信息 |
| 5 | 向后兼容 | 明文传输支持 | 当请求不包含 `X-Enable-Xor` header 时，保持原有的明文传输行为 |
| 6 | 客户端支持 | 多语言示例 | 提供 Python、JavaScript、Rust 等主流语言的客户端加密示例代码 |
| 7 | UI 集成 | Web UI 开关 | 在 taos-explorer 的 SQL 编辑器中添加"启用 XOR 加密"开关 |
| 8 | 日志记录 | 加密状态日志 | 在服务端日志中记录每个请求是否启用了 XOR 加密 |
| 9 | 监控指标 | Metrics 采集 | 采集 XOR 加密请求数、解密失败数等监控指标 |

## 5. 性能需求

### 5.1 性能目标

- **加密性能**：单次 XOR 加密操作耗时 < 1ms（对于 10KB SQL）
- **解密性能**：单次 XOR 解密操作耗时 < 1ms（对于 10KB SQL）
- **Base64 编解码**：编解码耗时 < 0.5ms（对于 10KB SQL）
- **总体延迟增加**：启用 XOR 加密后，端到端延迟增加 < 5ms
- **吞吐量影响**：启用 XOR 加密后，QPS 下降 < 5%

### 5.2 性能测试场景

1. **小型 SQL**（< 1KB）：典型的 SELECT 查询
2. **中型 SQL**（1KB - 10KB）：复杂的多表 JOIN 查询
3. **大型 SQL**（10KB - 100KB）：批量 INSERT 语句

### 5.3 性能基准

以明文传输为基准（100%），XOR 加密传输的性能应满足：
- 小型 SQL：≥ 98%
- 中型 SQL：≥ 95%
- 大型 SQL：≥ 90%

## 6. 安全需求

### 6.1 安全目标

1. **传输层混淆**：防止 SQL 语句在传输过程中被中间件明文记录
2. **密钥保护**：XOR 密钥硬编码在代码中，不暴露在配置文件或环境变量中
3. **错误信息安全**：解密失败时，不在错误信息中泄露密钥或加密细节

### 6.2 安全限制

明确告知用户以下安全限制：
1. **仅用于混淆**：XOR 不是安全的加密算法，不应作为唯一的安全措施

### 6.3 安全最佳实践

在文档中明确建议用户：
1. 在生产环境必须使用 HTTPS
2. XOR 加密仅用于防止日志明文记录，不能替代 HTTPS
3. 对于高安全要求的场景，应使用 TLS 客户端证书认证等更强的安全机制

## 7. 其他需求

### 7.1 兼容性需求

- **向后兼容**：不带 `X-Enable-Xor` header 的请求行为完全不变
- **客户端兼容**：现有客户端无需修改即可继续使用
- **版本兼容**：新版本服务端支持旧版本客户端，旧版本服务端拒绝新版本客户端的 XOR 请求（返回 400 错误）

### 7.2 接口需求

#### 7.2.1 HTTP API 接口

- **Endpoint**：`POST /api/-/rest/sql`
- **新增 Header**：`X-Enable-Xor: true|1`（可选）
- **请求体格式**：
  - 不启用 XOR：明文 SQL 字符串
  - 启用 XOR：Base64 编码的 XOR 加密数据
- **响应格式**：保持不变，标准 JSON 格式

#### 7.2.2 错误码定义

| 错误码 | HTTP 状态码 | 错误信息 | 说明 |
| --- | --- | --- | --- |
| 0x2701 | 400 | Invalid Base64 encoding in request body | Base64 解码失败 |
| 0x2702 | 400 | Decrypted content is not valid UTF-8 | UTF-8 解码失败 |
| 0x2703 | 400 | Decrypted SQL is empty | 解密后 SQL 为空 |

### 7.3 运维需求

- **部署要求**：无特殊部署要求，随 taos-explorer 正常升级
- **配置要求**：无需额外配置，XOR 密钥硬编码
- **日志要求**：记录 XOR 加密启用状态和解密错误
- **监控要求**：提供 Prometheus metrics 用于监控 XOR 加密使用情况

### 7.4 易用性需求

- **文档完整性**：提供详细的 API 文档、使用指南、故障排查文档
- **UI 集成**：在 Web UI 中集成，无需配置修改
- **错误提示**：解密失败时，提供清晰的错误信息和排查建议

### 7.5 测试需求（不含测试例）

- **单元测试**：覆盖 XOR 加密/解密、Base64 编解码、错误处理等核心逻辑
- **集成测试**：覆盖启用/禁用 XOR 加密的完整请求流程
- **性能测试**：验证性能需求中的各项指标
- **兼容性测试**：验证新旧客户端与新旧服务端的兼容性
- **安全测试**：验证密钥不会泄露，错误信息不包含敏感信息
- **E2E 测试**：在真实环境中验证完整的用户场景
