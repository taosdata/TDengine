## 2. 文档概述

### 2.1 目的

本文档旨在明确 TDengine TSDB v3.4.1 项目的质量管理目标、质量活动安排、角色职责划分及质量验收标准。v3.4.1 在 v3.4.0 安全加固版本的基础上，继续推进安全漏洞修复、存储功能增强（数据修复工具、批量标签修改）、查询能力提升（子查询时间范围优化、ANY/SOME/ALL/EXISTS 支持、窗口插值）及虚拟表完善等工作，同时将 v3.4.0 质量保证报告中提出的过程改进建议落实到本版本的质量管理活动中。

### 2.2 适用范围

本计划适用于 TSDB v3.4.1 全部开发活动，时间范围为 2026-01-01 至 2026-03-31（发布日期）；含系统测试延伸至 2026-04-25，项目总结至 2026-04-30。

## 3. 项目质量目标

### 3.1 整体质量目标

1. **过程合规性**：各开发阶段严格遵循质量保证制度要求，不符合项关闭率达到 100%。
2. **文档完整性**：需求、设计、测试等关键文档按计划编写并完成评审，文档完整率达到 95% 以上。
3. **缺陷管理**：系统测试阶段结束时，P0/P1 缺陷全部关闭，P2 缺陷关闭率达到 90% 以上。
4. **安全漏洞修复**：本版本识别的高优先级安全漏洞（含 SQL 注入风险）全部完成修复并通过安全验证。
5. **需求追踪**：相较 v3.4.0，改进需求追踪矩阵维护及时性，确保每周更新。
6. **缺陷报告规范率**：缺陷报告规范率（含完整重现步骤、优先级分类）≥ 95%，较 v3.4.0 提升 5%。

### 3.2 分阶段质量目标

| 阶段 | 时间范围 | 质量目标 |
| --- | --- | --- |
| 需求与设计阶段 | 2026-01-01 ~ 2026-01-31 | 需求文档评审通过率 100%；设计文档评审通过率 100% |
| 开发及功能测试阶段 | 2026-02-01 ~ 2026-03-31 | 功能测试缺陷报告规范率 ≥ 95%；代码评审覆盖率 ≥ 80% |
| 系统测试与验收阶段 | 2026-04-01 ~ 2026-04-25 | P0/P1 缺陷全部关闭；系统测试通过率 ≥ 95% |
| 项目总结阶段 | 2026-04-25 ~ 2026-04-30 | 质量保证报告完成；过程改进建议归档 |

## 5. 质量活动计划

### 5.1 项目立项阶段（2026-01-01 ~ 2026-01-07）

#### 5.1.1 项目策划审计

- **活动内容**：审计项目计划文档是否包含必要内容（范围、时间、资源、风险、质量计划等）；确认 v3.4.0 过程改进措施已纳入本版本计划。
- **交付物**：项目策划审计记录
- **责任人**：王旭

### 5.2 需求与设计阶段（2026-01-01 ~ 2026-01-31）

#### 5.2.1 需求与设计评审审计

- **活动内容**：
  - 审计需求文档（FS）是否按规定编写并组织评审
  - 审计设计文档（DS）是否与需求对应，是否完成设计评审
  - 重点审计安全漏洞修复（含 SQL 注入风险 Risk-341-01）相关的设计合理性
  - 审计需求追踪矩阵（RTM）维护情况（改进项：确保每周更新）
- **审计频次**：1 次（2026 年 1 月下旬）
- **交付物**：需求与设计评审审计记录
- **责任人**：王旭

#### 5.2.2 项目监控审计（首次）

- **活动内容**：审计项目进度跟踪、风险登记册更新情况
- **交付物**：项目监控审计记录
- **责任人**：王旭

### 5.3 开发及功能测试阶段（2026-02-01 ~ 2026-03-31）

#### 5.3.1 编码与单元测试审计

- **活动内容**：

- **审计频次**：2 次（2 月和 3 月各 1 次）
- **交付物**：编码与单元测试审计记录
- **责任人**：王旭

#### 5.3.2 项目监控审计（第二次）

- **活动内容**：审计开发进度与计划偏差，确认安全漏洞修复风险（Risk-341-01）应对措施落实情况

- **责任人**：王旭

### 5.4 系统测试与验收阶段（2026-04-01 ~ 2026-04-25）

### 5.6 配置与基线管理（贯穿全项目）

配置与基线管理活动贯穿项目全生命周期，由研发组长（关胜亮）主责实施，质量组长（王旭）执行配置审计。在 v3.4.0 经验基础上，本版本重点落实 v3.4.0 审计发现的两项改进：命名规范统一、RTM 更新及时性。

#### 5.6.1 基线建立与管理

- **活动内容**：
  - 需求评审通过后建立需求基线（BL-3410-001）；
  - 设计评审通过后建立设计基线（BL-3410-002）；
  - 功能测试完成后建立功能冻结基线（BL-3410-003）；
  - 正式发布后建立发布基线（BL-3410-004）；
  - 严格执行 v3.4.0 改进要求：所有配置项采用统一命名规范（`{版本前缀}-{类型}-{序号}` 格式），RTM 与基线配置项同步维护。
- **交付物**：[基线建立记录表](./基线建立记录表.md)
- **责任人**：关胜亮（主责），王旭（审计）

#### 5.6.2 基线变更控制

- **活动内容**：
  - 对已建立基线的配置项进行变更时，须提交 BCR，经项目经理审批后方可实施；
  - v3.4.1 共发生 2 次基线变更：
    - BCR-3410-001：SQL 注入修复设计变更（2026-02-15，关胜亮审批）；
    - BCR-3410-002：Parquet `strict_projection` 参数变更（2026-03-10，霍琳贺审批）；
  - 所有变更记录影响范围分析和验证结果。
- **交付物**：[基线变更审批记录](./基线变更审批记录.md)
- **责任人**：关胜亮（主责审批），霍琳贺（BCR-3410-002 审批）

#### 5.6.3 配置审计

- **活动内容**：
  - 在项目收尾阶段执行配置审计（AUDIT-3410-CM-001），验证配置项与基线记录一致性；
  - 审计包含对 v3.4.0 两项改进措施落地情况的专项验证（命名规范、RTM 更新及时性）；
  - v3.4.1 配置审计发现 2 项一般问题：CMISS-3410-001（`client_ip` 字段设计文档与代码不一致）和 CMISS-3410-002（RTM 测试用例对应机制未完全落地），均已关闭。
- **审计时机**：项目收尾阶段（2026-03-25 前后）
- **交付物**：[基线审计报告](./基线审计报告.md)、[问题跟踪和整改记录](./问题跟踪和整改记录.md)
- **责任人**：王旭

## 7. 质量度量指标

参照《[度量指标规范](https://taosdata.feishu.cn/wiki/L50dwsyiciOW8TkkbFZcZEpnn9e)》，本项目重点关注以下质量度量指标，在每个自然月的第三个周四进行度量：

| 指标名称 | 度量方法 | 目标值 |
| --- | --- | --- |
| 缺陷关闭周期 | 缺陷从发现到关闭的平均天数 | P0/P1 ≤ 3 天；P2 ≤ 7 天 |
| 各类缺陷数目 | 按优先级（P0~P3）统计缺陷数量及趋势 | 持续跟踪 |
| 缺陷报告规范率 | 规范缺陷数 / 总缺陷数（含完整重现步骤、正确优先级） | ≥ 95% |
| 需求追踪矩阵更新及时率 | 每周更新次数 / 计划更新次数 | 100% |
| 不符合项关闭率 | 已关闭 NCR 数 / 发现 NCR 总数 | 100%（项目结束时） |
| 文档评审通过率 | 一次评审通过文档数 / 总评审文档数 | ≥ 85% |

## 8. 不符合项（NCR）管理

### 8.1 不符合项类别

| 等级 | 定义 |
| --- | --- |
| 严重（Critical） | 违反关键制度要求，可能导致产品质量重大缺陷或项目重大风险的问题 |
| 一般（Major） | 违反过程规范要求，可能影响产品质量或交付效率的问题 |

### 8.2 不符合项处理流程

1. **发现**：QA 在审计过程中记录 NCR（含问题描述、发现日期、严重等级）。
2. **确认**：与被审计方确认问题事实。
3. **整改**：责任人制定整改措施，明确整改截止日期。
4. **跟踪**：质量组长跟踪整改进度，必要时上报项目经理。
5. **关闭**：QA 验证整改效果后关闭 NCR。
6. **汇总**：在质量保证报告中汇总 NCR 统计和分析结果。
