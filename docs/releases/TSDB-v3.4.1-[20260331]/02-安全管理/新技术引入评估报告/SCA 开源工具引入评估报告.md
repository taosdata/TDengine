### 3. **技术引入概述**

#### 3.1 **引入背景与目的**

随着项目规模扩大及第三方开源组件使用数量的持续增长，依赖组件已成为软件安全和合规风险的重要来源。第三方依赖中潜在的安全漏洞、许可证不合规问题，可能在未被及时发现的情况下被引入主干分支，进而影响产品安全性、稳定性及合规性。
为提升对第三方依赖风险的可视性与可控性，有必要在现有 CI/CD 流程中引入**软件成分分析（Software Composition Analysis，SCA）能力**，对依赖组件的安全漏洞和许可证风险进行自动化识别和持续管控。
- **待解决的痛点/需求：**
  - 缺乏对第三方依赖中**已知安全漏洞**的自动化识别机制，风险主要依赖人工评审
  - Pull Request 阶段无法及时发现**新增或升级依赖引入的安全隐患**
  - 对依赖组件的**许可证类型缺乏统一、可执行的校验策略**，存在合规风险
  - 已合入代码中的依赖在后续被披露漏洞时，**无法第一时间感知和响应**
- **预期达成的目标：**
  - 在 **Pull Request 阶段** 自动识别并阻断引入中高危漏洞或不合规许可证的依赖
  - 对项目依赖进行**持续性漏洞扫描**，及时发现新增披露的安全问题
  - 建立**依赖许可证白名单机制**，确保第三方组件使用符合合规要求
  - 将第三方依赖风险检查**前移至 CI 阶段**，减少安全问题进入主分支的概率
- **拟应用的核心场景：**
  **Pull Request 合并前检查**
  - 对新增或变更的依赖进行漏洞等级和许可证合规性审查
  - 不符合安全或合规策略的 PR 自动阻断
  **主分支持续集成扫描**
  - 在代码合入主分支后，对完整依赖树进行漏洞和许可证扫描
  **定时安全巡检**
  - 通过定时任务扫描现有依赖，发现新披露的安全漏洞

### 5. **详细评估内容**

#### 5.1 **技术可行性评估** `[负责人：架构师]`

1. **功能匹配度：** 
该方案完整覆盖第三方依赖安全与合规管理的核心需求，包括依赖变更审查、已知漏洞识别及许可证合规校验。通过 Pull Request 阶段的依赖审查与持续集成阶段的漏洞、许可证扫描，实现对新增依赖和存量依赖的双重管控，不存在功能缺失；同时方案聚焦依赖安全与合规本身，未引入与需求无关的复杂功能，功能边界清晰，不存在明显功能过剩问题。
1. **架构契合度：**
方案基于 GitHub Actions 实现，与现有 CI/CD 架构高度兼容，直接复用当前代码仓库、构建流程和权限体系。无需对现有系统架构、运行时环境或业务代码进行改造，仅通过配置方式集成安全扫描能力，对现有技术栈侵入性低，集成风险可控。
1. **性能影响：** 
该技术方案运行于 CI 环境，不影响生产系统的运行时性能。扫描过程主要消耗 CI 计算资源，对构建时间的影响可控，且可通过分阶段触发（PR / Push / 定时任务）进行合理分摊。目前方案采用成熟工具链，实际执行时间与依赖规模线性相关，未引入明显性能瓶颈，整体性能影响可接受。
1. **可靠性：**
所选用的工具均为成熟且被广泛使用的开源项目或官方工具，具备良好的稳定性和持续维护能力。扫描任务以 CI Job 形式独立运行，不参与业务系统运行路径，不会成为业务系统的新单点故障；即使扫描任务异常，仅影响 CI 结果，不影响系统正常运行，整体可靠性风险较低。
1. **可替代方案对比：** 
在同类解决方案中，该方案兼顾官方支持、社区成熟度与易集成性。相比引入额外的商业 SCA 平台或自研扫描系统，该方案部署成本低、学习成本小、维护负担轻，且已与当前研发流程深度集成。综合对比现有替代方案，当前方案在可控成本与实际效果之间具备明显优势。

#### 5.2 ** 安全风险评估** `[负责人：安全团队]`

1. **历史漏洞记录：** 
所采用的工具与技术均为官方或主流社区维护项目，历史漏洞信息可在 CVE、NVD 及官方漏洞数据库中追溯。整体来看，相关工具的高危漏洞数量较少，且一旦发现安全问题，社区或官方通常能够快速发布修复版本，漏洞响应与修复节奏符合企业级安全要求。
1. **默认安全配置：**
该方案以 CI 工具形式运行，不涉及对外服务暴露，不存在默认监听端口、默认账号或默认密码等传统配置风险。默认运行权限受 GitHub Actions 权限模型约束，遵循最小权限原则，整体默认安全配置风险较低。
1. **安全特性支持：**
方案在安全能力上满足依赖安全治理的核心需求，支持：
- 基于权威漏洞数据源的漏洞识别与分级
- 对第三方依赖的安全风险自动化扫描与阻断
- 扫描结果可审计、可追溯，便于安全复核
虽然该方案本身不直接提供认证、授权或加密等运行时安全能力，但其定位为供应链安全工具，功能范围与使用场景匹配，安全特性完整且合理。
1. **代码质量与维护活跃度：**
相关工具均为开源项目，代码质量较高，并长期接受社区审查与安全研究人员关注。整体来看，安全问题披露透明、修复及时，工具链本身的安全风险可控。
1. **对产品攻击面的影响：**
该方案仅运行于 CI/CD 环境，不随产品发布进入生产系统，不引入新的运行时组件或对外接口，因此不会显著增加产品本身的攻击面。相反，通过提前发现依赖漏洞和不安全组件，整体上有助于降低产品的实际攻击面。

#### 5.3 ** 许可合规性评估** `[负责人：法务]`

1. **许可证分析：**
本方案所涉及的第三方工具及其依赖均采用主流、成熟的开源许可证，主要包括 MIT、Apache-2.0、BSD、ISC 等宽松型许可证。通过在 CI 中启用许可证白名单机制，对引入的第三方依赖许可证进行自动化校验，确保其与公司现有产品许可证策略保持兼容，不存在明显的许可证冲突风险。
1. **传染性风险：**
在当前配置下，已明确禁止引入 GPL、AGPL 等具有强传染性的许可证类型。通过自动化扫描和阻断机制，可在依赖引入阶段及时发现潜在的传染性许可证风险，避免因依赖关系导致公司自有代码被要求开源的情形，整体传染性风险可控。
1. **义务履行：** 
针对所允许的开源许可证类型，其主要合规义务集中在版权声明保留、许可证文本包含等常规要求，均可通过文档或发布流程进行满足。项目已通过自动化工具生成和维护依赖许可证清单，便于后续在产品发布或对外交付时统一履行相关义务，义务履行难度低、可操作性强。
1. **专利风险：** 
方案中所采用的许可证大多包含明确的专利授权条款（如 Apache-2.0），能够在一定程度上降低专利侵权风险。同时，许可证扫描策略中已纳入对特殊 LicenseRef 的显式管理（如涉及专利声明的许可证），确保专利相关风险在引入阶段即被识别和评估。综合来看，当前方案不存在显著的已知专利风险。
