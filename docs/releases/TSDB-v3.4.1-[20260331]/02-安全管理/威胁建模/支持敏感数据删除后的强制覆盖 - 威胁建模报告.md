### 3. 分析报告

本报告针对「支持敏感数据删除后的强制覆盖」功能进行了威胁建模分析。该功能旨在解决 TDengine 现有 `DELETE` 仅做逻辑标记、物理存储位置仍残留原始数据的安全问题，提供同步强制覆盖（零值或随机数据）与定期 compact 清理两种互补机制，满足敏感数据删除后不可恢复的合规要求。

- **核心发现：** 共识别出 `6` 个潜在威胁，其中 `高危` `0` 个，`中危` `4` 个，`低危` `2` 个。
- **主要风险场景：**
   - **内部人员绕过安全删除：** 高权限用户先关闭 `secure_delete` 属性再执行普通 DELETE，致使数据未被覆盖，可被取证工具恢复。
   - **硬件层数据残留：** SSD/NVMe 固件的磨损均衡机制可能保留原始数据，超出软件覆盖能力范围。
   - **备份媒体数据残留：** 安全删除执行前已创建的备份中，敏感数据不受本功能保护。
   - **性能滥用拒绝服务：** 反复执行大范围 `SECURE_DELETE` 导致15%~35%的删除性能损耗累积，影响业务正常写入。
- **结论：** 该功能设计在满足敏感数据合规销毁方面价值显著，核心安全目标（软件层物理覆盖不可恢复）通过同步写入语义有效实现。识别的威胁均属中低风险，可通过现有 RBAC 控制、审计日志、文档说明等组合措施缓解，无需引入额外复杂安全机制。

### 4. 威胁识别与分析（STRIDE）

本功能在 TDengine Vnode 存储引擎层引入覆盖写入路径，核心数据流为：`DELETE 语句 → SQL 解析器 → 存储引擎 → 物理覆盖写入 → 审计日志记录 → 返回调用方`。

#### 4.1 关键实体与数据

| 实体/数据 | 描述 | 敏感性 |
| --- | --- | --- |
| 敏感时序数据 | 待安全删除的原始时序数据，存储于 Vnode 数据文件中 | 高（触发安全删除的核心对象） |
| `secure_delete` 属性 | 数据库/超级表级别的安全删除开关，控制覆盖行为 | 中（属性值变更可影响删除安全性） |
| `secure_erase_mode` 配置 | 全局覆盖模式配置（零值/随机数据） | 中 |
| Vnode 数据文件 | 物理存储文件，覆盖写入的目标位置 | 高（直接存储原始数据） |
| 审计日志 | 记录安全删除及 compact 操作的审计记录 | 中（用于操作溯源） |

#### 4.2 威胁评估

| 威胁ID | **威胁描述/攻击场景** | **STRIDE** | **相关组件/数据流** | **风险等级** |
| --- | --- | --- | --- | --- |
| T-SECDEL-01 | **内部人员关闭安全删除绕过覆盖：** 具有 `ALTER DATABASE/STABLE` 权限的恶意内部用户，先将 `secure_delete` 改为 0，再执行普通 `DELETE`，使原始数据未经覆盖仅做逻辑标记，后续可通过文件级取证工具恢复敏感数据。 | T（篡改）、R（抵赖） | `secure_delete` 属性 → Vnode 数据文件 | 中 |
| T-SECDEL-02 | **SSD/NVMe 固件磨损均衡导致物理残留：** 操作系统层面的覆盖写入触发固件将数据写入新物理扇区，原扇区数据仍存在于 SSD 内部保留区，可通过专业存储取证设备读取，软件层无法完全消除。 | I（信息泄露） | Vnode 数据文件 → 物理存储介质 | 中 |
| T-SECDEL-03 | **备份媒体中的敏感数据残留：** 在安全删除执行之前已创建的全量或增量备份中，被删除的敏感数据仍完整保留，不受本功能保护，攻击者通过访问备份文件即可恢复数据。 | I（信息泄露） | 数据库备份文件 | 中 |
| T-SECDEL-04 | **滥用 SECURE_DELETE 导致性能拒绝服务：** 具有 DELETE 权限的用户或被入侵的应用反复执行大范围 `SECURE_DELETE` 操作，利用15%~35%的额外覆盖开销持续拖慢数据库写入/删除吞吐，影响其他业务正常运行。 | D（拒绝服务） | `SECURE_DELETE` 关键字 → 存储引擎 | 中 |
| T-SECDEL-05 | **compact 未执行期间逻辑删除数据残留：** 对于通过普通 `DELETE`（未使用 `SECURE_DELETE` 关键字且 `secure_delete=0`）产生的逻辑删除数据，在 compact 执行前仍以标记形式存在于数据文件中，拥有文件系统访问权限的攻击者可直接解析数据文件读取已删除数据。 | I（信息泄露） | Vnode 数据文件（逻辑删除标记） | 低 |
| T-SECDEL-06 | **审计日志篡改导致安全删除操作抵赖：** 攻击者（或恶意管理员）在执行安全删除后清除或篡改对应审计日志条目，使删除操作无法溯源，无法证明操作是否按规范执行了覆盖写入。 | R（抵赖）、T（篡改） | 审计日志 | 低 |

### 5. 安全需求与设计约束

| 威胁ID | **转化后的安全需求/设计约束** | **类型** | **优先级** |
| --- | --- | --- | --- |
| T-SECDEL-01 | SEC-SECDEL-001（操作审计）：对 `ALTER DATABASE/STABLE SET secure_delete` 的所有修改操作必须记录审计日志，包含操作时间、执行用户、修改前后值，以便事后溯源。 | 审计需求 | 中 |
| T-SECDEL-02 | SEC-SECDEL-002（硬件限制告知）：官网文档必须明确说明本功能仅保证操作系统/文件系统层面的不可恢复性，SSD 固件磨损均衡可能导致硬件层残留，建议高安全场景配合存储加密（data-at-rest encryption）使用。 | 文档/告知需求 | 中 |
| T-SECDEL-03 | SEC-SECDEL-003（备份管理告知）：官网文档须说明安全删除不覆盖已有备份，用户须配合备份生命周期管理策略（定期清理含敏感数据的旧备份）实现完整的数据销毁。 | 文档/告知需求 | 中 |
| T-SECDEL-04 | SEC-SECDEL-004（使用建议）：官网文档建议用户仅对真正需要安全删除的敏感表/库开启 `secure_delete`，而非全库开启，以避免非必要的性能损耗和潜在滥用。 | 非功能安全建议 | 低 |
| T-SECDEL-05 | SEC-SECDEL-005（场景选择指引）：文档明确说明，对于须保证物理不可恢复的场景，应使用 `SECURE_DELETE` 关键字或开启 `secure_delete` 属性，而不应依赖 compact 周期作为唯一的安全手段。 | 文档/告知需求 | 低 |
| T-SECDEL-06 | SEC-SECDEL-006（审计日志保护）：审计日志的访问和修改权限需严格控制，仅审计管理员可读取，任何人不得删除或修改，依托现有审计框架保障日志完整性。 | 审计需求 | 低 |
