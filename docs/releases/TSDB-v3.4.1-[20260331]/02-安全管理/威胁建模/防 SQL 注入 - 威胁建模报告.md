### 3. 分析报告

本报告针对 TDengine 防 SQL 注入功能进行了威胁建模分析。该功能旨在通过「字符串级正则过滤」与「AST 语法树级语义检查」的双层防护机制，结合可配置的黑名单/白名单规则体系及自动学习模式，系统性地阻断 SQL 注入攻击，保障 TDengine 数据安全和系统稳定。

- **核心发现：** 共识别出 `7` 个潜在威胁，其中 `高危` `3` 个，`中危` `3` 个，`低危` `1` 个。
- **主要风险场景：**
  - **白名单投毒：** 攻击者在学习模式开启期间刻意重复执行恶意 SQL，使其超过学习阈值并被自动录入白名单，永久绕过后续检测。
  - **编码混淆绕过：** 攻击者利用 URL 编码、十六进制、Unicode 变体等手段混淆注入 payload，绕过第一层正则检测，在 AST 层仍可能构成威胁。
  - **安全配置篡改：** 攻击者若利用权限漏洞执行 `ALTER LOCAL` 命令，可将 `sqlSecurity` 关闭或切换为宽松的运行模式，直接禁用防护。
- **结论：** 该功能双层防护架构设计合理，针对主流 SQL 注入攻击向量覆盖全面。白名单学习模式和用户自定义正则规则是两个需要重点关注的攻击面。应在编码实现前，将本报告的安全需求作为核心设计约束予以落实。

### 4. 威胁识别与分析（STRIDE）

TDengine 防 SQL 注入功能部署在客户端 SQL 执行路径上，所有来自外部应用（通过 JDBC、RESTful API、taos-CLI 等）的 SQL 请求在进入 TDengine 解析引擎前，经过两层过滤：第一层在 `buildRequest()` 之后、SQL 解析之前基于 PCRE 正则对字符串进行模式匹配；第二层在 `qAnalyseSqlSemantic()` 之后、`translate()` 之前对 AST 语法树进行语义检查。规则由服务端统一管理，通过心跳同步至客户端缓存。

#### 4.1 关键实体与数据

| 实体/数据 | 描述 | 敏感性 |
| --- | --- | --- |
| SQL 安全规则文件 | `/etc/taos/sql_rules.json`，存储黑名单和白名单正则规则，由 taosk 密钥加密 | 高（规则泄露可协助攻击者构造绕过 payload） |
| SQL 安全配置项 | `taos.cfg` 中的 `sqlSecurity`、`sqlSecurityWhitelistMode` 等配置，taosd 启动时加载 | 高（配置篡改可直接关闭防护） |
| 白名单学习数据 | 学习模式期间记录的 SQL 模式及执行上下文（用户、数据库、时间） | 中（含业务 SQL 结构，可能泄露数据访问模式） |
| 被拒绝 SQL 的审计日志 | 存储在 taoslog 中，包含被拦截的 SQL 语句和触发的规则名称 | 中（可能含有注入 payload 和敏感的表/列名） |
| 客户端配置缓存 | 客户端首次连接后从服务端拉取并缓存的安全配置 | 中（缓存期间配置更新存在一个心跳周期延迟） |

#### 4.2 威胁评估

| 威胁ID | 威胁描述/攻击场景 | STRIDE | 相关组件/数据流 | 风险等级 |
| --- | --- | --- | --- | --- |
| T-SQLINJ-01 | **白名单投毒攻击：** 在白名单学习模式开启期间（`whitelistLearning=1`），攻击者（或被入侵的应用）持续重复执行精心构造的恶意 SQL 语句，使其执行次数超过 `whitelistLearningThreshold` 阈值（默认 10 次），从而被自动识别为"正常业务模式"并持久化写入白名单规则文件。学习期结束、白名单模式启用后，该恶意 SQL 将被永久放行，绕过所有后续检测。 | S（仿冒）、T（篡改） | 白名单学习模块 -> `sql_rules.json` | 高 |
| T-SQLINJ-02 | **编码混淆绕过第一层正则：** 攻击者利用 URL 编码（`%27`）、十六进制（`0x`）、Unicode 变体（`\u006f\u0072`）等方式对注入 payload 进行编码，混淆第一层基于字符串的 PCRE 正则检测，将原本可识别的注入特征（如 `OR 1=1`）变形为检测规则无法覆盖的形式后发送。尽管 FS 第 4.1.2 节声明包含编码绕过检测，但正则规则的完备性依赖具体实现，存在新型编码绕过的残余风险。 | T（篡改） | SQL 字符串 -> 第一层 PCRE 过滤 | 高 |
| T-SQLINJ-03 | **通过 ALTER LOCAL 禁用安全防护：** 若攻击者获取了足够高的数据库权限（或通过 SQL 注入漏洞本身获取权限），可执行 `ALTER LOCAL 'sqlSecurity' 'false'` 或 `ALTER LOCAL 'sqlSecurityWhitelistMode' '0'` 来关闭整个 SQL 安全检查体系，使后续所有 SQL 注入攻击不再受到拦截，同时修改对应的防护配置。 | E（权限提升）、T（篡改） | `ALTER LOCAL` 命令 -> `sqlSecurity` 配置 | 高 |
| T-SQLINJ-04 | **规则优先级竞争绕过：** FS 第 5.4 节说明，在黑白名单并存模式下，同等优先级时黑名单优先；但不同优先级时，高优先级规则胜出。若攻击者通过合法渠道（如运维失误）在白名单中添加了优先级为 HIGH 的宽泛规则（如匹配 `SELECT.*`），而黑名单中的危险规则优先级较低，则危险 SQL 有可能通过高优先级白名单放行，绕过低优先级黑名单拦截。 | T（篡改） | SQL 规则优先级判断逻辑 | 中 |
| T-SQLINJ-05 | **客户端配置缓存延迟窗口攻击：** FS 第 5.0.1 节说明，客户端在连接时拉取配置并缓存，后续更新需等待下一次心跳。在管理员通过 `ALTER LOCAL` 命令收紧安全配置后（如从黑名单模式切换为更严格的白名单模式），存在一个心跳周期的窗口期，期间仍有活跃连接使用旧配置运行，攻击者可利用此窗口继续使用旧配置下被允许的注入 payload。 | T（篡改）、D（拒绝服务） | 客户端配置缓存 <-> 服务端配置同步 | 中 |
| T-SQLINJ-06 | **PCRE ReDoS 攻击：** FS 第 4.1.2 节和第 4.2.1 节允许用户在 `sql_rules.json` 中自定义 PCRE 正则表达式规则。若用户配置了含有灾难性回溯特征的复杂正则（如嵌套量词 `(a+)+`），攻击者可提交特制的输入字符串，触发 PCRE 引擎指数级回溯，导致 `buildRequest()` 后的检查步骤 CPU 占用率飙升、SQL 请求处理阻塞，形成拒绝服务。 | D（拒绝服务） | 第一层 PCRE 正则匹配 -> 自定义 `sql_rules.json` 规则 | 中 |
| T-SQLINJ-07 | **安全事件抵赖/溯源困难：** FS 第 5.3 节描述的审计日志记录了被拒绝的 SQL 和触发的规则，但未明确说明日志中包含执行者的用户身份标识和客户端来源 IP。在发生 SQL 注入攻击后，若日志缺少这些字段，将无法确认攻击者身份，难以进行事后溯源分析和法律取证。 | R（抵赖） | 审计日志 taoslog | 低 |

### 5. 安全需求与设计约束

| 威胁ID | 转化后的安全需求/设计约束 | 类型 | 优先级 |
| --- | --- | --- | --- |
| T-SQLINJ-01 | **SEC-SQLINJ-001（学习模式访问控制）：** 白名单学习模式的启用、学习周期和阈值调整必须限制为高权限用户操作。同时，学习模式自动生成的候选规则在正式写入 `sql_rules.json` 之前，应提供人工审核确认机制（或至少在管理日志中高亮标记新增规则），防止恶意 SQL 被自动录入白名单。 | 安全功能需求 | 高 |
| T-SQLINJ-02 | **SEC-SQLINJ-002（编码规范化预处理）：** 在第一层 PCRE 正则匹配之前，建议增加输入字符串的编码规范化处理步骤（如 URL 解码、十六进制解码），将常见编码变体还原为标准形式后再进行规则匹配，提高编码混淆绕过的检测成功率。 | 安全设计约束 | 高 |
| T-SQLINJ-03 | **SEC-SQLINJ-003（安全配置变更审计）：** 对 `sqlSecurity`、`sqlSecurityWhitelistMode` 等核心安全配置项的 `ALTER LOCAL` 操作，必须在审计日志中记录操作者、时间、变更前后的值，并建议对关闭安全功能（`sqlSecurity=false`）的操作增加额外的二次确认或通知机制。 | 审计需求 | 高 |
| T-SQLINJ-04 | **SEC-SQLINJ-004（白名单规则范围约束）：** 在规则校验逻辑中，对覆盖范围过于宽泛的白名单规则（如匹配所有 SELECT 语句的通配符规则）添加警告或拒绝机制，防止运维人员无意间添加绕过黑名单保护的宽泛白名单规则。 | 安全设计约束 | 中 |
| T-SQLINJ-06 | **SEC-SQLINJ-005（正则复杂度限制）：** 在处理用户自定义 `pattern` 字段时，对正则表达式进行复杂度检测（如限制嵌套量词深度、最大回溯步数，或使用 PCRE 的执行时间限制接口），拒绝可能导致指数级回溯的恶意/错误正则表达式。 | 非功能安全需求 | 中 |
| T-SQLINJ-07 | **SEC-SQLINJ-006（增强安全审计日志）：** 安全审计日志（被拒绝 SQL 的 WARN 级别日志）中必须包含：执行用户（`user`）、客户端连接标识（IP 或 connection ID）、触发的规则 ID、被拒绝的 SQL（可截断）和时间戳，确保安全事件具备完整的溯源能力。 | 审计需求 | 中 |
