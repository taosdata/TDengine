### 3. 分析报告

本报告针对「数据修复工具」功能进行了威胁建模分析。该功能旨在将 TDengine 的本地修复能力统一收敛到 `taosd -r` 模式下，以显式的 `--repair-target` 参数描述修复对象，支持 vnode 范围内的 `meta`、`tsdb`、`wal` 三类目标的离线本地修复。

- **核心发现：** 共识别出 `7` 个潜在威胁，其中 `高危` `0` 个，`中危` `3` 个，`低危` `4` 个。
- **主要风险场景：**
  - **备份路径遍历**：`--backup-path` 参数如未做路径合法性校验，可能被构造为路径遍历攻击向量（T-REPAIR-02）。
  - **修复操作可追溯性**：`repair.log` 未明确规定记录操作者 OS 用户信息，存在事后溯源不足的风险（T-REPAIR-04）。
  - **临时目录备份泄露**：未指定 `--backup-path` 时回退到临时目录，可能将备份数据写入世界可读路径（T-REPAIR-05）。
- **结论：** 该功能设计整体安全性良好，遵循最小权限、安全默认、最小暴露面等核心安全原则。识别出的 3 个中危威胁均为实现层面的常规防护要点，对于本地离线运维工具属于可接受的残余风险。

### 4. 威胁识别与分析（STRIDE）

本工具为本地离线 CLI 工具，核心功能是通过命令行参数指定修复目标，对 TDengine vnode 的 meta 元数据、tsdb fileset、wal 日志文件进行离线修复，并可选地将修复前数据备份到指定路径。修复操作仅在 `taosd -r` 启动期执行，不改变正常在线读写路径，不引入新的网络接口。

#### 4.1 关键实体与数据

| 实体/数据 | 描述 | 敏感性 |
| --- | --- | --- |
| 运维人员 | 执行 `taosd -r` 的本地系统用户，需具备系统级执行权限 | 高（操作权限） |
| CLI 命令行参数 | `--repair-target`、`--backup-path`、`--mode`、`--node-type` 等参数 | 中 |
| vnode meta 文件 | vnode 元数据目录，记录表结构等元信息 | 高（数据库结构信息） |
| tsdb fileset | TSDB 数据文件集合（.head/.data/.sma/.stt），含原始时序数据 | 高（业务时序数据） |
| WAL 日志文件 | Write-Ahead Log，含未落盘的写入操作记录 | 高（含未提交事务数据） |
| 备份目录 | `${backup-path}/taos_backup_YYYYMMDD/vnode<id>/`，修复前的数据副本 | 高（含原始数据副本） |
| repair.log | 记录 fid、action、reason 等修复操作日志 | 低 |

#### 4.2 威胁评估

| 威胁ID | 威胁描述/攻击场景 | STRIDE | 相关组件/数据流 | 风险等级 |
| --- | --- | --- | --- | --- |
| T-REPAIR-01 | **未授权修复执行**：攻击者通过已获取的系统权限（如 sudo 提权、shell 劫持或恶意脚本），在无合法运维授权的情况下执行 `taosd -r` 修复命令，删除或重建 vnode 数据，造成数据永久损失。由于攻击者需要已具备系统级权限，此威胁前提较强。 | S（仿冒） | 运维人员 → CLI 命令行 → taosd -r | 低 |
| T-REPAIR-02 | **备份路径遍历**：攻击者或误操作的运维人员构造含 `../` 或绝对路径的 `--backup-path` 参数（如 `--backup-path /etc` 或 `--backup-path ../../sensitive`），若实现中未做路径合法性校验，备份数据可能写入敏感系统目录，存在覆盖关键配置文件的风险。 | T（篡改） | `--backup-path` 参数 → 文件系统写入 | 中 |
| T-REPAIR-03 | **通配符误操作扩大修复范围**：运维人员误用 `fileid=*` 触发某 vnode 下全部 fileset 的修复，远超实际损坏范围。FS 说明健康 fileset 在 repair 流程下应保持无变更，但结合 `full_rebuild` 等深度策略时，大范围操作仍存在意外影响健康数据的潜在风险。 | T（篡改） | `fileid=*` → vnode 全量 fileset | 低 |
| T-REPAIR-04 | **修复操作无充分溯源**：`repair.log` 记录了 fid、action、reason 字段，但 FS 未明确要求记录执行修复操作的 OS 用户信息及精确时间戳。若修复后数据出现异常，在多人共享运维账户的场景下，难以确定具体操作者，存在操作抵赖风险。 | R（抵赖） | repair.log → 事后审计 | 中 |
| T-REPAIR-05 | **临时目录备份数据泄露**：未指定 `--backup-path` 时，FS §4.3 说明"代码路径允许回退到临时目录作为备份根目录"。`/tmp` 等临时目录通常具有世界可读权限，同节点上的其他操作系统用户或进程可读取备份数据，造成业务时序数据泄露。 | I（信息泄露） | 备份目录（临时目录 /tmp） → 同节点其他用户 | 中 |
| T-REPAIR-06 | **高成本修复操作耗尽 IO 资源**：`full_rebuild` 策略需要重建完整 core 数据，是成本最高的修复策略（FS §5）。在磁盘 IO 资源有限或与其他服务混部的节点上，修复操作可能大量消耗磁盘 IO 带宽。虽然 FS §8 要求修复在停服后执行以缓解此风险，但在混部场景下仍需关注。 | D（拒绝服务） | taosd -r full_rebuild → 磁盘 IO | 低 |
| T-REPAIR-07 | **修复操作意外影响非目标 vnode**：若 vnode 路径解析逻辑存在边界错误或整数溢出，可能将修复操作的目标文件路径解析到非预期 vnode 目录，影响未声明的 vnode 数据文件。FS §4.2 的 grammar 强制要求显式指定 `vnode=<id>` 提供了一定约束。 | E（权限提升） | CLI 参数解析 → 文件系统路径计算 | 低 |

### 5. 安全需求与设计约束

| 威胁ID | 转化后的安全需求/设计约束 | 类型 | 优先级 |
| --- | --- | --- | --- |
| T-REPAIR-02 | SEC-DATAREP-001（路径校验）：`--backup-path` 参数在实现中应进行路径合法性校验，建议限制备份路径为绝对路径，并拒绝解析后指向系统敏感目录（如 `/etc`、`/bin`、`/lib`、`/usr` 等）的路径。 | 安全设计约束 | 中 |
| T-REPAIR-04 | SEC-DATAREP-002（日志增强）：`repair.log` 建议记录执行修复的 OS 用户名（通过 `getlogin()` 或环境变量获取）及修复开始/结束时间戳，以支持事后溯源和审计需求。 | 审计需求 | 中 |
| T-REPAIR-05 | SEC-DATAREP-003（临时目录权限）：当备份路径回退到临时目录时，应使用 `mkdtemp()` 创建具有独占权限（700）的临时目录，而非在 `/tmp` 根目录下创建世界可读的目录结构。 | 安全设计约束 | 中 |
