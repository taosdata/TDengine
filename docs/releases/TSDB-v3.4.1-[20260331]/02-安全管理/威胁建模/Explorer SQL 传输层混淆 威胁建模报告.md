### 3. 分析报告

本报告针对 Explorer SQL 传输层混淆功能进行了威胁建模分析。该功能旨在通过 XOR 混淆机制防止 SQL 语句在传输过程中被中间件明文记录，降低日志泄露风险和满足审计合规要求。
- **核心发现**：共识别出 `9` 个潜在威胁，其中 `高危` `3` 个，`中危` `4` 个，`低危` `2` 个。
- **主要风险场景**：
   - **密钥安全风险**：XOR 密钥硬编码在代码中，可能被逆向工程提取，导致混淆机制完全失效。
   - **安全假象风险**：用户可能误认为 XOR 混淆提供了加密保护，在生产环境中不部署 HTTPS，导致严重的安全漏洞。
   - **中间人攻击**：在没有 HTTPS 的情况下，攻击者可以截获并解密 XOR 混淆的数据，甚至篡改 SQL 语句。
   - **降级攻击**：攻击者可以移除 `X-Enable-Xor` header，强制使用明文传输。
- **结论**：该功能设计在防止日志明文记录方面有一定价值，但 XOR 混淆不是真正的加密算法，引入了新的攻击面和安全假象风险。必须在功能详细设计与编码实现前，将本报告提出的安全需求作为核心设计约束予以落实，特别是强化用户教育和文档警告。

### 4. 威胁识别与分析（STRIDE）

该功能为 taos-explorer 的 `/api/-/rest/sql` endpoint 添加可选的 XOR 混淆机制。客户端通过设置 `X-Enable-Xor: true` header，将 SQL 语句进行 XOR 加密后再 Base64 编码发送；服务端接收后进行 Base64 解码和 XOR 解密，然后执行 SQL。

#### 4.1 关键实体与数据

| 实体/数据 | 描述 | 敏感性 |
| --- | --- | --- |
| SQL 语句 | 用户提交的数据库查询或操作语句，可能包含敏感的业务逻辑和数据查询条件 | 高 |
| XOR 密钥 | 硬编码在客户端和服务端代码中的固定密钥，用于 XOR 加密/解密 | 高 |
| X-Enable-Xor Header | HTTP 请求头，用于标识是否启用 XOR 混淆 | 低 |
| Base64 编码数据 | XOR 加密后的二进制数据经过 Base64 编码的结果 | 中 |
| 中间件日志 | HTTP 代理、网关、负载均衡器等记录的请求日志 | 中 |
| 错误信息 | 解密失败时返回的错误码和错误消息 | 中 |

#### 4.2 威胁评估

| 威胁 ID | 威胁描述 / 攻击场景 | STRIDE | 相关组件 / 数据流 | 风险等级 |
| --- | --- | --- | --- | --- |
| T-XOR-01 | **密钥提取攻击**：攻击者通过逆向工程客户端代码（JavaScript、Python、Rust 等）或服务端二进制文件，提取硬编码的 XOR 密钥。一旦密钥泄露，所有使用该密钥的混淆数据都可以被解密。 | I（信息泄露） | XOR 密钥、客户端/服务端代码 | 高 |
| T-XOR-02 | **安全假象风险**：用户误认为启用 XOR 混淆后数据已被"加密"，在生产环境中不部署 HTTPS，导致 SQL 语句在网络传输中完全暴露。攻击者可以轻易截获并解密数据。 | I（信息泄露）/ E（权限提升） | 整个数据流、用户认知 | 高 |
| T-XOR-03 | **中间人攻击（无 HTTPS）**：在没有 HTTPS 的环境中，攻击者可以截获 XOR 混淆的数据包，使用已知或逆向得到的密钥解密 SQL 语句，甚至篡改 SQL 后重新加密发送给服务器。 | T（篡改）/ I（信息泄露） | 网络传输层、XOR 加密数据 | 高 |
| T-XOR-04 | **降级攻击**：攻击者作为中间人，移除客户端请求中的 `X-Enable-Xor` header，强制服务端使用明文传输模式，绕过混淆机制。 | T（篡改）/ I（信息泄露） | X-Enable-Xor Header、HTTP 请求 | 中 |
| T-XOR-05 | **密钥猜测攻击**：如果 XOR 密钥过于简单或可预测，攻击者可以通过已知明文攻击（例如猜测常见的 SQL 语句如 "SELECT * FROM"）快速推导出密钥。 | I（信息泄露） | XOR 密钥、加密算法 | 中 |
| T-XOR-06 | **错误信息泄露**：解密失败时，错误信息（如 "Invalid Base64 encoding"、"Decrypted content is not valid UTF-8"）可能帮助攻击者判断解密过程的哪个环节失败，辅助攻击者进行针对性攻击。 | I（信息泄露） | 错误处理、错误码 | 低 |
| T-XOR-07 | **重放攻击**：攻击者截获一次合法的 XOR 混淆请求，重复发送给服务器，导致 SQL 语句被多次执行（例如重复插入数据、重复删除数据）。 | T（篡改）/ S（仿冒） | HTTP 请求、XOR 加密数据 | 中 |

### 5. 安全需求与设计约束

| 威胁 ID | 转化后的安全需求 / 设计约束 | 类型 | 优先级 |
| --- | --- | --- | --- |
| T-XOR-01 | **SEC-XOR-001（密钥保护）**：XOR 密钥必须使用代码混淆技术（如字符串加密、控制流混淆）进行保护，增加逆向工程难度。考虑使用密钥派生函数（KDF）从多个来源派生密钥，而非直接硬编码。 | 安全设计约束 | 高 |
| T-XOR-02 | **SEC-XOR-002（强制 HTTPS 警告）**：在文档、UI、API 响应中必须明确警告用户：XOR 混淆不是加密，生产环境必须使用 HTTPS。 | 文档与用户教育 | 高 |
| T-XOR-03 | **SEC-XOR-003（HTTPS 部署指南）**：提供详细的 HTTPS 部署指南和最佳实践文档，包括证书配置、TLS 版本选择、密码套件配置等。 | 文档与用户教育 | 中 |
| T-XOR-04 | **SEC-XOR-004（防降级保护）**：客户端强制使用 XOR 混淆。 | 安全设计约束 | 中 |
| T-XOR-05 | **SEC-XOR-005（强密钥要求）**：XOR 密钥必须具有足够的长度（至少 32 字节）和随机性，避免使用简单的字符串或可预测的模式。密钥应通过密码学安全的随机数生成器生成。 | 安全设计约束 | 高 |
| T-XOR-06 | **SEC-XOR-006（错误信息脱敏）**：错误信息应避免泄露过多的技术细节。考虑使用通用的错误消息（如 "Request decryption failed"），详细的错误信息仅记录在服务端日志中。 | 安全设计约束 | 低 |
| T-XOR-07 | **SEC-XOR-007（防重放机制）**：在 XOR 混淆的请求中添加时间戳，服务端验证请求的新鲜性（例如时间戳在 5 分钟内有效）以防止重放。 | 安全功能需求 | 中 |
