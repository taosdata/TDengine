### 3. 分析报告

本报告针对 **三员权限（强制三权分立）+ 强制访问控制（MAC）** 功能进行了威胁建模分析。该功能旨在通过强制实施三权分立和基于 Bell-LaPadula 模型的强制访问控制，实现权力制衡、消除单点安全风险、建立不可抵赖的审计闭环，并通过安全等级（0-4）实现跨等级数据隔离。
- **核心发现**：共识别出 `15` 个潜在威胁，其中 `高危` `6` 个，`中危` `7` 个，`低危` `2` 个。
- **主要风险场景**：
   - **权限绕过与提升**：root 禁用机制被绕过、安全等级校验逻辑缺陷、元数据篡改导致权限提升。
   - **数据泄露与越权访问**：低等级用户通过旁路攻击读取高等级数据、缓存失效导致安全等级不一致、跨等级信息泄露。
   - **完整性破坏**：高等级用户非法修改低等级数据、继承关系被破坏、元数据不一致。
   - **可用性攻击**：三员角色回收导致系统不可用、安全等级配置错误锁定资源、审计日志被恶意填充。
   - **审计失效**：关键操作未记录审计日志、SYSTEM 用户被冒用、审计数据被篡改或删除。
- **结论**：该功能设计在安全性方面具有重大提升价值，但引入了复杂的权限管理逻辑和新的攻击面。必须在功能详细设计与编码实现前，将本报告提出的安全需求作为核心设计约束予以落实，特别是针对高危威胁的缓解措施。

### 4. 威胁识别与分析（STRIDE）

本功能实现了两个核心安全机制：
1. **强制三权分立（SoD）**：将最高管理权限拆分为 SYSDBA、SYSSEC、SYSAUDIT 三个互斥角色，通过 `ALTER CLUSTER 'SoD mandatory'` 命令启用后，永久禁用 root 超级用户。
2. **强制访问控制（MAC）**：基于 Bell-LaPadula 模型，为主体（用户）和客体（数据库、超级表等）分配安全等级（0-4），强制执行"禁止上读"（NRU）和"禁止下写"（NWD）规则，独立于 DAC 运行。

| T-MAC-08 | **安全等级配置错误锁定资源**：管理员错误地将关键数据库或超级表的 security_level 设置为 4，而所有业务用户的等级均 <= 3，导致业务数据完全不可访问（可用性故障）。 | D（拒绝服务） | 数据库/超级表 security_level 设置 | 中 |

| T-MAC-11 | **SYSTEM 用户冒用**：攻击者通过伪造或利用内部接口，以 SYSTEM 用户身份执行操作，绕过所有权限检查（包括 DAC 和 MAC）。注：设计文档中提到"不再允许用户创建 SYSTEM 的用户名"，但需防止其他冒用手段。 | S（仿冒）/ E（权限提升） | 用户认证、操作执行者标识 | 中 |
| T-MAC-12 | **审计库数据篡改**：拥有 SYSAUDIT 角色（Level 4）的用户利用其读取权限或系统漏洞，篡改或删除审计日志数据，掩盖攻击痕迹或误操作记录。 | T（篡改）/ R（抵赖） | 审计库、SYSAUDIT 角色权限 | 中 |
| T-MAC-13 | **跨等级信息泄露（Side Channel）**：低等级用户虽无法直接读取高等级数据，但通过旁路攻击（如 SHOW STABLES 返回的表数量、错误消息差异、响应时间差异）推断高等级对象的存在性、数量、结构等敏感信息。 | I（信息泄露） | SHOW/DESCRIBE 等元数据查询、错误处理 | 中 |
| T-MAC-14 | **升级/降级过程中的安全风险**：从低版本升级至 3.4.1.0 时，自动赋值 security_level 的逻辑存在漏洞（如未正确识别 owner/creator、默认值设置不当），导致升级后访问控制混乱或数据泄露。同时，不支持降级导致回退困难。 | T（篡改）/ I（信息泄露） | 升级脚本、元数据迁移 | 低 |
| T-MAC-15 | **错误消息信息泄露**：MAC 或 SoD 相关的错误消息（如 TSDB_CODE_MAC_NO_READ_UP）返回过于详细的信息（如具体的 security_level 数值、对象路径），帮助攻击者进行侦察和权限探测。 | I（信息泄露） | 错误处理、错误码返回 | 低 |

### 5. 安全需求与设计约束

| 威胁 ID | 转化后的安全需求 / 设计约束 | 类型 | 优先级 |
| --- | --- | --- | --- |
| T-MAC-01 | **SEC-MAC-001（root 禁用强化）**：在 SoD 启用后，必须在所有 root 用户认证入口（登录、token 验证、内部调用）强制检查 SClusterObj.flags 的 SoD 状态位。若 SoD 已启用且用户为 root，必须拒绝所有操作，无论其 enable 和 superUser 字段值。同时，元数据文件应包含校验和或签名，防止离线篡改。 | 安全设计约束 | 高 |
| T-MAC-01 | **SEC-MAC-002（元数据完整性保护）**：mnode 元数据文件（含用户表、SClusterObj）必须使用加密和完整性校验（如 HMAC）保护。启动时验证完整性，发现篡改应拒绝启动或进入安全模式。 | 安全功能需求 | 高 |
| T-MAC-02 | **SEC-MAC-003（原子化 SoD 启用）**：`ALTER CLUSTER 'SoD mandatory'` 必须在事务中原子执行：先对三员角色持有者加锁，再校验条件，最后禁用 root 并更新 SClusterObj。整个过程中禁止其他用户管理操作（如删除用户、撤销角色）。 | 安全设计约束 | 高 |
| T-MAC-03 | **SEC-MAC-004（安全等级修改权限控制）**：仅 SYSSEC 角色可修改 security_level。所有修改操作必须强制校验：(1) 操作者 level >= 目标对象新 level；(2) 用户降级时，新 level >= 已赋予角色的最高 level；(3) 角色提级时，新 level <= 已拥有该角色的用户的最低 level；(4) 输入验证：security_level 必须在 [0, 4] 范围内。 | 安全设计约束 | 高 |
| T-MAC-04 | **SEC-MAC-005（MAC 检查全覆盖）**：在所有数据访问路径（包括 SQL、RPC、系统函数、流计算、订阅等）必须在 DAC 检查通过后、实际访问前，强制执行 MAC 检查。建立 MAC 检查清单，覆盖所有操作类型（SELECT/INSERT/UPDATE/DELETE/ALTER/DROP/GRANT 等），并在代码审查中验证。 | 安全设计约束 | 高 |
| T-MAC-05 | **SEC-MAC-006（元数据一致性保证）**：(1) mnode 主从同步时，security_level 必须与对象元数据原子化同步；(2) Catalog Cache 刷新时，必须重新获取最新的 security_level；(3) 在 DB 等级变化时，增加全局 dbCfgVersion，强制失效继承自 DB 的对象（如普通表）的缓存；(4) 实现定期一致性检查任务，发现不一致时告警。 | 安全设计约束 | 高 |
| T-MAC-06 | **SEC-MAC-007（继承关系强制执行）**：(1) 子表和普通表的 security_level 不存储在 vnode.config 中，而在每次访问时从父超级表或所属 DB 动态获取；(2) 若必须存储，则在 DB/STB 等级变化时，通过 RPC 强制更新所有相关 vnode；(3) 启动时验证 vnode.config 中的 security_level 与 mnode 的一致性。 | 安全设计约束 | 高 |
| T-MAC-07 | **SEC-MAC-008（三员角色保护机制）**：在 SoD 启用后，实施以下保护：(1) 禁止撤销导致某角色无有效持有者的 REVOKE 操作；(2) 禁止禁用导致某角色无有效持有者的用户；(3) 实现"最后一个管理员"保护逻辑，并记录审计日志。 | 非功能安全需求 | 中 |
| T-MAC-08 | **SEC-MAC-009（安全等级配置验证与回退）**：(1) 在修改数据库或超级表 security_level 前，提供警告提示并要求二次确认；(2) 实现"安全等级配置审计"功能，定期检查是否存在业务用户均无法访问的高等级对象；(3) 提供紧急降级机制（需 SYSSEC + SYSDBA 双重授权）。 | 非功能安全需求 | 中 |
| T-MAC-09 | **SEC-MAC-010（NWD 规则严格执行）**：(1) INSERT/UPDATE 操作必须校验 `主体 level == 客体 level`（精确匹配，不允许高写低）；(2) DELETE 操作校验 `主体 level >= 客体 level`；(3) 在单元测试中包含所有 NRU/NWD 违反场景的负面测试用例。 | 安全设计约束 | 中 |
| T-MAC-10 | **SEC-MAC-011（增强审计覆盖）**：以下操作必须记录审计日志：(1) 启用 SoD；(2) 修改用户/角色/DB/STB 的 security_level；(3) 授予/撤销三员角色；(4) MAC 检查失败（含操作者、目标对象、双方 level、失败原因）；(5) root 用户尝试登录（SoD 启用后）。日志写入失败应导致操作回滚。 | 审计需求 | 中 |
| T-MAC-11 | **SEC-MAC-012（SYSTEM 用户保护）**：(1) 在用户创建时，禁止使用保留名称（SYSTEM, ROOT, ANONYMOUS, 三员角色名等，不区分大小写）；(2) 在内部接口中，SYSTEM 用户的操作必须通过独立的认证通道（如内核态标识），不可通过用户名/密码伪造；(3) 审计所有以 SYSTEM 身份执行的操作。 | 安全设计约束 | 中 |
| T-MAC-12 | **SEC-MAC-013（审计库防篡改）**：(1) 审计库（默认 security_level 4）只允许 SYSAUDIT_LOG 角色写入、SYSAUDIT 角色读取；(2) SYSAUDIT 角色对审计库只有读权限，无写权限；(3) 审计日志应包含数字签名或链式哈希，防止篡改；(4) 支持审计日志实时归档至外部不可变存储（如 WORM 设备）。 | 安全功能需求 | 中 |
| T-MAC-13 | **SEC-MAC-014（防止旁路信息泄露）**：(1) SHOW STABLES 等元数据查询，只返回当前用户有权访问的对象，不透露高等级对象的存在；(2) 错误消息统一化：访问拒绝时，不区分"对象不存在"和"权限不足"；(3) 响应时间归一化或添加随机延迟，防止时间侧信道攻击。 | 安全设计约束 | 中 |
| T-MAC-14 | **SEC-MAC-015（升级安全性）**：(1) 升级脚本必须正确识别用户的角色并赋予对应 security_level（参考：SYSAUDIT/SYSSEC=4, SYSDBA=3, SYSINFO_1=1, SYSINFO_0=0）；(2) 对象的 security_level 根据 owner/creator 的最高角色等级设置；(3) 升级后强制执行一致性检查，生成升级报告；(4) 提供升级前备份和验证工具。 | 非功能安全需求 | 低 |
| T-MAC-15 | **SEC-MAC-016（错误消息脱敏）**：MAC 相关错误消息不应包含：(1) 具体的 security_level 数值（操作者和目标对象的 level）；(2) 对象的完整路径或元数据；(3) 内部实现细节。统一返回通用错误消息如"Insufficient privilege"，详细信息仅记录在审计日志中（仅 SYSAUDIT 可见）。 | 安全设计约束 | 低 |

### 8. 附录：威胁优先级判定依据

- **高危**：可导致权限提升、数据泄露、完整性破坏或系统控制权丧失，且攻击路径相对直接。
- **中危**：可导致拒绝服务、审计失效、部分信息泄露，或需要较高权限才能利用。
- **低危**：影响有限，主要为信息泄露（不涉及数据内容）或需要多个前提条件才能利用。

### 9. 附录：STRIDE 映射说明

- **S (Spoofing / 仿冒)**：冒用身份（如 root、SYSTEM）。
- **T (Tampering / 篡改)**：修改元数据、数据、审计日志、安全等级。
- **R (Repudiation / 抵赖)**：无法追溯操作（审计日志缺失或被篡改）。
- **I (Information Disclosure / 信息泄露)**：未授权访问敏感数据或元数据。
- **D (Denial of Service / 拒绝服务)**：导致系统或功能不可用。
- **E (Elevation of Privilege / 权限提升)**：获得超出授权的权限。
