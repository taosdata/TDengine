### 3. 分析报告

本报告针对「批量标签修改」功能进行了威胁建模分析。该功能旨在扩展 TDengine `ALTER TABLE` DDL 语法，支持两种批量标签修改模式：（1）逐表模式：在一条语句中同时指定多个子表及各自的标签值；（2）超级表模式：通过 `ALTER TABLE USING stb SET TAG tag = REGEXP_REPLACE(...) WHERE condition` 语法，对满足条件的所有子表批量应用基于正则替换的标签更新。该功能同时涉及 Vnode 数据订阅 tablelist 更新、WAL 数据结构变更及流计算 ALTER TAG 消息处理。

- **核心发现：** 共识别出 `6` 个潜在威胁，其中 `高危` `0` 个，`中危` `3` 个，`低危` `3` 个。
- **主要风险场景：**
  - ReDoS 攻击：攻击者构造恶意正则表达式作为 REGEXP_REPLACE 参数，耗尽 Vnode 处理线程 CPU。
  - 大批量操作 DoS：对含千万级子表的超级表执行宽松 WHERE 条件的批量修改，消耗大量 Vnode I/O 和 WAL 资源。
  - 越权批量修改：利用 WHERE 条件匹配到自身无 WRITE 权限的子表，触发越权修改。
- **结论：** 该功能属于 SQL DDL 语法扩展，未引入新的认证机制或外部接口。主要新增攻击面在于 REGEXP_REPLACE 正则计算和超级表范围批量写入路径。现有查询超时、内存限制和权限校验机制可覆盖主要威胁，整体风险可控。

### 4. 威胁识别与分析（STRIDE）

该功能扩展了 TDengine 的 `ALTER TABLE` DDL 语法，新增两种批量标签修改模式。逐表模式在 Mnode 解析后分发至各 Vnode 执行；超级表模式在 Mnode 侧展开 WHERE 条件匹配，筛选出目标子表集合后再下发至各 Vnode 执行标签更新，更新结果写入 WAL 并同步至数据订阅的 tablelist 及流计算消费路径。`REGEXP_REPLACE` 作为本期唯一支持的标签值变换关键字，仅供内部使用，不对外公开（FS 第 3.2.2 节）。

#### 4.1 关键实体与数据

| 实体/数据 | 描述 | 敏感性 |
| --- | --- | --- |
| 标签值 | 子表的标签字段值，包含业务元数据（如设备编号、位置、厂商信息等） | 中 |
| 超级表元数据 | 超级表的标签定义（字段名、类型、枚举值），用于 WHERE 条件解析和类型兼容性校验 | 中 |
| 正则表达式参数 | REGEXP_REPLACE 的 regexp 和 replacement 参数，由用户输入，在 Vnode 侧执行计算 | 中（直接影响执行资源） |
| WAL 记录 | ALTER TAG 操作写入的 WAL 消息，供数据订阅和流计算消费 | 中 |
| 数据订阅 tablelist | Vnode 维护的子表订阅状态列表，批量修改后需同步更新 | 低 |

#### 4.2 威胁评估

| 威胁ID | 威胁描述/攻击场景 | STRIDE | 相关组件/数据流 | 风险等级 |
| --- | --- | --- | --- | --- |
| T-BTAG-01 | **ReDoS 攻击**：攻击者（或误操作用户）将具有指数级回溯特性的正则表达式（如 `(a+)+$` 或 `([a-z]+)*` 类型）作为 REGEXP_REPLACE 的 `regexp` 参数。Vnode 处理该请求时，正则引擎在标签值匹配过程中发生大量回溯，导致 Vnode 处理线程长时间阻塞，CPU 使用率飙升，影响同 Vnode 内其他正常读写请求的响应。 | D（拒绝服务） | REGEXP_REPLACE 关键字 → Vnode 正则引擎 | 中 |
| T-BTAG-02 | **大批量操作致 Vnode I/O 耗尽**：攻击者对含 3000 万子表的超级表执行不带过滤条件（或极宽松 WHERE 条件）的批量标签修改，触发对全量子表的标签更新。大量 WAL 写入、tablelist 更新和内存操作同时产生，可能导致 Vnode I/O 负载骤升、写入队列积压，影响同时段的时序数据正常写入。 | D（拒绝服务） | 超级表 WHERE 展开 → Vnode 批量写入 → WAL | 中 |
| T-BTAG-03 | **越权批量修改子表标签**：攻击者持有对某超级表的 READ 权限，利用 `ALTER TABLE USING stb SET TAG ... WHERE condition` 语法，通过构造 WHERE 条件尝试修改自身无 WRITE 权限的子表的标签值。若 Mnode 在展开子表集合时未对每个子表逐一校验 WRITE 权限，仅校验超级表层级权限，则可能导致越权修改。 | E（权限提升） | Mnode 权限校验 → 子表 WRITE 权限 | 中 |
| T-BTAG-04 | **部分失败引发数据不一致性利用**：FS 第 8.1 节明确"批量更新过程中，某个子表更新失败会导致整个操作失败，但已经更新成功的子表无法回滚"。攻击者可精心设计输入（如使某一子表的正则替换结果违反类型约束），在批量操作中点触发失败，造成同一超级表下部分子表标签值已更新、部分未更新的不一致状态，污染依赖标签进行过滤查询的结果准确性。 | T（篡改） | 批量 ALTER TAG → Vnode 部分提交 | 低 |
| T-BTAG-05 | **WAL 消息格式利用导致订阅数据污染**：FS 第 3.3 节涉及 WAL 数据结构变更（新增多表和超级表 ALTER TAG 消息格式）。若 WAL 消息的格式验证不严格，攻击者在拥有数据库访问权限的前提下，通过构造边界情况（如异常长度的标签值、特殊字符）写入 WAL，可能导致下游数据订阅消费者（taosX 数据迁移）在解析 `tmq_get_json_meta` 响应时处理异常，向目标数据库写入错误数据。 | T（篡改） | WAL ALTER TAG 消息 → 数据订阅消费者 → 目标数据库 | 低 |
| T-BTAG-06 | **错误信息泄露超级表内部结构**：当 REGEXP_REPLACE 参数类型不兼容、WHERE 条件中使用了受限语法（数据列、聚合函数等）或标签值类型校验失败时，详细的错误响应可能包含超级表的标签名称、标签类型定义或内部 schema 信息，为攻击者进一步构造精确攻击提供情报。 | I（信息泄露） | 错误处理 / 客户端响应 | 低 |

### 5. 安全需求与设计约束

| 威胁ID | 转化后的安全需求/设计约束 | 类型 | 优先级 |
| --- | --- | --- | --- |
| T-BTAG-01 | SEC-BTAG-001（正则超时保护）：REGEXP_REPLACE 的正则匹配执行应受现有查询超时机制（`queryTimeoutMs`）约束，超时后终止执行并返回明确错误，防止单次恶意正则长时间占用 Vnode 线程。 | 健壮性需求 | 中 |
| T-BTAG-02 | SEC-BTAG-002（批量操作资源约束）：超级表模式的批量修改应受现有 Vnode 写入流控机制约束，不应绕过现有背压保护路径，防止无限制的批量写入耗尽资源。 | 健壮性需求 | 中 |
| T-BTAG-03 | SEC-BTAG-003（子表级权限校验）：超级表 WHERE 展开后，对每个目标子表执行修改前，必须校验当前用户对该子表（而非仅超级表）的 WRITE 权限，防止通过超级表语法绕过子表级权限控制。 | 安全设计约束 | 中 |
