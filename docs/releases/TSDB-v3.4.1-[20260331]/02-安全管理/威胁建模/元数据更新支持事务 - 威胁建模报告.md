### 3. 分析报告

本报告针对「元数据更新支持事务」功能进行了威胁建模分析。该功能旨在为 TDengine 提供 BEGIN/COMMIT/ROLLBACK 元数据事务框架，支持虚拟子表/虚拟普通表的原子性批量创建、删除和修改，以简化上层应用（如 IDMP）对元数据批操作的实现。

- **核心发现：** 共识别出 `7` 个潜在威胁，其中 `高危` `3` 个，`中危` `3` 个，`低危` `1` 个。
- **主要风险场景：**
  - **全局事务锁 DoS：** 第一期全局仅支持单一事务，恶意或异常客户端可通过持续占用事务锁阻断所有用户的元数据操作。
  - **事务操作无审计追踪：** BEGIN/COMMIT/ROLLBACK 及事务内 DDL 若无审计日志，批量元数据变更事件无法溯源。
  - **权限校验时序绕过：** COMMIT 阶段若不重新校验权限，可能出现权限撤销后仍能执行事务的绕过场景。
- **结论：** 该功能的冲突检测与状态机设计较为完善（FS 4.4 节），但在全局锁 DoS 防护、审计日志和事务超时方面存在安全设计缺口。必须在进入编码实现前，将本报告提出的安全需求作为核心设计约束予以落实。

### 4. 威胁识别与分析（STRIDE）

本功能引入的核心新组件包括：MNode 侧的事务上下文管理（TID 分配与生命周期）、PREPARED 状态的影子元数据条目、以及全局事务锁机制。

#### 4.1 关键实体与数据

| 实体/数据 | 描述 | 敏感性 |
| --- | --- | --- |
| 事务上下文（TID） | MNode 维护的事务标识符，关联 BEGIN 到 COMMIT/ROLLBACK 之间的所有操作 | 高（可控制元数据批量变更） |
| PREPARED 状态影子条目 | 事务内创建/删除/修改操作在提交前产生的中间状态元数据 | 中（包含表结构信息） |
| 全局事务锁 | 保证第一期单事务独占的锁机制 | 高（锁定期间阻塞所有元数据操作） |
| SHOW TRANSACTIONS 输出 | 可查看活跃事务的 oper、TID 等信息 | 中（包含表操作类型及对象名） |
| 虚拟表元数据 | 事务操作的目标对象（表名、列定义、标签值） | 中（业务相关的 Schema 信息） |

#### 4.2 威胁评估

| 威胁ID | 威胁描述/攻击场景 | STRIDE | 相关组件/数据流 | 风险等级 |
| --- | --- | --- | --- | --- |
| T-IDMPTX-01 | **TID 劫持/事务接管**：若 TID 生成算法可预测（如简单递增整数），攻击者可枚举当前活跃事务的 TID，构造 COMMIT 或 ROLLBACK 提前终止他人事务，导致原事务发起者的批量元数据操作被意外提交或丢弃。 | S（仿冒） | MNode TID 管理 | 高 |
| T-IDMPTX-02 | **影子条目直接篡改**：在 PREPARED_CREATE 或 PREPARED_ALTER 状态期间，若影子元数据条目的存储权限设置不当（如文件权限过于开放），具有 MNode 主机访问权限的内部攻击者可直接修改影子条目内容，导致提交后出现非预期的表结构或标签值，且该变更不经过 SQL 层校验。 | T（篡改） | MNode 影子条目存储 | 中 |
| T-IDMPTX-03 | **事务操作无审计追踪**：BEGIN/COMMIT/ROLLBACK 以及事务内的 DDL 操作（CREATE/DROP/ALTER VTABLE）若未被记录到审计日志，操作者可否认对虚拟表结构的批量修改行为，在发生故障、数据不一致或安全事件时无法溯源责任人和操作内容。 | R（抵赖） | 审计日志模块 | 中 |
| T-IDMPTX-04 | **SHOW TRANSACTIONS 信息越权查看**：`SHOW TRANSACTIONS` 若缺乏用户粒度的权限过滤，普通用户可查看其他租户或用户正在进行的事务详情（包括正在操作的表名、操作类型），从而推断竞争对手或其他用户的业务结构信息。 | I（信息泄露） | SHOW TRANSACTIONS 命令 | 中 |
| T-IDMPTX-05 | **全局事务锁长期占用 DoS**：恶意或异常客户端执行 BEGIN 后不发出 COMMIT/ROLLBACK，或网络断开后连接未被及时清理，全局事务锁将被永久占用。由于第一期只支持单事务（FS 4.3 节），其他所有用户对虚拟表的元数据操作将被完全阻塞，形成针对元数据操作的拒绝服务攻击，且 FS 未描述任何超时保护机制。 | D（拒绝服务） | 全局事务锁、连接管理 | 高 |
| T-IDMPTX-06 | **事务内批量操作内存耗尽 DoS**：攻击者在单个事务中执行大量 CREATE VTABLE 操作（如数万张），MNode 需为每张表维护 PREPARED 状态的影子条目，若无事务内操作数量上限，可导致 MNode 内存持续增长直至 OOM，影响整个集群的元数据服务可用性。 | D（拒绝服务） | MNode 内存、影子条目 | 中 |
| T-IDMPTX-07 | **权限校验时序绕过**：若事务操作的权限仅在 BEGIN 时（或 DDL 指令入队时）校验，而非在 COMMIT 执行时重新校验，可能出现以下场景：用户 A 的 DROP VTABLE 权限在事务进行中被管理员撤销，但已加入事务队列的 DROP 操作在 COMMIT 时仍被执行，形成权限提升/绕过。 | E（权限提升） | MNode 权限校验流程 | 高 |

### 5. 安全需求与设计约束

| 威胁ID | 转化后的安全需求/设计约束 | 类型 | 优先级 |
| --- | --- | --- | --- |
| T-IDMPTX-01 | **SEC-IDMPTX-001（TID 安全生成）**：TID 必须使用密码学安全的随机数生成（如 UUID v4 或至少 128 位随机值），禁止使用递增整数或其他可预测算法，防止 TID 枚举和事务劫持。 | 安全设计约束 | 高 |
| T-IDMPTX-05 | **SEC-IDMPTX-002（事务超时机制）**：MNode 必须为每个活跃事务设置空闲超时时间（建议默认值 30 秒，可配置），超时后自动执行 ROLLBACK 并释放全局事务锁。客户端连接断开时，关联事务必须立即触发自动回滚。 | 安全功能需求 | 高 |
| T-IDMPTX-07 | **SEC-IDMPTX-003（COMMIT 时权限二次校验）**：在 COMMIT 阶段执行各项 DDL 时，必须重新校验当前用户对目标对象的操作权限，以防止"权限已撤销但事务内操作仍能执行"的时序绕过场景。 | 安全设计约束 | 高 |
| T-IDMPTX-03 | **SEC-IDMPTX-004（事务操作审计日志）**：BEGIN、COMMIT、ROLLBACK 以及事务内的每条 DDL 操作必须记录到审计日志，日志字段包括：操作时间、操作用户、TID、操作类型（BEGIN/COMMIT/ROLLBACK/CREATE/DROP/ALTER）、操作对象（表名）、执行结果。 | 审计需求 | 中 |
| T-IDMPTX-04 | **SEC-IDMPTX-005（SHOW TRANSACTIONS 权限控制）**：`SHOW TRANSACTIONS` 命令应遵循最小权限原则：普通用户仅可查看自己发起的事务；超级管理员可查看全局所有事务。 | 访问控制需求 | 中 |
| T-IDMPTX-06 | **SEC-IDMPTX-006（单事务操作数量上限）**：单个事务内允许的 DDL 操作数量应设置上限（建议默认 10000 条，可配置），超出上限时返回错误并自动回滚事务，防止内存耗尽攻击。 | 非功能安全需求 | 中 |
