### 3. 分析报告

本报告针对「TDengine TSDB 文件损坏场景与修复方案」进行威胁建模分析。该文档旨在系统性地梳理 WAL 文件、TDB 元数据文件及 TSDB 时序数据文件三类核心存储组件发生损坏后的诊断步骤和修复方法，并给出预防最佳实践。

- **核心发现：** 共识别出 `5` 个潜在威胁，其中 `高危` `0` 个，`中危` `2` 个，`低危` `3` 个。
- **主要风险场景：**
  - 配置项篡改触发自动数据删除：攻击者或误操作将 `walDeleteOnCorruption` 设为 1，触发系统自动清除 WAL 数据，导致数据永久丢失。
  - 修复操作无应用层审计轨迹：手动修复操作（删除目录、修改索引文件、执行修复模式）不经过 TDengine 审计日志，无法从应用层追溯操作历史。
- **结论：** 该文档为运维修复规范，不引入新的网络接口、持久化逻辑变更或外部依赖。主要安全风险源自运维操作本身的权限控制和审计覆盖，而非架构设计缺陷。依托操作系统权限模型和 SSH 加密传输，整体安全风险低，设计可通过评审。

### 4. 威胁识别与分析（STRIDE）

本文档描述三类文件的修复操作：(1) WAL 损坏修复（手动删除、配置自动跳过、备份恢复）；(2) TDB 元数据损坏修复（副本恢复、`taosd -r` 重建）；(3) TSDB 时序文件损坏修复（手动修改索引、备份恢复、restore 命令）。所有修复操作均需要操作系统 taos/root 用户权限，在停止 taosd 服务后离线执行，不涉及在线 SQL 接口或网络协议变更。

#### 4.1 关键实体与数据

| 实体/数据 | 描述 | 敏感性 |
| --- | --- | --- |
| WAL 文件目录 | `/var/lib/taos/vnode/vnode{id}/wal/`，存储未持久化的写入操作日志 | 高（含原始时序数据） |
| TDB 文件（main.tdb） | `/var/lib/taos/vnode/vnode{id}/main.tdb`，存储 VNode 元数据和表结构 | 中（含表结构和索引信息） |
| TSDB 数据文件（.data/.head/.sma） | `/var/lib/taos/vnode/vnode{id}/tsdb/`，存储实际时序数据 | 高（含原始时序数据） |
| TSDB 索引文件（current.json） | 记录 TSDB 文件系统中各文件组的引用关系 | 中（结构元数据） |
| TDengine 配置文件 | `/etc/taos/taos.cfg`，包含 `walDeleteOnCorruption` 等影响修复行为的参数 | 中（运维配置） |
| 临时备份文件 | 修复操作中建议备份至 `/tmp/` 的 WAL/TDB 副本 | 高（含完整时序数据） |

#### 4.2 威胁评估

| 威胁ID | **威胁描述/攻击场景** | **STRIDE** | **相关组件/数据流** | **风险等级** |
| --- | --- | --- | --- | --- |
| T-FILECORR-01 | **恶意篡改配置触发 WAL 自动删除**：攻击者或被入侵的运维账号修改 `/etc/taos/taos.cfg`，将 `walDeleteOnCorruption` 设为 1。在下次 taosd 启动检测到 WAL 损坏时，系统自动将损坏 WAL 备份并删除原目录，导致该 VNode 未持久化的时序数据永久丢失，且整个过程无需人工确认。 | T（篡改）D（拒绝服务） | 配置文件 → taosd 启动 → WAL 自动删除 | 中 |
| T-FILECORR-02 | **备份文件写入 /tmp 导致数据泄露**：文档第 1.1.5 节方法一和第 1.2.5 节方法一建议将 WAL 和 TDB 备份文件写入 `/tmp` 目录（如 `/tmp/wal_backup_vnode1234_*`）。`/tmp` 通常对本机所有登录用户可读（权限 1777），在多用户共享主机环境下，攻击者可直接读取包含完整时序数据的备份文件，导致数据泄露。 | I（信息泄露） | WAL/TDB 数据 → /tmp 备份文件 → 本机其他用户 | 中 |
| T-FILECORR-03 | **`taosd -r` 修复模式滥用**：`taosd -r` 模式会以 taosd 服务账号权限读取并重建 VNode 元数据，恢复过程访问 WAL 和 TSDB 全部数据。若该模式被非授权用户触发（如利用 taosd 可执行文件权限配置不当），可以在不通过 TDengine 认证层的情况下完整读取所有 VNode 数据，构成权限提升风险。 | E（权限提升） | 操作系统账号 → taosd -r → 全量 VNode 数据 | 中 |
| T-FILECORR-04 | **scp 跨节点传输中间人攻击**：多副本修复场景（第 1.2.5 节方法一）通过 `scp` 从健康副本节点拷贝 TDB 文件。若运维人员首次操作时未严格验证 SSH 主机指纹（接受 unknown host），攻击者可通过 ARP 欺骗等手段实施 MITM 攻击，将被篡改的 TDB 文件传输至目标节点，导致恢复后的元数据不可信。 | T（篡改） | 副本节点 → scp/SSH → 目标节点 | 低 |
| T-FILECORR-05 | **修复操作无应用层审计轨迹**：手动修复操作（`rm -rf /var/lib/taos/vnode/vnode1234/wal`、修改 `current.json`、执行 `taosd -r`）均属于操作系统层面的文件操作，不经过 TDengine 的审计日志模块，TDengine 层面无法记录"谁在何时对哪个 VNode 执行了修复操作"。若发生误操作导致数据丢失，事后溯源只能依赖 bash history 或 OS 级审计工具（auditd），可追溯性受限。 | R（抵赖） | 运维操作 → 文件系统 → TDengine 数据 | 低 |

### 5. 安全需求与设计约束

| 威胁ID | **转化后的安全需求/设计约束** | **类型** | **优先级** |
| --- | --- | --- | --- |
| T-FILECORR-01 | SEC-FILECORR-001（配置文件访问控制）：`/etc/taos/taos.cfg` 文件权限应限制为仅 root 或 taos 用户可写（如 640 模式），防止低权限用户篡改 `walDeleteOnCorruption` 等高危参数。此为 OS 配置层面的安全要求，由运维规范落实。 | 安全设计约束 | 中 |
| T-FILECORR-02 | SEC-FILECORR-002（备份路径安全）：运维操作规范应将备份目标路径从 `/tmp` 修改为受限目录（如 `/var/lib/taos/backup/`，权限 700，属主 taos），防止同机其他用户读取备份数据。文档中的示例命令应同步更新。 | 非功能安全需求 | 中 |
| T-FILECORR-03 | SEC-FILECORR-003（taosd 可执行文件权限管控）：`taosd` 可执行文件权限应确保仅 root 或 taos 用户可执行（如 750 模式，属主 root，属组 taos），防止任意系统用户触发修复模式。此为安装包默认配置要求。 | 安全设计约束 | 中 |
| T-FILECORR-05 | SEC-FILECORR-004（运维操作审计建议）：建议在运维规范中要求在执行修复操作前记录操作计划（工单/变更单），并在修复完成后在 TDengine 审计日志或运维系统中留存操作记录，以弥补应用层审计空白。 | 审计需求 | 低 |
