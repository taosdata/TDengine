### 3. 分析报告

本报告针对「虚拟表和源表的引用校验」功能进行了威胁建模分析。该功能旨在管理虚拟表（VTABLE）与源表之间的引用关系，提供源表结构变更时的引用感知机制，并通过新增系统表 `ins_virtual_tables_referencing` 和 SQL 命令（`SHOW VTABLE VALIDATE FOR`、`SHOW REFERENCES FOR`）为用户提供引用关系查询能力。

- **核心发现：** 共识别出 `7` 个潜在威胁，其中 `高危` `1` 个，`中危` `3` 个，`低危` `3` 个。
- **主要风险场景：**
  - **重量级查询拒绝服务：** `SHOW REFERENCES FOR` 需遍历所有 VNODE 元数据，恶意用户可反复执行该命令消耗集群资源。
  - **跨 DB 信息泄露：** 遍历所有 DB 的查询操作（SHOW REFERENCES、SHOW VTABLE VALIDATE 超级表场景）结果集可能包含当前用户无权访问的 DB/表的存在性信息。
  - **错误信息暴露内部结构：** 虚拟表查询报错时"尽可能清晰"的错误信息，若实现不当可能暴露内部表结构路径。
- **结论：** 该功能设计以元数据管理和引用可见性为核心，攻击面相对有限。FS 第 6 节已对权限管控、数据隔离、元数据安全进行了明确设计，整体安全性较好。重量级查询 DoS 风险是需要在实现阶段重点关注的问题，其余威胁风险均处于低中水平。

### 4. 威胁识别与分析（STRIDE）

本功能核心数据流：**用户** → SQL 解析器 → mnode/vnode 元数据层 → **系统表 ins_virtual_tables_referencing** / 源表引用关系 → 返回结果。

#### 4.1 关键实体与数据

| 实体/数据 | 描述 | 敏感性 |
| --- | --- | --- |
| 系统表 ins_virtual_tables_referencing | 存储源表与虚拟表列之间的引用关系（库名、表名、列名、错误状态） | 中（暴露表结构关系） |
| 虚拟表元数据 | 虚拟表的列定义及其对源表列的映射关系 | 中 |
| VNODE 元数据遍历 | SHOW REFERENCES 操作时对集群所有 VNODE 元数据的全量扫描 | 高（涉及全集群资源） |
| 错误信息 | 虚拟表查询时因源表变更产生的报错内容 | 低（可能含表结构提示） |
| 源表数据（列/标签） | 虚拟表查询时动态从源表获取的实际时序数据 | 高 |

#### 4.2 威胁评估

| 威胁ID | 威胁描述/攻击场景 | STRIDE | 相关组件/数据流 | 风险等级 |
| --- | --- | --- | --- | --- |
| T-VTREF-01 | **重量级查询 DoS**：具有合法连接权限的用户（或恶意内部人员）反复执行 `SHOW REFERENCES FOR TB_NAME`，该操作需遍历所有 VNODE 元数据，在集群元数据量较大时可占用大量 CPU 和 I/O 资源，影响正常业务查询。FS 第 5 节已承认此为重量级查询，第 8 节仅以运维建议方式告知，未设计执行限流。 | D（拒绝服务） | SHOW REFERENCES → 全量 VNODE 元数据遍历 | 高 |
| T-VTREF-02 | **SHOW REFERENCES 跨 DB 信息泄露**：`SHOW REFERENCES FOR TB_NAME` 返回所有引用该源表的虚拟表信息，包括跨 DB 的结果。若结果集未按调用用户的 DB 访问权限进行过滤，调用者可能获知其无权访问的其他 DB 中虚拟表的存在性及列名信息。 | I（信息泄露） | SHOW REFERENCES 结果集 → 跨 DB 虚拟表元数据 | 中 |
| T-VTREF-03 | **SHOW VTABLE VALIDATE 超级表遍历跨 DB 信息泄露**：当 `SHOW VTABLE VALIDATE FOR tableName` 的对象为虚拟超级表时，需遍历所有 DB（FS 第 4.2 节）。返回的系统表结果中若包含其他 DB 的引用关系，可能暴露用户无权访问的 DB 的表结构信息。 | I（信息泄露） | SHOW VTABLE VALIDATE（超级表场景）→ 跨 DB 元数据 | 中 |
| T-VTREF-04 | **列级权限绕过尝试**：攻击者拥有源表 A 部分列的合法查询权限，尝试通过创建映射更多列的虚拟表来访问源表中未被授权的列数据。若权限校验仅在表级而非列级执行，可绕过列级权限限制。 | E（权限提升）/ I（信息泄露） | 虚拟表列映射 → 源表列数据 | 中 |
| T-VTREF-05 | **系统表篡改尝试**：攻击者尝试通过 INSERT/UPDATE/DELETE 语句修改系统表 `ins_virtual_tables_referencing`，伪造或删除引用关系记录，以误导运维人员的源表下线决策。 | T（篡改） | ins_virtual_tables_referencing | 低 |
| T-VTREF-06 | **错误信息泄露内部结构**：虚拟表查询因源表列被删除或重命名而报错，FS 要求「出错信息尽可能清晰」（第 4.1.2/4.1.4 节）。若错误信息中包含内部文件路径、节点 ID 或详细的内部架构描述，可帮助攻击者了解集群拓扑。 | I（信息泄露） | 错误信息处理 | 低 |
| T-VTREF-07 | **重量级操作抵赖**：DBA 恶意或误操作反复执行 `SHOW REFERENCES`，导致集群性能劣化，但事后声称从未执行过。若操作日志不完整，无法有效溯源追责。 | R（抵赖） | SHOW REFERENCES 操作日志 | 低 |

### 5. 安全需求与设计约束

| 威胁ID | 转化后的安全需求/设计约束 | 类型 | 优先级 |
| --- | --- | --- | --- |
| T-VTREF-01 | **SEC-VTREF-001（执行限流/保护）**：`SHOW REFERENCES FOR` 命令应在服务端实现执行频率约束或并发限制（如同一用户/连接在短时间内的执行次数上限），防止恶意用户利用该重量级命令耗尽集群资源。至少应在文档中明确告知此操作为高代价操作且建议在业务低峰期执行。 | 非功能安全需求 | 高 |
| T-VTREF-02 | **SEC-VTREF-002（跨 DB 结果权限过滤）**：`SHOW REFERENCES FOR` 返回的虚拟表引用列表，应按调用用户的数据库访问权限进行过滤，仅返回用户有权访问的 DB 中的虚拟表信息。 | 安全设计约束 | 中 |
| T-VTREF-03 | **SEC-VTREF-003（VALIDATE 跨 DB 结果权限过滤）**：`SHOW VTABLE VALIDATE FOR` 在超级表场景下遍历所有 DB 时，返回结果应仅包含当前用户有权访问的 DB 中的引用关系信息。 | 安全设计约束 | 中 |
| T-VTREF-04 | **SEC-VTREF-004（列级权限校验确认）**：明确虚拟表列映射所引用的源表列在查询时须通过列级（或表级，视 TDengine 权限粒度）权限校验。在架构设计文档中描述权限校验点位置，确保无法通过虚拟表绕过权限限制。 | 安全设计约束 | 中 |
| T-VTREF-05 | **SEC-VTREF-005（系统表写保护）**：系统表 `ins_virtual_tables_referencing` 必须在 DDL/DML 层面拒绝所有非查询操作，返回明确的权限错误，而非静默忽略。（FS 第 6 节已设计为只读，此为实现层面的验收标准。） | 安全设计约束 | 低 |
| T-VTREF-06 | **SEC-VTREF-006（错误信息规范）**：虚拟表查询报错信息中不得包含内部文件路径、节点 ID、内存地址等系统敏感信息。错误消息应仅包含用户可操作的诊断信息（如"源表 X 的列 Y 不存在"），遵循 TDengine 统一错误信息规范。 | 安全设计约束 | 低 |
