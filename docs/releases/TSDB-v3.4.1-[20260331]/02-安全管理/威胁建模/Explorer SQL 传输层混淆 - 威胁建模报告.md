### 3. 分析报告

本报告针对 Explorer SQL 传输层混淆功能进行了威胁建模分析。该功能旨在通过 XOR 异或运算对 taos-explorer REST API 的 SQL 语句进行传输层混淆，防止中间代理或日志系统直接记录明文 SQL 内容，通过 HTTP Header `X-Enable-Xor` 控制是否启用。

- **核心发现：** 共识别出 `6` 个潜在威胁，其中 `高危` `0` 个，`中危` `3` 个，`低危` `3` 个。
- **主要风险场景：**
   - **密钥可提取性：** XOR 密钥硬编码于客户端 JavaScript 和服务端 Rust 代码中，攻击者可通过逆向工程提取密钥。
   - **已知明文攻击：** SQL 语句存在大量已知模式（SELECT、INSERT 等关键字），攻击者可据此推导 XOR 密钥。
   - **密文篡改：** XOR 加密无完整性保护，中间人可修改密文中的特定字节来篡改对应的 SQL 字符。
- **结论：** 该功能明确定位为轻量级传输混淆（非安全加密），在防止代理日志和审计系统明文记录 SQL 方面有实际价值。上述威胁均在 FS 设计预期范围内——FS 已明确声明必须配合 HTTPS 使用、不防中间人攻击。在 HTTPS 保护下，上述威胁的实际可利用性显著降低。

### 4. 威胁识别与分析（STRIDE）

本特性在 taos-explorer 的 `/api/-/rest/sql` endpoint 上增加了可选的 XOR 混淆传输通道。客户端将 SQL 语句进行 XOR 加密并 Base64 编码后发送，服务端检测 `X-Enable-Xor` header 后进行解码和解密，随后正常执行 SQL。

#### 4.1 关键实体与数据

| 实体/数据 | 描述 | 敏感性 |
| --- | --- | --- |
| XOR 密钥 | 硬编码于客户端和服务端代码中的固定密钥 `TDengine-Explorer-XOR-Key-2026` | 中（非安全密钥，为混淆密钥） |
| SQL 语句（明文） | 用户通过 Explorer 执行的 SQL 查询/写入语句 | 中（可能包含业务逻辑和表结构信息） |
| SQL 语句（混淆后） | 经 XOR + Base64 编码后的 SQL 传输数据 | 低（已混淆但可逆） |
| REST API 响应 | SQL 执行结果，以明文 JSON 返回 | 中（包含查询结果数据） |
| X-Enable-Xor Header | 控制是否启用 XOR 混淆的 HTTP 请求头 | 低 |

#### 4.2 威胁评估

| 威胁ID | **威胁描述/攻击场景** | **STRIDE** | **相关组件/数据流** | **风险等级** |
| --- | --- | --- | --- | --- |
| T-SQLXOR-01 | **硬编码密钥提取：** 攻击者通过逆向工程 taos-explorer 前端 JavaScript 代码（`xorEncrypt` 函数）或反编译服务端 Rust 二进制文件，提取硬编码的 XOR 密钥 `TDengine-Explorer-XOR-Key-2026`，从而能解密所有截获的混淆 SQL 语句。 | I (信息泄露) | 客户端 JS 代码、服务端二进制、XOR 密钥 | 中 |
| T-SQLXOR-02 | **已知明文攻击推导密钥：** 攻击者截获混淆后的 SQL 数据，利用 SQL 语句中的已知模式（如 `SELECT `、`INSERT INTO `、`FROM ` 等高频关键字），将密文与已知明文 XOR 即可推导出密钥的对应字节，密钥长度仅 29 字节，少量样本即可完整还原。 | I (信息泄露) | 网络传输层、加密 SQL 数据 | 中 |
| T-SQLXOR-03 | **密文篡改注入：** 在无 HTTPS 保护的场景下，中间人攻击者可修改 Base64 编码的密文数据。由于 XOR 运算的特性，翻转密文中的特定比特会导致明文中对应位置的比特翻转，攻击者可精确修改 SQL 语句中的特定字符（如将 `WHERE id=1` 改为 `WHERE id=9`），且无完整性校验机制可检测此篡改。 | T (篡改) | 网络传输层、Base64 密文 | 中 |
| T-SQLXOR-04 | **响应数据明文泄露：** 请求中的 SQL 语句经过混淆传输，但 API 响应（查询结果）仍以明文 JSON 格式返回（FS 4.1.5 节）。代理日志系统虽无法记录原始 SQL，但可记录完整的查询结果数据，攻击者可从响应内容反推查询意图和数据结构。 | I (信息泄露) | REST API 响应、代理日志 | 低 |
| T-SQLXOR-05 | **恶意 Base64 载荷消耗资源：** 攻击者发送超大 Base64 编码数据（如数百 MB）并设置 `X-Enable-Xor: true`，触发服务端执行 Base64 解码 + XOR 解密的完整流程，消耗内存和 CPU 资源。虽然单次开销较小，但高并发场景下可能影响正常请求处理。 | D (拒绝服务) | REST API endpoint、服务端解密流程 | 低 |
| T-SQLXOR-06 | **混淆日志增加溯源难度：** 启用 XOR 混淆后，安全审计日志中的 SQL 请求体为 Base64 密文，安全运维人员在事件响应和取证分析时无法直接阅读 SQL 内容，需要额外的解密步骤才能还原原始查询，增加了安全事件的响应时间。 | R (抵赖) | 安全日志系统、事件响应流程 | 低 |

### 5. 安全需求与设计约束

| 威胁ID | **转化后的安全需求/设计约束** | **类型** | **优先级** | **FS 落实状态** |
| --- | --- | --- | --- | --- |
| T-SQLXOR-01 | SEC-SQLXOR-001（功能定位声明）：文档和 API 说明中应明确声明 XOR 混淆不提供安全保密性，硬编码密钥可被提取，用户如需真正的传输安全应使用 HTTPS。 | 文档需求 | 中 | ✅ 已落实（FS 6.1 节明确声明"混淆而非加密"） |
| T-SQLXOR-02 | SEC-SQLXOR-002（HTTPS 配合使用）：应在文档中强调本特性必须配合 HTTPS 使用，不应作为唯一的传输安全措施。 | 文档需求 | 中 | ✅ 已落实（FS 6.1 节、6.2 节、10.1 节均有说明） |
