### 3. 分析报告

本报告针对「流计算分组空闲触发」功能进行了威胁建模分析。该功能旨在为 TDengine 流计算新增"分组空闲/恢复触发"能力：在创建流时配置 `IDLE_TIMEOUT(duration)` 选项，系统按分组跟踪最后一次数据到达的处理时间，在分组进入空闲（`IDLE`）或从空闲恢复（`RESUME`）时触发计算写库和/或向外部 URL 发送 WebSocket 通知，用于监控告警与运维可观测性场景。

- **核心发现：** 共识别出 `6` 个潜在威胁，其中 `高危` `0` 个，`中危` `3` 个，`低危` `3` 个。
- **主要风险场景：**
  - **通知明文传输风险：** 若通知 URL 使用 `ws://` 非加密方式，事件 payload 中的分组标识与时间戳将以明文在网络中传输，面临窃听或篡改风险。
  - **无限分组状态内存增长：** 高基数 PARTITION BY 键场景下，分组状态内存无淘汰机制，存在资源耗尽风险。
  - **乱序数据触发误恢复事件：** 由于空闲判定基于 processing time 而非 event time，补写历史数据会意外触发 RESUME 事件，可能导致监控系统误判设备已恢复。
- **结论：** 该功能为现有流计算的 SQL 语法扩展，不引入新的网络接口或认证模型，整体攻击面增量有限。识别到的威胁均为中低危级别，且大部分与现有通知框架的安全配置相关（存量风险），或属于设计层面已知并文档化的限制。建议在实现和部署阶段关注通知信道加密配置和分组容量规划。

### 4. 威胁识别与分析（STRIDE）

本特性的核心数据流为：外部数据写入 → 流任务分组状态机（ACTIVE/IDLE 判定）→ 触发计算（写入输出表）/ 触发通知（向外部 WebSocket URL 推送 payload）。

#### 4.1 关键实体与数据

| 实体/数据 | 描述 | 敏感性 |
| --- | --- | --- |
| 分组状态记录 | 每个分组的运行时内存状态：`last_recv_time`（单调时钟时间戳）、状态枚举（ACTIVE/IDLE）。任务重启清空，不持久化。 | 低 |
| `IDLE_TIMEOUT` 配置参数 | 建流时在 `STREAM_OPTIONS(...)` 中指定的空闲超时时长，范围 1s~10d。 | 低 |
| 通知 payload | 发往外部 WebSocket URL 的 JSON 消息，包含 `eventType`、`eventTime`、`triggerId`、`tableName`、`groupId`、`idleStart`、`idleEnd`、`idleDurationMs` 等字段。 | 中（含业务实体标识） |
| `tableName` / `groupId` | 分别为输出子表名和分组键哈希十进制字符串，可能间接映射到业务实体（如设备 ID、厂商标识）。 | 中 |
| 外部通知 URL | 用户在 `NOTIFY(url)` 中配置的 WebSocket 地址，是事件 payload 的出口。 | 高（决定通知信道安全性） |

#### 4.2 威胁评估

| 威胁ID | **威胁描述/攻击场景** | **STRIDE** | **相关组件/数据流** | **风险等级** |
| --- | --- | --- | --- | --- |
| T-SIDLE-01 | **通知信道明文传输：** 若通知 URL 配置为 `ws://`（非加密），空闲/恢复事件 payload 在网络传输中以明文发送。中间人可窃取 payload 中的 `tableName`、`groupId`（业务实体标识），或篡改通知内容使接收端误判分组状态。 | I（信息泄露）、T（篡改） | 通知 payload → 外部 WebSocket URL | 中 |
| T-SIDLE-02 | **高基数分组内存耗尽：** 具有建流权限的用户（内部威胁或误用场景）以高基数字段（如客户端 IP、随机 UUID 列）作为 `PARTITION BY` 键，配合 `IDLE_TIMEOUT` 使用，导致分组状态持续积累直至 TDengine 服务端内存耗尽，影响整体服务可用性。FS §10 已明确该场景为已知限制。 | D（拒绝服务） | 分组状态内存 | 中 |
| T-SIDLE-03 | **乱序补写历史数据触发误恢复：** 攻击者或故障客户端向已处于 IDLE 状态的分组批量补写历史数据，这些数据的 processing time 为当前时间，立即触发 RESUME 事件。监控系统收到 RESUME 通知后误判设备已恢复上线，掩盖真实的设备离线故障。FS §10 已明确"乱序/补写历史数据会触发恢复事件"为设计约束。 | T（篡改）、S（仿冒） | 数据写入 → 分组状态机 → RESUME 事件 → 通知/计算 | 中 |
| T-SIDLE-04 | **IDLE/RESUME 抖动告警轰炸：** 异常客户端在某分组上以接近 `idle_timeout` 的频率间歇性写入数据（如每隔 `timeout - 1s` 发一次后暂停），人为制造持续的 IDLE/RESUME 交替事件，以大量告警消息淹没通知接收端或消耗接收端处理资源。 | D（拒绝服务） | 通知接收端、流计算调度器 | 低 |
| T-SIDLE-05 | **通知 payload 业务拓扑泄露：** `tableName`（子表名）和 `groupId` 直接暴露于通知 payload 中，第三方若能访问到通知 URL 或截获 WebSocket 数据帧，可通过分析 `tableName` 推断业务设备分布与分组策略，间接获取系统内部业务拓扑信息。 | I（信息泄露） | 通知 payload 中的 `tableName`/`groupId` 字段 | 低 |
| T-SIDLE-06 | **重启后空闲告警盲区：** 流任务重启清空所有分组状态（FS §4.2.4），原本处于 IDLE 的分组若在重启后一直不再上报数据，则永远不会再触发 IDLE 事件。攻击者可借此在系统重启窗口内使异常设备持续离线而不产生告警，逃脱监控检测。 | R（抵赖） | 分组状态机（重启清空策略）→ IDLE 告警 | 低 |

### 5. 安全需求与设计约束

| 威胁ID | **转化后的安全需求/设计约束** | **类型** | **优先级** |
| --- | --- | --- | --- |
| T-SIDLE-01 | SEC-SIDLE-001（通知信道加密）：生产环境中通知 URL 应配置为 `wss://`（TLS 加密的 WebSocket），禁止使用 `ws://` 明文协议传输敏感分组标识信息。此约束属于现有通知框架的部署配置要求，应在部署文档和安全基线中明确。 | 安全配置要求 | 中 |
| T-SIDLE-02 | SEC-SIDLE-002（分组容量规划）：`IDLE_TIMEOUT` 功能应在文档中明确警告高基数 `PARTITION BY` 场景的内存风险，建议用户在生产环境配置分组数量监控告警，并结合业务基数进行容量评估（FS §5、§8 已有相关说明，建议在官方文档中进一步强调）。 | 非功能安全需求 | 中 |
| T-SIDLE-03 | SEC-SIDLE-003（接收端防误判设计）：在文档和最佳实践中明确告知通知接收端：`RESUME` 事件基于 processing time 触发，历史数据补写会产生 RESUME；接收端如需严格的"设备恢复"语义，应结合 `idleStart`/`idleEnd` 与业务预期时间窗口进行二次校验，或参考 FS §16.2 的告警去抖策略。 | 文档约束 | 中 |
| T-SIDLE-04 | SEC-SIDLE-004（告警去抖）：通知接收端应实现去抖策略（FS §16.2 已提供参考建议）。服务端可在文档中建议用户将 `IDLE_TIMEOUT` 设置为业务实际期望的最小告警间隔，避免过短导致告警风暴。 | 文档约束 | 低 |
| T-SIDLE-06 | SEC-SIDLE-005（重启监控补充）：在运维文档中明确说明流任务重启后的告警盲区，建议依赖空闲告警的用户在外部监控系统额外维护"最后上报时间"基线，独立于 TDengine 流任务状态进行离线检测（FS §8、§11 已提供相关运维建议）。 | 运维安全建议 | 低 |
