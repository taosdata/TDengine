### 3. 分析报告

本报告针对「订阅支持 token 登录」功能进行了威胁建模分析。该功能旨在为 TDengine TMQ（消息队列/订阅）的 consumer 新增 token 认证方式，允许通过 `td.connect.token` 参数代替用户名/密码建立订阅连接，并通过心跳机制持续检测 token 的有效性。

- **核心发现：** 共识别出 `5` 个潜在威胁，其中 `高危` `0` 个，`中危` `3` 个，`低危` `2` 个。
- **主要风险场景：**
  - **凭证泄露：** `td.connect.token` 可能以明文形式存储在客户端配置文件中，与密码参数具有相同的泄露风险。
  - **心跳延迟窗口：** Token 被撤销后，在下一次心跳检测前存在短暂的认证延迟窗口，期间消费者仍可继续拉取数据。
  - **权限混淆：** Token 与 user/pass 并存时，若管理员对优先级规则理解有误，可能导致非预期的认证身份与权限。
- **结论：** 该功能设计在提升订阅认证灵活性方面价值显著，整体安全风险较低。识别出的威胁均为中低风险，且核心风险已通过现有设计（mnode 权威校验、即时撤销、原子操作）得到有效缓解。建议在客户端文档中强调 token 安全存储实践，并文档化心跳延迟说明。

### 4. 威胁识别与分析（STRIDE）

本功能扩展了 TDengine TMQ 消费者 API：`tmq_consumer_new` 接收 `td.connect.token` 参数并优先使用 token 建立连接；`tmq_t` 结构新增原子字段 `tokenCode` 记录 token 有效性；consumer 心跳消息定期向 mnode 验证 token 状态；token 失效时 `tmq_consumer_poll` 返回 NULL 并通过 `terrno` 返回错误码。

#### 4.1 关键实体与数据

| 实体/数据 | 描述 | 敏感性 |
| --- | --- | --- |
| td.connect.token | 消费者配置中的 token 参数值，传入 `tmq_consumer_new` | 高（等同连接凭证） |
| tokenCode 字段 | tmq_t 结构内记录 token 有效性的原子状态字段 | 中（状态标志，驻留内存） |
| Consumer 心跳消息 | 定期向 mnode 发送、携带 token 有效性查询的心跳请求 | 中（包含连接上下文） |
| mnode token 管理 | TDengine mnode 侧负责 token 生命周期（创建/禁用/删除）的核心组件 | 高（权威认证源） |
| terrno / taos_errstr | 错误码与错误描述的对外输出接口 | 低（公开 API） |

#### 4.2 威胁评估

| 威胁ID | 威胁描述/攻击场景 | STRIDE | 相关组件/数据流 | 风险等级 |
| --- | --- | --- | --- | --- |
| T-SUBTK-01 | **Token 凭证泄露（配置文件）：** 消费者通过配置文件设置 `td.connect.token` 时，token 以明文形式存储在磁盘上。若客户端所在主机被攻陷，攻击者可直接读取 token 并复用，建立未授权订阅连接，访问订阅主题下的时序数据流。 | I（信息泄露） | td.connect.token → 客户端配置文件 | 中 |
| T-SUBTK-02 | **心跳周期内的认证延迟窗口：** 管理员禁用或删除 token 后，消费者需等到下一次心跳检测才能感知失效，在此窗口期内仍可继续拉取订阅数据。若心跳周期较长，可能造成短暂的权限撤销延迟，已离职人员的 token 可能仍短暂有效。 | S（仿冒） | tokenCode ← mnode 心跳响应 | 中 |
| T-SUBTK-03 | **Token 与 user/pass 并存时的权限混淆：** 若 consumer 同时配置了 token 和 user/pass，但两者关联的权限不同，由于 token 优先级高于 user/pass，实际使用的认证身份和权限可能与配置人员预期不符，存在超权访问订阅数据的风险。 | E（权限提升） | tmq_consumer_new → 认证逻辑选择分支 | 中 |
| T-SUBTK-04 | **错误消息中的 token 状态枚举：** `taos_errstr` 返回的错误描述区分了"不存在"、"不合法"和"无效（过期/禁用）"等状态，攻击者可通过多次探测利用此差异推断系统中是否存在某个 token，辅助更复杂的攻击。 | I（信息泄露） | terrno / taos_errstr 错误处理 | 低 |
| T-SUBTK-05 | **订阅访问无专项审计记录：** FS 未设计针对 token 认证订阅连接建立、断开及 token 失效事件的专项安全日志。若发生未授权数据访问，难以事后追溯哪个 token 在何时访问了哪个订阅主题，存在抵赖风险。 | R（抵赖） | 整体数据流 → 日志/审计系统 | 低 |

### 5. 安全需求与设计约束

| 威胁ID | 转化后的安全需求/设计约束 | 类型 | 优先级 |
| --- | --- | --- | --- |
| T-SUBTK-01 | SEC-SUBTK-001（客户端凭证保护文档化）：在官网使用文档中明确说明 `td.connect.token` 与 `td.connect.password` 具有同等敏感性，建议通过环境变量或加密配置中心传递，避免明文写入版本控制的代码或配置文件。 | 文档/最佳实践需求 | 中 |
| T-SUBTK-02 | SEC-SUBTK-002（心跳延迟告知）：在 token 管理文档中说明认证撤销的延迟特性，建议管理员禁用 token 后等待一个心跳周期确认生效；如需立即中断，应通过终止对应连接会话（close session）的方式实现。 | 文档/运维规范需求 | 中 |
| T-SUBTK-03 | SEC-SUBTK-003（token 认证身份说明）：在文档中明确 token 认证时所使用的用户身份与权限继承规则，帮助管理员根据最小权限原则为订阅场景选择合适的认证方式，避免非预期超权访问。 | 文档/设计约束 | 中 |
| T-SUBTK-05 | SEC-SUBTK-004（建议补充审计日志）：建议在后续版本中，于 mnode 侧为 token 认证的订阅连接建立/断开/心跳失效事件增加审计日志记录，支持事后追溯与合规审计。 | 非功能安全需求（建议） | 低 |
