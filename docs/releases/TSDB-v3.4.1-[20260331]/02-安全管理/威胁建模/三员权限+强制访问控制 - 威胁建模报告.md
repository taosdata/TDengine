### 3. 分析报告

本报告针对 **三员权限（强制三权分立）+ 强制访问控制（MAC）** 功能进行了威胁建模分析。该功能旨在通过强制实施三权分立和基于 Bell-LaPadula 模型的强制访问控制，实现权力制衡、消除单点安全风险、建立不可抵赖的审计闭环，并通过安全等级（0-4）实现跨等级数据隔离。

- **核心发现**：共识别出 `10` 个潜在威胁，其中 `高危` `4` 个，`中危` `5` 个，`低危` `1` 个。
- **主要风险场景**：
   - **权限绕过与提升**：root 禁用机制被绕过、安全等级校验逻辑缺陷、元数据篡改导致权限提升。
   - **数据泄露与越权访问**：低等级用户通过旁路攻击读取高等级数据、MAC 检查路径覆盖不全。
   - **完整性破坏**：元数据持久化文件被离线篡改、分布式环境下安全等级不一致。
   - **审计失效与抵赖**：关键操作未记录审计日志或日志被篡改。
- **结论**：该功能设计在安全性方面具有重大提升价值，采用正式的 Bell-LaPadula 安全模型，但引入了复杂的权限管理逻辑和新的攻击面。需在功能详细设计与编码实现前，将本报告提出的核心安全需求作为设计约束予以落实，特别是针对高危威胁的缓解措施（元数据完整性保护、MAC 检查全路径覆盖）。

### 4. 威胁识别与分析（STRIDE）

本功能实现了两个核心安全机制：
1. **强制三权分立（SoD）**：将最高管理权限拆分为 SYSDBA、SYSSEC、SYSAUDIT 三个互斥角色，通过 `ALTER CLUSTER 'SoD mandatory'` 命令启用后，永久禁用 root 超级用户。
2. **强制访问控制（MAC）**：基于 Bell-LaPadula 模型，为主体（用户）和客体（数据库、超级表等）分配安全等级（0-4），强制执行"禁止上读"（NRU）和"禁止下写"（NWD）规则，独立于 DAC 运行。

#### 4.1 关键实体与数据

| 实体/数据 | 描述 | 敏感性 |
| --- | --- | --- |
| root 超级用户 | 系统初始超级管理员，拥有绕过所有权限检查的能力，SoD 启用后永久禁用 | 极高（系统控制权） |
| SClusterObj.flags | 集群对象中标识 SoD 状态的持久化字段，随用户对象下发 | 极高（状态控制） |
| 用户 security_level | 用户表中的安全等级区间 [min_level, max_level]，决定读写范围 | 高（访问控制基础） |
| 数据库/超级表 security_level | 客体元数据的安全等级字段（0-4），决定数据保护强度 | 高（数据保护等级） |
| 三员角色（SYSDBA/SYSSEC/SYSAUDIT） | 系统内置的三权分立角色，各自管理运维/安全/审计 | 极高（管理权限） |
| Catalog Cache | 缓存元数据对象（含 security_level）的内存结构 | 高（性能与一致性） |
| 审计日志 | 记录关键操作的日志数据，默认 security_level 为 4 | 极高（审计追溯） |
| vnode.json | 存储 vnode 级别 security_level 的持久化配置文件 | 高（数据等级基础） |

#### 4.2 威胁评估

| 威胁 ID | 威胁描述 / 攻击场景 | STRIDE | 相关组件 / 数据流 | 风险等级 |
| --- | --- | --- | --- | --- |
| T-MAC-01 | **root 禁用绕过**：攻击者通过直接修改 mnode 数据文件，恢复 root 用户的 superUser 标志或 enable 标志，重新获得超级权限，绕过三权分立机制。FS §4.1.3.3 将 SoD 状态随用户对象下发而非全局变量，部分降低了风险，但持久化文件本身仍需保护。 | S（仿冒）/ E（权限提升） | root 用户元数据、SClusterObj.flags | 高 |
| T-MAC-02 | **前置条件校验 TOCTOU 漏洞**：执行 `ALTER CLUSTER 'SoD mandatory'` 时，在校验三员角色已分配完成后、实际禁用 root 前，存在竞态窗口——若此间最后一个持有某角色的用户被并发删除或禁用，系统可能进入无有效三员管理员的不可恢复状态。FS §4.1.3.2 的 mandatory(enforcing) 中间状态设计针对此风险，需确保实现正确。 | D（拒绝服务） | SoD 启用流程、用户管理事务 | 高 |
| T-MAC-03 | **MAC 检查路径覆盖不全**：攻击者发现某些操作路径（如流计算、订阅、内部 RPC 调用）未正确集成 MAC 检查，导致低等级用户能读取高等级数据（违反 NRU）或高等级用户能写入低等级数据（违反 NWD）。FS §10 已明确 view/topic/stream 在 3.4.1.0 版本暂不支持 MAC，需关注此类旁路场景。 | I（信息泄露）/ T（篡改） | MAC 检查逻辑、各操作入口 | 高 |
| T-MAC-04 | **元数据不一致攻击**：分布式环境下，mnode 故障切换或 Catalog Cache 未正确刷新，造成不同节点或内存缓存中 security_level 与持久化值不一致，导致访问控制决策错误（应拒绝的请求被允许，或已更新等级未及时生效）。 | T（篡改）/ I（信息泄露） | mnode 元数据同步、Catalog Cache | 高 |
| T-MAC-05 | **三员角色空置导致系统锁定**：SoD 启用后，SYSSEC 用户撤销所有 SYSDBA 角色持有者（如通过禁用用户），导致系统无有效管理员，陷入不可自恢复的锁定状态。FS §4.1.4 测试用例 F1-T9 对此有覆盖，但需确保实现中每个角色的最后一个持有者检查在所有操作路径上均生效。 | D（拒绝服务） | GRANT/REVOKE、用户禁用/删除逻辑 | 中 |
| T-MAC-06 | **安全等级提升权限滥用**：SYSSEC 用户将特定业务用户的 security_level 恶意提升，使其可读取超出其业务需要的高等级数据。现有设计通过 TSDB_CODE_MAC_LEVEL_ESCALATION 限制不能超过自身等级，但 SYSSEC 仍有较大安全等级调整空间，操作行为须依赖审计日志约束。 | E（权限提升） | ALTER USER security_level、SYSSEC 角色权限 | 中 |
| T-MAC-07 | **审计日志完整性破坏**：拥有高权限的攻击者（或 mnode 访问权限）篡改或删除审计日志，掩盖安全操作痕迹。审计库默认 security_level 为 4，仅高等级用户可访问，但其持久化文件与普通数据库文件位于同一存储系统，缺乏额外的防篡改保护。 | T（篡改）/ R（抵赖） | 审计库、审计日志持久化 | 中 |
| T-MAC-08 | **安全等级配置错误锁定资源**：管理员将关键数据库或超级表的 security_level 设置为高于所有业务用户的 max_level，导致业务数据完全不可访问，造成可用性故障。FS §8.2 注意事项已警示此风险，但无自动检测机制。 | D（拒绝服务） | DB/STable security_level 设置 | 中 |
| T-MAC-09 | **跨等级旁路信息泄露**：低等级用户无法直接读取高等级数据，但通过 `SHOW STABLES`/`SHOW DATABASES` 等元数据查询的错误码差异（"对象不存在" vs "权限不足"）推断高等级对象的存在性，进行侦察。 | I（信息泄露） | SHOW 类元数据查询、MAC 错误处理 | 中 |
| T-MAC-10 | **升级过程安全等级自动赋值偏差**：从低版本升级时，对象 security_level 根据 owner/creator 自动赋值的逻辑存在异常，导致某些对象等级异常偏高，原有业务用户无法正常访问。FS §7 已将对象默认设为 0 以规避此问题，但 root 等级 [0,4] 的自动赋值仍需测试覆盖。 | T（篡改）/ I（信息泄露） | 升级脚本、元数据迁移逻辑 | 低 |

### 5. 安全需求与设计约束

| 威胁 ID | 转化后的安全需求 / 设计约束 | 类型 | 优先级 |
| --- | --- | --- | --- |
| T-MAC-01 | **SEC-MAC-001（元数据完整性保护）**：mnode 元数据文件（含用户表、SClusterObj）须通过加密和完整性校验（如 HMAC）保护；vnode.json 中的 security_level 字段须结合配置文件加密机制，启动时验证完整性，发现篡改应拒绝启动或进入安全模式。 | 安全功能需求 | 高 |
| T-MAC-02 | **SEC-MAC-002（原子化 SoD 启用）**：`ALTER CLUSTER 'SoD mandatory'` 须在数据库事务中原子执行：先锁定三员角色持有者，再校验条件，最后禁用 root 并更新 SClusterObj；整个过程中禁止其他用户管理操作（mandatory(enforcing) 状态），已在 FS §4.1.3.2 中设计，需确保实现正确覆盖所有并发路径。 | 安全设计约束 | 高 |
| T-MAC-03 | **SEC-MAC-003（MAC 检查全覆盖）**：在所有数据访问路径（SQL、RPC、流计算、订阅等）须在 DAC 检查通过后强制执行 MAC 检查；建立 MAC 检查覆盖矩阵，覆盖所有操作类型；3.4.1.0 版本中暂不支持 MAC 的对象（view/topic/stream）须在文档中明确标注安全约束，避免通过此类对象间接绕过 MAC。 | 安全设计约束 | 高 |
| T-MAC-04 | **SEC-MAC-004（元数据一致性保证）**：mnode 主从同步时 security_level 须与对象元数据原子化同步；DB 等级变化时通过 dbCfgVersion 强制失效继承自 DB 的对象（普通表等）的 Catalog Cache；定期执行一致性检查，发现不一致时告警。 | 安全设计约束 | 高 |
| T-MAC-05 | **SEC-MAC-005（三员角色保护机制）**：SoD 启用后，禁止执行导致任一系统角色无有效持有者的 REVOKE/DISABLE/DROP 操作；"最后一个管理员"保护逻辑须在所有操作路径上均生效，并记录审计日志。 | 非功能安全需求 | 中 |
| T-MAC-07 | **SEC-MAC-006（增强审计覆盖）**：以下操作须记录审计日志：启用 SoD、修改 security_level、授予/撤销三员角色、MAC 检查失败（含操作者、目标对象、双方 level、失败原因）、SoD 启用后 root 尝试登录；日志写入失败须导致操作回滚。 | 审计需求 | 中 |
| T-MAC-09 | **SEC-MAC-007（防止旁路信息泄露）**：SHOW STABLES/SHOW DATABASES 等元数据查询只返回当前用户有权访问（满足 NRU）的对象，不透露高等级对象的存在；访问拒绝时，错误消息不区分"对象不存在"与"权限不足"，统一返回通用拒绝响应。 | 安全设计约束 | 中 |
