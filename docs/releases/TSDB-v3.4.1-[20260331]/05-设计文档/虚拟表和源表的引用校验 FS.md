## 3. 定义

| 术语 | 定义 |
| --- | --- |
| 源表 | 被虚拟表引用的物理表，包含超级表、普通子表，是虚拟表数据与标签的原始来源 |
| 虚拟表（VTABLE） | 基于源表创建的逻辑表，自身不存储实际数据，查询时动态从源表获取数据 / 标签值，表结构与标签可通过源表引用定义 |
| 系统表 ins_virtual_tables_referencing | 新增的系统信息表，用于存储源表（库、表、列）与虚拟表（库、表、列）的引用关系，支持灵活的条件查询 |

新增系统表名 ins_virtual_tables_referencing，其 schema 定义为如下所示：

| 字段 | 含义 | 类型 | 备注 |
| --- | --- | --- | --- |
| virtual_db_name | 虚拟表DB名称 | Varchar |  |
| virutal_stable_name | 虚拟超级表名称 | Varchar |  |
| virtual_table_name | 虚拟表表名称 | Varchar |  |
| virtual_column_name | 虚拟表列名称 | Varchar |  |
| src_db_name | 源表DB 名称 | varchar |  |
| src_table_name | 源表表名称 | varchar |  |
| src_column_name | 源表表列名称 | Varchar |  |
| type | 源表类型（物理表还是虚拟表） | Varchar | virtual / physical |
| err_code | 错误码 | INT (0 为正常，其他为错误) |  |
| err_msg | 错误信息 | Varchar |  |

## 4. 行为说明

### 4.1 修改源表

#### 4.1.1 增加源表列 

不影响虚拟表的行为

#### 4.1.2 删除源表列 

查询虚拟表时，如果涉及到被删除的源表列，查询报告错误。出错信息会尽可能的清晰。

#### 4.1.3 修改源表列

##### 4.1.3.1 修改源表列的名称

只有普通表能 rename column。
查询虚拟表时，如果涉及到被重命名的源表列，查询报告错误。出错信息会尽可能清晰。  

##### 4.1.3.2 修改源表列的类型和长度。

不支持修改源表的类型，支持修改字符类型的列的长度，只支持列长度改大，不支持变小。
查询虚拟表时，不论源表的列长度是否发生修改，始终返回源表列的完整数据，因此返回的数据长度可能大于虚拟表的列定义长度，虚拟表 schema 列长度不会跟随原始表列长度变化。 

#### 4.1.4 删除源表

查询虚拟表时，如果设计到被删除的源表列，查询报告错误。报错信息尽可能的清晰。 

### 4.2 虚拟表的可用性

SQL 语法
```sql
SHOW VTABLE VALIDATE FOR [db_name.]tableName
```

 **行为**： 验证 table_name 的 ref col 的可用性。 
** 限制**： tableName 只能是虚拟子表/普通虚拟表/虚拟超级表，其他类型报错。 
 **输出**： 见 ins_virtual_tables_referencing 的 schema。 
 **性能**： 如果 tableName 是虚拟子表或者普通表虚拟表，性能比较高，不需要遍历整个 DB，如果是虚拟超级表，则需要遍所有 DB。

### 4.3 查询源表（或者源表的列）被哪些虚拟表引用（快捷命令）

 SQL 语法
```sql
  SHOW REFERNCES FOR [DB_NMAE].TB_NAME
```

**行为**：验证表被哪些虚拟表引用
**限制**：TB_NAME 只能是物理表。 
**性能**：需要遍历所有的 DB， 
**输出**：输出为**多行**** ****4**** ****列**。

| 列名 | 描述 | 类型 |
| --- | --- | --- |
| virtual_db_name | 虚拟表 DB 名称 | varchar |
| virtual_stable_name | 虚拟超级表名称 | varchar |
| virutal_table_name | 虚拟表表名称 | varchar |
| virtual_col_name | 虚拟表列名称 | Varchar |

该命令等价于针对系统表 ins_virtual_tables_referencing 的条件查询，如下 SQL 所示， 更灵活的方式是直接查询系统表, 
```sql {wrap}
 select virtual_db_name, virtaul_stable_name, virtual_table_name, virtual_col_name from information_shema.ins_virtual_tables_referencing where src_table_name='TB_NAME' 
```

## 5. 性能

**查询源表被哪些虚拟表引用**（`SHOW REFERENCES` 或直接查系统表）为重量级查询，该操作需要遍历所有 VNODE 的元数据（meta），筛选出所有虚拟表并匹配其源表引用关系，查询性能主要取决于集群中元数据的整体大小，元数据量越大，查询耗时越长；
虚拟表常规查询（基于源表数据 / 标签）的性能与直接查询源表基本一致，无额外比较大的性能损耗。

## 6. 安全

**数据完整性**：源表结构变更时，虚拟表仅返回 NULL 而非查询报错，保证查询操作的完整性，避免因源表变更导致业务查询中断；
**权限管控**：虚拟表的创建、查询与源表的权限体系保持一致，无额外权限配置，仅拥有源表查询权限的用户可创建并查询关联的虚拟表，防止未授权的源表数据访问；
**元数据安全**：系统表 `ins_virtual_tables_referencing` 仅支持查询操作，不支持插入、更新、删除，保证源表 - 虚拟表引用关系的元数据不被篡改；
**数据隔离**：虚拟表为逻辑表，自身不存储任何实际数据，所有数据均动态从源表获取，避免数据冗余，同时保证源表数据的机密性，虚拟表无法访问源表中未被引用的列 / 标签

## 8. 运维

1. 源表日常维护（如结构调整、表清理）时，需提前通过 `SHOW REFERENCES` 或系统表查询该源表是否被虚拟表引用，避免因源表列 / 表删除导致虚拟表查询返回大量 NULL，影响业务使用；
2. 对源表字符 / 二进制类列进行长度修改时，需严格遵循「只能改大、不超过虚拟表定义长度」的规则，运维操作前需核对虚拟表对应列的定义长度；
3. 普通表列名重命名操作前，需检查是否有虚拟表引用该列，防止重命名后虚拟表对应列返回 NULL；
4. 集群元数据量较大时，应尽量避免频繁执行「源表引用关系查询」操作，防止遍历 VNODE 元数据占用过多集群资源，影响正常业务查询。

## 9. 使用场景

#### 9.0.1 场景 1：源表结构动态调整，业务查询无感知

智能电表业务中，运维人员因需求变更需删除源表 `meter_001` 的 `power` 列，而该列被业务侧的虚拟表 `v_meter_biz` 引用。通过本特性，删除列后查询 `v_meter_biz` 仅 `power` 列返回 NULL，其他列数据正常，业务查询无需修改代码，保证业务连续性。

#### 9.0.2 场景 2：源表生命周期管理，快速排查引用关系

运维人员需要清理过期的智能电表源表 `meter_999`，为避免误删导致关联虚拟表异常，可通过 `SHOW REFERENCES FOR meter_999` 快速查询该表被哪些虚拟表引用，再通知业务侧做虚拟表调整，完成源表的安全下线。
