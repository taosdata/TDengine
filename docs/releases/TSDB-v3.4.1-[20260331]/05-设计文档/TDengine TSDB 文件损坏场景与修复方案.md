# TDengine TSDB 文件损坏场景与修复方案

## 1. 常见文件损坏场景及修复方法

### 1.1 WAL 损坏

#### 1.1.1 WAL技术背景

WAL（Write-Ahead Logging，预写式日志）是 TDengine 数据库系统中的关键组件，用于确保数据的持久性和一致性。WAL 通过先将数据写入日志文件，再写入主数据文件的方式，保证即使在系统崩溃等异常情况下，数据也不会丢失。WAL 文件存储在每个 VNode 的数据目录中，记录了未持久化到 TSDB 文件的写入操作。
WAL 的主要作用包括：
1. **数据持久性保障**：确保已确认的写入操作不会因系统故障而丢失
2. **崩溃恢复**：系统重启时通过重放 WAL 日志恢复未持久化的数据
3. **数据一致性**：在分布式多副本场景下，WAL 用于保证副本间数据的一致性

#### 1.1.2 损坏后的表现

WAL 文件损坏后通常表现为以下几种形式：
**1. 服务启动失败**
- TDengine 无法正常启动，日志中出现类似以下错误信息：
  ```plaintext
  WAL file is corrupted
  ```

- 启动过程中卡住或异常退出，系统日志显示 WAL 相关错误
**2. 校验和验证失败**
- WAL 文件校验和不匹配，日志中出现以下错误：
  ```plaintext
  WAL checksum mismatch
  ```

- 更具体的校验和错误信息：
  ```plaintext
  head checksum not passed
  body checksum not passed
  ```

**3. 日志完整性错误**
- WAL 日志条目不完整，日志中出现范围错误：
  ```plaintext
  WAL log entries incomplete in range [2837, 3043]
  ```

- WAL 日志不完整的通用错误：
  ```plaintext
  WAL log incomplete
  ```

**4. 版本和格式错误**
- WAL 文件版本无效或格式错误：
  ```plaintext
  WAL invalid version
  ```

- WAL 日志文件不存在（可能被意外删除或损坏）：
  ```plaintext
  WAL log not exist
  ```

**5. 系统行为异常**
- 数据写入失败：应用程序在写入数据时返回错误或超时
- 查询结果异常：查询返回的数据不完整或包含错误数据
- 服务不稳定：TDengine 服务频繁重启或崩溃
**6. 日志特征**
- 在 TDengine 日志（通常为 `/var/log/taos/taosdlog.?`）中频繁出现 WAL 相关错误
- 错误信息通常包含 VNode ID，格式如：`vgId:1234`
- 错误信息中可能包含文件路径、偏移量等详细信息
- 系统日志（`/var/log/messages` 或 `dmesg`）中可能出现磁盘 I/O 错误或文件系统错误

#### 1.1.3 常见出现原因

1. **软件缺陷或 bug 导致 WAL 文件写入异常**
  这类问题通常出现在特定版本的 TDengine 中，尤其是较早的 TDengine 版本，可能由于代码中的缺陷导致 WAL 文件在写入过程中出现异常，进而引发文件损坏。
1. **非正常断电或系统崩溃，导致 WAL 文件未能正确写入或关闭**
  这类问题通常发生在系统突然断电或崩溃时，导致正在写入的 WAL 文件未能正确完成写入操作，从而引发文件损坏。
1. **磁盘空间不足，导致 WAL 文件写入失败**
  当磁盘空间不足时，TDengine 可能无法成功写入 WAL 文件，进而导致文件损坏。通常情况下磁盘空间不足的情况，TDengine 已经做了相应的处理，如返回错误码等，但是磁盘空间不足通常导致一些其他的问题，从而可能导致 WAL 文件的损坏
1. **文件系统损坏或硬件故障**
  底层存储设备（如硬盘、SSD）故障或文件系统损坏可能导致 WAL 文件物理损坏。这类问题通常伴随磁盘 I/O 错误或文件系统错误日志。
1. **网络存储问题**
  当 WAL 文件存储在网络附加存储（NAS）或分布式文件系统上时，网络中断、存储节点故障或存储系统软件问题可能导致 WAL 文件损坏。
1. **并发访问冲突**
  在多进程或多线程环境下，如果存在对 WAL 文件的非法并发访问（如第三方工具直接操作 WAL 文件），可能导致文件内容不一致或损坏。
1. **内存错误或操作系统异常**
  服务器内存故障、内核错误或操作系统 bug 可能导致写入 WAL 文件的数据在传输过程中被破坏。

#### 1.1.4 诊断步骤

当怀疑 WAL 文件损坏时，可按以下步骤进行诊断：
1. **检查 TDengine 日志**
  - 使用 `grep -i "corrupt\|WAL.*error\|WAL.*fail" /var/log/taos/taosdlog.?` 命令搜索相关错误信息
  - 确认错误信息中是否包含 "WAL file is corrupted" 或类似内容
1. **确认损坏的 VNode ID**
  - 从日志中提取损坏的 VNode ID，通常错误信息会包含类似 "vgId:1234" 的标识
  - 示例日志：`WAL vgId:1234 file is corrupted`
1. **检查系统日志**
  - 查看系统日志（`/var/log/messages` 或 `dmesg`）中是否有磁盘错误、文件系统错误或硬件故障记录
  - 检查是否有 "I/O error"、"filesystem error" 或类似错误
1. **检查磁盘空间**
  - 使用 `df -h` 命令确认数据目录所在分区的可用空间
  - 检查是否有 "No space left on device" 相关错误
1. **排除其他可能性**
  - 确认是否为单点故障：检查集群中其他节点是否正常
  - 确认是否为版本兼容性问题：检查 TDengine 版本是否一致
  - 确认是否有近期系统变更（如系统升级、配置修改、硬件更换）

#### 1.1.5 修复方法

**方法一：手动删除损坏的 WAL 文件**
**适用场景**：单副本集群或紧急情况下需要快速恢复服务，且可以接受一定程度的数据丢失。
**操作步骤**：
1. **停止 TDengine 服务**：
  ```bash
  systemctl stop taosd
  ```

1. **定位损坏的 VNode ID**：
  ```bash
  grep -i "WAL.*corrupt\|vgId.*corrupt" /var/log/taos/taosdlog.? | tail -20
  ```

  从日志中提取 VNode ID，通常格式为 `vgId:1234` 或类似。
1. **备份损坏的 WAL 文件（可选但建议）**：
  ```bash
  cp -r /var/lib/taos/vnode/vnode1234/wal /tmp/wal_backup_vnode1234_$(date +%Y%m%d_%H%M%S)
  ```

1. **删除损坏的 WAL 目录**：
  TDengine 会在启动时自动重建
  ```bash
  rm -rf /var/lib/taos/vnode/vnode1234/wal
  ```

1. **启动 TDengine 服务**：
  ```bash
  systemctl start taosd
  ```

1. **监控启动过程**：
  ```bash
  tail -f /var/log/taos/taosdlog.? | grep -i "WAL\|vgId:1234"
  ```

**风险说明**：
1. **数据丢失风险**：
  - 单副本集群：会丢失该 VNode 中尚未持久化到 TSDB 文件的所有数据（通常为最近几分钟的写入数据）
  - 多副本集群：数据丢失风险较低，系统会自动从其他副本同步数据，但可能丢失最新的部分写入
1. **业务影响**：
  - 该 VNode 对应的表在恢复期间不可用
  - 可能需要重新创建受影响的数据表（极端情况下）
1. **建议**：
  - 优先在多副本集群中使用此方法
  - 在执行前评估数据丢失的可接受范围
  - 如有备份，优先考虑从备份恢复

**方法二：通过配置跳过损坏的 WAL 继续启动**
**适用场景**：TDengine 3.3.6.34 及以上版本，需要自动处理 WAL 损坏问题，减少人工干预。
**操作步骤**：
1. **停止 TDengine 服务**：
  ```bash
  systemctl stop taosd
  ```

1. **修改配置文件**：
  - 编辑 TDengine 配置文件 `/etc/taos/taos.cfg`
  - 添加或修改以下配置项：
    ```plaintext
    walDeleteOnCorruption 1
    ```

  - 保存配置文件
1. **启动 TDengine 服务**：
  ```bash
  systemctl start taosd
  ```

1. **监控启动过程**：
  ```bash
  tail -f /var/log/taos/taosdlog.?
  ```

**功能说明**：
1. **自动处理机制**：
  - 当设置为 `1` 时，TDengine 在启动检测到 WAL 损坏时，会自动将损坏的 WAL 目录备份到 `wal_bak` 目录
  - 系统会创建新的 WAL 目录并继续启动
  - 备份的 WAL 文件可用于后续分析或数据恢复尝试
1. **备份位置**：
  - 备份目录：`/var/lib/taos/data/vnode{id}/wal_bak/`
  - 备份命名：`wal_bak_YYYYMMDD_HHMMSS`
1. **版本要求**：
  - 此功能从 TDengine 3.3.6.34 版本开始支持
  - 由 JIRA 任务 [TD-38615](https://jira.taosdata.com:18080/browse/TD-38615) 实现
**风险说明**：
1. **数据丢失**：与手动删除 WAL 文件类似，会丢失未持久化的数据
2. **自动执行**：系统自动执行，无需人工确认，适用于自动化运维场景
3. **备份保留**：自动保留损坏的 WAL 文件备份，便于后续分析

**方法三：从备份恢复完整数据**
**适用场景**：有定期数据备份，对数据完整性要求高，可以接受较长的恢复时间。
**操作步骤**：
1. **停止 TDengine 服务**：
  ```bash
  systemctl stop taosd
  ```

1. **恢复完整数据目录**：
  - 如果有完整的 VNode 数据备份，恢复整个 VNode 目录：
    ```bash
    rm -rf /var/lib/taos/vnode/vnode1234
    cp -r /backup/vnode1234 /var/lib/taos/vnode/
    ```

1. **启动 TDengine 服务**：
  ```bash
  systemctl start taosd
  ```

**优势**：
1. **数据完整性**：最大程度保证数据不丢失
2. **系统一致性**：恢复完整的 VNode 状态，避免部分数据不一致
**限制**：
1. **恢复时间**：数据量越大，恢复时间越长
2. **备份要求**：需要有可用的最新备份
3. **服务中断**：在恢复期间服务不可用
**修复后验证**：
无论采用哪种修复方法，修复后都应进行以下验证：
1. **服务状态检查**：
  ```bash
  systemctl status taosd
  taos -s "show dnodes;"
  ```

1. **数据完整性检查**：
  ```bash
  taos -s "use db_name; select count(*) from table_name;"
  ```

1. **监控告警确认**：
  - 确认监控系统中无相关错误告警
  - 检查系统日志中无新的 WAL 相关错误
1. **业务功能测试**：
  - 执行数据写入测试，确认功能正常
  - 执行数据查询测试，确认结果正确

#### 1.1.6 预防措施与最佳实践

为减少 WAL 文件损坏的风险，建议采取以下预防措施：
**1. 硬件与基础设施**
- 使用企业级 SSD 或高性能硬盘，避免使用低质量存储设备
- 配置 RAID 或使用分布式存储提高数据可靠性
- 确保 UPS（不间断电源）保护，防止突然断电
- 定期检查磁盘健康状况
**2. 系统配置优化**
- 确保足够的磁盘空间，设置磁盘使用率监控告警
- 合理配置 WAL 相关参数：
  ```plaintext
  walLevel 1           # 设置适当的 WAL 级别
  walRetentionPeriod 0 # 根据业务需求设置保留期
  walRollPeriod 0      # 根据数据量设置滚动周期
  ```

- 使用多副本部署（至少 3 副本）提高数据可靠性
**3. 运维管理**
- 定期备份重要数据，测试备份恢复流程
- 实施变更管理，避免未经测试的配置变更
- 监控系统日志，设置 WAL 相关错误告警
- 定期进行灾难恢复演练
**4. 软件与版本管理**
- 保持 TDengine 版本更新，及时修复已知 bug
- 在生产环境部署前充分测试新版本
- 关注官方发布的安全更新和补丁
**5. 监控与告警**
- 监控 WAL 文件大小和增长趋势
- 监控磁盘 I/O 性能和错误率
- 设置磁盘空间不足告警（阈值建议 80%）
- 监控 TDengine 日志中的 WAL 相关错误
**最佳实践总结**：
1. **预防优于修复**：通过可靠的硬件和合理的配置预防问题发生
2. **多层防护**：结合硬件冗余、软件配置和运维管理多层次防护
3. **快速响应**：建立完善的监控告警和应急响应机制
4. **定期验证**：定期测试备份恢复和灾难恢复流程

### 1.2 TDB 文件损坏

#### 1.2.1 TDB 技术背景

TDB 是 TDengine 数据库系统中的嵌入式 Key-Value 存储引擎，用于管理 VNode 的元数据和索引信息。TDB 基于 B+ 树结构实现，提供高效的数据插入、删除、查询和事务支持。
TDB 在 TDengine TSDB 中主要用在两个地方：
1. 元数据存储：存储 VNode 中所有表的元数据信息，包括表结构、索引信息等
2. TMQ Checkpoint 存储：存储 TMQ 的消费进度检查点
文件名后缀为`.tdb`，存储格式为自定义的二进制格式。

#### 1.2.2 损坏后的表现

TDB 文件损坏后通常表现为以下几种形式：
1. **服务启动失败**
  - TDengine 无法正常启动，日志中出现类似以下错误信息：
    ```plaintext
    metaOpenImpl failed at
    ```

  - 启动过程中产生 core dump 文件，系统异常退出
1. **元数据操作异常**
  - 创建、删除表时出现 META 模块的 Internal Error 日志报错：
    ```plaintext
    MTA.*internal error
    ```

  - 表结构查询返回错误或超时
  - 索引创建或重建失败
1. **文件大小异常**
  - TDB 文件大小异常增长，可能达到数 TB 级别
  - 文件大小与正常情况明显不符，远超过预期大小
  - **此异常通常为 TDB 模块未解决的一个 BUG 导致的**
1. **数据不一致**
  - 查询结果与预期不符，返回错误数据
  - 表数量统计异常，与实际表数量不一致
  - 索引查询返回错误结果或超时
1. **系统行为异常**
  - VNode 状态异常，无法正常提供服务
  - 数据写入失败，返回元数据相关错误
  - 服务频繁重启或崩溃
1. **日志特征**
  - 在 TDengine 日志中频繁出现 TDB 相关错误
  - 错误信息通常包含文件路径、页号等详细信息
  - 可能伴随磁盘 I/O 错误或文件系统错误日志

#### 1.2.3 常见出现原因

1. **非正常断电或系统崩溃**
  - 系统突然断电或崩溃时，正在写入的 TDB 文件未能正确完成写入操作
  - 事务未正常提交，导致文件状态不一致
  - 此原因的可能性非常小
1. **磁盘空间不足**
  - 磁盘空间不足导致 TDB 文件扩展失败
  - 文件写入过程中因空间不足而中断
1. **文件系统损坏或硬件故障**
  - 底层存储设备（硬盘、SSD）故障导致文件物理损坏
  - 文件系统损坏导致 TDB 文件结构破坏
  - 内存故障导致写入数据损坏
1. **软件缺陷或 bug**
  - TDengine 特定版本中的 TDB 实现缺陷
  - 并发访问冲突导致的文件状态不一致
  - 内存管理错误导致的数据损坏
1. **并发访问冲突**
  - 多进程或多线程环境下对 TDB 文件的非法并发访问
  - 第三方工具直接操作 TDB 文件导致结构破坏

#### 1.2.4 诊断步骤

当怀疑 TDB 文件损坏时，可按以下步骤进行诊断：
1. **检查 TDengine 日志**
  - 使用 `grep -i "tdb\|corrupt\|MTA.*error" /var/log/taos/taosdlog.?` 命令搜索相关错误信息
  - 确认错误信息中是否包含 TDB 相关的错误信息。
1. **检查 core dump 文件**
  - 检查是否有 core dump 文件生成：`ls -la /var/lib/taos/core*`
  - 使用 gdb 分析 core dump 文件，定位问题原因
1. **检查 TDB 文件状态**
  - 定位 TDB 文件：`find /var/lib/taos/vnode/ -name "*.tdb" -type f`
  - 检查文件大小：`ls -lh /var/lib/taos/vnode/vnode*/*.tdb`
1. **检查系统日志**
  - 查看系统日志（`/var/log/messages` 或 `dmesg`）中是否有磁盘错误
  - 检查是否有 "I/O error"、"filesystem error" 或硬件故障记录
1. **检查磁盘空间**
  - 使用 `df -h` 命令确认数据目录所在分区的可用空间
  - 检查磁盘使用率是否过高
1. **排除其他可能性**
  - 确认是否为单点故障：检查集群中其他节点是否正常
  - 确认是否有近期系统变更（如系统升级、配置修改）

#### 1.2.5 修复方法：

**方法一：从完好副本恢复 TDB 文件（多副本场景）**
**适用场景**：多副本集群，且至少有一个副本的 TDB 文件完好无损。
**操作步骤**：
1. **停止 TDengine 服务**：
  ```bash
  systemctl stop taosd
  ```

1. **定位损坏的 VNode**：
  ```bash
  grep -i "tdb.*corrupt\|vgId.*tdb" /var/log/taos/taosdlog.? | tail -20
  ```

  从日志中提取 VNode ID，通常格式为 `vgId:1234`。
1. **备份损坏的 TDB 文件**：
  ```bash
  cp /var/lib/taos/vnode/vnode1234/main.tdb /tmp/tdb_backup_vnode1234_$(date +%Y%m%d_%H%M%S)
  ```

1. **从完好副本拷贝 TDB 文件**：
  - 如果集群中有其他副本节点，从该节点拷贝完好的 TDB 文件：
    ```bash
    scp other_node:/var/lib/taos/vnode/vnode1234/main.tdb /var/lib/taos/vnode/vnode1234/
    ```

  - 确保文件权限正确：
    ```bash
    chown taos:taos /var/lib/taos/data/vnode1234/tdb
    chmod 644 /var/lib/taos/data/vnode1234/tdb
    ```

1. **启动 TDengine 服务**：
  ```bash
  systemctl start taosd
  ```

1. **监控启动过程**：
  ```bash
  tail -f /var/log/taos/taosdlog.?
  ```

**风险说明**：
1. **数据一致性**：确保拷贝的 TDB 文件来自同一时间点的副本，必要情况下要停止服务
2. **版本兼容性**：确保源节点和目标节点的 TDengine 版本一致
3. **网络传输**：大文件传输可能耗时较长，确保网络稳定
**方法二：使用 **`**taosd -r**`** 命令重建元数据（单副本或所有副本损坏）**
**适用场景**：单副本集群，或所有副本的 TDB 文件均损坏，且损坏的是 VNode 元数据存储，只能尽可能多地拯救数据。
**操作步骤**：
1. **停止 TDengine 服务**：
  ```bash
  systemctl stop taosd
  ```

1. **备份数据目录**
2. **使用恢复模式启动 taosd**：
  ```bash
  taosd -r
  ```

1. **监控恢复过程**：
  - 恢复过程会重新解析 WAL 日志和 TSDB 文件，重建元数据
  - 查看日志确认恢复进度：
1. **正常启动服务**：
  - 恢复完成后，使用 Ctrl+C 停止手启的服务，正常启动 TDengine 服务：
    ```bash
    systemctl start taosd
    ```

**功能说明**：
1. **恢复原理**：`taosd -r` 命令会将原 TDB 中的文件重新构建，尽可能多的恢复，并不能保证一定能够完全恢复
2. **恢复范围**：仅恢复元数据信息，原始时间序列数据保持不变
3. **恢复时间**：数据量越大，恢复时间越长
**风险说明**：
1. **数据丢失风险**：如果 WAL 日志也损坏，可能丢失部分未持久化的数据
2. **恢复时间**：大数据量场景下恢复时间可能较长
3. **服务中断**：恢复期间服务完全不可用

### 1.3 TSDB 时序数据存储文件损坏

#### 1.3.1 TSDB技术背景

TSDB 是 TDengine 数据库系统中的核心时序数据存储引擎，负责存储和管理时间序列数据。TSDB 采用列式存储结构，针对时序数据的特点进行了高度优化，支持高效的数据写入、查询和压缩。
TSDB 在 TDengine 中的主要作用包括：
1. **时序数据存储**：存储所有时间序列数据的实际值，包括时间戳和对应的测量值
2. **数据压缩**：采用多种压缩算法（如 TSZ、LZ4 等）对时序数据进行高效压缩
3. **数据分区**：按照时间范围对数据进行分区管理，支持数据生命周期管理
4. **查询优化**：提供高效的时间范围查询和聚合计算支持
5. **数据合并**：定期将小文件合并为大文件，优化存储和查询性能
TSDB 文件系统由多种类型的文件组成：
- **数据文件（.data）**：存储实际的时序数据
- **头文件（.head）**：存储数据文件的元数据和索引信息
- **最后文件（.sma）**：存储最新的数据块信息
- **STT 文件**：存储小时间范围的数据，等待合并到主数据文件
- **VNode 配置文件**：存储 VNode 的配置信息

#### 1.3.2 损坏后的表现

TSDB 文件损坏后通常表现为以下几种形式：
1. **服务启动失败**
  - TDengine 无法正常启动，日志中出现类似以下错误信息：
    ```plaintext
    TSD.*file is corrupted
    ```

  - 启动过程中产生 core dump 文件，系统异常退出
  - VNode 无法正常挂载，状态显示为异常
1. **数据文件完整性错误**
  - 数据文件校验和失败，日志中出现以下错误：
    ```plaintext
    checksum mismatch in data file
    ```

  - 文件大小异常，与预期大小不符
  - 文件格式错误，无法正确解析文件结构
1. **文件系统状态异常**
  - TSDB 文件系统状态变为 `TSDB_FS_STATE_INCOMPLETE`
  - 文件引用关系不一致，存在孤立的文件
  - 文件版本信息不一致或无效
1. **数据查询异常**
  - 查询返回错误数据或空结果
  - 时间范围查询失败，返回文件读取错误
  - 聚合计算返回异常值或错误
1. **数据写入失败**
  - 数据写入时返回文件系统错误
  - 数据压缩或持久化过程失败
  - 文件扩展或创建失败
1. **系统行为异常**
  - VNode 状态不稳定，频繁切换状态
  - 数据合并过程失败或异常中断
  - 磁盘 I/O 错误率升高
1. **日志特征**
  - 在 TDengine 日志中频繁出现 TSDB 相关错误
  - 错误信息通常包含文件路径、VNode ID 等详细信息
  - 可能伴随磁盘空间不足或文件系统错误日志

#### 1.3.3 常见出现原因

1. **非正常断电或系统崩溃**
  - 系统突然断电或崩溃时，正在写入的 TSDB 文件未能正确完成写入操作
  - 数据压缩过程中断，导致文件结构不一致
  - 文件元数据更新未完成，导致文件状态不一致
1. **磁盘空间不足**
  - 磁盘空间不足导致 TSDB 文件扩展失败
  - 临时文件无法创建，导致数据写入失败
  - 数据合并过程因空间不足而中断
1. **文件系统损坏或硬件故障**
  - 底层存储设备（硬盘、SSD）故障导致文件物理损坏
  - 文件系统损坏导致 TSDB 文件结构破坏
  - 内存故障（ECC 内存错误）导致写入数据损坏
  - RAID 阵列故障或重建失败
1. **软件缺陷或 bug**
  - TDengine 特定版本中的 TSDB 实现缺陷
  - 数据压缩算法实现错误
  - 文件锁管理或并发控制缺陷
  - 内存管理错误导致的数据损坏
  - **最新版本极少出现软件 bug 引起的文件损坏**
1. **并发访问冲突**
  - 多进程或多线程环境下对 TSDB 文件的非法并发访问
  - 第三方工具直接操作 TSDB 文件导致结构破坏
  - 备份工具在运行时修改文件内容
1. **网络存储问题**
  - TSDB 文件存储在网络附加存储（NAS）上时，网络中断导致写入失败
  - 分布式文件系统的同步问题
  - NFS 或 CIFS 协议兼容性问题

#### 1.3.4 诊断步骤

当怀疑 TSDB 文件损坏时，可按以下步骤进行诊断：
1. **检查 TDengine 日志**
  - 使用 `grep -i "TSD.*corrupt\|data.*file.*corrupt\|TSD.*error" /var/log/taos/taosdlog.?` 命令搜索相关错误信息
  - 确认错误信息中是否包含 "TSD file system is corrupted" 或 "Data file corrupted"
  - 检查错误信息中是否包含具体的文件路径和 VNode ID
1. **检查 VNode 状态**
  - 使用 `taos -s "show vgroups;"` 命令检查 VNode 状态
  - 确认是否有 VNode 处于异常状态（如 offline 等）
  - 检查 VNode 的同步状态和健康状态
1. **检查 TSDB 文件系统状态**
  - 定位 TSDB 数据目录：`find /var/lib/taos/vnode -name "*.data" -o -name "*.head" -o -name "*.last" | head -20`
  - 检查文件大小是否异常：`ls -lh /var/lib/taos/vnode/vnode*/tsdb/*`
  - 检查文件权限和所有者：`ls -la /var/lib/taos/vnode/vnode*/tsdb/*`
1. **检查系统日志**
  - 查看系统日志（`/var/log/messages` 或 `dmesg`）中是否有磁盘错误
  - 检查是否有 "I/O error"、"filesystem error" 或硬件故障记录
1. **检查磁盘空间**
  - 使用 `df -h` 命令确认数据目录所在分区的可用空间
  - 检查磁盘使用率是否过高，特别是 `/var/lib/taos` 目录
1. **排除其他可能性**
  - 确认是否为单点故障：检查集群中其他节点是否正常
  - 确认是否有近期系统变更（如系统升级、配置修改、硬件更换）
  - 确认是否为版本兼容性问题：检查 TDengine 版本是否一致

#### 1.3.5 修复方法

**方法一：手动修复 TSDB 文件系统**
**适用场景**：单副本且通过日志可以明确部分文件组的文件出现问题且允许部分数据的丢失。
**操作步骤**：
1. **停止 TDengine 服务**：
  ```bash
  systemctl stop taosd
  ```

1. **备份损坏的文件组：**
  将损坏的文件组备份到其他目录
1. **修改损坏 vnode 的 current.json 索引文件**：
  在 current.json 文件中找到损坏的文件组，删除整个文件组，保存。
1. **正常启动服务**：
  ```bash
  systemctl start taosd
  ```

**功能说明**：
1. **恢复原理**：删除索引后的文件组不会被重新检查，避免文件损坏阻碍服务启动
2. **恢复范围**：仅恢复可用的数据，损坏的数据可能丢失
**风险说明**：
1. **数据丢失风险**：可能丢失大量数据

**方法二：从备份恢复 TSDB 数据**
**适用场景**：有多副本或有完整的 TSDB 数据备份，对数据完整性要求高。
**操作步骤**：
1. **停止 TDengine 服务**：
  ```bash
  systemctl stop taosd
  ```

1. **恢复 TSDB 数据目录**：
  - 如果有完整的 VNode 备份，恢复整个 VNode 目录：
  ```bash
  rm -rf /var/lib/vnode/data/vnode1234
  cp -r /backup/vnode1234 /var/lib/taos/vnode/
  ```

  - 如有副本，则整体停服后，从副本将整个 VNode 目录拷贝过来
1. **修复文件权限**：
  ```bash
  chown -R taos:taos /var/lib/taos/data/vnode1234
  chmod -R 755 /var/lib/taos/data/vnode1234
  ```

1. **启动 TDengine 服务**：
  ```bash
  systemctl start taosd
  ```

**优势**：
1. **数据完整性**：最大程度保证数据不丢失
2. **系统一致性**：恢复完整的 VNode 状态
3. **可靠性高**：经过验证的备份数据
**限制**：
1. **恢复时间**：数据量越大，恢复时间越长
2. **备份要求**：需要有可用的最新备份
3. **服务中断**：在恢复期间服务不可用

**方法三：通过 restore 命令恢复数据**
**适用场景**：有多副本且存在数据完好的多副本
