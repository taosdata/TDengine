## 2. 评审记录

1. 改造背景与目标：
   - 讨论：评审组认为，方案围绕代码资产集中管理、构建流程简化、安全隔离和文档纳入版本管理四个核心问题展开，能够承接迁移计划中提出的治理目标。尤其是将代码、文档、构建配置和 AI Agent 配置统一纳入 GitLab 管理，有利于形成一致的研发入口和长期知识沉淀。评审中建议在方案正文中进一步区分“必须首批落地”的能力与“可在后续迭代完善”的能力，避免实施期目标过宽影响交付节奏。
   - 结论：改造目标明确，能够支撑研发资产统一治理和后续持续演进。
2. 仓库规划与同步策略：
   - 讨论：方案对主仓库、秘密代码仓库、GitHub 子仓库来源及同步策略进行了较完整的描述，明确了开源代码继续在 GitHub 工作、内部代码逐步切换到 GitLab 的思路，整体方向合理。评审组建议补充各类仓库之间的边界说明，包括哪些仓库保留双端同步、哪些仓库完成归档后仅保留 GitLab 作为主工作面，以及同步失败时的应急处理方式。
   - 结论：仓库规划和同步方向可行；需补充边界与异常处置规则。
3. 代码组织与构建方案：
   - 讨论：方案提出以 tsdb 为核心采用 monorepo 方式组织源码，使用 `source/`、`tools/`、`tests/`、`packaging/` 等目录统一管理，并通过顶层 `CMakeLists.txt` 和 `cmake/` 目录按 option 控制组件构建，能够降低多仓库依赖带来的构建复杂度。评审组认为这一方案有利于统一构建入口和提升协同效率，但需要同步明确各组件 owner、目录边界和代码评审机制，避免 monorepo 扩大后造成职责不清和变更范围失控。
   - 结论：monorepo + CMake 的技术路线可行，需配套明确目录治理与评审规则。
4. 文档管理与知识沉淀机制：
   - 讨论：方案将发布文档、模板、报告和非计划文档统一纳入 `docs/` 目录管理，能够解决文档分散、版本不可追溯和 AI Agent 读取成本高的问题，方向明确。评审组建议优先保障版本发布文档、项目管理文档、设计与测试文档迁入，并建立目录命名规则、模板约束、文档 owner 和评审机制，确保文档迁移后可以长期维护。
   - 结论：文档内嵌管理策略合理，需同步完善治理规范与责任机制。
5. 安全策略与权限控制：
   - 讨论：方案已区分 GitHub 公开仓库与 GitLab 内部仓库的权限策略，并提出秘密代码仓库和敏感文档隔离要求，基本满足安可背景下的管理诉求。评审组建议进一步细化分组授权、分支保护、敏感目录访问控制、秘密信息扫描和例外审批流程，确保方案在落地时具备可审计、可追踪、可回收的权限闭环。
   - 结论：安全控制方向正确；需补充更细粒度的权限和审计措施。
6. 时间安排与实施控制：
   - 讨论：方案给出了代码仓库改造、打包脚本、CI/CD、文档迁移和测试迁移等主要工作项，并对各阶段时间安排和责任人做了初步分配，具备实施基础。评审组建议增加里程碑验收标准、关键依赖项和上线切换标准，特别是对打包脚本完善、CI/CD 改造和上线宣贯等关键节点，应明确完成定义与回退条件。
   - 结论：实施安排基本可执行；需补充验收口径和关键节点控制要求。
7. CI/CD 编译基础设施（tsdb-builder 概要设计）：
   - 讨论：方案新增了 tsdb-builder 概要设计章节，对现有编译环境（TDengine build.sh、发版 build_installer.py、GitHub Actions CI、遗留 Jenkins）进行了全面现状分析，提出了"标准化 Docker 镜像 + 统一构建脚本"的容器化编译方案。评审组认为，双镜像体系（core 基于 manylinux2014 锁定 glibc 2.17、others 基于 manylinux_2_28）能有效解决 glibc 兼容性和编译环境碎片化问题，统一构建入口 build.sh 覆盖 MR CI、发版 CD 和开发者本地编译三个场景的设计方向合理。基于 Build Runner 本地持久目录的缓存体系（Conan/externals/Go/Cargo/pnpm/Maven/NuGet）可以根本性解决 GitHub Actions cache 10GB 上限和跨 PR 不共享的痛点。评审组建议在实施过程中重点关注以下事项：一是首批镜像构建后需在各架构 Build Runner 上进行全组件编译验证，确保 P0 基础对接阶段通过后再推进 CI 集成；二是镜像标签管理需严格执行版本锁定策略，发版 CI 禁止使用 latest 标签；三是缓存目录权限（容器内 root vs 宿主机 gitlab-runner）需在 Runner 初始化时一次性解决；四是跨架构编译必须使用原生 Runner，严禁 QEMU 模拟。
   - 结论：tsdb-builder 技术路线和设计方案合理，能够为 GitLab CI/CD 迁移提供可靠的编译层基础；需按 P0→P1→P2 分阶段推进，确保每阶段验收通过后再启动下一阶段。
