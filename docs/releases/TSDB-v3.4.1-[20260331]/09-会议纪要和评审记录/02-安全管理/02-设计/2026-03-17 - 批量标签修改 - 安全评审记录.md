### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** 批量标签修改涉及两种操作路径：（1）逐表模式（FS 第 3.1 节）需要调用方对每个目标子表持有 WRITE 权限；（2）超级表 WHERE 模式（FS 第 3.2.2 节）通过 Mnode 展开满足条件的子表集合后批量下发至 Vnode 执行。核心安全问题在于超级表模式下是否对每个展开后的子表独立校验 WRITE 权限，而非仅在超级表层级进行一次性校验——若后者，攻击者可通过持有超级表权限绕过对特定子表的保护（见威胁建模报告 T-BTAG-03）。FS 未显式描述权限校验粒度，依托 TDengine 现有 DDL 权限体系执行。
- **状态：** 通过
- **说明/依据：** TDengine 现有 `ALTER TABLE` 语句在 Mnode 侧对每个涉及的子表均执行独立权限校验，该功能沿用此机制；建议编码阶段通过代码评审确认超级表 WHERE 展开路径同样经过子表级校验。

#### 2.2 数据安全

- **评审意见与发现：** 该功能操作的标签数据为设备元数据（如设备编号、位置等业务属性），不涉及时序测量值或个人敏感数据。标签数据的存储和传输安全由 TDengine 现有机制统一处理，无新增加密或隔离需求。
- **状态：** 不适用
- **说明/依据：** 功能未引入新的数据存储路径或加密需求，不适用本维度评审。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** 本功能最主要的新增输入验证关注点集中在 `REGEXP_REPLACE` 的正则表达式参数上（FS 第 3.2.2 节）。恶意或构造不当的正则表达式可能触发正则引擎的回溯爆炸（ReDoS），导致 Vnode 处理线程长时间阻塞（见威胁建模报告 T-BTAG-01）。FS 已对其他输入约束做出明确说明：`WHERE` 条件不允许数据列和聚合函数、标签值表达式结果类型必须兼容目标标签类型、`REGEXP_REPLACE` 仅适用于字符串类型标签，这些约束有效限制了输入攻击面。FS 第 3.2.2 节明确"此语法仅供内部使用，不对外公开"，进一步降低了被外部攻击者滥用的风险。
- **状态：** 通过
- **说明/依据：** FS 已对输入类型和语法范围做出明确约束；ReDoS 风险由 TDengine 现有查询超时机制（`queryTimeoutMs`）兜底，超时后终止执行并返回错误，与现有复杂查询处理行为一致。

#### 2.4 会话与通信安全

- **评审意见与发现：** 该功能为 DDL 语法扩展，通过 TDengine 现有客户端连接通道（TCP/taosc 或 REST API）提交，不引入任何新的通信协议、连接类型或会话状态管理机制。通信安全（TLS、认证令牌）由现有框架统一处理。
- **状态：** 不适用
- **说明/依据：** 无新引入的通信路径或会话管理变更。

#### 2.5 安全日志与监控

- **评审意见与发现：** FS 第 10 节（可观测性）标注为"不涉及"。`ALTER TABLE` 属于 DDL 操作，执行记录会通过 TDengine 现有慢查询日志和审计日志机制完整保留（含语句文本、执行时间、用户信息），满足基本的操作溯源要求。批量修改操作影响范围较广（可波及千万级子表），建议通过慢查询日志监控此类操作的执行频率和耗时，识别异常批量操作行为。
- **状态：** 通过
- **说明/依据：** 依赖现有审计日志和慢查询日志机制，无需额外日志设计。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 对照威胁建模报告（TM-TSDB-BTAG-001）中识别的威胁：T-BTAG-01（ReDoS）由查询超时机制兜底；T-BTAG-02（大批量 DoS）由 Vnode 写入流控和背压机制约束；T-BTAG-03（越权修改）由 DDL 权限校验框架覆盖，编码阶段需确认子表级粒度；T-BTAG-04（部分失败数据不一致）为已知设计约束（FS 第 8.1 节明确声明），非新引入的安全漏洞；T-BTAG-05（WAL 消息篡改）受 TDengine 现有数据订阅框架的消息格式解析保护；T-BTAG-06（错误信息泄露）由现有统一错误处理层控制，不返回内部实现细节。
- **状态：** 通过
- **说明/依据：** 主要威胁均由现有框架机制覆盖，或已通过 FS 中明确的功能约束（内部专用、语法限制）收窄攻击面。

#### 2.7 默认安全配置

- **评审意见与发现：** FS 第 3.2.2 节明确 `REGEXP_REPLACE` 超级表批量修改语法"仅供内部使用，不对外公开"，默认不暴露给外部用户，从配置层面限制了攻击面。逐表模式（FS 第 3.1 节）作为公开 API 扩展，延续现有 `ALTER TABLE` 的权限要求，无默认安全配置退化。
- **状态：** 通过
- **说明/依据：** 高风险的超级表模式默认不对外公开，与最小暴露原则一致。

#### 2.8 依赖组件安全

- **评审意见与发现：** 该功能依赖 TDengine 现有 SQL 解析器、Mnode 执行框架、Vnode 正则引擎（用于 REGEXP_REPLACE）以及数据订阅/流计算的 WAL 消费模块，不引入任何新的第三方依赖库。正则引擎为 TDengine 内部复用的已有实现，其安全性与现有 REGEXP 查询函数一致。
- **状态：** 不适用
- **说明/依据：** 无新增外部依赖组件。

#### 2.9 隐私设计

- **评审意见与发现：** 该功能操作的标签数据为设备元数据，不涉及个人身份信息（PII）或隐私数据的特殊处理逻辑。隐私数据访问控制由现有权限体系保障。
- **状态：** 不适用
- **说明/依据：** 无隐私相关设计变更。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** FS 第 6 节（兼容性）指出 `ALTER TABLE` 消息格式有变更，新旧版本客户端与服务端之间存在双向不兼容，需在版本升级/降级场景下注意。FS 第 3.3 节涉及数据订阅 WAL 数据结构变更（多表和超级表两种情况），以及 `taosAlterTable` 写入逻辑修改，这些变更影响到数据迁移管道的完整性，运维时需确保数据订阅消费端与服务端版本一致，防止因版本错配导致订阅数据解析异常。FS 第 3.2.2 节对本期超级表语法的约束（仅支持 `REGEXP_REPLACE`，不支持任意函数/表达式）明确了版本边界，后续扩展至通用表达式时需重新评审安全影响。
- **状态：** 通过
- **说明/依据：** 兼容性约束已在 FS 中明确声明，版本管理由现有发布流程保障；数据订阅变更范围明确，消费端版本一致性由运维操作规范约束。

### 3. 评审结论

1. **总体安全风险等级：** 低风险
   - 该功能为 SQL DDL 语法扩展，未引入新的认证机制、外部接口或第三方依赖。主要新增攻击面为 REGEXP_REPLACE 正则计算（存在 ReDoS 潜在风险）和超级表范围批量写入路径（存在 DoS 和越权风险），均由 TDengine 现有查询超时、写入流控和权限校验机制覆盖。内部专用语法不对外公开的设计决策进一步收窄了攻击面。

2. **评审结论：** 通过
   - 准予进入下一阶段（编码实现）。建议编码阶段通过代码评审确认以下两点：（1）超级表 WHERE 展开路径对每个目标子表均执行独立 WRITE 权限校验；（2）REGEXP_REPLACE 正则匹配执行受现有查询超时机制约束。
