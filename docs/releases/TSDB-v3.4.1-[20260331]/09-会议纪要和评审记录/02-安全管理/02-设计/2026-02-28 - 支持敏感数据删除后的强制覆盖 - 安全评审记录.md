1. **评审目的：** 评估「支持敏感数据删除后的强制覆盖」的技术设计方案是否有效、合理地实现了安全需求，识别架构与详细设计中的安全缺陷，并提出改进建议。

### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** `secure_delete` 属性的开启与关闭通过标准 SQL 语句（`ALTER DATABASE`/`ALTER STABLE`）完成，受 TDengine 现有 RBAC 访问控制体系约束；`SECURE_DELETE` 关键字的使用权限与 `DELETE` 命令一致，无需额外权限设计。FS 未单独定义新角色或新权限，设计合理。
- **状态：** 通过
- **说明/依据：** 本功能复用现有权限体系，未引入新的认证或授权设计需求，现有最小权限原则可覆盖。

#### 2.2 数据安全

- **评审意见与发现：** 设计提供零值覆盖（`secure_erase_mode=0`）和随机数据覆盖（`secure_erase_mode=1`）两种模式，覆盖操作在 `DELETE` 语句返回前同步执行，确保调用方获得结果时原始物理存储已被覆盖（FS 第4.3节）。密码数据通过直接更新磁盘文件处理，不走覆盖流程，逻辑合理（FS 第6节第1点）。需注意：SSD/NVMe 固件磨损均衡机制可能在硬件层保留原始数据，属已知硬件限制，建议在文档中告知用户；已有备份中的数据不受本功能保护，亦应在文档中明确说明。
- **状态：** 通过
- **说明/依据：** 核心安全目标（软件层不可恢复）已通过同步覆盖设计实现。SSD 固件层残留属硬件限制，超出软件能力范围，属可接受风险，在文档中说明即可。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** `secure_erase_mode` 参数有明确的取值范围约束（0 或 1），`SECURE_DELETE` 关键字作为 SQL 语法扩展经由现有解析器处理。FS 第10节和第11节均标注"无"约束与错误，遵循现有错误处理规范，不会因本功能引入新的信息泄露点。
- **状态：** 通过
- **说明/依据：** 参数校验由配置框架和 SQL 解析器保障，无额外验证需求。

#### 2.4 会话与通信安全

- **评审意见与发现：** 安全删除为存储引擎内部操作，覆盖写入在本地 Vnode 执行，不涉及新的网络通信路径或会话管理需求。
- **状态：** 不适用
- **说明/依据：** 本功能不引入新的通信接口，现有 TLS 传输层保护完整覆盖。

#### 2.5 安全日志与监控

- **评审意见与发现：** FS 第6节第4点及第12节第2点明确要求对安全删除操作和定期清理（compact）均记录审计日志，设计意图明确。审计日志应包含操作时间、执行用户、操作对象（库/表名）、删除的时间范围、所用覆盖模式及操作结果，依托现有审计框架实现。
- **状态：** 通过
- **说明/依据：** 审计日志需求已在 FS 中明确，对 `ALTER DATABASE/STABLE SET secure_delete` 的修改操作亦应纳入审计范围，建议实现时确认覆盖。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 针对敏感数据删除后被恢复的核心威胁，设计通过同步覆盖语义（DELETE 返回前完成物理写入）直接缓解；并发安全由同步执行保证；定期 compact 作为补充机制处理逻辑删除残留数据（T-SECDEL-06）。对于高权限用户先关闭 `secure_delete` 再删除的内部威胁（T-SECDEL-01），由 RBAC 及审计日志形成联合防护。详见威胁建模报告 T-SECDEL-01 至 T-SECDEL-06。
- **状态：** 通过
- **说明/依据：** 主要威胁已有对应的设计缓解措施，残余风险（SSD 固件残留、备份残留）属可接受范围。

#### 2.7 默认安全配置

- **评审意见与发现：** `secure_delete` 默认关闭（FS 第4.2.1节），符合最小功能原则，仅对有需求的库/表显式开启；`secure_erase_mode` 默认为零值填充（0），满足基本安全需求，用户可按更高安全级别升级为随机数据覆盖（1）。
- **状态：** 通过
- **说明/依据：** 默认配置安全，不会对现有业务产生非预期影响（FS 第7节）。

#### 2.8 依赖组件安全

- **评审意见与发现：** 本功能完全依托 TDengine 内部存储引擎（Vnode）实现覆盖写入，定期清理依赖企业版内置 compact 能力，未引入任何新的第三方库或外部服务。
- **状态：** 不适用
- **说明/依据：** 无新增外部依赖，无第三方组件安全风险。

#### 2.9 隐私设计

- **评审意见与发现：** 本功能是实现数据主体"被遗忘权"（Right to Erasure）的关键技术手段，通过物理覆盖确保敏感数据删除后不可从存储层恢复，直接满足数据安全合规（如 GDPR、等保）对敏感数据销毁的要求（FS 第2节背景）。
- **状态：** 通过
- **说明/依据：** 功能目标与隐私数据销毁合规需求高度吻合，设计方案可支撑合规交付。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** 单次删除耗时增加 15%~35%（FS 第5节），FS 建议仅对敏感表开启，运维建议合理。企业版通过 `COMPACT_INTERVAL` 实现自动定期清理，社区版用户依赖手动 compact 或 `SECURE_DELETE` 关键字直接覆盖，功能边界清晰。`SHOW CREATE TABLE`/`SHOW DATABASES` 可观察 `secure_delete` 属性（FS 第12节），运维可见性满足。
- **状态：** 通过
- **说明/依据：** 性能影响已量化并给出使用建议，可扩展性良好，运维接口完整。

### 3. 评审结论

1. **总体安全风险等级：**
   - **低风险**：安全设计完备，同步覆盖机制有效实现了敏感数据物理删除的安全需求，可进入开发阶段。

2. **评审结论：**
   - **通过**：准予进入下一阶段（编码实现）。各安全评审维度均通过，无阻断性安全设计缺陷。建议在官网文档中补充 SSD 固件磨损均衡限制及备份数据残留的说明，帮助用户建立正确的安全预期。
