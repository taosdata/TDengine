### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** 文档描述的所有修复操作（停止服务、删除/备份 WAL 目录、执行 `taosd -r`、修改 `current.json`）均需要操作系统级别的 root 或 taos 用户权限。该文档属于运维操作规范，依赖主机操作系统的账号认证体系而非 TDengine 自身的认证机制。文档隐含"操作者必须具有数据目录访问权限"的前提，与现有运维规范一致。`taosd -r` 修复模式通过操作系统进程权限自然限制了执行者身份，无需 TDengine 内部额外的认证设计。
- **状态：** 通过
- **说明/依据：** 修复操作依赖 OS 级别权限控制（sudo/su taos），与现有运维安全策略一致，不引入新的认证机制。

#### 2.2 数据安全

- **评审意见与发现：** 文档在 WAL 修复方法一（第 1.1.5 节）和 TDB 修复方法一（第 1.2.5 节）中建议将备份文件写入 `/tmp` 目录，例如 `cp -r /var/lib/taos/vnode/vnode1234/wal /tmp/wal_backup_vnode1234_$(date +%Y%m%d_%H%M%S)`。`/tmp` 目录通常对本机所有用户可读，若多用户共享主机，备份中的时序数据可能被非授权用户访问。建议将备份目标改为 `/var/lib/taos/backup/` 等受限目录，并确保权限为 700（仅 taos 用户可读）。此外，通过 `scp` 从副本节点拷贝 TDB 文件时（第 1.2.5 节方法一），依赖 SSH 传输加密，未引入明文传输风险。`walDeleteOnCorruption 1` 配置项（第 1.1.5 节方法二）会自动将损坏 WAL 备份至 `wal_bak` 目录后删除原目录，备份目录位于 VNode 数据路径下，权限受 taosd 进程管控，数据暴露面小于 `/tmp` 方案。
- **状态：** 通过
- **说明/依据：** 主要风险为备份路径建议不当（/tmp），但为可选操作步骤，文档已标注"可选但建议"。`walDeleteOnCorruption` 的自动备份路径相对安全。结合 T-FILECORR-02 所描述的威胁，此项整体风险低，已有替代的安全做法。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** 文档描述的修复操作均为手动 shell 命令，不涉及用户界面或 API 输入验证。`walDeleteOnCorruption` 配置项为布尔型（0/1），由配置文件解析层处理，不存在注入风险。`taosd -r` 修复模式通过命令行参数触发，参数值固定，无动态输入。修复过程中的日志输出（`tail -f /var/log/taos/taosdlog.?`）为只读监控，不涉及输出编码风险。
- **状态：** 不适用
- **说明/依据：** 此文档为运维操作规范，不涉及 API 输入或用户界面，无需专项输入验证设计。

#### 2.4 会话与通信安全

- **评审意见与发现：** TDB 多副本恢复方案（第 1.2.5 节方法一）使用 `scp` 进行跨节点文件传输，依赖 SSH 协议加密传输通道，符合现有集群节点间通信安全实践。修复操作在本地执行，不引入新的网络通信通道。`taosd -r` 模式为本地离线操作，不涉及网络通信。
- **状态：** 通过
- **说明/依据：** `scp` 基于 SSH，传输层加密有保障。本地修复操作无网络通信，无需额外安全配置。

#### 2.5 安全日志与监控

- **评审意见与发现：** 文档第 1.1.5 节（WAL 修复）、第 1.2.5 节（TDB 修复）和第 1.3.5 节（TSDB 修复）均包含"修复后验证"步骤，要求检查服务状态、数据完整性和系统日志，体现了一定的日志核查意识。`walDeleteOnCorruption 1` 触发的自动修复会生成系统日志记录。然而，手动执行的修复操作（删除 WAL 目录、修改 `current.json`、执行 `taosd -r`）属于 OS 层操作，在 TDengine 应用层审计日志中不会留下操作记录，仅依赖操作系统的 bash history 或审计工具（如 auditd）追溯，存在抵赖风险（见 T-FILECORR-05）。
- **状态：** 通过
- **说明/依据：** 该文档为运维规范，依赖 OS 级别审计能力。修复步骤中包含验证环节，日志核查有一定覆盖。操作审计的责任归属于运维安全体系，不属于本功能设计范畴。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 针对威胁建模报告中识别的威胁，评估如下：
  - **T-FILECORR-01（恶意篡改配置触发 WAL 自动删除）**：`walDeleteOnCorruption 1` 需要修改 `/etc/taos/taos.cfg`，该文件通常仅 root 可写，已通过 OS 权限隔离提供基本防护。
  - **T-FILECORR-02（备份目录信息泄露）**：文档建议备份至 `/tmp`，风险存在但为可选操作，实际风险低。
  - **T-FILECORR-03（`taosd -r` 模式滥用）**：taosd 进程执行需要 taos 用户权限，操作系统权限控制提供防护，非授权用户无法执行。
  - **T-FILECORR-04（scp 传输中间人攻击）**：依赖 SSH 主机密钥验证，首次建立连接后密钥固定，MITM 风险低。
  - **T-FILECORR-05（修复操作无应用层审计）**：已知局限，依赖运维侧 OS 审计工具补全。
- **状态：** 通过
- **说明/依据：** 所有威胁均为低至中风险，现有 OS 权限控制和 SSH 加密提供了基础防护。剩余风险通过运维规范可以接受。

#### 2.7 默认安全配置

- **评审意见与发现：** `walDeleteOnCorruption` 配置项默认值为 0（关闭），即系统默认不自动删除损坏 WAL，符合安全默认原则（fail-safe）——WAL 损坏时系统选择停止服务而非静默数据丢失。第 1.1.6 节的预防措施中，WAL 相关参数（`walLevel`、`walRetentionPeriod`、`walRollPeriod`）给出了合理的配置建议，未设置危险的默认值。
- **状态：** 通过
- **说明/依据：** `walDeleteOnCorruption` 默认关闭符合安全默认（fail-safe）原则，需要显式启用才会触发自动删除行为。

#### 2.8 依赖组件安全

- **评审意见与发现：** 文档中使用的运维工具均为标准系统工具：`systemctl`、`grep`、`cp`、`rm`、`scp`、`df`、`ls`、`gdb`、`taos` CLI。这些工具均属于操作系统自带或 TDengine 配套工具，无新增第三方依赖。`gdb` 用于分析 core dump（第 1.2.4 节），属于诊断工具，不参与修复执行链路，风险可控。
- **状态：** 不适用
- **说明/依据：** 无新增外部依赖，使用标准系统工具，安全特性已由操作系统和软件包管理系统维护。

#### 2.9 隐私设计

- **评审意见与发现：** TSDB 存储时序数据（传感器读数、设备状态等工业物联网数据），通常不含个人身份信息（PII）。修复方案不涉及个人数据采集或处理，无隐私合规需求。
- **状态：** 不适用
- **说明/依据：** 时序数据库场景下数据为工业/设备类数据，无个人隐私数据处理。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** 文档第 1.1.6 节（WAL 预防措施）系统性地涵盖了硬件基础设施、系统配置、运维管理、软件版本管理和监控告警五个维度，形成了完整的预防体系。多副本部署（至少 3 副本）的建议有效降低了单点数据损坏导致服务中断的风险。磁盘空间监控告警阈值建议（80%）是合理的运维实践。`taosd -r` 修复模式（第 1.2.5 节）需要完全停止服务，运维侧应建立变更管理流程，避免在业务高峰期执行，减少服务中断影响。
- **状态：** 通过
- **说明/依据：** 预防措施设计全面，多副本建议体现了高可用安全设计思想，运维安全责任界定清晰。

### 3. 评审结论

1. **总体安全风险等级：**
   - 低风险：本文档为 TSDB 文件损坏的运维修复规范，不引入新的网络接口、认证机制或数据处理逻辑。主要安全关注点为：临时备份文件建议写入 `/tmp` 目录（可通过运维规范纠正）、`walDeleteOnCorruption` 配置项的访问控制（已由 OS 权限保障）。整体设计遵循安全默认原则，依赖成熟的 OS 权限模型和 SSH 传输加密，风险可接受。
2. **评审结论：**
   - 通过：准予进入下一阶段（编码实现）。
