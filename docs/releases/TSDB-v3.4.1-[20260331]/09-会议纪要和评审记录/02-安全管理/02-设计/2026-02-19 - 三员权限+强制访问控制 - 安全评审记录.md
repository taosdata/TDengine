### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** FS 定义了完整的三权分立权限体系，将最高管理权限拆分为 SYSDBA（数据库运维）、SYSSEC（安全管理）、SYSAUDIT（审计管理）三个互斥角色（§3.1），职责边界清晰。启用强制三权分立的前置条件设计严格（§4.1.3.1），要求三个角色各有独立的非 root 有效持有者；启用后永久禁用 root（清除 superUser 标志及 enable 字段，§4.1.3.3），且不可逆，彻底消除超级用户单点安全风险。MAC 与 DAC 双重访问控制叠加执行，先检查 MAC 再检查 DAC，采用 Fast-Fail 设计（§4.2.1.1），并通过独立错误码区分 MAC 与 DAC 拒绝原因（`TSDB_CODE_MAC_NO_READ_UP`、`TSDB_CODE_MND_MAC_NO_WRITE_DOWN`）。仅 SYSSEC 可设置/修改 security_level，权责归属明确。
- **状态：** 通过
- **说明/依据：** FS §4.1.3.1："当前用户必须是 root（超级用户）或持有 SYSSEC 角色"；§4.1.3.3："将 root 用户的 enable 和 superUser 字段均置为 0"；§4.2.1.1："仅 SYSSEC 可以设置/修改用户和对象的安全等级"，MAC 先于 DAC 执行。

#### 2.2 数据安全

- **评审意见与发现：** FS 设计了五级安全等级体系（公开0 ~ 绝密4，§3.2），并基于 Bell-LaPadula 模型实施 NRU（禁止上读）和 NWD（禁止下写）规则，实现数据跨等级安全隔离（§4.2.1.1）。用户 security_level 采用区间表示 [min_level, max_level]，有效解决了等级调整期间的读写一致性问题（§4.2.1.1 callout）。审计库默认安全等级为 4（绝密，§4.2.1.2），提供最高等级保护。FS §6 已识别 vnode.json 中 security_level 被篡改的风险，并明确需结合配置文件加密使用，风险意识到位。
- **状态：** 通过
- **说明/依据：** FS §4.2.1.1 描述了完整的 NRU/NWD 规则及各操作的 MAC 检查逻辑；§6："针对 vnode.json 中的 security_level 被篡改的风险，需要结合配置文件加密使用"；§4.2.1.2 审计库 security_level 默认为 4。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** security_level 取值范围严格限制在 [0, 4]，越界时返回专用错误码 `TSDB_CODE_MAC_INVALID_SECURITY_LEVEL`（§11）。安全等级提升有校验约束：操作者的等级上限约束目标等级上限（`TSDB_CODE_MAC_LEVEL_ESCALATION`，§11）。用户/角色命名规则有明确白名单限制（§4.3），禁止 SYSTEM、ROOT 等保留关键词及特殊字符，防止命名混淆攻击。CREATE/ALTER 时对 security_level 参数语法有明确规范（§4.2.2.1）。
- **状态：** 通过
- **说明/依据：** FS §11 错误码表：`TSDB_CODE_MAC_INVALID_SECURITY_LEVEL`、`TSDB_CODE_MAC_LEVEL_ESCALATION`；§4.3 列举了7类禁止命名规则。

#### 2.4 会话与通信安全

- **评审意见与发现：** 本 FS 聚焦于权限控制逻辑（三权分立与 MAC），不涉及新的会话管理机制或通信协议设计。会话管理与通信安全依托 TDengine 现有认证与传输层保护体系，与本功能无直接交互设计。
- **状态：** 不适用
- **说明/依据：** 本功能为权限控制框架扩展，不修改认证流程、会话管理逻辑或通信协议。

#### 2.5 安全日志与监控

- **评审意见与发现：** FS §12.3 明确要求以下操作无论成功与否均记录审计日志和日志文件：SoD 通过命令行参数或 SQL 命令开启的动作、security_level 的设置和修改动作。可观测性设计完整：`show security_policies` 命令提供集群安全策略状态的实时查询（§12.1），含操作者、最后更新时间、状态描述；`show users` 和 `ins_users` 展示 `sec_levels` 列（§12.2），可用于审计用户安全等级配置；`ins_databases`、`ins_stables` 展示 `sec_level` 列（§4.2.4 测试用例 F2-T15 至 F2-T18），满足管理员监控需求。审计日志详细行为参考安全审计 FS，接口已明确定义。
- **状态：** 通过
- **说明/依据：** FS §12.3："SoD 通过命令行参数或 SQL 命令开启的动作，无论成功或失败，均会记录审计日志和日志文件。设置和修改 security_level 的动作，无论成功或失败，均会记录审计日志和日志文件。"

#### 2.6 威胁缓解机制

- **评审意见与发现：** 主要威胁缓解措施覆盖全面：（1）防超级用户滥用：强制永久禁用 root，不可恢复，superUser 标志清除（§4.1.3.3）；（2）防状态篡改：SoD 状态不设全局变量，而是随用户对象下发（§4.1.3.3 callout），降低全局标志被单点篡改的风险；（3）防角色空置：SoD 启用后，每个系统角色必须至少保留一个有效持有者，尝试撤销最后一个持有者的操作将被拒绝（测试用例 F1-T9，§4.1.4）；（4）防越权等级提升：`TSDB_CODE_MAC_LEVEL_ESCALATION` 限制 SYSSEC 不能将用户等级提升至超过自身等级（§11）；（5）防状态切换竞态：引入 mandatory(enforcing) 中间状态，期间禁止 DROP/DISABLE USER 及 REVOKE ROLE 操作（§4.1.3.2），保证 SoD 切换的原子性。详细威胁分析见威胁建模报告 TM-TSDB-MAC-SOD-001。
- **状态：** 通过
- **说明/依据：** FS §4.1.3.2、§4.1.3.3、§4.1.4（F1-T9）、§11；详见威胁建模报告 TM-TSDB-MAC-SOD-001（`docs/releases/TSDB-v3.4.1-[20260331]/02-安全管理/威胁建模/三员权限 + 强制访问控制 - 威胁建模报告.md`）。

#### 2.7 默认安全配置

- **评审意见与发现：** MAC 默认开启且不支持关闭（§4.2.1.1），体现"安全默认值"原则。普通用户默认 security_level 为 [0,1]，遵循最小权限原则（§4.2.1.2）。新建 DB 默认 security_level 继承 user.min_level（而非最高值），确保新建对象不过度提权（§4.2.1.2）。系统库 information_schema/performance_schema 默认等级为 0，保持公开可查（§4.2.1.2）。审计库默认等级为 4，最高保护。社区版中安全字段展示但不生效，边界清晰，不会误导用户（§9.3）。
- **状态：** 通过
- **说明/依据：** FS §4.2.1.1："MAC 默认开启，且不支持关闭"；§4.2.1.2 各元数据类型默认值表，用户默认 [0,1]，审计库默认 4。

#### 2.8 依赖组件安全

- **评审意见与发现：** 本功能的实现依赖 TDengine 现有 RBAC（DAC）权限体系正确运行，MAC 作为 DAC 之上的叠加层，不直接引入新的第三方库依赖。依赖安全审计 FS 中定义的审计日志机制（§12.3，有明确文档引用），接口边界清晰。内部依赖 SClusterObj、用户表等核心数据结构，其完整性保护是功能安全的基础，FS §6 已对此作出要求。
- **状态：** 通过
- **说明/依据：** FS §4.2.1.1："MAC 在 DAC 之上叠加执行"；§12.3 引用安全审计 FS；无新增第三方库依赖。

#### 2.9 隐私设计

- **评审意见与发现：** 本功能为权限控制框架，不涉及个人可识别信息（PII）的收集、存储或处理，无专项隐私设计需求。用户 security_level 信息通过 `show users` 可查，但属于系统管理信息，可见范围受到 DAC 权限控制。
- **状态：** 不适用
- **说明/依据：** 本功能为系统安全架构扩展，不处理隐私数据。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** 升级安全性设计合理：仅支持停机升级，不支持滚动升级和降级（§7）；升级后自动赋予合理 security_level（root 为 [0,4]，普通用户按拥有角色取并集，DB/STable 默认为 0 以保障存量访问不中断，§7）。SoD 切换过程中的一致性保护设计完善，mandatory(initial) 和 mandatory(enforcing) 两个中间状态设计科学（§12.1），防止状态转换期间的并发破坏。运维最佳实践和注意事项有专节说明（§8、§9），提供了等级提升/降级的详细操作步骤。社区版行为边界明确（§9.3、§10），字段展示但控制逻辑不生效，防止社区版用户误认为安全功能已启用。
- **状态：** 通过
- **说明/依据：** FS §7 升级兼容性；§12.1 show security_policies 四种状态设计；§8.1/§8.2 运维最佳实践和注意事项；§9.3/§10 社区版边界说明。

### 3. 评审结论

1. **总体安全风险等级：** 低风险
   - 三权分立与强制访问控制设计体系完整、层次清晰，采用 MAC+DAC 双重验证、多重防篡改机制；Bell-LaPadula 模型的正式安全理论保障了访问控制的完备性。安全默认值配置合理（MAC 默认开启、root 永久禁用不可逆）。vnode.json 配置文件加密为已识别的改善项，不构成阻断性安全缺陷。

2. **评审结论：** 有条件通过
   - 需完成"后续行动项"中的项目，并经安全代表确认后，方可进入下一阶段。
