### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** FS 设计了 token 作为 TMQ consumer 的身份认证方式，通过新增配置参数 `td.connect.token` 实现。具体设计要点：（1）Token 由 `CREATE TOKEN` 命令生成，与 TDengine 现有 token 管理体系集成，认证来源可信；（2）Token 优先级明确高于用户名/密码，不存在优先级混淆问题；（3）Token 有效性通过 consumer 心跳机制定期向 mnode 验证，能动态感知 token 到期、被删除或被禁用状态；（4）`tmq_t` 结构新增 `tokenCode` 字段，使用原子操作保证多线程并发安全；（5）Token 失效时 `tmq_consumer_poll` 返回 NULL 并通过 `terrno` 携带错误码，提供了明确通知机制，且 token 恢复后可自动继续消费，体现良好的可恢复性。
- **状态：** 通过
- **说明/依据：** 认证方案集成现有 token 体系，token 优先级、有效性校验、失效响应及多线程安全均有明确设计，整体认证逻辑完整可靠。

#### 2.2 数据安全

- **评审意见与发现：** FS 未单独描述 token 参数在客户端的存储安全，但 `td.connect.token` 作为连接参数的处理方式与现有 `td.connect.password` 一致，其传输安全依赖 TDengine 现有连接层加密机制。FS 安全章节标注"不涉及"，数据安全属于平台层已覆盖范围。
- **状态：** 通过
- **说明/依据：** Token 的数据安全保护与现有密码参数处于同等保护水位，无需额外设计独立加密方案；Token 存储安全属于客户端配置管理最佳实践范畴，超出本功能设计责任边界。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** Token 格式与合法性校验由 mnode 服务端负责，错误类型为"token 不存在、不合法、无效"三类通用描述，通过 `taos_errstr(NULL)` 返回给调用方。错误信息粒度适当，未过度暴露系统内部区分逻辑，不存在敏感信息泄露风险（详见 T-SUBTK-04 分析，枚举风险为低危）。
- **状态：** 通过
- **说明/依据：** 输入的 token 值经服务端 mnode 权威校验，错误提示为通用性描述，未在错误消息中暴露敏感系统信息。

#### 2.4 会话与通信安全

- **评审意见与发现：** Token 通过 `tmq_consumer_new` 创建连接时传递，连接建立后的网络传输遵循 TDengine 现有通信安全机制。心跳检测通过向 mnode 发送消息自动附带 token 有效性校验，未引入新的通信信道或绕过现有安全控制。
- **状态：** 通过
- **说明/依据：** 通信安全依托 TDengine 现有连接框架，本功能不引入额外的外部通信风险面。

#### 2.5 安全日志与监控

- **评审意见与发现：** FS 可观测性章节标注"不涉及"，未设计针对 token 认证失败或 token 失效事件的专项安全日志。从安全监控视角，审计日志属于平台层统一能力，本功能定位为认证方式的简单扩展，现阶段不单独引入日志体系。
- **状态：** 不适用
- **说明/依据：** 日志审计能力由平台层统一覆盖，非本功能设计范围，建议后续在平台层统一补充 token 认证的审计日志（见 TM-TSDB-SUBTK-001 T-SUBTK-05）。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 针对威胁建模（参见 TM-TSDB-SUBTK-001）识别的主要威胁，设计中的缓解措施如下：T-SUBTK-01（凭证泄露）—— 与现有密码参数风险同级，通过文档说明缓解；T-SUBTK-02（心跳延迟窗口）—— 可接受的设计折衷，通过操作文档告知管理员；T-SUBTK-03（权限混淆）—— token 优先级规则在 FS 中明确定义；T-SUBTK-04（错误枚举）—— 低危可接受。
- **状态：** 通过
- **说明/依据：** 主要威胁场景均有对应缓解措施，核心依赖 mnode 侧 token 权威管理和即时撤销能力（禁用/删除 token 后心跳周期内生效）。

#### 2.7 默认安全配置

- **评审意见与发现：** Token 认证为用户主动选配（设置 `td.connect.token` 参数），未配置时系统行为与原有版本完全一致，默认安全状态无退化。opt-in 设计保证了向后兼容性。
- **状态：** 通过
- **说明/依据：** 默认不启用 token 认证，现有 consumer 不受影响，无安全配置默认变更风险。

#### 2.8 依赖组件安全

- **评审意见与发现：** 本功能依赖 TDengine 现有 token 管理体系（`CREATE TOKEN` 命令、mnode token 管理模块），token 生命周期由 mnode 集中控制，无新增第三方库或外部服务依赖。
- **状态：** 通过
- **说明/依据：** 复用经过评审的基础组件，无引入新依赖风险。

#### 2.9 隐私设计

- **评审意见与发现：** 本功能处理的是数据库连接凭证（token），不涉及个人身份信息（PII）或隐私数据，无隐私设计需求。
- **状态：** 不适用
- **说明/依据：** 功能范围内无个人隐私数据处理需求。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** （1）Token 撤销机制完备：通过禁用（disable）或删除 token，可在心跳周期内中止正在进行的订阅消费，撤销响应时间可接受；（2）恢复能力良好：token 恢复有效后消费者可自动继续拉取数据，无需人工重建连接；（3）多线程安全：`tokenCode` 字段原子操作保证并发场景下状态一致性，运维风险低。
- **状态：** 通过
- **说明/依据：** Token 撤销与恢复的生命周期管理设计完整，运维安全风险低。

   - 安全设计完备，token 认证复用现有安全体系，核心设计（原子操作、心跳校验、即时撤销）合理，能有效实现安全需求，可进入开发阶段。
2. **评审结论：** 通过
