### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** CAPTCHA 作为登录辅助认证措施，与用户名/密码认证组合使用。FS §3 设计原则明确"服务端强校验：开关启用时，登录请求必须携带验证码且校验通过"，保证了服务端强制执行不可绕过。`/api/-/login-options` 和 `/api/-/captcha` 接口为无认证公开接口，符合登录前获取选项的合理需求。`/api/-/login` 接口在开关开启时对 captcha 字段做强校验，缺失或错误均返回 HTTP 401。
- **状态：** 通过
- **说明/依据：** 认证逻辑完整，服务端校验路径清晰，不存在绕过路径。

#### 2.2 数据安全

- **评审意见与发现：** 验证码本身不属于敏感数据，但需确保传输安全。FS §9 运维章节明确建议同时开启 HTTPS。服务端缓存 key 为 `captcha-<username>`，username 为后端内部数据，不对外暴露。FS §7 安全章节明确要求"不能在日志中记录用户输入的验证码明文"，数据不落地保护措施到位。验证码校验通过后立即从缓存删除（FS §5.2.3），不存在重复使用风险。
- **状态：** 通过
- **说明/依据：** 验证码数据生命周期短，日志脱敏要求明确，整体数据安全设计合理。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** `/api/-/captcha` 接口对 `phone_email` 参数做了空值校验，为空时返回 `400 application/json`（FS §5.2.2）。登录失败时错误响应使用固定错误码字符串（`captchaRequired`、`captchaInputError`），不暴露内部实现细节。前端 i18n 错误提示同样采用固定 key，不泄露服务端内部信息。
- **状态：** 通过
- **说明/依据：** 错误信息设计合理，复用已有注册接口的输入验证逻辑，无新增验证风险。

#### 2.4 会话与通信安全

- **评审意见与发现：** 验证码采用一次性使用机制，校验通过后立即从缓存删除（FS §5.2.3），有效防止验证码重用。缓存具备 5 分钟过期机制（FS §6），限制了有效攻击窗口。前端通过 `ts` 参数实现浏览器缓存 bust（FS §5.2.2），确保每次刷新获取新图片。FS §9 建议搭配 HTTPS 使用，通信加密依赖外部基础设施。
- **状态：** 通过
- **说明/依据：** 一次性使用 + 短期过期的双重机制有效限制验证码重用攻击面。

#### 2.5 安全日志与监控

- **评审意见与发现：** FS §7 明确要求不在日志中记录验证码明文，满足日志脱敏基本要求。CAPTCHA 作为辅助安全措施，验证码校验失败事件（`captchaInputError`）会通过 HTTP 401 响应体反馈给客户端，可依赖上层登录失败的已有日志审计链路覆盖。
- **状态：** 通过
- **说明/依据：** 验证码相关安全日志需求已被现有登录失败日志机制覆盖，无需额外要求。

#### 2.6 威胁缓解机制

- **评审意见与发现：** FS §7 明确界定 CAPTCHA 的安全定位为"增加攻击成本的辅助措施，不替代密码强度、限速、锁定等策略"，并在 §9 建议搭配 HTTPS、反向代理限速使用，体现了纵深防御思路。针对已识别的主要威胁（见威胁建模报告 TM-TSDB-LOGCAP-001）：验证码重用（T-LOGCAP-04）通过一次性使用机制缓解；缓存耗尽（T-LOGCAP-03）依赖反向代理限速缓解；CAPTCHA 爆破（T-LOGCAP-02）通过图片验证码本身的人机识别能力缓解。
- **状态：** 通过
- **说明/依据：** 设计文档对安全定位的准确描述体现了良好的安全意识，缓解措施与威胁等级匹配。

#### 2.7 默认安全配置

- **评审意见与发现：** CAPTCHA 默认不启用（FS §3.1"默认不启用，显式配置才启用"），符合最小影响原则，不改变现有用户体验。启用方式通过三种等价途径（配置文件/环境变量/CLI，FS §5.1）明确定义，无歧义，管理员可根据部署环境选择合适的配置方式。
- **状态：** 通过
- **说明/依据：** 默认关闭策略合理，显式启用流程清晰，不存在意外激活风险。

#### 2.8 依赖组件安全

- **评审意见与发现：** 本功能复用已有注册流程的 `/api/-/captcha` 接口（FS §3.3、§5.2.2），未引入新的第三方依赖。缓存机制沿用已有 5 分钟过期逻辑（FS §6），前端复用注册页弹窗结构和样式（FS §5.3.2）。所依赖的组件已在注册功能中经过验证。
- **状态：** 通过
- **说明/依据：** 无新增外部依赖，复用已审查组件，降低了引入新风险的可能性。

#### 2.9 隐私设计

- **评审意见与发现：** 功能仅处理用户名和验证码字符串，不涉及个人敏感信息的额外收集或存储。服务端缓存条目（`captcha-<username>`）在 5 分钟后自动过期删除，数据最小化原则得到满足。
- **状态：** 通过
- **说明/依据：** 无新增个人信息处理，数据生命周期短，隐私风险极低。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** FS §15 明确要求更新企业版 Explorer 配置文档，运维变更管理完整。§9 运维章节对功能启用后的用户体验影响和推荐搭配策略有清晰说明，便于运维人员正确使用。功能通过配置热开关控制，具备良好的可运维性。
- **状态：** 通过
- **说明/依据：** 运维文档更新需求已识别，配置管理设计清晰。

2. **评审结论：**
   - **通过**：设计方案安全合理，准予进入下一阶段（编码实现）。
