### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。该功能为构建系统层面的改进——将 TDengine 的第三方依赖管理从 CMake ExternalProject 模式迁移到 Conan 包管理器模式，主要影响构建过程，不改变运行时行为。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** Conan 包管理器集成属于构建工具链变更，不涉及 TDengine 运行时的身份认证与访问控制机制。FS 中未引入新的用户认证流程或权限模型，所有的包操作在开发者本地或 CI 环境中进行。
- **状态：** 不适用
- **说明/依据：** 该功能仅影响编译构建阶段，不改变 TDengine 服务端或客户端的认证授权逻辑，无需评审此维度。

#### 2.2 数据安全

- **评审意见与发现：** 该功能不涉及用户数据的存储、传输或处理。Conan 本地缓存（`~/.conan2`）中存储的是预编译二进制包和包元数据，不包含业务敏感数据。FS 第 19 节提到了包完整性验证（sha256 校验），确保下载的包未被篡改。
- **状态：** 通过
- **说明/依据：** Conan 在下载包时会自动验证 sha256 校验和（FS 第 19.1 节），确保包内容完整性。本地缓存仅存储构建产物，不涉及业务数据安全。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** 该功能不涉及运行时的外部输入处理。构建过程中的输入主要是 `conanfile.py` 配置文件和 Conan 包元数据，均由开发者或 CI 系统控制。FS 中自定义包配方（cppstub、fast-lzma2、avro-c）的 `test_package` 目录包含基本的功能验证测试。
- **状态：** 不适用
- **说明/依据：** 构建工具链无运行时输入/输出验证需求。自定义包配方中的构建脚本由团队内部维护和审查。

#### 2.4 会话与通信安全

- **评审意见与发现：** Conan 从远程仓库下载包时使用 HTTPS 协议（ConanCenter 默认使用 HTTPS）。FS 第 22.1 节提到了私有仓库配置（`conan remote add private-repo https://private.conan.io`），使用 HTTPS 链接。通信安全依赖 Conan 工具本身的 TLS 实现。
- **状态：** 通过
- **说明/依据：** Conan 2.x 默认使用 HTTPS 与远程仓库通信，ConanCenter 官方仓库强制 HTTPS。FS 中示例的私有仓库地址也使用 HTTPS 协议，满足传输安全要求。

#### 2.5 安全日志与监控

- **评审意见与发现：** 该功能为构建工具集成，不影响 TDengine 运行时的安全日志与监控体系。Conan 自身提供详细的构建日志（可通过 `-vvv` 参数启用），用于排查构建问题。FS 第 20.1 节提到依赖审计能力（`conan graph info`），可生成依赖关系图。
- **状态：** 不适用
- **说明/依据：** 构建阶段的日志由 Conan 和 CMake 工具链自行管理，不属于产品运行时安全日志范畴。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 针对构建供应链安全威胁，FS 设计了以下缓解措施：（1）包完整性校验——Conan 的 `get()` 函数支持 sha256 校验（FS 第 19.1 节）；（2）版本锁定——`conanfile.py` 中所有依赖均指定了精确版本号（FS 第 4.2.3 节）；（3）依赖锁文件——支持 `conan lock create` 生成锁文件（FS 第 20.1 节）；（4）离线构建——支持缓存导出/导入（FS 第 24.1 节），降低对外部网络的依赖。参见威胁建模报告 T-CONAN-01 至 T-CONAN-07 的分析。
- **状态：** 通过
- **说明/依据：** FS 已覆盖了供应链安全的关键缓解措施：完整性校验、版本固定、锁文件和离线构建能力。对于自定义包（cppstub、fast-lzma2、avro-c），源码随项目仓库管理，降低了外部供应链风险。

#### 2.7 默认安全配置

- **评审意见与发现：** FS 中默认配置具有以下安全特性：（1）所有依赖默认静态链接（`self.options["*"].shared = False`，FS 第 4.2.4 节），避免动态库劫持风险；（2）默认启用 fPIC（`fPIC = True`），支持 ASLR 地址随机化；（3）OpenSSL 使用较新版本（3.6.0），与 libcurl 配合使用 TLS。
- **状态：** 通过
- **说明/依据：** 默认静态链接是 C/C++ 项目的安全最佳实践之一，减少了运行时动态库替换攻击面。依赖版本选择较新且稳定的版本，降低已知漏洞风险。

#### 2.8 依赖组件安全

- **评审意见与发现：** 该功能的核心正是第三方依赖管理。FS 附录 A 列出了 19 个已迁移依赖，版本均为明确固定版本。主要安全相关依赖：（1）OpenSSL 3.6.0 — 密码学基础库，版本较新；（2）libcurl 8.2.1 — HTTP 客户端库，配置了 OpenSSL 后端和 zlib 压缩；（3）RocksDB 9.7.4 — 存储引擎。三个自定义包（cppstub、fast-lzma2、avro-c）由团队内部维护，源码随项目管理。FS 提供了 `conan graph info` 和 `conan lock create` 工具用于依赖审计和锁定。
- **状态：** 通过
- **说明/依据：** 所有依赖版本明确固定，避免了隐式升级风险。核心安全依赖（OpenSSL、libcurl）使用较新版本。自定义包源码可控。建议在后续实践中定期执行依赖版本审计。

#### 2.9 隐私设计

- **评审意见与发现：** 该功能为构建工具链集成，不涉及用户个人信息的收集、存储或处理，无隐私设计需求。
- **状态：** 不适用
- **说明/依据：** 构建系统变更不影响产品的隐私功能。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** （1）**可扩展性**：FS 设计支持逐步迁移（附录 B 列出了待迁移依赖），新依赖可通过修改 `conanfile.py` 方便添加，扩展性良好；（2）**CI/CD 安全**：FS 第 29.1 节描述了 CI 集成方案，使用 `pip install conan` 安装工具并缓存 `~/.conan2`，CI 缓存安全依赖 CI 平台自身的隔离机制；（3）**构建可重现性**：支持依赖锁文件和离线缓存，确保构建一致性；（4）**向后兼容**：FS 明确 ExternalProject 和 Conan 可共存，不引入破坏性变更。
- **状态：** 通过
- **说明/依据：** 设计充分考虑了可扩展性和向后兼容性。CI/CD 缓存安全建议依赖 CI 平台的隔离机制保障。

### 3. 评审结论

1. **总体安全风险等级：**
    - **低风险**：该功能为构建工具链优化，不引入新的运行时攻击面。安全设计完备，Conan 自身提供了完整性校验、版本锁定、离线构建等供应链安全能力，可进入开发阶段。

2. **评审结论：**
    - **通过**：准予进入下一阶段（编码实现）。该功能设计合理，安全机制充分，构建供应链风险已得到有效控制。
