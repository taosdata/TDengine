### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** FS 新增了 Token 认证作为 xnoded 连接 taosd 的认证方式，与原有的用户名/密码认证并列支持，认证逻辑清晰。具体设计要点：（1）FS 4.4 明确了三种认证方式的优先级顺序：TOKEN > USER/PASS > 自动创建默认 Token，优先级无歧义；（2）自动创建的默认 Token 专用账户名为 `xnode`，是独立的最小权限服务账户，不复用 `root` 等管理账户，符合最小权限原则；（3）ALTER XNODE 支持凭证动态变更，可从用户名密码切换至 Token 或反向切换，满足凭证轮换需求；（4）Token 及用户名密码的合法性校验（空值、长度）在 FS 4.5 节有明确设计。
- **状态：** 通过
- **说明/依据：** 认证方案设计合理，优先级规则明确，服务账户遵循最小权限原则，凭证变更机制完备。

#### 2.2 数据安全

- **评审意见与发现：** FS 安全章节（第6节）明确声明：（1）"Token 通过加密方式创建"，说明 Token 值本身具有加密保护；（2）"无任何位置可以打印显示 Token 信息"，Token 在日志、响应及命令行输出中均不可见，有效防止凭证泄露。Token 存储在 `SXnodeUserPassObj` 结构体中，并通过 `SRWLatch` 读写锁保护并发访问。xnoded 启动时通过环境变量 `XNODED_TOKEN` 传递 Token，这是父子进程间传递敏感参数的常见模式，在可信进程边界内可接受。`passIsMd5` 字段表明密码走 MD5 哈希（历史遗留设计），属于平台层已知问题，不在本次功能评审范围内。
- **状态：** 通过
- **说明/依据：** Token 不在任何位置明文显示，加密创建，内存访问有读写锁保护；环境变量传递为进程内部通信标准模式，风险可控。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** FS 4.5 节对所有外部输入均设计了明确校验：（1）Token 空值检查（`Xnode token should not be empty`）；（2）Token 长度合法性检查（`Xnode token length is illegal`）；（3）用户名/密码空值检查（`xnode user should not be NULL or empty`，`xnode password should not be NULL or empty`）。错误信息描述充分但无敏感数据泄露，未在消息中回显用户输入内容。
- **状态：** 通过
- **说明/依据：** 关键输入均有格式与内容校验，错误信息设计合理，无过度信息披露。

#### 2.4 会话与通信安全

- **评审意见与发现：** xnoded 使用 Token 或用户名密码连接 taosd 的通信安全依赖 TDengine 现有连接框架。Token 通过环境变量 `XNODED_TOKEN` 由 mnode 传递给 xnoded 子进程，属于系统内部进程通信路径，在同一主机可信边界内。本功能不引入新的外部通信信道，无需额外的 TLS 配置。
- **状态：** 通过
- **说明/依据：** 通信安全依托平台层已有机制，进程间传参为系统内部路径，未扩大外部攻击面。

#### 2.5 安全日志与监控

- **评审意见与发现：** FS 第11节（可观测性）说明 xnoded 重启时会记录相关日志；运维章节（第7节）建议监控 `SHOW TOKENS` 中的 `__xnode__` Token 状态。FS 未专项设计 CREATE/ALTER XNODE 操作的安全审计日志，属于平台层审计能力的统一覆盖范围。
- **状态：** 不适用
- **说明/依据：** 安全审计日志能力由平台层统一覆盖，本功能不单独引入日志体系；SHOW TOKENS 提供了基本的运维可视性。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 针对威胁建模（参见 TM-TSDB-XNTKN-001）识别的主要威胁，设计中的缓解措施如下：T-XNTKN-01（环境变量信息泄露）—— 属于系统内部进程通信，可信边界内可接受，风险中等；T-XNTKN-02（默认 Token 可见性）—— SHOW TOKENS 权限受 TDengine 访问控制约束；T-XNTKN-03（CREATE/ALTER XNODE 权限）—— 依赖 TDengine SQL 层权限控制；T-XNTKN-04/T-XNTKN-05/T-XNTKN-06 —— 均为低危，可接受。
- **状态：** 通过
- **说明/依据：** 核心威胁场景均有对应缓解措施或依赖平台层已有控制，无未覆盖的高危威胁。

#### 2.7 默认安全配置

- **评审意见与发现：** FS 9.2 节（约束和限制）明确：默认 Token 创建是企业版功能，社区版返回 `TSDB_CODE_OPS_NOT_SUPPORT`。企业版自动创建的默认 Token 采用独立的 `xnode` 账户而非 `root`，降低了默认配置的权限范围。运维建议（第7节）推荐新部署优先使用 Token 认证，方向合理。
- **状态：** 通过
- **说明/依据：** 自动创建的默认 Token 使用最小权限服务账户；企业版/社区版功能分层控制，默认安全状态合理。

#### 2.8 依赖组件安全

- **评审意见与发现：** 本功能使用 TDengine 内部数据类型 `CowStr` 管理 Token 字符串，使用 `SRWLatch` 读写锁保护并发访问。涉及的实现模块（parser、mnode、xnode、序列化）均为 TDengine 内部组件，无新增第三方库或外部服务依赖。
- **状态：** 通过
- **说明/依据：** 复用内部已有组件，无新增外部依赖风险。

#### 2.9 隐私设计

- **评审意见与发现：** 本功能涉及的数据为数据库连接凭证（Token/用户名密码），属于系统认证信息而非个人身份信息（PII），无隐私设计需求。
- **状态：** 不适用
- **说明/依据：** 功能范围内无个人隐私数据处理需求。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** （1）凭证轮换机制完备：ALTER XNODE 支持随时替换 Token 或用户名密码，FS 8.3 节专门描述了密码轮换场景，FS 8.4 节描述了凭证泄露应急替换流程，运维安全设计充分；（2）修改凭证后 xnoded 自动重启（约 2s 中断）属于设计折衷，FS 已在约束章节明确说明，运维人员可预期；（3）企业版/社区版功能分层（默认 Token 创建限企业版）有效控制了功能暴露面。
- **状态：** 通过
- **说明/依据：** 凭证生命周期管理设计完整，包含轮换、应急替换场景；功能限制清晰，运维安全风险低。

2. **评审结论：** 通过
