### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** FS §6 明确声明本特性"不引入新的网络接口与鉴权模型，触发的计算与通知权限控制沿用现有流计算权限体系：建流权限、读源表权限、写目标表权限、以及通知相关权限（若存在）保持不变"。新增的 `IDLE_TIMEOUT(duration)` 选项、`IDLE`/`RESUME` 事件类型均在现有 `CREATE STREAM` 权限框架内执行，不存在绕过认证或越权操作的新路径。
- **状态：** 通过
- **说明/依据：** 本特性为现有流计算 SQL 语法的扩展，全部操作均受原有权限体系约束，未引入新的认证要求或权限校验缺口。

#### 2.2 数据安全

- **评审意见与发现：** 本特性在运行时为每个分组维护的状态（`last_recv_time`、ACTIVE/IDLE 状态标志）均为内存数据，任务重启后清空（FS §4.2.4），不持久化到磁盘，不含业务原始数据行内容。通知 payload 中 `idleStart`/`idleEnd` 为 processing time 时间戳，`idleDurationMs` 为时间间隔，均不携带任何用户写入的时序业务数据（如传感器读数、设备状态值）。FS §6 亦明确"新增的日志与指标不应泄露敏感数据内容"。
- **状态：** 通过
- **说明/依据：** 分组状态仅含时间戳与状态枚举值，通知 payload 仅含元数据字段，设计上已规避业务数据暴露风险。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** FS §4.1.1 规定 `IDLE_TIMEOUT(duration)` 的有效范围为 `1s` 到 `10d`，超出范围或格式非法时 `CREATE STREAM` 必须报错（FS §10 约束、§11 排查表均有对应条目）。SQL 编译阶段设有语义互斥校验：当 `EVENT_TYPE(...)` 包含 `IDLE` 或 `RESUME` 时，禁止计算 SQL 引用 `_twstart`/`_twend`；反向亦然，仅由窗口事件触发的计算禁止引用 `_tidlestart`/`_tidleend`（FS §4.3.2）。错误提示应仅包含语义错误描述，FS §11 排查建议中的错误信息示例均未包含内部路径或系统状态。
- **状态：** 通过
- **说明/依据：** 参数校验与语义互斥校验在建流时前置完成，有效阻断畸形输入进入运行时。

#### 2.4 会话与通信安全

- **评审意见与发现：** 本特性的通知输出（`NOTIFY('ws://...')`）使用与现有流计算相同的 WebSocket 通知框架。FS §6 明确"通知 URL 的安全策略、网络访问控制等沿用现有机制"，未引入新的连接建立方式或新的通信端口。值得注意的是，FS 示例中通知 URL 使用 `ws://`（非加密），但这是现有框架层面的配置问题，属于存量风险范畴，不在本特性新增攻击面内。
- **状态：** 通过
- **说明/依据：** 通信安全完全依赖现有通知框架配置，本特性无变更，属于存量范畴。

#### 2.5 安全日志与监控

- **评审意见与发现：** FS §6 明确"新增的日志与指标不应泄露敏感数据内容；日志中建议仅记录必要的流名、分组标识与状态信息"。FS §12"可观测性"标注为"无"，表明本特性不引入新的监控端点或指标接口，不增加额外攻击面。关键安全相关事件（如分组进入空闲、恢复活跃、状态迁移）通过日志体现，足以支撑基本的运维溯源。
- **状态：** 通过
- **说明/依据：** 日志内容约束已在 FS §6 明确，不引入新的监控接口。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 针对威胁建模报告（`流计算分组空闲触发 - 威胁建模报告.md`）中识别的主要威胁：
  - **T-SIDLE-01**（通知明文传输）：属于现有框架存量问题，本特性未加重。
  - **T-SIDLE-02**（无限分组内存耗尽）：FS §5 与 §10 已明确标注为已知限制，建议用户合理设置 `IDLE_TIMEOUT` 并结合指标观察，属于设计已知权衡。
  - **T-SIDLE-04**（乱序数据触发误恢复）：FS §10 约束中已明确"空闲判定基于 processing time，不是 event time；乱序/补写历史数据会触发恢复事件"，这是设计选择，接收端应结合业务语义过滤。
  - 通知 payload 中 `triggerId` 使同一空闲周期的 `IDLE`/`RESUME` 事件强关联（FS §4.4.2.1），有助于接收端识别配对关系、防止事件混淆。
  - `idleDurationMs` 使用单调时钟计算（FS §4.4.2.2），防止 NTP 时钟跳变被利用篡改空闲判定逻辑。
- **状态：** 通过
- **说明/依据：** 已识别威胁中，高危威胁不存在；中危威胁均为已知设计权衡并在 FS 中有明确说明；防御机制（triggerId 关联、单调时钟）已内置于设计。

#### 2.7 默认安全配置

- **评审意见与发现：** FS §4.1.1 明确"默认值：未配置则不启用空闲检测（行为与现有版本一致）"。本特性完全遵循最小化默认原则，仅在用户主动配置 `STREAM_OPTIONS(IDLE_TIMEOUT(...))` 时才启用，不影响任何现有流任务的行为（FS §7 兼容性保证）。
- **状态：** 通过
- **说明/依据：** 默认不启用，符合安全最小权限原则。

#### 2.8 依赖组件安全

- **评审意见与发现：** FS §13 明确"本特性不引入新的独立组件与安装依赖"。本特性复用现有流计算调度器、通知框架（WebSocket）和失败处理机制（FS §4.3.3、§4.4.3），均与现有通知和流计算功能共享同一实现。无新增第三方依赖，无新的依赖组件安全风险。
- **状态：** 通过
- **说明/依据：** 无新引入第三方库或服务，依赖安全风险与现有组件一致。

#### 2.9 隐私设计

- **评审意见与发现：** 通知 payload 中包含 `tableName`（子表名）和 `groupId`（分组键哈希的十进制字符串），这两个字段可能间接映射到业务实体（如设备编号、厂商标识），存在通过通知内容推断业务拓扑的潜在隐私风险（对应威胁建模报告 T-SIDLE-05）。FS §6 已对日志内容做了最小化约束。如通知 URL 安全得到保障（使用 WSS），该风险可控。
- **状态：** 通过
- **说明/依据：** 通知 payload 不携带原始业务数据内容，分组标识的隐私风险依赖通知信道安全（属于现有框架层面），FS 约束已覆盖日志场景。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：**
  - **内存无淘汰策略**（FS §10 限制）：分组状态只增不减，在分组键空间持续增长的场景下，内存使用量将线性增长；FS 已明确标注为已知限制，并建议用户结合业务分组基数进行容量评估（FS §8）。
  - **重启状态清空**（FS §4.2.4）：重启前处于 IDLE 的分组，重启后若长期不再上报则永远无法触发下一次 IDLE 告警，产生监控盲区；FS §8 已明确运维建议："对强依赖告警的用户，应在运维流程中将该特性纳入重启评估"，并建议在外部监控系统补充"最后上报时间"逻辑（FS §11）。
  - 以上两项均为已知设计权衡，FS 中有明确说明和运维指引，不构成安全缺陷。
- **状态：** 通过
- **说明/依据：** 已知限制已在 FS 中明确文档化并提供运维建议。

### 3. 评审结论

2. **评审结论：** 通过
   - 准予进入下一阶段（编码实现）。安全设计完备，能有效覆盖本特性新增的有限攻击面，无需额外后续行动项。
