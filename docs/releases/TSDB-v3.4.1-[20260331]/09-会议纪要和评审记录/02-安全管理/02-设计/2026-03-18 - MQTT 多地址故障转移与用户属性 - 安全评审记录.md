### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** 本特性在 MQTT 连接层面支持用户名/密码认证（FS 第 4.2.3 节 auth_options 区块），并将认证参数从连接配置中独立出来，结构更清晰。多地址场景下，所有 Broker 候选地址使用相同的认证凭据，符合同一信任域的使用假设。TLS 配置提供三档（不开启/单向/双向），双向 TLS 支持最强认证。本特性不修改 taosx 对用户的访问控制模型，任务配置操作的权限校验沿用现有机制。
- **状态：** 通过
- **说明/依据：** 认证配置区块化设计降低了用户错误配置的概率。多 Broker 地址均使用统一凭据，避免了凭据不一致导致的认证混淆。FS 未引入新的身份认证机制，风险范围可控。

#### 2.2 数据安全

- **评审意见与发现：** FS 第 6 节明确说明密码通过 password 类型输入框输入，不以明文展示，保护了 UI 层的凭据安全。TLS 证书上传机制沿用现有安全机制不变。用户属性（connect_user_properties / subscribe_user_properties）为业务元数据，不涉及 TDengine 的敏感数据存储。DSN 字符串中包含 MQTT Broker 的用户名和密码，taosx 对 DSN 的存储安全依赖现有配置管理机制。
- **状态：** 通过
- **说明/依据：** UI 层密码保护明确，TLS 证书管理延续现有机制。本特性不引入新的数据存储变更，风险边界与现有设计一致。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** FS 第 4.4 节定义了完整的错误处理规范：用户属性 key 或 value 为空时后端返回明确错误信息；所有 Broker 地址连接失败时返回最后一个地址的连接错误；MQTT v3 下传入用户属性时静默忽略，不报错。FS 第 6 节明确说明用户属性值不进行任何特殊解释或执行，避免注入风险。parse_kv_pairs 函数对键值对格式进行严格校验（拒绝空 key 和空 value）。错误信息均为功能性描述，未发现敏感信息泄露设计。
- **状态：** 通过
- **说明/依据：** 输入验证覆盖了用户属性的主要边界情况。用户属性值以透传方式发送给 Broker，后端不执行或解释其内容，有效限制了注入攻击面。用户属性值不支持逗号（FS 第 10 节约束），进一步限制了分隔符注入的可能性。

#### 2.4 会话与通信安全

- **评审意见与发现：** FS 第 4.2.3 节的 auth_options 区块提供 TLS 证书配置，支持不开启/单向/双向三种 TLS 验证模式，覆盖了从内网明文到高安全双向认证的全部场景。clean_session 默认值为 true，避免了 Broker 端会话状态累积导致的资源消耗。多地址故障转移为顺序尝试，每次切换均执行完整的 TLS 握手和认证流程，不存在降级路径。MQTT v5 协议版本的选择由用户明确配置，不自动降级。
- **状态：** 通过
- **说明/依据：** TLS 配置选项完整，满足不同安全等级的部署需求。clean_session 默认安全，减少会话状态残留风险。

#### 2.5 安全日志与监控

- **评审意见与发现：** FS 第 8 节明确说明故障转移过程会产生日志，记录每个地址的连接尝试和结果，为故障排查和安全审计提供了基础溯源能力。这对于识别反复连接失败（可能反映 Broker 侧的攻击或配置错误）具有实际价值。
- **状态：** 通过
- **说明/依据：** 连接尝试日志覆盖了故障转移的关键事件，包含了足够的操作溯源信息。作为数据采集连接器，本特性的安全事件边界清晰，无需额外的登录/权限变更类日志。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 对照威胁建模报告中识别的威胁，FS 设计包含以下缓解：(1) 针对仿冒 Broker（T-MQTTFOV-01）——提供双向 TLS 配置选项，用户可启用 mTLS 以验证 Broker 身份；(2) 针对用户属性注入（T-MQTTFOV-03）——FS 明确说明值不进行解释执行，且禁止逗号字符；(3) 针对明文传输中间人（T-MQTTFOV-06）——提供完整 TLS 配置选项；(4) 针对凭据泄露（T-MQTTFOV-02）——UI 层密码框保护明文不展示，TLS 保护传输安全。
- **状态：** 通过
- **说明/依据：** 主要威胁均有对应的设计缓解措施。默认不启用 TLS 是 IoT/工业场景的常见做法，与 TDengine 的整体部署假设一致。

#### 2.7 默认安全配置

- **评审意见与发现：** clean_session 默认值为 true，行为保守，避免 Broker 端保留会话状态。TLS 默认不开启，与工业 IoT 场景的典型内网部署假设一致。最少需配置 1 个 Broker 地址的约束防止了空配置的无效连接尝试。MQTT v3 下用户属性静默忽略，不因版本误配置产生非预期行为。
- **状态：** 通过
- **说明/依据：** 默认配置与 taosx 现有 MQTT 任务的一致性良好，不引入行为突变。在公网或高安全场景下，文档应建议用户启用 TLS。

#### 2.8 依赖组件安全

- **评审意见与发现：** FS 第 15 节引用 rumqttc 0.25.x 作为 Rust MQTT 客户端库。rumqttc 是活跃维护的开源库，支持 MQTT v3/v5 和 TLS。本特性扩展了对 rumqttc 多地址连接和用户属性 API 的使用，未引入新的外部依赖。TLS 实现依赖 rumqttc 集成的 rustls/native-tls，沿用现有安全基础设施。
- **状态：** 通过
- **说明/依据：** rumqttc 0.25.x 在本特性开发周期内无已知高危 CVE。依赖组件范围未扩大，风险边界与现有实现一致。

#### 2.9 隐私设计

- **评审意见与发现：** 本特性为 MQTT 数据采集连接器的功能增强，不涉及用户个人数据的采集、存储或处理。用户属性（connect/subscribe_user_properties）为透传元数据，传递给 MQTT Broker，不被 taosx 解析或留存。
- **状态：** 不适用
- **说明/依据：** 本特性不引入新的个人数据处理场景，无隐私合规设计要求。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** TLS 证书和私钥的上传机制沿用现有实现，证书轮换由运维人员通过更新任务配置完成，流程清晰。多地址故障转移为顺序尝试（非并发），设计简单，减少了并发连接带来的竞争条件和资源争用风险。功能随 taosx 版本升级自动启用，无需额外运维操作，降低了人为错误配置的概率。旧版 user_properties DSN 参数不再被解析（FS 第 7 节），需在升级文档中明确说明以避免运维误判。
- **状态：** 通过
- **说明/依据：** 运维操作路径简单，不引入新的管理接口或配置文件。证书轮换通过任务重配置实现，与现有 taosx 运维模式一致。

### 3. 评审结论

1. **总体安全风险等级：**
   - **低风险**：安全设计完备，能有效实现安全需求，可进入开发阶段。

   - **通过**：准予进入下一阶段（编码实现）。本特性为 taosx MQTT 连接器的功能性增强，新增攻击面有限，主要风险（凭据传输、中间人攻击）均有对应的 TLS 缓解选项，设计安全基础扎实。
