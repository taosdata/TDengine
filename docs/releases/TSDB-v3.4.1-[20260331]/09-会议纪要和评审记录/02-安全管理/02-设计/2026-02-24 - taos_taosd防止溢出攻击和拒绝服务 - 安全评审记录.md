### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** FS 4.2.4 列举了认证层面的威胁场景（暴力破解用户名密码、认证票据伪造、会话劫持），但标注"暂时不确定"，未给出具体防护设计方案。本 FS 核心设计目标为内存安全与网络层 DoS 防护，认证安全机制不在本次设计范围内。
- **状态：** 不适用
- **说明/依据：** 认证防护超出本 FS 设计边界，属于独立安全模块管控范围。

#### 2.2 数据安全

- **评审意见与发现：** FS 未涉及敏感数据加密或传输加密方案。内存安全机制（安全函数封装、边界检查、ASAN 检测）可间接防止因内存漏洞导致内存中数据被非法读取或篡改，但不属于专项数据安全设计。
- **状态：** 不适用
- **说明/依据：** 数据加密和传输安全不在本 FS 范围内，由其他专项 FS 覆盖。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** FS 4.1.2.1 明确定义了业务边界，要求所有对外 API 参数均需边界检查，覆盖 dbname/tablename/colName/hostname/FQDN、SQL 长度、列数量、用户名及密码长度、用户数量上限、超级表数量上限等场景。FS 4.1.2.3 明确要求使用安全字符串处理函数（`tstrncpy` 替代 `strcpy`、`snprintf` 替代 `sprintf`），并通过 CI 编译阶段检测不安全函数使用。FS 4.2.2 针对协议畸形包、恶意数据包格式、超长字段值、不完整请求均有防护要求，并通过 CI 运行阶段验证覆盖。
- **状态：** 通过
- **说明/依据：** 设计从开发约定、编译检测、运行时检测三层保障了输入边界验证和安全编码，覆盖面合理全面。

#### 2.4 会话与通信安全

- **评审意见与发现：** FS 4.2.1 设计了针对 TCP 连接洪流和慢速连接攻击的防护，客户端侧已有 session 控制（每用户连接限制）。FS 4.2.3 说明服务端现有队列容量限制与用户级 session 控制可提供基础限流保护，并明确当前待补充"最大连接数限制"机制。具体通信加密（TLS 配置）不在本 FS 范围内。
- **状态：** 通过
- **说明/依据：** 连接管理与流量控制设计在本 FS 范围内已覆盖，最大连接数限制已识别为待补充项并列入开发任务。

#### 2.5 安全日志与监控

- **评审意见与发现：** FS 第 12 节可观测性标注为"无"，未涉及安全事件日志记录、异常告警等设计。
- **状态：** 不适用
- **说明/依据：** 安全日志与监控不在本 FS 设计范围内。

#### 2.6 威胁缓解机制

- **评审意见与发现：** FS 建立了四层溢出防护体系：① 静态检查（4.1.1）；② 开发阶段约定，包括业务边界定义、函数返回值检查、安全函数使用（4.1.2）；③ 编译阶段启用 `-fstack-protector` 及函数返回值检查（4.1.3）；④ 运行阶段 CI 集成 ASAN 运行时内存检测（4.1.4）。网络层 DoS 防护覆盖连接数耗尽（4.2.1）、协议层攻击（4.2.2）、流量控制（4.2.3）。各威胁缓解措施与威胁建模报告中 T-OVDOS-01 至 T-OVDOS-08 交叉对应。
- **状态：** 通过
- **说明/依据：** 多层次防护体系设计合理，覆盖了溢出和 DoS 的主要攻击场景，各层互为补充。

#### 2.7 默认安全配置

- **评审意见与发现：** FS 4.1.3 明确要求编译阶段默认启用 `-fstack-protector` 栈保护，体现安全默认原则。FS 4.1.4 在 CI 阶段默认集成 ASAN，确保每次代码提交均有内存安全检测覆盖。
- **状态：** 通过
- **说明/依据：** 编译级和运行级安全配置均以默认开启方式集成，降低了人为遗漏的风险。

#### 2.8 依赖组件安全

- **评审意见与发现：** FS 实现主要依赖内部封装的安全库（`osString.h`、`tarray.h`、`tdatablock.c`、`tmsg.c` 等），减少了外部第三方库带来的供应链风险。运行时检测工具 AddressSanitizer（ASAN）为业界成熟的 Google 内存检测框架，集成风险可控。
- **状态：** 通过
- **说明/依据：** 以内部封装库为主的设计策略有效降低了依赖组件的安全风险暴露面。

#### 2.9 隐私设计

- **评审意见与发现：** 本 FS 不涉及个人数据采集、存储或处理，溢出与 DoS 防护机制本身不引入新的隐私风险。
- **状态：** 不适用
- **说明/依据：** 本 FS 无隐私设计相关内容。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** FS 4.1.5 设计了完整的验证与演示计划，包括：对外 API 超限场景边界检查脚本、CI 编译阶段不安全函数检测 PR 验证、函数返回值漏检 PR 验证、运行时数组越界 ASAN 检测演示。多层防护体系具备良好的可扩展性，后续可通过增加静态分析规则、扩展 CI 检测范围进一步强化。
- **状态：** 通过
- **说明/依据：** 验证计划完备，自动化 CI 集成保障了安全特性的可持续验证能力。

### 3. 评审结论

1. **总体安全风险等级：** 低风险
   - 安全设计覆盖了溢出攻击和 DoS 攻击的核心防护路径，通过开发约定、编译保护、运行时检测的三层体系有效控制了主要风险，可进入开发阶段。

2. **评审结论：** 通过
   - 准予进入下一阶段（编码实现）。各安全维度在本 FS 范围内评审均通过，无需强制行动项。
