### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** 本特性为审计写入路径变更，不涉及身份认证与访问控制机制的变更。`AuditSaveInSelf=1` 时审计数据经集群内部 RPC 直接写入 vnode，写入权限由集群现有 RPC 认证机制管控。审计库本身的读取权限由 TDengine 现有用户权限体系保护，IS_AUDIT 标志标识的审计库受到特殊访问控制约束。
- **状态：** 通过
- **说明/依据：** 认证授权机制不受本特性影响，审计数据的访问控制复用现有集群权限体系。

#### 2.2 数据安全

- **评审意见与发现：** 审计数据不再流出至外部 taoskeeper，全程保存在本集群 vnode 内，消除了数据在外部传输路径上的泄露风险。FS 第 4.1 节明确：`AuditSaveInSelf=1` 时，原有 `auditHttps`、`auditUseToken` 参数不再起作用，通信安全机制由 RPC 整体配置决定，不单独设置。这与审计数据已在集群内部流转的事实一致——内部 RPC 通道已受集群级加密保护。
- **状态：** 通过
- **说明/依据：** 审计数据由外部传输路径收敛至集群内部 RPC，数据面风险降低。通信安全继承 RPC 整体配置，设计合理。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** 审计事件由集群内部组件（taosd）产生并经内部 RPC 写入 vnode，非外部不可信来源输入。operations 超级表的字段定义中包含明确的类型和长度约束（如 `user_name varchar(25)`、`details varchar(50000)`），可防止异常大值写入。错误信息（如 `Audit database is not allowed to keep multiple vgroups`）为通用描述，不泄露内部实现细节。
- **状态：** 通过
- **说明/依据：** 审计数据来源为可信的集群内部路径，表结构字段约束完整，错误信息设计合理。

#### 2.4 会话与通信安全

- **评审意见与发现：** `AuditSaveInSelf=1` 模式下通信路径由「taosd → taoskeeper（HTTP）」切换为「taosd → vnode（内部 RPC）」。FS 第 4.1 节明确说明"通讯的安全机制采用 RPC 的整体设置，没有单独设置"，`monitorFQDN`、`monitorPort`、`auditHttps`、`auditUseToken` 在此模式下不再起作用。内部 RPC 通道为集群内部通信标准路径，其加密与认证由集群统一配置，无需单独管控。
- **状态：** 通过
- **说明/依据：** 通信路径由外部 HTTP 收敛为内部 RPC，安全性不低于原路径。安全配置继承 RPC 整体设置，设计明确合理。

#### 2.5 安全日志与监控

- **评审意见与发现：** 本特性本身即为审计日志机制的改进。operations 超级表字段完整覆盖审计溯源所需信息：`ts`（时间）、`user_name`（用户）、`operation`（操作类型）、`db`（数据库）、`resource`（资源）、`client_address`（来源 IP）、`details`（详情）、`affected_rows`（影响行数）、`duration`（操作耗时）。相比经 taoskeeper 路由的旧路径，新路径消除了 taoskeeper 宕机导致审计记录丢失的风险（FS 第 6 节），提升了审计完整性。
- **状态：** 通过
- **说明/依据：** 审计字段覆盖全面，能有效支持操作溯源。新路径在 taoskeeper 故障场景下审计可靠性更高。

#### 2.6 威胁缓解机制

- **评审意见与发现：** FS 第 6 节明确列出了本特性相对原方案的安全优势：（1）消除了模拟 taoskeeper 截获审计信息的攻击面；（2）taoskeeper 宕机不再导致审计记录丢失。内部 RPC 路径相比外部 HTTP 接口具有更小的暴露面。审计库限定 vgroup=1 与原 taoskeeper 行为一致，保持了设计连贯性。具体威胁分析详见威胁建模报告（T-AUDSIF-01 至 T-AUDSIF-06）。
- **状态：** 通过
- **说明/依据：** 本特性在消除原有攻击面方面效果明确，新引入的风险（见威胁建模报告）均属中低风险，整体安全态势改善。

#### 2.7 默认安全配置

- **评审意见与发现：** `AuditSaveInSelf` 默认值为 `0`，即默认保持原有经 taoskeeper 路由的行为，不强制启用新路径（FS 第 4.1 节）。升级时无需删除重建审计库，与现有审计库和 taoskeeper 创建的 operations 表完全兼容（FS 第 7 节）。默认安全配置保守、向后兼容，不引入破坏性变更。
- **状态：** 通过
- **说明/依据：** 默认关闭新路径，按需启用，保证升级安全和行为可预期。

#### 2.8 依赖组件安全

- **评审意见与发现：** 本特性将审计数据写入对外部组件（taoskeeper）的依赖消除，转为使用集群内部 RPC 机制，减少了对外部服务的信任边界。创建审计库使用标准 SQL DDL 扩展（`IS_AUDIT 1`），不引入新的第三方库或外部依赖。内部 RPC 为集群现有成熟机制。
- **状态：** 通过
- **说明/依据：** 外部依赖减少，依赖安全性提升。无新增第三方安全敏感依赖。

#### 2.9 隐私设计

- **评审意见与发现：** 本特性为 TDengine 服务端内部审计路径优化，面向企业客户的数据库产品，不涉及个人隐私数据的专门处理场景。审计库中的 `user_name`、`client_address` 字段存储运维层面的身份信息，受现有集群访问控制保护。
- **状态：** 不适用
- **说明/依据：** 服务端数据库产品，不在个人隐私合规需求范畴内。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** `AuditSaveInSelf=1` 时，`monitorFQDN`、`monitorPort`、`monitorComp`、`auditHttps`、`auditUseToken` 五个参数失效，FS 第 4.1 节对此有明确文档说明，不存在歧义。vgroup=1 的限制为技术实现约束，已在 FS 第 4.2 节如实说明，运维人员有充分预期。新增 `AuditSaveInSelf` 配置项需补充文档（FS 第 14 节已列入）。运维和安装卸载无特殊要求（FS 第 8、13 节）。
- **状态：** 通过
- **说明/依据：** 参数失效行为有明确文档，vgroup 限制已声明，运维复杂度低。

### 3. 评审结论

1. **总体安全风险等级：**
    - **低风险**：本特性通过消除外部 taoskeeper 依赖，主动降低了审计数据的攻击面，安全设计合理，各维度评审均通过或不适用，可进入开发阶段。

2. **评审结论：**
    - **通过**：准予进入下一阶段（编码实现）。
