### 1. 评审信息

1. **评审目的：** 评估「Node.js 连接器支持负载均衡和 Failover」的技术设计方案是否有效、合理地实现了安全需求，识别架构与详细设计中的安全缺陷，并提出改进建议。

### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** FS 第 6 节明确要求"Failover 切换后，新连接应使用相同的认证信息（用户名、密码、Token）"，第 10 节约束"所有配置的节点必须使用相同的认证信息"，且"所有配置的节点必须属于同一个 TDengine 集群"。认证由 taosAdapter 服务端负责校验，连接器侧仅负责传递凭据，职责分离合理。Failover 过程中认证一致性得到保障。
- **状态：** 通过
- **说明/依据：** Failover 切换不改变认证凭据，所有候选节点处于同一信任域内，认证校验由服务端统一执行，符合职责分离原则。Token 过期场景已在第 11 节错误排查表中给出处理建议。

#### 2.2 数据安全

- **评审意见与发现：** FS 第 6.2 节明确支持 wss:// 协议（TLS 加密传输），第 6.3 节明确要求"日志及连接池 key 输出不应包含明文 password/token/bearer_token"。传输层加密和敏感信息脱敏均已在设计中落实。本特性为客户端连接管理增强，不改变数据存储方案，不引入新的数据处理逻辑。
- **状态：** 通过
- **说明/依据：** wss:// 提供传输层加密，密码/Token 脱敏要求覆盖日志输出场景，满足基本数据安全要求。多节点场景下凭据传递范围受用户配置的地址列表约束。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** FS 第 4.1.1 节定义了重连参数的有效范围（retries >= 0，retry_backoff_ms > 0，retry_backoff_max_ms > 0），并明确"当参数缺失、非法或越界时，连接器会回退到默认值"，采用 fail-safe 策略。DSN 多地址格式（`host1:6041,host2:6042,[::1]:6043`）已在第 4.1.2 节给出规范示例，支持 IPv4/IPv6/带端口格式。
- **状态：** 通过
- **说明/依据：** 参数越界回退默认值策略有效防范配置注入风险，格式规范覆盖常见地址形式。

#### 2.4 会话与通信安全

- **评审意见与发现：** FS 第 4.3.2 节设计了"重连锁"机制，保证"同一时刻仅有一个重连流程执行"，防止并发重连竞争。第 4.4 节对各模块（SQL 写入、SQL 查询、STMT2 参数绑定、无模式写入、数据订阅）均明确了 Failover 后的会话恢复策略，覆盖连接重建和请求重放场景。wss:// 支持传输加密，故障切换期间不存在安全降级路径（同一 DSN 参数适用于所有候选地址）。
- **状态：** 通过
- **说明/依据：** 重连锁防止连接竞争，各模块会话恢复逻辑设计完整，通信加密通过 wss:// 统一实现。

#### 2.5 安全日志与监控

- **评审意见与发现：** FS 第 6.3 节明确禁止日志中输出明文 password/token/bearer_token；第 8 节和第 12 节规定记录"重连开始、重连成功、地址切换、重放中断、连接失败、会话恢复与请求重放结果"等关键事件，具备 Failover 全流程的基本操作溯源能力。
- **状态：** 通过
- **说明/依据：** 敏感信息脱敏要求明确，关键安全事件日志涵盖 Failover 全流程，满足基本审计需求。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 针对威胁建模报告中识别的威胁，FS 设计已包含以下缓解措施：
  - T-NODELBF-01（凭据泄露）：第 6.3 节日志脱敏要求部分缓解；
  - T-NODELBF-03（写入重放污染）：第 4.4 节已明确标注幂等性问题，要求业务层处理；
  - T-NODELBF-04（重连 DoS）：第 4.3.2 节重连锁 + 指数退避策略限制重连频率；
  - T-NODELBF-05（订阅重复消费）：第 4.4 节明确说明从最后提交 offset 继续，业务层容忍重复。
- **状态：** 通过
- **说明/依据：** 主要威胁均有对应缓解设计，遗留的幂等性/重复消费问题在 FS 中已明确说明并转交业务层处理，符合职责分层原则。

#### 2.7 默认安全配置

- **评审意见与发现：** FS 第 4.1.2、第 9 节的示例代码均使用 `ws://root:taosdata@...` 弱默认凭据。此配置若被用户直接复制到生产环境将产生安全风险。FS 未对此给出安全提示或警告。重试参数默认值（retries=5，退避 200ms/2000ms）设计合理，不存在默认安全风险。
- **状态：** 待定
- **说明/依据：** 示例代码使用默认弱凭据，建议在 API 文档/代码注释中添加安全提示，提醒用户在生产环境替换 `root:taosdata`。

#### 2.8 依赖组件安全

- **评审意见与发现：** 本特性通过 `@tdengine/websocket` npm 包对外发布，该包为内部维护包。WebSocket 底层依赖库的安全状态由 npm 依赖管理与 SBOM 流程统一管控，不在本次设计评审范围内。
- **状态：** 不适用
- **说明/依据：** 无新增高风险第三方依赖，现有依赖安全由 SBOM 管理流程覆盖。

#### 2.9 隐私设计

- **评审意见与发现：** Node.js 连接器作为数据库客户端 SDK，不直接收集或处理终端用户个人信息，隐私设计要求不适用。
- **状态：** 不适用
- **说明/依据：** 纯连接管理功能，无个人隐私数据的采集与处理。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** FS 第 6.2 节声明支持 wss:// 协议，但未明确说明 TLS 证书校验策略（是否默认验证 CA 证书、是否提供跳过证书校验的配置项）。在私有化部署场景下，用户可能使用自签名证书，若连接器未提供 rejectUnauthorized 等配置项，将导致要么连接失败、要么强制跳过验证（中间人风险）。此设计细节需在 FS 或实现设计中明确。
- **状态：** 待定
- **说明/依据：** TLS 证书校验策略是 wss:// 安全的关键配置，需在设计文档中补充说明，确保私有化部署场景的安全可用性。

### 3. 评审结论

1. **总体安全风险等级：**
   - **低风险**：本特性为客户端侧连接管理增强，不改变认证授权模型，不引入新的数据处理逻辑，不增加服务端攻击面。现有的 TLS 支持、参数校验、日志脱敏和重连锁设计构成了充分的安全防护基础，存在的两个待定项属于文档完善性问题，不构成严重安全缺陷。

2. **评审结论：**
   - **有条件通过**：需完成"后续行动项"中的所有项目，并经安全代表确认后，方可进入下一阶段。
