### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** ExternalWindow 功能引入了 `EXTERNAL_WINDOW ((subquery) alias)` 语法，允许在外层查询中引用由子查询生成的窗口进行计算。子查询可以访问与外层查询不同的表（如 FS 第 5.1.1 节示例中外层查询 `alarm1` 表，子查询访问 `fault1` 表）。权限校验依赖现有 SQL 执行引擎的表级权限检查机制——用户必须对子查询和外层查询涉及的所有表均具有读权限。FS 第 7.1.1 节明确禁止在流计算和订阅中使用 external window（语法报错），避免了通过持续运行的流/订阅通道绕过权限检查的风险。`INSERT INTO ... SELECT` 场景允许使用（第 7.1.1 第 3 条），此时写入目标表的权限校验同样由现有机制保障。
- **状态：** 通过
- **说明/依据：** 子查询和外层查询的权限校验由已有 SQL 执行链路统一处理，未引入新的认证或授权机制。流计算和订阅的显式禁用是合理的安全边界设定。

#### 2.2 数据安全

- **评审意见与发现：** ExternalWindow 的核心功能是将子查询产生的窗口应用于外层数据进行聚合计算，不涉及数据的持久化存储变更、加密方案或数据销毁。子查询结果（Window Relation）为临时数据集，生命周期限于查询执行期间。FS 第 4.3.2 节的分组对齐机制（groupKey 匹配）确保了不同分组的数据不会交叉计算——当内外均有 `PARTITION BY` 时，仅 `calcGroupKey = inputGroupKey` 的分组进行匹配输出，实现了计算层面的数据隔离。
- **状态：** 不适用
- **说明/依据：** 该功能为查询时的窗口化计算能力，不涉及数据存储、加密或销毁场景。分组对齐机制提供了合理的计算隔离。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** FS 对输入验证做了较为完整的设计：
  - **语法层验证**：FS 第 7.1.2 节要求子查询前两列必须为 timestamp 类型的表达式，否则视为语义错误；第 7.1.4 节禁止在 `WHERE` 子句中引用 Window Instance 属性列。
  - **运行时验证**：FS 第 7.2 节定义了无效 Window Instance 的处理——窗口开始时间大于结束时间、窗口起始时间乱序、时间区间出现 NULL 均作为运行时错误。FS 第 6.0.1 节对窗口排序要求做了分层处理——语法阶段可发现的乱序直接报错，执行阶段发现的乱序报运行时错误。
  - **重复窗口处理**：FS 第 6.0.2 节明确对完全重复的窗口只计算第一次、只输出一个窗口，避免了重复计算导致的结果膨胀。
  - **lag/lead 函数**：offset 参数只允许正值（FS 第 3.3 节），限制了参数范围。
- **状态：** 通过
- **说明/依据：** 输入验证在语法层和运行时层均有明确设计，覆盖了时间类型校验、区间有效性、排序约束等关键场景。

#### 2.4 会话与通信安全

- **评审意见与发现：** ExternalWindow 的执行涉及客户端与多个 vnode 之间的查询交互，但完全复用现有 SQL 查询的 RPC 通信链路。子查询和外层查询的执行均通过已有的查询分发和结果收集机制完成，未引入新的通信通道或协议变更。
- **状态：** 不适用
- **说明/依据：** 该功能未改变通信协议和通道，仅在现有查询执行框架内增加窗口化计算逻辑。

#### 2.5 安全日志与监控

- **评审意见与发现：** `EXTERNAL_WINDOW` 语句作为标准 SQL 查询的一部分，其执行会被现有审计日志系统记录。FS 未引入新的安全事件类型，也不需要独立的安全日志设计。嵌套使用场景（FS 第 5.1.3 节）产生的复杂查询同样会作为完整 SQL 语句被审计系统捕获。
- **状态：** 不适用
- **说明/依据：** 该功能不产生新的安全事件类型，现有 SQL 审计机制已覆盖。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 针对威胁建模报告中识别的威胁，评估如下：
  - **T-EXTWIN-01（子查询跨表权限校验）**：现有 SQL 执行引擎对子查询涉及的所有表进行权限校验，ExternalWindow 复用此机制，未绕过权限检查链路。风险可接受。
  - **T-EXTWIN-02（嵌套查询资源耗尽）**：FS 第 4.4 节允许多层嵌套 external window，嵌套深度理论上无限制。现有查询超时和内存限制机制可提供基本防护，但未在 FS 中显式设置嵌套深度上限。此为低优先级改进项。
  - **T-EXTWIN-03（大量窗口资源消耗）**：子查询可能产生海量 Window Instance，FS 第 7.3 节已提及"分组/窗口数量影响关联计算开销"。现有查询资源管控机制适用。
  - **T-EXTWIN-04（运行时错误信息泄露）**：FS 中定义的运行时错误（无效窗口、乱序窗口）返回的错误信息应遵循现有错误处理规范，不暴露内部实现细节。
  - **T-EXTWIN-05（重叠窗口重复扫描）**：FS 第 6.0.2 节明确重叠窗口各自独立计算，完全重复窗口只输出一个，设计合理。
- **状态：** 通过
- **说明/依据：** 威胁建模中识别的风险均为低至中风险，现有安全机制已提供基本防护。嵌套深度限制可作为后续优化项。

#### 2.7 默认安全配置

- **评审意见与发现：** ExternalWindow 不引入新的配置项或端口。FS 第 7.1.1 节的约束设计遵循了安全默认原则：流计算和订阅默认禁用 external window（语法报错），FILL 子句仅支持 `NONE` 模式（第 7.1.3 节），STMT 不支持绑定 external_window 参数（第 7.1.1 第 4 条）。这些限制减少了初始版本的攻击面，后续版本可按需逐步放开。
- **状态：** 通过
- **说明/依据：** 默认配置遵循最小功能原则，流/订阅/FILL 扩展选项等均默认禁用或受限。

#### 2.8 依赖组件安全

- **评审意见与发现：** ExternalWindow 功能完全基于 TDengine 内部的查询执行框架实现，包括 SQL 解析器、查询计划生成器、算子执行引擎。新增的 `lag()`/`lead()` 函数也是内部实现。未引入任何新的第三方库或外部服务依赖。
- **状态：** 不适用
- **说明/依据：** 无新增外部依赖，功能基于现有内部组件实现。

#### 2.9 隐私设计

- **评审意见与发现：** ExternalWindow 为查询语法扩展，不涉及个人信息采集、存储或处理。查询结果的内容由用户查询的数据决定，与该功能本身无关。
- **状态：** 不适用
- **说明/依据：** 该功能不涉及隐私数据处理场景。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** FS 第 8 节规划了明确的功能分期策略：本期实现基本功能和简单 lag/lead，后续版本扩展 CSV 文件子查询、TEXT 子查询、lag/lead N 行增强、窗口乱序支持等。这种渐进式发布策略有利于控制每个版本的安全评审范围。FS 第 7.3 节提到嵌套深度增加计算复杂度，建议在运维文档中给出嵌套使用的性能建议。FS 中未涉及管理通道或运维接口的变更。
- **状态：** 通过
- **说明/依据：** 渐进式功能发布策略合理，当前版本范围内无运维安全问题。

### 3. 评审结论

1. **总体安全风险等级：**
   - 低风险：ExternalWindow 为查询语法层面的功能扩展，不涉及新的认证机制、通信协议或数据存储变更。设计中对流/订阅的显式禁用、输入验证的分层处理（语法层 + 运行时层）、分组对齐的数据隔离机制均为合理的安全设计。安全设计完备，可进入开发阶段。
2. **评审结论：**
   - 通过：准予进入下一阶段（编码实现）。
