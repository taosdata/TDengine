### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** FS 第 5.0.1 节明确指出，对 `sql_rules.json` 和 `taos.cfg` 的修改只能通过 `ALTER LOCAL` SQL 命令执行，且包含权限检查，配置文件本身由 taosk 生成的密钥加密保护。学习模式的开启/关闭、白名单模式切换等敏感操作均通过 `ALTER LOCAL` 命令完成，与现有权限体系集成，未绕过已有访问控制机制。总体设计合理。
- **状态：** 通过
- **说明/依据：** FS 第 5.0.1 节："想要修改配置参数只能通过SQL的 alter 命令（包含权限检查）"；配置文件通过 taosk 密钥加密，防止直接篡改。

#### 2.2 数据安全

- **评审意见与发现：** SQL 安全功能本身不直接处理业务数据的加密存储与传输，其保护的核心资产为 SQL 安全规则配置。FS 第 5.0.1 节说明规则文件（`sql_rules.json`）和主配置文件（`taos.cfg`）会通过 taosk 生成的密钥进行加密存储，防止静态配置被篡改。白名单学习模式会将正常 SQL 模式持久化到规则文件，其中可能包含业务 SQL 结构信息，已通过配置文件加密一并保护。
- **状态：** 通过
- **说明/依据：** FS 第 5.0.1 节说明配置持久化时通过 taosk 密钥加密保护。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** 本功能的核心即是对 SQL 输入的两层防护验证：第一层（FS 第 4.1.2 节）在 SQL 解析前通过 PCRE 正则表达式对原始字符串进行关键字黑名单检查、注释注入检测、编码绕过检测及长度限制检查；第二层（FS 第 4.1.3 节）在 AST 解析后对语法树进行精确的语义检查，覆盖恒真/恒假条件、危险函数、异常操作符、深层子查询和 JOIN 注入等场景。该双层设计能有效对抗格式混淆类绕过攻击。FS 未明确说明 SQL 被拒绝时向客户端返回的错误响应内容，建议确认错误消息不泄露安全规则细节。
- **状态：** 通过
- **说明/依据：** FS 第 4.1.2 节和 4.1.3 节详细描述了双层过滤机制，覆盖范围全面；轻微建议确认错误响应内容，但不构成阻断性问题。

#### 2.4 会话与通信安全

- **评审意见与发现：** SQL 安全过滤功能作用于 SQL 执行路径的解析层，不涉及会话管理和通信协议的直接设计。配置项通过服务端下发，客户端在首次连接时拉取并缓存，后续通过心跳更新（存在一个心跳周期的延迟，FS 第 5.0.1 节），通信安全依托 TDengine 现有传输层保护机制。
- **状态：** 不适用
- **说明/依据：** 本功能不涉及新的会话管理或通信协议设计。

#### 2.5 安全日志与监控

- **评审意见与发现：** FS 第 5.3 节说明系统会记录被拒绝的 SQL 语句、触发的安全规则以及学习模式新增的 SQL，使用 TSC 的 cDebugFlag 机制，黑名单拦截使用 WARN 级别，白名单拦截使用 DEBUG 级别，学习模式添加使用 INFO 级别，日志存储在 taoslog 中。但 FS 未明确说明安全日志中是否包含执行用户身份标识（user）和客户端来源地址（IP/连接 ID），缺少这些关键溯源字段将导致事后审计无法追溯攻击来源。
- **状态：** 待定
- **说明/依据：** FS 第 5.3 节描述的日志内容（被拒绝的SQL、触发规则、学习模式添加记录）中未提及用户身份和来源IP，存在溯源信息不完整的风险。

#### 2.6 威胁缓解机制

- **评审意见与发现：** FS 第 5.2 节系统性地列举了 8 类常见 SQL 注入攻击场景，并通过双层防护机制（字符串级 + AST 级）逐一应对。黑名单覆盖恒真条件注入、UNION 结果集拼接、注释截断、多语句注入、系统表探测、子查询/EXISTS 注入、编码混淆以及危险权限操作；AST 层额外处理了大小写不敏感、注释嵌入等格式混淆绕过场景（FS 第 4.1.3 节示例）。威胁缓解机制设计完整，与本报告威胁建模（TM-TSDB-SQLINJ-001）中识别的威胁 T-SQLINJ-02、T-SQLINJ-04 等直接对应。
- **状态：** 通过
- **说明/依据：** FS 第 5.2 节和第 4.1 节的设计覆盖了主要 SQL 注入攻击向量；详见威胁建模报告 TM-TSDB-SQLINJ-001。

#### 2.7 默认安全配置

- **评审意见与发现：** FS 第 4.2.1 节显示 `sqlSecurity` 配置项默认值为 `false`，即 SQL 安全检查功能默认关闭。这一设计决策出于兼容性考虑（避免对存量合法 SQL 模式产生影响），在时序数据库场景中有其合理性。用户需要显式启用该功能并配置规则文件。由于此为可选安全增强功能而非基础防护，且默认关闭有明确的兼容性原因，整体可接受。
- **状态：** 通过
- **说明/依据：** FS 第 4.2.1 节：`sqlSecurity false # 是否启用 SQL 安全检查，默认 false`；默认关闭是数据库类产品在引入可能影响现有业务的安全特性时的常见做法。

#### 2.8 依赖组件安全

- **评审意见与发现：** FS 第 4.1.2 节指出第一层过滤使用 PCRE（Perl Compatible Regular Expressions）库实现正则匹配。PCRE 为成熟组件，但用户可通过 `sql_rules.json` 自定义正则表达式规则（FS 第 4.2.1 节），若用户填写了高复杂度（如指数级回溯）的正则表达式，存在正则表达式拒绝服务（ReDoS）的风险，可能导致 SQL 执行路径被阻塞或 CPU 使用率异常升高。
- **状态：** 待定
- **说明/依据：** FS 第 4.1.2 节："使用 PCRE（Perl Compatible Regular Expressions）库"；FS 第 4.2.1 节允许用户在 `sql_rules.json` 中自定义 pattern 字段，缺少对正则表达式复杂度的约束说明。

#### 2.9 隐私设计

- **评审意见与发现：** SQL 注入防护功能本身不涉及个人可识别信息（PII）的收集、存储或处理，无专项隐私设计需求。
- **状态：** 不适用
- **说明/依据：** 本功能为 SQL 执行路径安全增强，不涉及隐私数据处理。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** FS 第 4.2.1 节说明规则支持动态增删改（通过 `ALTER LOCAL` 命令），具备良好的运维可操作性。配置项变更存在一个心跳周期的延迟生效机制（FS 第 5.0.1 节），在紧急情况下管理员需了解此延迟。FS 第 5.1 节的白名单学习模式提供了良好的运维辅助能力，便于初始规则生成。性能影响方面，FS 第 6 节说明关闭时不影响性能，开启后略有下降，并提出了高优先级规则先检查和 AST 缓存的优化方向，设计合理。
- **状态：** 通过
- **说明/依据：** 功能整体可扩展性良好；一个心跳周期的配置延迟在文档中已有说明，属已知设计取舍。

### 3. 评审结论

1. **总体安全风险等级：** 低风险
   - SQL 注入防护机制设计完整，采用双层防护架构，覆盖了主要攻击向量；配置安全依托成熟的 taosk 加密机制；审计日志溯源字段和 PCRE ReDoS 防护为两个待完善点，但不构成高风险缺陷。

2. **评审结论：** 有条件通过
   - 需完成"后续行动项"中的所有项目，并经安全代表确认后，方可进入下一阶段。
