### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** CULS 注册采用 Ed25519 密钥对，实例连接 CULS 时验证公钥签名（见 §29.1.1），`DROP LICENSE` 命令明确要求 `security_officer` 角色并需通过安全审计（见 §32.0.3），实例级授权分发具备黑名单防控机制。但 CLS 管理端（`taos-cls-admin` CLI 和 Web UI）的管理员身份认证方式在 FS 中未做任何说明，攻击者若能访问 CLS 所在主机或网络，可直接发放或撤销授权。此为设计缺失，需补充。
- **状态：** 待定
- **说明/依据：** FS §4.2 描述了 CLI 子命令（`issue`、`revoke`、`blacklist` 等），但未提及操作员登录认证、会话管理或多因素认证；Web UI 部分（§6.0.1）仅描述展示功能，也未说明认证方式。

#### 2.2 数据安全

- **评审意见与发现：** CLS 与 CULS 之间的传输层采用 QUIC + TLS 1.3 + Noise Protocol XX 握手（见 §32.1.1），License 包含 CLS 私钥签名（`bytes signature` 字段，见 §32.1.2），授权数据本身标注为加密存储（`bytes license_data = 3; // 加密的授权数据`）。CLS 侧 PostgreSQL 数据库的静态加密方案（at-rest encryption）未在 FS 中说明；CULS 侧使用 RocksDB/REDB 存储 License 数据、实例列表及审计日志（§32.3.2），同样未提及数据库文件是否加密。整体传输安全设计完善，静态存储加密有一定缺失。
- **状态：** 通过
- **说明/依据：** 授权系统的核心敏感数据（License 包）在传输中已加密且有签名保护，客户侧本地存储的内容在有 OS 文件权限保护的部署环境中风险可接受；静态加密属实现细节，可在编码阶段补充。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** CLI 接受的参数（`--customer-id`、`--culs-id`、`--valid-until` 等，见 §4.2.1）及 REST API（`POST /api/v1/licenses/issue`）均涉及外部输入，FS 未明确输入验证和格式校验策略。CLS 后端使用 PostgreSQL，需防范 SQL 注入；REST API 和 Protobuf 消息体（§32.1.2）中含字符串字段，应进行边界检查。错误码定义清晰（0x2601～0x2603，见 §32.0.3），不暴露内部堆栈信息。
- **状态：** 通过
- **说明/依据：** 输入验证属实现层要求，FS 中对数据结构有类型约束（Rust 强类型 `LicenseGrants`），基础防护框架已存在；具体防注入措施可在编码阶段落实。

#### 2.4 会话与通信安全

- **评审意见与发现：** CLS ↔ CULS 通信采用 QUIC + TLS 1.3 + Noise Protocol（XX handshake），使用 Ed25519 密钥交换（见 §32.1.1），安全强度高。CULS ↔ Instance 通信使用 `culs://` 协议（端口 7443），实例侧验证 CULS 公钥（见 §29.1.1），防止 CULS 仿冒。CLS Web UI 的 HTTPS 配置未在 FS 中明确，但属部署层面配置，风险可控。
- **状态：** 通过
- **说明/依据：** 核心授权链路（CLS ↔ CULS ↔ Instance）均有加密和双向认证设计，满足安全通信要求。

#### 2.5 安全日志与监控

- **评审意见与发现：** CLS 侧设计了 `audit_logs` 表（见 §32.3.1），记录字段包括时间戳、操作类型（`operation`）、操作者（`actor`）、目标类型/ID（`target_type`/`target_id`）、操作详情（`details JSONB`）和结果（`result`），覆盖了授权发放、撤销、黑名单等敏感操作。FS §34 明确说明审计日志保留 1 年。CULS 侧有本地审计日志（§32.3.2）。`DROP LICENSE` 操作需通过安全审计（§32.0.3）。Prometheus metrics 监控连接数、License 数量、到期天数（§41.2）。整体日志设计完善。
- **状态：** 通过
- **说明/依据：** 日志结构字段完整，包含溯源所需的操作者和时间信息；保留周期 1 年符合常规要求；双侧（CLS + CULS）均有日志设计。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 针对威胁建模（见《License Center - 威胁建模报告》）中识别的威胁，FS 设计了以下缓解措施：
  - **T-LC-01（仿冒 CULS）**：Ed25519 密钥对注册 + 实例侧公钥验证（§29.1.1）✅
  - **T-LC-02（License 篡改）**：CLS 私钥签名（§32.1.2）✅
  - **T-LC-03（License 重放）**：消息体含 `timestamp`（§32.1.2），但未明确 nonce/单次性令牌机制 ⚠️
  - **T-LC-04（黑名单绕过）**：三级黑名单（CULS/License/Instance，见 §3、§26.0.2）✅
  - **T-LC-05（CLS 管理端越权）**：FS 未说明 CLS 管理端认证（见 2.1 节）⚠️
  - **T-LC-06（离线 Token 泄露）**：离线 Token 绑定 CULS ID，但未提及 Token 加密存储要求 ⚠️
  - **T-LC-07（客户侧数据泄露）**：依赖 OS 文件权限 ✅（可接受）
  - **T-LC-08（操作抵赖）**：双侧审计日志（§32.3.1、§32.3.2）✅
  - **T-LC-09（CLS DoS）**：FS 未提及注册频率限制或速率控制机制 ⚠️
  - **T-LC-10（宽限期滥用）**：宽限期固定 14 天不可配置，属设计约束（§45.1）✅
- **状态：** 待定
- **说明/依据：** 核心防护（身份认证、数据签名、黑名单）设计完善；防重放 nonce 和 CLS 注册速率限制有所缺失，需补充。

#### 2.7 默认安全配置

- **评审意见与发现：** 默认通信端口 8443（CLS）和 7443（CULS）均为非标准高位端口，默认启用 TLS，默认加密通信（§32.1.1）。宽限期默认 14 天不可配置，防止运维误操作（§45.1）。`DROP LICENSE` 仅限 `security_officer` 角色，默认权限最小化（§32.0.3）。整体默认配置安全。
- **状态：** 通过
- **说明/依据：** 关键安全特性（TLS、签名验证、权限控制）默认开启，无默认开放高危端口或默认弱凭证的情况。

#### 2.8 依赖组件安全

- **评审意见与发现：** 主要依赖组件包括：libp2p（QUIC + Noise Protocol，业界成熟 P2P 网络库）、Ed25519（标准椭圆曲线签名算法）、PostgreSQL（CLS 侧，主流数据库）、RocksDB/REDB（CULS 侧嵌入式数据库）、Prometheus（监控指标）。libp2p 和加密原语均为业界主流选型，风险已知可控。PostgreSQL 连接安全配置（如 TLS、最小权限账号）未在 FS 中说明，但属部署层面。
- **状态：** 通过
- **说明/依据：** 依赖组件选型合理，无明显高风险第三方库；具体安全配置细节在部署文档中补充即可。

#### 2.9 隐私设计

- **评审意见与发现：** License Center 处理的数据主要为授权维度（时间序列数量、CPU 核数、功能模块等）、实例 IP/端口、客户 ID 和合同信息。不涉及终端用户个人数据，隐私风险低。CRM 集成（§14.0.1）中访问客户合同信息，仅限内部系统间交互，无个人数据收集告知场景。
- **状态：** 不适用
- **说明/依据：** 该功能属 B2B 授权管理，不处理自然人个人信息，隐私设计要求不适用。

#### 2.10 其他（密钥轮换、运维安全等）

- **评审意见与发现：** Ed25519 密钥对是整个授权信任链的核心（CULS 注册密钥、CLS 签名密钥），但 FS 中未描述密钥轮换、密钥泄露应急响应和吊销机制。CLS 的高可用部署（§41.1）和 PostgreSQL 主从复制已设计，运维安全基础良好。向后兼容保留单机 License 文件模式作为 fallback（§35），需确保该模式不会成为绕过 License Center 安全控制的后门。
- **状态：** 待定
- **说明/依据：** 密钥轮换是授权系统长期运维的必要能力，需在设计阶段明确流程；fallback 兼容模式的安全边界需明确。

### 3. 评审结论

1. **总体安全风险等级：** 中风险
   - 安全设计核心框架完备（TLS 1.3、Ed25519 签名、三级黑名单、审计日志），但 CLS 管理端认证缺失和防重放机制不完整属设计缺陷，需在"后续行动项"中解决。

2. **评审结论：** 有条件通过
   - 需完成后续行动项中的所有项目，并经安全代表确认后，方可进入下一阶段。
