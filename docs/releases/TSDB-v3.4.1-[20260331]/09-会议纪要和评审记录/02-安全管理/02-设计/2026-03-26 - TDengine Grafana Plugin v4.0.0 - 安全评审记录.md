### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。本次评审重点关注 v4.0.0 的核心变更：从 `DataSourceApi` 迁移至 `DataSourceWithBackend` 后端代理架构、SQL 宏扩展，以及 CVE 修复。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** v4.0.0 迁移至 `DataSourceWithBackend` 后，TDengine 连接凭证（用户名、密码、Token）通过 Grafana 的 `secureJsonData` 机制加密存储于 Grafana 后端，不再通过前端 JavaScript 代码或 API 响应暴露。插件本身不实现自定义认证逻辑，而是完全委托 Grafana 平台的 RBAC 机制管理仪表板和数据源的访问权限，这符合最小权限和职责分离原则。
- **状态：** 通过
- **说明/依据：** FS 安全章节明确说明"后端代理模式增强了数据源凭证的安全性，敏感信息（如密码、Token）仅存储在 Grafana 后端，不暴露给前端"，这是相较 v3.x DataSourceApi（凭证会暴露在前端请求中）的显著安全提升。

#### 2.2 数据安全

- **评审意见与发现：** 凭证隔离机制已通过架构升级得到落实。查询数据经由 Grafana 后端代理转发至 TDengine REST API，遵循 Grafana 数据源的 TLS/HTTPS 配置，数据传输安全性依赖 Grafana 的标准 HTTP 安全配置，架构上无额外风险引入。后端数据处理流程（附录 B：QueryDataHandler → SQL宏替换 → REST API → DataFrame 转换）整体在 Grafana 后端可信域内完成，不涉及客户端侧的敏感数据暂存。
- **状态：** 通过
- **说明/依据：** 架构迁移（章节 4.2）将数据流从"前端直连 TDengine REST API"改为"后端代理访问"，消除了浏览器直接接触 TDengine 连接凭证的风险。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** SQL 宏（`$__timeFilter`、`$__timeFrom`、`$__timeTo`）在后端由 Go 代码替换为 RFC3339 格式的时间戳字符串（附录 B 第 3 步），替换内容来自 Grafana 时间范围参数，不受用户界面的直接自由输入控制，安全性较高。但 FS 章节 3.2 展示的 SQL 示例中，Grafana 仪表板模板变量直接拼接进 SQL（如 `AND location = '$location'`、`FROM ${table_name}`），FS 未描述插件对这类变量值是否进行 SQL 特殊字符转义或白名单校验，存在通过变量值进行 SQL 注入的风险（对应威胁 T-GRAFPLUGIN-01）。
- **状态：** 待定
- **说明/依据：** FS 用例章节（Use Case 1、2）及 SQL 宏示例（章节 3.2）均展示了将 Grafana 变量嵌入 SQL 的模式，但未说明变量值的净化机制。需在文档层面补充使用规范。

#### 2.4 会话与通信安全

- **评审意见与发现：** 会话管理完全委托 Grafana 平台，插件不实现任何自定义会话机制，设计正确。前端与 Grafana 后端插件之间采用 Grafana 内部 gRPC 通道通信，CVE-2026-33186 已通过升级 `google.golang.org/grpc` 至 v1.79.3 修复，通信安全有保障。Grafana 后端与 TDengine REST API 之间的 TLS 配置由数据源的 HTTP 配置选项控制（如"Skip TLS Verify"），属于部署配置范畴，FS 不需要额外约束。
- **状态：** 通过
- **说明/依据：** v4.0.0 主动修复了 gRPC 传输层漏洞（CVE-2026-33186），通信安全较 v3.x 有明确改善。

#### 2.5 安全日志与监控

- **评审意见与发现：** 本插件为 Grafana 数据源插件，自身不处理用户认证、权限变更等安全事件，此类事件由 Grafana 平台的审计日志统一记录。插件的可观测性说明（章节"可观测性"）关注的是业务监控（TDinsight），无需在插件内部重复实现安全日志。
- **状态：** 不适用
- **说明/依据：** 插件架构决定了安全审计责任在 Grafana 平台侧，插件本身无独立的安全日志需求。

#### 2.6 威胁缓解机制

- **评审意见与发现：** CVE 修复已明确落实：CVE-2026-33186（gRPC 远程代码执行）通过升级依赖修复；CVE-2026-24051（OpenTelemetry SDK）通过 `replace` 指令固定版本修复。这两项修复消除了已知高危漏洞的风险。针对 SQL 模板变量注入（T-GRAFPLUGIN-01），FS 未描述具体缓解措施；针对大查询拒绝服务（T-GRAFPLUGIN-03），FS 亦未描述查询资源限制机制。
- **状态：** 待定
- **说明/依据：** CVE 修复部分通过，威胁建模识别出的 T-GRAFPLUGIN-01 缓解措施需在文档层面补充（参见威胁建模报告 `TDengine Grafana Plugin v4.0.0 - 威胁建模报告.md`）。

#### 2.7 默认安全配置

- **评审意见与发现：** `DataSourceWithBackend` 后端代理模式作为 v4.0.0 的默认架构，相较旧版 `DataSourceApi`（前端直连）默认安全性更高；最低 Grafana 版本提升至 8.0（章节 6），确保插件运行环境具备完整的后端插件 SDK 安全能力；移除废弃功能（章节 1、2、5）减小了攻击面，降低了因历史遗留代码引入漏洞的风险。
- **状态：** 通过
- **说明/依据：** 架构迁移本身即是默认安全配置的提升，无需额外配置步骤即可获得更高的安全基线。

#### 2.8 依赖组件安全

- **评审意见与发现：** FS 安全章节明确列出并修复了两个已知 CVE：CVE-2026-33186（`google.golang.org/grpc`，升级至 v1.79.3）和 CVE-2026-24051（`go.opentelemetry.io/otel/sdk`，添加 replace 指令固定至 v1.40.0）。版本升级和 replace 指令均为标准 Go 模块依赖管理方式，能有效控制依赖版本。前端 npm 依赖的安全扫描情况 FS 未提及，但 v4.0.0 移除了约 15% 的废弃代码，客观上减少了前端依赖的维护面。
- **状态：** 通过
- **说明/依据：** 两个高危 CVE 已在 v4.0.0 中明确修复，依赖安全管理主动到位。

#### 2.9 隐私设计

- **评审意见与发现：** Grafana 插件本质上是时序数据可视化工具，负责将 TDengine 的时序数据（如传感器读数、监控指标）在 Grafana 界面展示。插件不收集、处理或存储最终用户的个人信息（PII），不涉及用户行为追踪，无隐私合规义务。
- **状态：** 不适用
- **说明/依据：** 功能定位为数据可视化，无个人信息处理场景。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** TDengine 连接凭证的轮换通过 Grafana 数据源配置界面完成，操作路径标准清晰。v4.0.0 提供明确的回滚方案（章节"回滚方案"：卸载 v4.0.0 → 安装 v3.8.0），运维安全可控。附录 C 显示测试覆盖率显著提升（后端模块从 40% 提升至 75%，SQL 宏替换从 0% 提升至 100%），降低了因代码质量问题引入安全漏洞的概率。
- **状态：** 通过
- **说明/依据：** 运维安全路径清晰，测试覆盖率提升有助于安全漏洞的早期发现。

### 3. 评审结论

1. **总体安全风险等级：** 低风险
   - 安全设计整体合理，核心安全改进（后端代理架构、CVE 修复）均已落实。仅存在 SQL 模板变量注入风险在文档层面的说明缺失，不影响架构安全性，可在设计评审阶段通过补充文档解决。

2. **评审结论：** 有条件通过
   - 核心安全设计（凭证隔离、CVE 修复、默认安全配置）均已通过评审，准予进入下一阶段。需完成"后续行动项"中的第 1 项，并经安全代表确认后，视为完全通过。
