### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** FS 设计了完整的多因素认证方案：用户可选择密码登录或 Token 登录两种方式，密码登录后支持可选的 TOTP 二次验证。认证流程图（4.1.1）清晰展示了登录判断逻辑——先验证密码，再根据用户是否启用 TOTP 决定是否要求输入验证码。Token 认证方案中，Token 具有 expire_time 过期控制，通过 `CREATE token` / `ALTER token` / `DROP token` SQL 命令进行全生命周期管理。TOTP 认证通过 `ALTER USER ... TOTPSEED` 命令支持启用/禁用/更新，用户可自主控制。兼容性设计（第15节）合理地处理了社区版和旧版本不支持新认证方式的场景。
- **状态：** 通过
- **说明/依据：** 认证方案支持密码+TOTP 双因素，Token 有过期时间控制，兼容性降级策略合理。整体认证架构满足安全要求。

#### 2.2 数据安全

- **评审意见与发现：** 本功能涉及的敏感数据主要包括 TOTP seed（共享密钥）和认证 Token。TOTP seed 通过 SQL 命令 `ALTER USER ... TOTPSEED` 写入，存储于 TSDB 服务端用户元数据中，其存储安全由服务端统一保障。Token 同样由服务端管理，通过 `ins_tokens` 系统表查询。FS 设计中 Token 具备 expire_time 机制，限制了 Token 泄露后的影响窗口。TOTP seed 支持通过 `TOTPSEED NULL` 清除，满足密钥销毁需求。
- **状态：** 通过
- **说明/依据：** TOTP seed 和 Token 的存储、管理均依赖 TSDB 服务端的安全机制，Token 具有过期控制，TOTP seed 支持清除。数据安全由底层平台统一保障。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** Explorer 登录页面接收的外部输入包括：用户名/密码、TOTP 6位验证码、Token 字符串。TOTP 验证码为固定6位数字格式，验证逻辑由 TSDB 服务端 TOTP 算法完成。Token 为系统生成的字符串，由服务端校验有效性和过期状态。Explorer 作为 Web 前端，SQL 命令通过服务端 API 执行，不直接拼接 SQL，降低了注入风险。
- **状态：** 通过
- **说明/依据：** 输入类型简单且格式固定（数字验证码、系统生成的 Token），验证逻辑由服务端处理，Explorer 前端不直接执行 SQL。

#### 2.4 会话与通信安全

- **评审意见与发现：** 本功能是 Explorer Web 应用的认证增强，复用 Explorer 现有的会话管理（Session/Cookie）和 HTTPS 通信机制。FS 未引入新的通信协议或会话管理方式，不改变现有通信安全架构。
- **状态：** 不适用
- **说明/依据：** 本功能继承 Explorer 现有的会话与通信安全机制，未引入新的通信通道或会话管理方式。

#### 2.5 安全日志与监控

- **评审意见与发现：** FS 未专门设计认证相关的安全日志方案。登录成功/失败、Token 使用、TOTP 验证等安全事件的日志记录由 TSDB 服务端的统一日志机制处理。Explorer 前端的操作日志依赖现有基础设施。
- **状态：** 不适用
- **说明/依据：** 认证事件的日志记录由 TSDB 服务端统一处理，Explorer 前端复用现有日志基础设施，本功能 FS 层面无需额外设计。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 设计方案中包含以下威胁缓解措施：（1）TOTP 双因素认证有效防止单一凭证泄露导致的账户被盗（对应威胁 T-EXPAUTH-01）；（2）Token 过期时间机制限制了 Token 泄露后的可利用时间窗口（对应威胁 T-EXPAUTH-02）；（3）TOTP 为可选启用，不影响现有用户体验的同时为安全敏感用户提供增强保护（对应威胁 T-EXPAUTH-07）；（4）Token 全生命周期管理（创建、修改过期时间、删除）提供了完整的凭证控制能力（对应威胁 T-EXPAUTH-08）。
- **状态：** 通过
- **说明/依据：** 设计方案针对主要威胁场景提供了合理的缓解措施，具体威胁分析详见「Explorer 支持 Token 和 TOTP 认证 - 威胁建模报告」。

#### 2.7 默认安全配置

- **评审意见与发现：** FS 兼容性设计（第15节）明确：（1）社区版不展示 Token 和 2FA 登录选项；（2）3.4.0.0 之前的版本不展示新认证选项；（3）3.4.0.0 之后的版本，TOTP 仅在用户主动启用后才显示 2FA 入口。这种渐进式启用策略确保了默认安装配置的安全性——新功能不会改变现有用户的认证行为，同时避免了未配置完成的安全功能暴露攻击面。
- **状态：** 通过
- **说明/依据：** TOTP 默认不启用（需用户主动配置 TOTPSEED），Token 需显式创建，兼容性降级策略合理。默认配置不引入新的风险。

#### 2.8 依赖组件安全

- **评审意见与发现：** 本功能依赖的核心组件包括：（1）TOTP 算法——基于 RFC 6238 标准，是业界成熟的双因素认证方案；（2）TSDB 服务端的用户管理和 Token 管理能力——由身份鉴别 FS 统一定义和实现。Explorer 前端不引入额外的认证相关第三方依赖。
- **状态：** 不适用
- **说明/依据：** 核心认证逻辑依赖 TSDB 服务端实现（身份鉴别 FS 统一管理），Explorer 层面未引入额外的安全相关第三方组件。

#### 2.9 隐私设计

- **评审意见与发现：** 本功能不涉及额外的用户隐私数据收集。TOTP seed 属于安全凭证而非个人隐私信息，Token 为系统生成的认证凭据。功能设计未引入用户行为追踪、个人信息采集等隐私相关变更。
- **状态：** 不适用
- **说明/依据：** 本功能仅涉及认证方式增强，不涉及隐私数据的新增收集或处理。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** （1）密钥轮换：TOTP seed 支持通过 `ALTER USER ... TOTPSEED` 更新，Token 支持通过 `ALTER token SET expire_time` 和 `DROP token` 进行管理和撤销，满足凭证轮换需求；（2）可扩展性：认证方式通过兼容性判断按版本渐进启用，架构可扩展；（3）运维安全：Token 和 TOTP 管理均通过标准 SQL 命令操作，可纳入现有运维流程。
- **状态：** 通过
- **说明/依据：** TOTP seed 和 Token 均支持更新、删除操作，满足凭证生命周期管理需求，运维操作通过标准 SQL 接口完成。

### 3. 评审结论

1. **总体安全风险等级：**
  - 低风险：Explorer 支持 Token 和 TOTP 认证的设计方案整体安全，核心认证逻辑依赖 TSDB 服务端（身份鉴别 FS）的统一实现，Explorer 前端主要负责 UI 交互和认证流程编排。设计中包含了 Token 过期控制、TOTP 可选启用、版本兼容降级等安全机制，能有效满足安全需求。
2. **评审结论：**
  - 通过：设计方案安全合理，认证流程清晰完整，安全机制覆盖主要威胁场景，准予进入编码实现阶段。
