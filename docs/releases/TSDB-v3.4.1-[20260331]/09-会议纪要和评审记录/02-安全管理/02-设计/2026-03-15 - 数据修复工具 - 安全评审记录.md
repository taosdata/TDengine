### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** 本工具为本地离线 CLI 工具，FS §6 明确说明"不引入新的认证、鉴权或网络暴露面"。操作入口为 `taosd -r`，需要本地系统级执行权限，访问控制完全依赖操作系统用户权限管控。修复流程仅在显式传入 `-r` 参数时触发，正常启动路径不会自动进入修复模式，满足安全默认原则。对于离线本地运维工具，此方案合理，无需额外认证层。
- **状态：** 通过
- **说明/依据：** FS §6："修复流程必须由本地运维显式使用 taosd -r 触发，不会在正常启动中自动进入。" 符合最小暴露面原则。

#### 2.2 数据安全

- **评审意见与发现：** FS §4.3 和 §6 设计了 `--backup-path` 备份机制，在执行破坏性修复前于 `${backup-path}/taos_backup_YYYYMMDD/vnode<id>/` 目录下生成备份副本，提供取证与回滚能力。备份内容与正常 TDengine 数据文件一致，采用明文存储，与 TDengine 现有数据存储安全策略一致，不是本次变更引入的新风险。未指定 `--backup-path` 时，代码允许回退到临时目录，临时目录受 OS 权限控制。
- **状态：** 通过
- **说明/依据：** 备份机制作为可选的安全保障手段设计合理；数据存储策略与现有方案一致。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** FS §4.7 定义了完整的命令行参数解析错误契约，对所有非法输入场景（未知 file type、重复 key、非法 strategy、缺少必填字段、重复 target 命中同一对象、`fileid=*` 与显式 fileset 混用等）均有结构化错误提示，不暴露内部状态细节。`--repair-target` 采用结构化 grammar 设计（`<file-type>:<key>=<value>...`），有效约束了输入范围，且明确禁止重复 key 和重复 target。错误信息均为描述性文本，不包含内存地址、堆栈信息等敏感系统细节。
- **状态：** 通过
- **说明/依据：** FS §4.7 错误契约设计完备，grammar 的结构化约束有效限制了输入攻击面。

#### 2.4 会话与通信安全

- **评审意见与发现：** 本工具为纯本地离线 CLI 工具，不涉及任何网络通信、会话管理或远程接口。FS §2 明确说明"不引入新的 SQL 接口，不改变在线写入流程"；FS §7 明确说明"不改变客户端协议"；FS §6 明确说明"不扩大到更高层级的远程或集群控制面"。
- **状态：** 不适用
- **说明/依据：** 无网络通信路径，会话与通信安全维度不适用。

#### 2.5 安全日志与监控

- **评审意见与发现：** FS §12 说明修复过程会产生可观测性输出：CLI/日志中出现 repair 调度痕迹（如 `tsdb force repair dispatch`）；TSDB repair 场景会生成 `repair.log`，记录 `fid`、`action`、`reason` 等字段；带备份路径运行时可在备份目录下观察到 `taos_backup_YYYYMMDD/vnodeX/...` 结构。上述日志信息结合操作系统审计日志（如 auditd）可满足运维溯源需求。`repair.log` 中记录的字段（fid、action、reason）覆盖了修复操作的关键决策点。
- **状态：** 通过
- **说明/依据：** 现有日志设计满足基本运维溯源需求；配合 OS 层审计日志可实现完整溯源。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 针对威胁建模报告（TM-TSDB-DATAREP-001）中识别的主要威胁，设计中已有对应缓解措施：
  - **T-REPAIR-03（误操作扩大范围）**：严格的 grammar 设计禁止 `fileid=*` 与显式 fileset target 在同一 vnode 下混用，禁止重复 target 命中同一对象（FS §4.2）；
  - **T-REPAIR-02（备份路径风险）**：`--backup-path` 为可选参数，设计上允许运维人员选择受控目录存放备份（FS §4.3）；
  - **T-REPAIR-06（资源耗尽）**：修复为离线操作，应在停服后执行（FS §8），缓解在线服务影响；
  - **T-REPAIR-07（意外影响非目标 vnode）**：grammar 强制要求显式指定 `vnode=<id>`，每个 target 精确定位修复对象（FS §4.2）；
  - **意外进入修复模式**：需显式 `-r` 参数，不会在正常启动中自动激活（FS §4.1）。
- **状态：** 通过
- **说明/依据：** 已识别的关键威胁均有对应的设计或运维层面缓解措施。

#### 2.7 默认安全配置

- **评审意见与发现：** 默认不进入修复模式（需显式 `-r`），满足"安全默认"原则。meta 默认策略为 `from_uid`，TSDB 默认策略为 `drop_invalid_only`（最保守策略，仅处理显式缺失文件，不做 size mismatch 深度扫描），符合最小破坏原则（FS §4.2）。需要更激进修复（`head_only_rebuild`、`full_rebuild`）时必须显式声明，避免默认操作超出预期范围。
- **状态：** 通过
- **说明/依据：** 默认策略设计遵循最小破坏原则，激进策略需显式启用，安全默认配置合理。

#### 2.8 依赖组件安全

- **评审意见与发现：** 本功能复用 TDengine 现有的本地文件系统操作库和 WAL 损坏修复路径（FS §4.5），不引入新的第三方库、外部框架或外部服务。FS §13 明确说明"不新增安装包组件，不修改用户安装/卸载脚本接口"。
- **状态：** 不适用
- **说明/依据：** 无新增外部依赖组件。

#### 2.9 隐私设计

- **评审意见与发现：** 数据修复工具处理的是存储结构层面的数据文件（meta 元数据、tsdb fileset、wal 日志），不新增个人数据处理路径。TDengine 作为时序数据库，存储内容通常为设备/传感器数据，不直接处理个人身份信息（PII）。备份文件的访问控制依赖操作系统权限，与现有 TDengine 数据文件访问控制策略一致。
- **状态：** 不适用
- **说明/依据：** 无新增个人数据处理路径，隐私设计维度不适用。

#### 2.10 其他（运维安全等）

- **评审意见与发现：** FS §8 提出了完整的运维安全要求，涵盖以下关键约束：
  - 修复为离线动作，应在目标节点停服或明确进入本地 repair 启动流程后执行；
  - 使用 `fileid=*` 前需确认修复范围，避免误修复超出预期；
  - 指定 `--backup-path` 时需预留足够磁盘空间，防止备份过程中磁盘写满；
  - 修复后应重新正常启动 `taosd` 并验证数据可读可写，形成完整运维闭环。
  
  上述运维安全要求已明确写入 FS，并已同步更新至官网运维文档（`docs/zh/08-operation/05-maintenance.md` 等，FS §14），运维规范传达路径完整。
- **状态：** 通过
- **说明/依据：** 运维安全要求完整且已同步至外部文档，满足运维可操作性要求。

2. **评审结论：** 通过
   - 准予进入下一阶段（编码实现）。
