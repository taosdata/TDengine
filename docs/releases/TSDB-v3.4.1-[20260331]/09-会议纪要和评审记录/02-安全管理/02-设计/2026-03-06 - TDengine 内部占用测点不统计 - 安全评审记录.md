### 2. 安全评审记录

评审团队对设计文档进行了审查，评估其安全机制、架构和实现细节是否足以抵御威胁。具体评审意见如下：

#### 2.1 身份认证与访问控制

- **评审意见与发现：** 本功能仅调整内部测点统计逻辑，不引入新的认证或授权机制。`show grants` 命令的查询权限由 TDengine 现有权限体系管控，不在本次变更范围内。
- **状态：** 不适用
- **说明/依据：** FS 中无涉及认证与访问控制的新设计，现有 TDengine 权限模型不受影响。

#### 2.2 数据安全

- **评审意见与发现：** 本功能不涉及新的敏感数据存储或传输。测点计数属于内部统计指标，不包含用户业务数据。
- **状态：** 不适用
- **说明/依据：** FS 中无加密、脱敏或数据隔离相关设计变更。

#### 2.3 输入/输出验证与编码

- **评审意见与发现：** 系统超级表名单以代码常量形式硬编码维护，不依赖外部输入。`show grants` 输出展示实际测点值（不含冗余缓冲），信息准确、无敏感泄露风险。FS 明确指出 "show grants 均展示实际的测点值"，与许可证校验逻辑分离。
- **状态：** 通过
- **说明/依据：** 排除逻辑基于代码内置名单，不存在外部可控注入点；输出字段为统计整数，无格式化风险。

#### 2.4 会话与通信安全

- **评审意见与发现：** 本功能不引入新的会话管理或通信协议，无需评审。
- **状态：** 不适用
- **说明/依据：** FS 无相关变更。

#### 2.5 安全日志与监控

- **评审意见与发现：** 本功能正是为了保证 log 库和审计库中的系统表不被纳入测点统计，从而确保监控和审计基础设施本身的数据不干扰许可证计量。现有审计库（operations 超级表等）的写入与查询行为不受影响。
- **状态：** 通过
- **说明/依据：** 审计库 operations 表已列入方案 3 的系统超级表名单（见 FS §4.2），其子表测点将被正确排除。

#### 2.6 威胁缓解机制

- **评审意见与发现：** 参见威胁建模报告（TM-TSDB-SYSMET-001）。主要威胁为测点统计绕过（T-SYSMET-01），现有设计通过仅排除已知系统超级表（而非整个 log/审计库）加以缓解，用户自建的同名表仍会被计入，风险可接受。
- **状态：** 通过
- **说明/依据：** 方案 3 采用"排除已知系统超级表对应子表"的精确匹配策略，优于排除整库（方案 2），减少了绕过空间。

#### 2.7 默认安全配置

- **评审意见与发现：** 自 TDengine 3.4.0.0 起审计库名称可配置，不再固定为 `audit`。FS §4.1 方案 3 描述中已将排除对象定义为 "log 库/审计库中已知的系统超级表对应的子表"，要求系统在运行时正确识别当前配置的审计库名，该机制属于已知设计范围。
- **状态：** 通过
- **说明/依据：** FS §4.2 明确注明"TDengine 3.4.0.0 及后续版本，审计库名称可以指定，不再固定为 audit"，说明设计已知晓此情况并纳入考虑范围。

#### 2.8 依赖组件安全

- **评审意见与发现：** 本功能依赖硬编码的系统超级表名单（FS §4.2 中已列出数十个表名），名单需随系统表新增手工更新。FS 已通过两个机制缓解维护遗漏风险：① 约定新增系统表均通过超级表/子表创建，明确由使用方通知 TDengine 更新名单；② 额外冗余 1000 测点作为容差，防止短暂未更新期间误触发许可证超限告警。
- **状态：** 通过
- **说明/依据：** 1000 点容差仅影响超限判断门槛，不影响 `show grants` 展示的真实值，工程上合理且已有流程约束。

#### 2.9 隐私设计

- **评审意见与发现：** 本功能不涉及用户个人数据的采集、存储或处理，无隐私相关需求。
- **状态：** 不适用
- **说明/依据：** FS §6 安全和 §9 使用场景均未提及隐私相关内容。

#### 2.10 其他（可扩展性、运维安全等）

- **评审意见与发现：** 1000 点冗余缓冲仅用于许可证超限判断，`show grants` 展示真实值，运维人员可准确感知实际测点使用情况，不影响计费透明度。名单的维护流程（"由使用方通知 TDengine 更新"）为明确的运维约定。
- **状态：** 通过
- **说明/依据：** 设计兼顾了准确性（精确排除已知系统表）与健壮性（1000 点容差），工程权衡合理。

### 3. 评审结论

1. **总体安全风险等级：**
   - **低风险**：本功能仅调整内部测点计数逻辑，不引入新的认证、通信或数据处理机制。主要风险为测点统计精度问题（许可证层面），已通过精确名单匹配和容差缓冲充分缓解。

2. **评审结论：**
   - **通过**：准予进入下一阶段（编码实现）。所有评审维度均通过或不适用，无待定项。
