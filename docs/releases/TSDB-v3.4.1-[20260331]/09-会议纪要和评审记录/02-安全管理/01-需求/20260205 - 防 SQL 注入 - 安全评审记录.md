### 一、安全资产与信任边界识别

- 状态：待定
- 评审意见与发现：
  - 文档已识别 SQL 查询链路上的主要攻击面（恒真注入、UNION、多语句、编码混淆、危险函数、异常 JOIN 等），说明对“查询语义被篡改”这一核心资产风险已有较完整视角。
  - 对“资产分级”描述不足：未明确区分账号凭证、业务时序数据、系统配置（如 taos.cfg、规则文件）、审计日志、密钥材料等资产等级与保护要求。
  - 信任边界描述不完整：仅以“客户端/解析前置/语义分析/审计”等模块呈现防护层次，但未明确定义边界（客户端输入边界、连接协议边界、集群节点间边界、UDF 执行边界、外部 API 边界）。
- 说明/依据：
  - 需求文档已列出多类注入场景与模块落点，具备技术分层基础。
  - 若未明确资产等级与边界，后续权限、日志、密钥和告警策略将难以做差异化控制。

### 二、安全功能需求

- 状态：待定
- 评审意见与发现：
  - 优点：对输入验证与语义检查覆盖较充分，提出字符串级（PCRE/关键字/注释/编码）+ AST 级（WHERE/HAVING/函数/子查询/JOIN）双层检测，并定义黑白名单优先级。
  - 优点：包含配置管理、自动学习、审计日志与告警方向，具备从“阻断”到“可追溯”的闭环雏形。
  - 缺口：缺少“参数化查询/参数绑定优先”作为首要控制策略的强制要求，当前方案偏检测拦截，仍有绕过与误报成本。
  - 缺口：认证与授权章节为能力罗列，未明确与注入防护的联动要求（如被判定高风险 SQL 的账号冻结策略、按角色差异化策略、失败重试节流）。
  - 缺口：加密通信、配置加密仅为原则性表述，未给出协议/密钥轮换/兼容模式/降级禁止策略等验收标准。
- 说明/依据：
  - 需求在检测层很详细，但“预防优先（参数绑定）+ 最小权限 + 密钥治理”三项未形成强约束，会影响长期安全稳定性。

### 三、隐私保护需求

- 状态：不适用
- 评审意见与发现：
  - 文档主题聚焦 SQL 注入防护，未涉及新增个人信息采集、画像、跨境传输、用户同意管理等隐私处理流程。
  - 当前风险主要是业务/系统数据被越权访问或篡改，不属于新增隐私处理场景设计问题。
- 说明/依据：
  - 若后续审计日志新增用户标识、客户端 IP、请求体持久化等字段，应补充最小化采集与脱敏策略评审。

### 四、合规性需求

- 状态：待定
- 评审意见与发现：
  - 文档未将需求与具体合规控制项建立映射（如等保 2.0 的身份鉴别、访问控制、安全审计、通信保密、入侵防范要求）。
  - 缺少“证据可审计性”要求：未规定安全规则变更、策略启停、告警处置、审计日志保留期限与防篡改机制。
- 说明/依据：
  - 当前有“审计日志/权限/加密通信”能力描述，但缺乏面向监管检查的“条款-控制点-证据”闭环，合规可证明性不足。

### 五、威胁与滥用场景

- 状态：待定
- 评审意见与发现：
  - 优点：已覆盖主流注入与语义绕过场景，尤其包括编码混淆、危险函数、多语句、子查询和异常 JOIN，方向正确。
  - 缺口：对 TDengine 典型高吞吐写入与时序查询场景下的资源耗尽攻击（复杂表达式、恶意大查询、笛卡尔积放大）缺少速率限制与资源配额要求。
  - 缺口：未定义“学习模式被投毒”威胁（攻击者通过高频恶意样本污染白名单）及对应防护（人工审批、灰度、生效延迟、回滚）。
  - 缺口：未定义旁路风险（REST API、连接器、订阅链路、UDF 执行路径）的一致策略要求。
- 说明/依据：
  - 该文档已具备威胁清单基础，但对可滥用机制与运维路径的攻击面建模仍不足，影响防护完整性。

### 六、默认安全与易用性

- 状态：待定
- 评审意见与发现：
  - 文档强调可配置与学习模式，利于业务兼容，但未明确“默认配置”安全基线（例如默认开启哪些检测、默认拒绝哪些高危行为）。
  - 未给出策略启用路径中的“安全兜底”要求：仅靠运维手工配置可能导致初次部署阶段保护不足。
  - 运维可用性优化已有方向（批量编辑、规则校验、日志筛选），但缺少误拦截处置流程（快速豁免、影响面评估、回滚窗口）。
- 说明/依据：
  - 对数据库产品而言，默认安全策略与低摩擦运维流程决定了功能是否真正可持续落地。

### 七、依赖与供应链安全

- 状态：待定
- 评审意见与发现：
  - 文档提及 PCRE 等依赖，但未定义第三方组件版本基线、漏洞响应 SLA、许可证合规审查与升级策略。
  - 对 UDF 生态仅从函数调用权限看待，未覆盖 UDF 脚本来源可信性、签名校验要求。
- 说明/依据：
  - 注入防护强依赖解析与正则组件正确性；若依赖治理缺失，可能引入新漏洞或合规风险。

### 八、可观测性与响应

- 状态：待定
- 评审意见与发现：
  - 文档已提出记录被拒绝 SQL、触发规则、学习模式行为，并区分日志级别，具备良好基础。
  - 缺口：未定义最小告警集合（高危注入命中率、同源多次触发、规则误报率、规则更新失败率）与告警阈值。
  - 缺口：未定义事件分级响应流程（研判、隔离、封禁、复盘）与时效目标（如 P1/P2 响应时限）。
  - 缺口：未明确日志完整性保护（防篡改、时钟同步、跨节点关联 ID）。
- 说明/依据：
  - 没有监控指标与响应流程，审计日志只能“记录”，难以形成真实防守能力。

### 九、综合评估

- 总体安全风险等级：中风险
- 风险等级理由：
  - 需求对 SQL 注入检测维度覆盖较广，且具备分层防护思路，基础方向正确。
  - 但在资产/边界建模、默认安全基线、供应链治理、合规映射、运行期告警响应方面存在可利用空档，落地后仍有被绕过或运维失效风险。
- 评审结论：有条件通过
- 结论理由：
  - 在“高优先级注入防护增强”方向可推进实施；
  - 需在版本冻结前完成本记录中待定项的关键补强并形成可验证验收标准。
