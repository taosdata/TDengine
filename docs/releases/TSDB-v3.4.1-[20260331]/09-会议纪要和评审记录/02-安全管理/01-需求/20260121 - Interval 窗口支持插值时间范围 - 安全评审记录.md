## 安全评审记录

评审团队对需求文档进行了审查，重点关注安全、隐私与合规要求的覆盖度与合理性。具体评审意见如下：

### 1 安全资产与信任边界识别

- **评审意见与发现：** 本需求为 TDengine SQL 查询语法的功能扩展，在 `fill(prev/next)` 中新增 `window_num` 参数以限制插值查找的时间窗口个数。该功能作用于查询路径，不涉及新的数据资产引入（无凭证、配置变更、用户敏感数据处理）。信任边界未发生变化——查询请求仍经由现有的客户端→taosd 查询引擎路径处理，`window_num` 参数在 SQL 解析层被消费，不跨越额外的信任边界。
- **状态：** 通过
- **说明/依据：** 功能仅扩展现有 Interval 查询的填充行为，数据资产与信任边界与现有 fill 语句一致，无新增风险面。

### 2 安全功能需求

- **评审意见与发现：** 该需求为纯查询侧语法扩展，不涉及身份认证、访问控制、授权模型的变更。查询权限沿用现有的数据库/表级权限控制。需关注的安全功能点为输入验证——`window_num` 参数需在 SQL 解析阶段进行严格校验：需求文档中未明确 `window_num` 的取值范围与边界条件，建议在 FS 阶段补充。
  - 类型校验：必须为非负整数
  - 范围校验：应设定合理上限，防止极大值导致查询引擎遍历过多窗口造成资源消耗
  - 仅在 `prev`/`next` 填充模式下有效，其他填充模式应拒绝该参数
- **状态：** 待定
- **说明/依据：** 输入验证是本需求唯一需要关注的安全功能点。需求文档未定义 `window_num` 的合法取值范围（最小值、最大值、为 0 时的语义），建议在功能规格中明确，以防止非法输入导致的异常行为。

### 3 隐私保护需求

- **评审意见与发现：** 本需求不涉及个人信息或隐私数据的处理。功能仅改变时序数据聚合结果的填充策略，不新增数据采集、存储或传输环节。
- **状态：** 不适用
- **说明/依据：** Interval 填充为纯计算逻辑，不涉及 PII 或隐私数据处理。

### 4 合规性需求

- **评审意见与发现：** 本需求为查询语法扩展，不涉及数据存储方式、加密机制、访问控制模型的变更，不影响等保 2.0、关基条例等合规要求的满足状态。
- **状态：** 不适用
- **说明/依据：** 功能变更范围限于查询结果填充逻辑，不触及合规敏感领域。

### 5 威胁与滥用场景

- **评审意见与发现：** 从攻击者视角分析，本需求的主要威胁场景为：需求文档的「安全需求」章节标注为"不涉及"，对于纯查询语法扩展基本合理，但建议在 FS/DS 阶段补充 `window_num` 上限约束以防范资源耗尽场景。
   - **资源耗尽（DoS）：** 若 `window_num` 允许极大值（如 INT\_MAX），攻击者可构造恶意查询，迫使查询引擎遍历海量时间窗口，消耗 CPU 和内存资源。缓解措施：在 SQL 解析层设定 `window_num` 上限，并依赖现有的查询超时机制。
   - **SQL 注入：** `window_num` 作为整数参数在 SQL 解析器中处理，TDengine 的 SQL 解析器基于语法树构建，非字符串拼接，注入风险极低。
- **状态：** 待定
- **说明/依据：** 主要风险为通过极大 `window_num` 值触发资源耗尽。建议在功能设计中明确参数上限，并确认现有查询超时/资源限制机制对该场景的覆盖。

### 6 默认安全与易用性

- **评审意见与发现：** 当用户不指定 `window_num` 时，行为与现有 `fill(prev/next)` 完全一致（向前/向后无限查找），保持了向后兼容。新增参数为可选项，符合最小惊讶原则。默认行为安全，不会因功能扩展引入意外的安全降级。
- **状态：** 通过
- **说明/依据：** 语法设计为向后兼容的可选参数扩展，默认行为不变，符合默认安全原则。

### 7 依赖与供应链安全

- **评审意见与发现：** 本需求为 TDengine 内部查询引擎的逻辑扩展，不引入新的第三方组件、外部服务或依赖库。实现预期在现有 SQL 解析器和查询执行器代码基础上修改。
- **状态：** 不适用
- **说明/依据：** 无新增外部依赖。

### 8 可观测性与响应

- **评审意见与发现：** 本需求为查询语法扩展，现有的慢查询日志、查询审计日志机制可覆盖包含 `window_num` 参数的查询语句记录。无需新增专门的安全日志或监控指标。
- **状态：** 通过
- **说明/依据：** 现有查询日志与监控机制足以覆盖本功能的可观测性需求。

### 9 其他意见

- **评审意见与发现：** 需求文档的性能需求提到"衰减程度小于 5%"，建议在 FS/DS 阶段明确性能基准测试方案，确保大 `window_num` 值场景下的性能表现可控。
- **状态：** 通过
- **说明/依据：** 性能相关建议，非安全阻塞项。

## 评审结论

1. **总体安全风险等级：** 低风险
  - 本需求为纯查询语法扩展，不涉及认证、授权、数据存储、隐私等安全敏感领域。唯一需关注的是 `window_num` 参数的输入验证与资源耗尽防护，属于常规的输入校验范畴，风险可控。
1. **评审结论：** 有条件通过
  - 需完成下述行动项中关于 `window_num` 取值范围定义的工作，经确认后可进入设计阶段。
