# 窗口查询功能增强

## 一、功能背景与问题来源

### 1.1 业务痛点

在实际工业场景中,用户在使用窗口查询和插值功能时经常遇到以下挑战:

**插值探索范围无限制:**
- **FILL(PREV/NEXT) 探索范围过大** - 无法控制数据探索范围,可能引用过远的历史数据
- **无法设置默认值** - 未找到有效数据时无法指定兜底值,业务逻辑不灵活
- **NULL 值处理不灵活** - 无法跳过 NULL 值继续探索有效数据

**功能使用不统一:**
- **INTERP 和 INTERVAL 功能不一致** - INTERP 已支持时间范围限制,但 INTERVAL 窗口不支持
- **学习成本高** - 两个功能的使用方式不同,增加用户学习负担

### 1.2 典型场景示例

**场景一:电表数据异常检测**
- 问题:按小时统计电表数据,对缺失数据使用 FILL(PREV) 填充,但希望只使用最近 2 小时内的数据,超过 2 小时则填充为 0,现有功能无法实现
- 影响:数据填充逻辑不符合业务要求,需要应用层二次处理

**场景二:设备状态监控**
- 问题:设备传感器经常产生 NULL 值,使用 FILL(PREV) 时希望跳过 NULL 继续向前查找有效数据,而不是直接用 NULL 填充
- 影响:填充结果不准确,影响数据分析质量

**场景三:生产报表生成**
- 问题:按班次统计生产数据,缺失班次希望用最近一个班次数据填充,但不能跨天,现有功能无法精确控制
- 影响:跨天填充导致统计结果失真

### 1.3 为什么需要窗口查询增强?

**窗口函数是时序数据分析的核心:**
- 插值填充是处理缺失数据的常用手段,需要更灵活的控制能力
- 不同业务场景对数据探索范围有不同要求,需要可配置
- 与 INTERP 功能保持一致,降低用户学习成本

**TDengine 3.4.0/3.4.1** 通过增强窗口查询功能,提供精确的插值控制能力,满足复杂业务需求。

## 二、功能介绍与核心特性

### 2.1 INTERVAL 窗口插值增强 (3.4.1)

#### 2.1.1 功能概述

INTERVAL 窗口查询使用 FILL(PREV/NEXT/NEAR) 模式时,现在可以通过 SURROUND 子句限制插值的数据探索范围,并设置找不到有效数据时的默认值。

#### 2.1.2 语法格式

```sql
SELECT ... 
FROM table_name
WHERE ...
INTERVAL(interval_val) 
FILL(fill_mode) 
SURROUND(surrounding_time_interval, fill_values);
```

**参数说明:**

| 参数 | 说明 | 取值范围 |
| --- | --- | --- |
| fill_mode | 插值模式 | PREV / NEXT / NEAR |
| surrounding_time_interval | 数据探索时间范围 | >0,且 ≥ interval,不支持年(y)月(n) |
| fill_values | 未找到有效数据时的默认值 | 必须与 SELECT 列数一致,类型兼容 |

#### 2.1.3 核心行为说明

**数据探索范围计算:**
- FILL(PREV):探索 [当前窗口时间 - surrounding_time_interval, 当前窗口时间] 范围内的数据
- FILL(NEXT):探索 [当前窗口时间, 当前窗口时间 + surrounding_time_interval] 范围内的数据
- FILL(NEAR):探索 [当前窗口时间 - sti, 当前窗口时间 + sti] 范围内的数据

**实际探索窗口数计算:**
- 公式:floor(surrounding_time_interval / interval)
- 示例:INTERVAL(1h) SURROUND(80m, ...),实际探索 1 个窗口 (floor(80/60)=1)
- 示例:INTERVAL(1h) SURROUND(59m, ...),实际探索 0 个窗口 (floor(59/60)=0),直接使用默认值

**约束条件:**
- surrounding_time_interval 不会破坏 WHERE 条件,探索数据必须同时满足两者
- 探索范围内未找到有效数据时,使用 fill_values 填充

#### 2.1.4 使用示例

**场景:电表小时级统计,只使用最近 2 小时数据填充**

```sql
-- 创建电表数据表
CREATE STABLE meters (ts TIMESTAMP, voltage DOUBLE, current DOUBLE, power DOUBLE) 
TAGS (meter_id INT, region VARCHAR(50));

-- 小时级聚合,缺失数据用前值填充,但只探索 2 小时内
SELECT _WSTART, 
       AVG(voltage) AS avg_voltage, 
       AVG(current) AS avg_current,
       SUM(power) AS total_power
FROM meters
WHERE ts >= '2026-04-01' AND ts < '2026-04-08'
  AND meter_id = 1001
INTERVAL(1h) 
FILL(PREV) 
SURROUND(2h, 0, 0, 0);
-- 如果某小时无数据,会在前 2 小时内查找有效数据
-- 超过 2 小时未找到,则填充为 (0, 0, 0)
```

**结果说明:**
```
_WSTART              | avg_voltage | avg_current | total_power
---------------------|-------------|-------------|------------
2026-04-01 00:00:00 |  220.5      |  10.2       |  2250.0     (实际数据)
2026-04-01 01:00:00 |  220.5      |  10.2       |  2250.0     (使用 00:00 数据填充)
2026-04-01 02:00:00 |  220.5      |  10.2       |  2250.0     (使用 00:00 数据填充)
2026-04-01 03:00:00 |  0.0        |  0.0        |  0.0        (超过 2h,使用默认值)
2026-04-01 04:00:00 |  221.8      |  10.5       |  2330.0     (实际数据)
```

**场景:生产线设备效率统计,按班次聚合**

```sql
-- 每 8 小时一个班次,缺失班次用最近数据填充,但不跨天
SELECT _WSTART,
       workshop,
       AVG(oee) AS avg_oee,
       SUM(output_count) AS total_output
FROM production_metrics
WHERE ts >= '2026-04-01' AND ts < '2026-04-08'
PARTITION BY workshop
INTERVAL(8h)
FILL(NEAR)
SURROUND(16h, NULL, NULL);
-- 班次数据缺失时,在前后 16 小时内查找最近数据
-- 超过 16 小时未找到,填充为 NULL
```

#### 2.1.5 伪列行为

配合 INTERP 函数使用时,可通过伪列了解填充来源:

| 伪列 | 含义 | 说明 |
| --- | --- | --- |
| _isfilled | 数据是否来自插值 | 使用 fill_values 填充时为 TRUE |
| _irowts_origin | 引用的原始数据时间戳 | 使用 fill_values 填充时为 NULL |

### 2.2 INTERP 插值忽略 NULL 值 (3.4.0)

#### 2.2.1 功能概述

INTERP 函数新增 `ignore_null_values` 参数,支持在插值时跳过 NULL 值,继续向前/向后探索非 NULL 数据进行填充。

#### 2.2.2 语法格式

```sql
SELECT INTERP(column, ignore_null_values) 
FROM table_name 
WHERE ... 
RANGE(ts1, ts2) 
FILL(prev/next/near/linear);
```

**参数说明:**

| 参数 | 说明 | 取值范围 |
| --- | --- | --- |
| ignore_null_values | 是否忽略 NULL 值 | 0 (默认,NULL 也是有效值) / 1 (忽略 NULL) |

#### 2.2.3 核心行为说明

**3.3.8.x 及之前版本:**
- Prev/Next scan 只扫描一行数据,无论是否为 NULL 都用于插值

**3.4.0.0 及以后版本:**
- `ignore_null_values = 0` (默认):NULL 和 non-NULL 都是有效数据,行为与之前版本一致
- `ignore_null_values = 1`:只有 non-NULL 数据才是有效数据,Prev/Next scan 会跳过 NULL 继续探索

**性能影响:**
- `ignore_null_values = 0`:性能无明显变化
- `ignore_null_values = 1`:性能受数据中 NULL 密度影响,最坏情况需要扫描全表

#### 2.2.4 使用示例

**场景:传感器数据插值,跳过 NULL 值**

```sql
-- 传感器经常产生 NULL 值,需要跳过 NULL 查找有效数据
SELECT _IROWTS, 
       INTERP(temperature, 1) AS temp,  -- ignore_null_values = 1
       INTERP(humidity, 1) AS hum
FROM sensors
WHERE sensor_id = 1001
  AND ts >= '2026-04-01' 
  AND ts < '2026-04-08'
RANGE('2026-04-01 00:00:00', '2026-04-01 23:59:59')
EVERY(1h)
FILL(PREV);
-- 向前探索时会跳过 NULL 值,继续查找非 NULL 数据
```

**数据示例:**

**原始数据:**
```
ts                   | temperature | humidity
---------------------|-------------|----------
2026-04-01 00:00:00 | 25.5        | 60
2026-04-01 01:00:00 | NULL        | NULL
2026-04-01 02:00:00 | NULL        | 62
2026-04-01 03:00:00 | 26.0        | NULL
```

**ignore_null_values = 0 (默认):**
```
_IROWTS              | temp  | hum
---------------------|-------|-----
2026-04-01 00:00:00 | 25.5  | 60
2026-04-01 01:00:00 | 25.5  | 60    (使用前一个值,包括 NULL)
2026-04-01 02:00:00 | NULL  | NULL  (使用前一个值 NULL)
2026-04-01 03:00:00 | NULL  | 62    (使用前一个值)
```

**ignore_null_values = 1:**
```
_IROWTS              | temp  | hum
---------------------|-------|-----
2026-04-01 00:00:00 | 25.5  | 60
2026-04-01 01:00:00 | 25.5  | 60    (跳过 NULL,使用 00:00 的非 NULL 值)
2026-04-01 02:00:00 | 25.5  | 62    (temp 跳过 NULL 使用 00:00,hum 使用 02:00)
2026-04-01 03:00:00 | 26.0  | 62    (temp 使用 03:00,hum 跳过 NULL 使用 02:00)
```

#### 2.2.5 注意事项

**找不到非 NULL 值的情况:**
- `ignore_null_values = 1` 不代表一定能找到 non-NULL 值
- 如果 Prev/Next scan 扫描到的数据全部为 NULL,该时间点无法插值,不会输出结果

**性能优化建议:**
- 使用 WHERE 条件限定扫描数据的时间范围,避免全表扫描
- 非必要情况使用默认值 (ignore_null_values = 0)

## 三、典型应用场景与价值

### 3.1 场景一:电表数据缺失智能填充

**业务需求:**
电力公司按小时统计电表数据,对缺失小时使用前值填充,但只允许使用最近 2 小时内的数据,超过 2 小时则认为设备故障,填充为 0。

**客户价值:**
- ✅ 使用 SURROUND 子句精确控制数据探索范围
- ✅ 设置合理的默认值,避免使用过远的历史数据
- ✅ 一条 SQL 完成复杂填充逻辑,无需应用层处理

**实现方案:**

```sql
-- 小时级电表统计,限制填充范围为 2 小时
SELECT _WSTART,
       meter_id,
       AVG(voltage) AS avg_voltage,
       AVG(current) AS avg_current,
       SUM(power) AS total_power_kwh
FROM meters
WHERE ts >= '2026-04-01' AND ts < '2026-04-08'
PARTITION BY meter_id
INTERVAL(1h)
FILL(PREV)
SURROUND(2h, 0, 0, 0);
-- 缺失小时会在前 2 小时内查找有效数据
-- 超过 2 小时未找到,填充为 (0, 0, 0),标记为设备故障
```

**业务价值:**
- 避免使用过远的历史数据误导分析
- 自动识别设备故障 (填充为 0 的记录)
- 符合电力行业数据质量要求

### 3.2 场景二:传感器数据质量提升

**业务需求:**
工业传感器经常产生 NULL 值 (通信故障、传感器故障等),在数据分析时需要跳过 NULL 值,使用最近的有效数据进行填充。

**客户价值:**
- ✅ 使用 ignore_null_values 参数跳过 NULL 值
- ✅ 自动查找最近的有效数据,提升数据质量
- ✅ 无需应用层清洗 NULL 数据

**实现方案:**

```sql
-- 每 10 分钟插值一次,跳过 NULL 值
SELECT _IROWTS,
       device_id,
       INTERP(temperature, 1) AS temp,
       INTERP(pressure, 1) AS pressure,
       INTERP(vibration, 1) AS vibration
FROM device_sensors
WHERE device_id = 'device_001'
  AND ts >= '2026-04-01'
  AND ts < '2026-04-02'
RANGE('2026-04-01 00:00:00', '2026-04-01 23:59:59')
EVERY(10m)
FILL(PREV);
-- 向前探索时跳过 NULL,查找最近的有效数据
```

**业务价值:**
- 提升数据完整性和准确性
- 减少因 NULL 值导致的分析误差
- 自动化数据清洗,降低运维成本

## 四、运维最佳实践

### 4.1 窗口插值使用建议

**合理设置探索范围:**
- 根据业务容忍度设置 surrounding_time_interval
- 公式:floor(sti / interval) 确定实际探索窗口数
- 示例:INTERVAL(1h) SURROUND(2h30m, ...) 实际探索 2 个窗口 (floor(150/60)=2)
- 示例:INTERVAL(1h) SURROUND(59m, ...) 实际探索 0 个窗口 (floor(59/60)=0),直接使用默认值

**默认值选择原则:**
- **数值类型:**使用 0 或业务阈值 (如设备故障、停机状态)
- **NULL:**表示数据缺失,便于后续识别和处理
- **避免极端值:**不建议使用 -999、-9999 等极端值,容易污染统计结果

**WHERE 条件配合使用:**
- surrounding_time_interval 不会破坏 WHERE 条件
- 探索数据必须同时满足 WHERE 和 surrounding_time_interval 限制
- 建议使用 WHERE 条件进一步缩小扫描范围,提升性能

### 4.2 INTERP ignore_null_values 使用建议

**何时使用 ignore_null_values = 1:**
- 数据中 NULL 值是异常值 (传感器故障、通信中断)
- 需要跳过 NULL 查找最近的有效数据
- 数据质量优先于性能

**何时使用 ignore_null_values = 0 (默认):**
- NULL 值有业务含义 (如设备未启动、测点未激活)
- 数据中 NULL 密度较高,性能优先
- 不希望改变原有 INTERP 行为

**性能优化建议:**
- 使用 WHERE 条件限定扫描数据的时间范围
- 避免在全表数据上使用 ignore_null_values = 1
- 如果 NULL 密度很高 (>50%),考虑使用默认值或应用层处理

**注意未找到非 NULL 值的情况:**
- `ignore_null_values = 1` 不保证一定能找到 non-NULL 值
- 如果扫描范围内全是 NULL,该时间点不会输出结果
- 建议结合 WHERE 条件缩小扫描范围,提高找到有效值的概率

### 4.3 流计算中的限制

**INTERVAL FILL SURROUND 在流计算中的行为:**
- 每个触发窗口独立计算,无法引用前一触发窗口的数据
- FILL(PREV) 只在当前触发窗口内探索数据
- 示例:
  - 触发窗口 1: [00:00, 01:00),FILL(PREV) 只能探索该窗口内的数据
  - 触发窗口 2: [01:00, 02:00),无法引用触发窗口 1 的数据

**建议:**
- 流计算场景下,合理设置触发窗口大小和 surrounding_time_interval
- 确保 surrounding_time_interval 小于触发窗口大小
- 如需跨触发窗口填充,考虑使用更长的触发窗口或调整流计算策略

### 4.4 常见问题排查

**问题一:SURROUND 没有生效**
```sql
-- 检查 surrounding_time_interval 是否 < interval
INTERVAL(1h) SURROUND(30m, ...)  -- 错误: 30m < 1h,实际探索 0 个窗口

-- 正确设置:surrounding_time_interval >= interval
INTERVAL(1h) SURROUND(2h, ...)   -- 正确: 实际探索 2 个窗口
```

**问题二:ignore_null_values = 1 性能很慢**
```sql
-- 检查数据中 NULL 密度
SELECT COUNT(*) AS total,
       COUNT(temperature) AS non_null,
       (COUNT(*) - COUNT(temperature)) / COUNT(*) * 100 AS null_rate
FROM sensors
WHERE ts >= '2026-04-01' AND ts < '2026-04-08';

-- 如果 null_rate > 50%,考虑:
-- 1. 使用默认值 (ignore_null_values = 0)
-- 2. 缩小 WHERE 条件的时间范围
-- 3. 应用层处理 NULL 值
```

**问题三:INTERP 结果时间点缺失**
```sql
-- ignore_null_values = 1 时,如果找不到非 NULL 值,该时间点不输出
-- 检查扫描范围内是否有非 NULL 值:
```

## 五、总结

### 核心价值

TDengine 3.4.0/3.4.1 的窗口查询增强为时序数据分析带来了**更灵活的插值控制**:

1. **精确的探索范围控制** - SURROUND 子句实现精确的时间范围限制,避免使用过远历史数据
2. **合理的默认值设置** - 未找到有效数据时可指定兜底值,符合业务逻辑
3. **智能的 NULL 值处理** - ignore_null_values 参数支持跳过 NULL 继续探索
4. **统一的功能体验** - INTERVAL 和 INTERP 功能保持一致,降低学习成本
5. **灵活的业务适配** - 满足电力、制造、能源等多行业的复杂填充需求

### 快速上手建议

1. **INTERVAL FILL SURROUND:**
   - 理解 surrounding_time_interval 与 interval 的关系
   - 公式 floor(sti/interval) 确定实际探索窗口数
   - 合理设置默认值,避免极端值污染统计
   - 注意:sti 必须 >= interval,否则实际探索为 0

2. **INTERP ignore_null_values:**
   - 默认值 0 保持原有行为,向后兼容
   - 使用 1 时注意性能影响,建议配合 WHERE 条件
   - 找不到非 NULL 值时该时间点不输出
   - 适用于 NULL 值是异常值的场景

3. **最佳实践:**
   - 根据业务容忍度设置探索范围
   - 使用 NULL 作为默认值标记数据缺失
   - WHERE 条件配合使用提升性能
   - 流计算场景注意触发窗口限制
