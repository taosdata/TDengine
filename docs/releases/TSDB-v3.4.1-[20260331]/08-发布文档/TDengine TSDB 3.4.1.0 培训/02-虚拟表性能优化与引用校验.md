# 虚拟表性能优化与引用校验

## 一、功能背景与问题来源

### 1.1 业务痛点

虚拟表（VTABLE）是 TDengine 的重要特性，它允许用户基于现有物理表创建逻辑视图，无需存储实际数据即可实现数据聚合和重组。然而，在实际使用中，用户经常遇到以下挑战：

**性能问题：**
- **窗口查询性能不佳** - 在虚拟表上执行时间窗口、会话窗口、事件窗口、状态窗口查询时，性能明显低于直接查询物理表
- **多列多表场景慢** - 当虚拟表列数较多且引用多个原始表时，查询性能急剧下降
- **聚合查询效率低** - 虚拟表聚合查询结合 GROUP BY 时，无法充分利用优化策略
- **简单场景未优化** - 即使虚拟表只引用单个原始表的简单场景，也未针对性优化

**运维问题：**
- **源表变更影响不可控** - 删除或修改源表列后，不清楚哪些虚拟表会受影响
- **引用关系不透明** - 无法快速查询源表被哪些虚拟表引用
- **错误排查困难** - 虚拟表查询失败时，难以定位是哪个源表或列出现问题

### 1.2 典型场景示例

**场景一：设备监控数据聚合**
- 问题：基于 100 个设备表创建虚拟超级表，执行按小时聚合的窗口查询，耗时是直接查询物理表的 5-10 倍
- 影响：实时监控大屏刷新缓慢，用户体验差

**场景二：多维度数据整合**
- 问题：虚拟表整合了来自 5 个不同物理表的 20 个列，简单的 SELECT 查询都需要数秒才能返回
- 影响：业务分析报表生成缓慢，影响决策效率

**场景三：源表维护风险**
- 问题：DBA 需要删除一个不再使用的物理表列，但不清楚是否有虚拟表在引用，担心影响业务
- 影响：运维操作谨小慎微，数据库清理工作难以推进

### 1.3 为什么需要虚拟表优化？

虚拟表本质上是一个逻辑视图，查询时需要动态从源表获取数据。之前的实现中，对虚拟表的查询采用了通用的执行路径，未针对虚拟表的特点进行优化，导致：

1. **无法下推窗口算子** - 窗口计算在虚拟表层执行，无法利用物理表的窗口优化
2. **列映射开销大** - 每次查询都需要解析列引用关系，多列多表时开销显著
3. **未识别简化场景** - 单表引用、tbname 列等特殊场景可以走快速路径，但未实现识别
4. **缺乏引用关系管理** - 没有系统化的机制管理虚拟表与源表的依赖关系

**TDengine 3.4.1** 通过引擎层优化和新增引用校验机制，全面解决这些问题。

## 二、功能介绍与核心特性

### 2.1 性能优化概览

TDengine 3.4.1 针对虚拟表实施了多项性能优化，覆盖窗口查询、多列多表、单表引用、聚合查询等核心场景。

#### 2.1.1 窗口查询性能优化

**优化内容：**
- 支持将窗口算子（Interval、Session、Event、State Window）下推到源表层执行
- 利用物理表的原生窗口优化能力，避免虚拟表层的二次计算

**性能提升：**
- **Interval Window（时间窗口）**：性能提升 **3-8 倍**
- **Session Window（会话窗口）**：性能提升 **2-5 倍**
- **Event Window（事件窗口）**：性能提升 **2-4 倍**
- **State Window（状态窗口）**：性能提升 **2-4 倍**

**示例：**
```sql
-- 优化前：虚拟表层执行窗口计算，性能较慢
SELECT _WSTART, AVG(temperature), MAX(humidity) 
FROM v_sensors 
INTERVAL(1h);

-- 优化后：窗口算子下推到源表，利用物理表优化
-- 查询语法不变，但执行计划自动优化
SELECT _WSTART, AVG(temperature), MAX(humidity) 
FROM v_sensors 
INTERVAL(1h);
-- 性能提升 3-8 倍
```

#### 2.1.2 多列多表场景优化

**优化内容：**
- 改进虚拟表列映射机制，减少列解析开销
- 优化多源表数据合并策略，降低内存消耗

**适用场景：**
- 虚拟表列数 ≥10 且引用 ≥3 个原始表

**性能提升：**
- 查询耗时降低 **30-60%**
- 内存占用降低 **20-40%**

**示例：**
```sql
-- 虚拟表整合多个源表的列
CREATE VIRTUAL STABLE v_device_full USING 
  (ts TIMESTAMP, 
   power DOUBLE REF device_power.power,
   temp DOUBLE REF device_temp.temperature,
   voltage DOUBLE REF device_voltage.volt,
   ...  -- 共 15 列，来自 5 个不同物理表
  ) TAGS (device_id INT);

-- 优化后，多列查询性能显著提升
SELECT ts, power, temp, voltage, current, pressure
FROM v_device_full
WHERE device_id = 1001;
-- 性能提升 30-60%
```

#### 2.1.3 单表引用场景优化

**优化内容：**
- 检测虚拟表仅引用单个原始表时，直接透传查询到源表
- 避免虚拟表层的中间处理，接近直接查询源表性能

**适用场景：**
- 虚拟表所有列均来自同一个物理表

**性能提升：**
- 查询性能与直接查询源表基本一致，开销 **<5%**

**示例：**
```sql
-- 虚拟表仅用于重命名列或过滤列
CREATE VIRTUAL STABLE v_sensors_simple USING 
  (ts TIMESTAMP, 
   temp DOUBLE REF raw_sensors.temperature,
   hum DOUBLE REF raw_sensors.humidity
  ) TAGS (sensor_id INT);

-- 优化后，查询性能接近直接查询 raw_sensors
SELECT ts, temp, hum FROM v_sensors_simple WHERE sensor_id = 1;
```

#### 2.1.4 聚合查询 + GROUP BY 优化

**优化内容：**
- 识别虚拟表上的聚合 + 分组查询，将算子下推到源表
- 支持 tbname 列的高效分组

**适用场景：**
- 使用 COUNT、AVG、SUM、MIN、MAX 等聚合函数
- 结合 GROUP BY tbname 或其他标签列

**性能提升：**
- 聚合查询性能提升 **2-5 倍**

**示例：**
```sql
-- 按设备统计数据量和平均值
SELECT tbname, COUNT(*), AVG(temperature)
FROM v_sensors
GROUP BY tbname;
-- 优化后性能提升 2-5 倍
```

### 2.2 引用校验功能

#### 2.2.1 核心概念

**术语定义：**
- **源表（Source Table）**：被虚拟表引用的物理表（超级表、普通子表），是虚拟表数据与标签的原始来源
- **虚拟表（VTABLE）**：基于源表创建的逻辑表，自身不存储实际数据，查询时动态从源表获取数据/标签值

**引用关系管理：**
- 新增系统表 `INFORMATION_SCHEMA.INS_VIRTUAL_TABLES_REFERENCING`
- 记录源表（库、表、列）与虚拟表（库、表、列）的完整引用关系

#### 2.2.2 系统表 Schema

系统表 `INS_VIRTUAL_TABLES_REFERENCING` 的字段定义：

| 字段 | 含义 | 类型 |
| --- | --- | --- |
| virtual_db_name | 虚拟表数据库名称 | VARCHAR |
| virtual_stable_name | 虚拟超级表名称 | VARCHAR |
| virtual_table_name | 虚拟表名称 | VARCHAR |
| virtual_column_name | 虚拟表列名称 | VARCHAR |
| src_db_name | 源表数据库名称 | VARCHAR |
| src_table_name | 源表名称 | VARCHAR |
| src_column_name | 源表列名称 | VARCHAR |
| type | 源表类型 | VARCHAR（virtual / physical） |
| err_code | 错误码 | INT（0 为正常，其他为错误） |
| err_msg | 错误信息 | VARCHAR |

#### 2.2.3 新增 SQL 命令

**命令一：验证虚拟表可用性**

```sql
SHOW VTABLE VALIDATE FOR [db_name.]table_name;
```

**功能：** 验证虚拟表的所有引用列是否可用，检测源表列是否被删除或重命名

**限制：** table_name 必须是虚拟子表/普通虚拟表/虚拟超级表

**输出：** 返回 INS_VIRTUAL_TABLES_REFERENCING 系统表格式的数据，err_code 非 0 表示引用异常

**示例：**
```sql
-- 验证虚拟表 v_sensors 的引用是否正常
SHOW VTABLE VALIDATE FOR test.v_sensors;
```

**命令二：查询源表被哪些虚拟表引用**

```sql
SHOW REFERENCES FOR [db_name.]table_name;
```

**功能：** 查询指定源表被哪些虚拟表引用

**限制：** table_name 必须是物理表

**输出：** 多行 4 列数据（virtual_db_name, virtual_stable_name, virtual_table_name, virtual_col_name）

**示例：**
```sql
-- 查询 raw_sensors 表被哪些虚拟表引用
SHOW REFERENCES FOR test.raw_sensors;
```

**命令三：直接查询系统表（更灵活）**

```sql
-- 查询特定源表的引用关系
SELECT virtual_db_name, virtual_stable_name, virtual_table_name, virtual_column_name
FROM INFORMATION_SCHEMA.INS_VIRTUAL_TABLES_REFERENCING
WHERE src_table_name = 'raw_sensors';

-- 查询所有引用异常的虚拟表列
SELECT virtual_db_name, virtual_table_name, virtual_column_name, err_msg
FROM INFORMATION_SCHEMA.INS_VIRTUAL_TABLES_REFERENCING
WHERE err_code != 0;
```

#### 2.2.4 源表变更行为

**增加源表列：** 不影响虚拟表行为

**删除源表列：** 
- 虚拟表查询引用该列时返回 NULL（而非报错）
- 保证业务查询连续性

**重命名源表列（仅普通表支持）：**
- 虚拟表查询引用该列时返回 NULL
- 建议重命名前先通过 `SHOW REFERENCES` 检查

**修改源表列长度（仅字符类型，只能变大）：**
- 虚拟表始终返回源表列的完整数据
- 虚拟表 schema 定义的列长度不会自动跟随变化

**删除源表：**
- 虚拟表查询引用该表时报错
- 建议删除前先通过 `SHOW REFERENCES` 检查

## 三、典型应用场景与价值

### 3.1 场景一：设备监控实时大屏

**业务需求：**
智能工厂需要实时监控 1000 台设备的运行状态，大屏每 10 秒刷新一次，展示每小时的平均温度、湿度、能耗等指标。设备数据分散在多个物理表中，通过虚拟超级表聚合。

**客户价值：**
- ✅ 窗口查询性能提升 **3-8 倍**，大屏刷新流畅，用户体验显著改善
- ✅ 支持更高频率的数据刷新（从 30 秒缩短到 10 秒）
- ✅ 降低服务器 CPU 和内存占用，节省硬件成本

**实现方案：**

```sql
-- 创建虚拟超级表整合设备数据
CREATE VIRTUAL STABLE v_devices USING 
  (ts TIMESTAMP, 
   temperature DOUBLE REF device_metrics.temp,
   humidity DOUBLE REF device_metrics.hum,
   power DOUBLE REF device_power.consumption
  ) TAGS (device_id INT, workshop VARCHAR(50));

-- 优化后的小时级聚合查询
SELECT _WSTART, 
       workshop,
       AVG(temperature) AS avg_temp,
       AVG(humidity) AS avg_hum,
       SUM(power) AS total_power
FROM v_devices
WHERE ts >= NOW - 24h
PARTITION BY workshop
INTERVAL(1h);
-- 性能提升 3-8 倍，查询时间从 5 秒降至 0.6-1.7 秒
```

### 3.2 场景二：生产线综合监控报表

**业务需求：**
汽车制造企业需要生成包含设备运行状态、生产质量、能耗、原料消耗等多维度的综合生产报表。数据分散在设备监控表、质检表、能源表、物料表等不同的物理表中，通过虚拟表整合成一张宽表供 MES 系统和 BI 工具查询。

**客户价值：**
- ✅ 多列多表查询性能提升 **30-60%**，报表生成时间大幅缩短
- ✅ 内存占用降低 **20-40%**，支持更复杂的查询
- ✅ 提升生产管理效率，实现数据驱动的生产决策

**实现方案：**

```sql
-- 创建整合 5 个源表、15 个列的虚拟表
CREATE VIRTUAL STABLE v_production_analytics USING 
  (ts TIMESTAMP, 
   temperature DOUBLE REF device_status.temp,
   pressure DOUBLE REF device_status.pressure,
   defect_rate DOUBLE REF quality_inspection.defect_rate,
   power_consumption DOUBLE REF energy_monitor.power,
   material_usage DOUBLE REF material_logs.usage,
   oee DOUBLE REF device_status.oee,
   product_count INT REF production_counter.count,
   alarm_count INT REF alarm_logs.alarm_cnt,
   ...  -- 共 15 列，来自 5 个不同物理表
  ) TAGS (line_id INT, workshop VARCHAR(50), device_type VARCHAR(50));

-- 优化后的多维度生产分析查询
SELECT workshop, device_type, line_id,
       COUNT(*) AS record_count,
       AVG(temperature) AS avg_temp,
       AVG(defect_rate) AS avg_defect_rate,
       SUM(power_consumption) AS total_power,
       SUM(product_count) AS total_products,
       AVG(oee) AS avg_oee
FROM v_production_analytics
WHERE ts >= '2026-04-01' AND ts < '2026-04-08'
  AND workshop IN ('车间A', '车间B')
GROUP BY workshop, device_type, line_id
ORDER BY avg_oee DESC;
-- 性能提升 30-60%，查询时间从 8 秒降至 3-5 秒
```

### 3.3 场景三：安全的源表维护

**业务需求：**
DBA 需要定期清理过期的设备监控表，删除不再使用的列以节省存储空间。但担心影响正在使用的虚拟表，导致业务查询异常。

**客户价值：**
- ✅ 通过 `SHOW REFERENCES` 快速识别源表的虚拟表依赖关系
- ✅ 源表列删除后，虚拟表返回 NULL 而非报错，业务连续性有保障
- ✅ 通过系统表查询，精准定位引用异常的虚拟表列，降低运维风险

**实现方案：**

```sql
-- 步骤 1：删除列前，检查源表引用关系
SHOW REFERENCES FOR test.device_metrics;
-- 输出示例：
-- | virtual_db_name | virtual_stable_name | virtual_table_name | virtual_col_name |
-- | test            | v_devices          | v_device_d001      | old_column       |

-- 步骤 2：通知业务侧调整虚拟表，或确认影响可接受

-- 步骤 3：安全删除源表列
ALTER TABLE device_metrics DROP COLUMN old_column;

-- 步骤 4：验证虚拟表状态
SHOW VTABLE VALIDATE FOR test.v_devices;
-- 输出显示 old_column 引用异常（err_code != 0）

-- 步骤 5：查询系统表，定位所有受影响的虚拟表列
SELECT virtual_db_name, virtual_table_name, virtual_column_name, err_msg
FROM INFORMATION_SCHEMA.INS_VIRTUAL_TABLES_REFERENCING
WHERE src_table_name = 'device_metrics' 
  AND src_column_name = 'old_column'
  AND err_code != 0;
```

### 3.4 场景四：单表引用快速视图

**业务需求：**
某业务系统的原始日志表有 50 个列，但大部分查询只需要其中 5-8 个核心列。为了简化查询和提升安全性，创建虚拟表仅暴露必要列。

**客户价值：**
- ✅ 查询性能接近直接查询源表，开销 **<5%**
- ✅ 简化应用层代码，提升开发效率
- ✅ 增强数据安全性，隐藏敏感列

**实现方案：**

```sql
-- 创建仅引用单个源表的虚拟表（视图）
CREATE VIRTUAL STABLE v_logs_simple USING 
  (ts TIMESTAMP, 
   level VARCHAR(10) REF raw_logs.log_level,
   message VARCHAR(1024) REF raw_logs.log_message,
   module VARCHAR(50) REF raw_logs.module_name
  ) TAGS (server_id INT);

-- 优化后，查询性能接近直接查询 raw_logs
SELECT ts, level, message, module
FROM v_logs_simple
WHERE server_id = 101 AND level = 'ERROR'
  AND ts >= NOW - 1h;
-- 性能几乎无损耗
```

## 四、运维最佳实践

### 4.1 源表维护前的检查清单

**删除源表列前：**
1. 执行 `SHOW REFERENCES FOR table_name` 查看引用关系
2. 通知业务侧，确认虚拟表是否需要调整
3. 确认删除后虚拟表返回 NULL 的影响可接受

**重命名源表列前：**
1. 执行 `SHOW REFERENCES FOR table_name` 查看引用关系
2. 更新所有引用该列的虚拟表定义（或接受返回 NULL）
3. 或选择增加新列、保留旧列的渐进式迁移

**删除源表前：**
1. 执行 `SHOW REFERENCES FOR table_name` 确认无虚拟表引用
2. 如有引用，先删除或调整虚拟表
3. 再安全删除源表

### 4.2 虚拟表健康检查

**定期验证虚拟表可用性：**
```sql
-- 检查特定虚拟表
SHOW VTABLE VALIDATE FOR mydb.v_sensors;

-- 批量检查所有虚拟表（通过系统表）
SELECT DISTINCT virtual_db_name, virtual_stable_name, virtual_table_name
FROM INFORMATION_SCHEMA.INS_VIRTUAL_TABLES_REFERENCING
WHERE err_code != 0;
```

**监控引用异常：**
```sql
-- 查询所有引用异常的虚拟表列
SELECT virtual_db_name, virtual_table_name, virtual_column_name, 
       src_db_name, src_table_name, src_column_name, err_msg
FROM INFORMATION_SCHEMA.INS_VIRTUAL_TABLES_REFERENCING
WHERE err_code != 0
ORDER BY virtual_db_name, virtual_table_name;
```

1. **全面性能提升** - 覆盖窗口查询、多列多表、单表引用、聚合分组等核心场景，性能提升 2-8 倍

4. **降低使用门槛** - 性能优化自动生效，无需修改 SQL 语法，用户无感知
5. **提升运维效率** - 快速定位引用关系和异常，降低数据库维护风险
