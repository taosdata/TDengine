# 查询性能诊断增强 (EXPLAIN ANALYZE)

## 一、功能背景与问题来源

### 1.1 业务痛点

在实际工业场景中,用户在进行查询性能优化时经常遇到以下挑战:

**性能诊断困难:**
- **执行计划信息不足** - EXPLAIN ANALYZE 提供的性能指标有限,难以定位查询瓶颈
- **算子耗时统计不准确** - 无法区分算子实际计算时间和等待时间,误导优化方向
- **缺少 I/O 详细信息** - 无法了解文件读取、内存访问的具体开销
- **多节点性能对比困难** - 分布式查询时无法快速识别慢节点和数据倾斜问题

### 1.2 典型场景示例

**场景一:慢查询性能诊断**
- 问题:用户反馈某个聚合查询耗时 5 秒,但 EXPLAIN ANALYZE 输出信息有限,无法判断是扫描慢还是聚合慢,也不知道是哪个节点拖累了性能
- 影响:问题定位效率低,优化方向不明确

**场景二:分布式查询性能不均衡**
- 问题:8 个 VNode 的查询,总耗时 10 秒,但不知道是否有慢节点,也不清楚是数据倾斜还是节点故障
- 影响:无法针对性优化,集群资源利用率低

**场景三:I/O 瓶颈难以定位**
- 问题:查询耗时长,怀疑磁盘 I/O 慢,但不知道是文件读取慢还是内存访问慢,也不清楚 SMA 优化是否生效
- 影响:优化措施无的放矢,投入产出比低

### 1.3 为什么需要增强诊断能力?

**查询性能诊断是数据库优化的基础:**
- 准确的性能指标能帮助 DBA 快速定位瓶颈,提升优化效率
- 分布式环境下需要识别慢节点和数据倾斜,保证查询性能均衡
- 详细的 I/O 指标能指导存储优化和硬件升级决策

**TDengine 3.4.1** 通过全面增强 EXPLAIN ANALYZE 功能,提供准确、丰富的性能指标,显著提升问题定位效率。

## 二、功能介绍与核心特性

### 2.1 功能概述

EXPLAIN ANALYZE 会实际执行查询语句,并在物理执行计划的基础上,输出详细的执行信息,帮助诊断性能瓶颈。TDengine 3.4.1 全面增强了性能指标的准确性和丰富度。

### 2.2 新增算子执行时间指标

精确区分算子的实际计算时间和等待时间,提供 8 个核心指标:

| 指标 | 含义 | 诊断价值 | 输出级别 |
| --- | --- | --- | --- |
| exec_first_row | 算子返回第一条数据的时刻 | 算子何时开始产出 | 普通 |
| exec_last_row | 算子最后一次返回数据的时刻 | 算子何时完成 | 普通 |
| exec_elapsed | 算子的实际执行时间 | **算子本身的计算开销** | verbose |
| exec_create | 算子的创建时间 | 算子何时被调度 | verbose |
| exec_start | 算子首次开始执行的时刻 | 算子调度延迟 | verbose |
| exec_times | 算子执行次数 | 算子调用频率 | verbose |
| input_wait_elapsed | 等待下游数据的时间 | **下游是否是瓶颈** | verbose |
| output_wait_elapsed | 等待上游消费的时间 | **上游是否是瓶颈** | verbose |

**关键改进:**
- ✅ 准确统计算子实际计算时间 (exec_elapsed),剥离等待时间
- ✅ 区分等待下游 (input_wait) 和等待上游 (output_wait),精准定位瓶颈
- ✅ 时间精度达到微秒级 (毫秒精确到小数点后三位)

### 2.3 新增 I/O 性能指标

针对 Table Scan 算子,提供详细的 I/O 成本分析:

| 指标 | 含义 | 诊断价值 | 输出级别 |
| --- | --- | --- | --- |
| file_load_blocks | Data/SST 文件读取 block 数 | 磁盘 I/O 量 | verbose |
| file_load_elapsed | 文件读取耗时 | 磁盘 I/O 耗时 | verbose |
| stt_load_blocks | SST 文件读取 block 数 | SST 优化效果 | verbose |
| stt_load_elapsed | SST 文件读取耗时 | SST 性能影响 | verbose |
| mem_load_blocks | 内存读取 block 数 | 内存命中情况 | verbose |
| mem_load_elapsed | 内存读取耗时 | 内存访问开销 | verbose |
| sma_load_blocks | SMA 读取 block 数 | SMA 优化效果 | verbose |
| sma_load_elapsed | SMA 读取耗时 | SMA 性能影响 | verbose |
| composed_blocks | 数据交织合成 block 数 | 数据交织情况 | verbose |
| composed_elapsed | 数据交织合成耗时 | 交织处理开销 | verbose |

**关键价值:**
- ✅ 区分文件、内存、SMA 的读取开销,精准定位 I/O 瓶颈
- ✅ 识别数据交织问题,指导数据写入优化

### 2.4 新增分布式诊断指标

针对多 VGroup 场景,新增慢节点和数据倾斜分析:

| 指标 | 含义 | 诊断价值 | 输出级别 |
| --- | --- | --- | --- |
| slowest_vgroup_id | 最慢节点的 VGroup ID | 定位慢节点 | verbose |
| slow_deviation_rate | 最慢节点耗时相对中位数偏离率 | 慢节点离群程度 | verbose |
| cost_ratio | 最慢/最快耗时倍数 | 性能分布均衡性 | verbose |
| data_deviation_rate | 最慢节点行数相对中位数偏离率 | **区分数据倾斜/节点异常** | verbose |

**计算公式:**
- slow_deviation_rate = (max_time - median_time) / median_time × 100%
- cost_ratio = max_time / min_time
- data_deviation_rate = (max_rows - median_rows) / median_rows × 100%

**关键价值:**
- ✅ 快速识别慢节点,判断是否为节点异常
- ✅ 区分性能慢是数据倾斜还是节点故障
- ✅ 指导数据分片和集群扩容决策

### 2.5 新增网络传输指标

针对 Exchange 算子,新增网络层性能分析:

| 指标 | 含义 | 诊断价值 | 输出级别 |
| --- | --- | --- | --- |
| mode | 并发还是顺序请求数据 | 数据获取策略 | verbose |
| fetch_times | 数据源 fetch 次数 | 网络往返次数 | verbose |
| fetch_rows | 数据源获取数据行数 | 网络传输数据量 | verbose |
| fetch_cost | 数据源 RPC 往返耗时 | 网络传输延迟 | verbose |

## 三、典型应用场景与价值

### 3.1 场景一:慢查询性能诊断与优化

**业务需求:**
智能工厂的运营监控大屏查询响应缓慢,需要快速定位是哪个环节拖累了性能,是扫描慢、聚合慢,还是网络传输慢,或者是某个节点异常。

**客户价值:**
- ✅ 使用 EXPLAIN ANALYZE VERBOSE TRUE 获取详细性能指标
- ✅ 区分算子实际计算时间和等待时间,判断是算子本身慢还是上下游拖累
- ✅ 识别慢节点和数据倾斜,快速定位分布式查询瓶颈
- ✅ 查看 I/O 详细指标,判断是文件 I/O 还是内存访问慢

**实现方案:**

```sql
-- 执行慢查询诊断
EXPLAIN ANALYZE VERBOSE TRUE
SELECT workshop, device_type,
       COUNT(*) AS device_count,
       AVG(temperature) AS avg_temp,
       AVG(oee) AS avg_oee
FROM production_metrics
WHERE ts >= '2026-04-01' AND ts < '2026-04-08'
PARTITION BY workshop, device_type
INTERVAL(1h);

-- 分析输出结果:
-- 1. 查看 exec_elapsed:判断哪个算子计算时间最长
-- 2. 查看 input_wait_elapsed:判断是否等待下游数据
-- 3. 查看 output_wait_elapsed:判断是否等待上游消费
-- 4. 查看 slowest_vgroup_id 和 slow_deviation_rate:识别慢节点
-- 5. 查看 data_deviation_rate:判断是数据倾斜还是节点异常
-- 6. 查看 I/O cost:判断文件、内存、SMA 的读取开销
```

**诊断示例:**

假设输出显示:
- `slow_deviation_rate = 200%`:最慢节点耗时是中位数的 3 倍
- `data_deviation_rate = 5%`:数据量基本均衡
- **结论:节点异常而非数据倾斜,需检查慢节点硬件或网络**

假设输出显示:
- `exec_elapsed = 0.05ms`,`input_wait_elapsed = 5000ms`
- **结论:算子本身很快,但等待下游数据耗时长,瓶颈在下游算子**

### 3.2 场景二:I/O 性能优化

**业务需求:**
设备历史数据查询耗时长,需要判断是磁盘 I/O 慢还是内存访问慢,以便采取针对性的优化措施 (如增加内存、升级磁盘、优化 SMA 配置)。

**客户价值:**
- ✅ 精确区分文件 I/O 和内存 I/O 的开销
- ✅ 判断 SMA 优化是否生效
- ✅ 识别数据交织问题,指导写入优化
- ✅ 为硬件升级提供数据支撑

**实现方案:**

```sql
-- 执行 I/O 密集型查询诊断
EXPLAIN ANALYZE VERBOSE TRUE
SELECT tbname,
       FIRST(ts) AS first_ts,
       LAST(ts) AS last_ts,
       COUNT(*) AS record_count,
       AVG(temperature) AS avg_temp
FROM device_history
WHERE ts >= '2025-01-01' AND ts < '2026-04-01'
GROUP BY tbname;

-- 重点分析 Table Scan 算子的 I/O cost:
-- 1. file_load_elapsed:磁盘文件读取耗时
-- 2. mem_load_elapsed:内存读取耗时
-- 3. sma_load_elapsed:SMA 读取耗时
-- 4. composed_elapsed:数据交织处理耗时
-- 5. file_load_blocks / total_blocks:磁盘 I/O 占比
```

**优化建议:**

假设输出显示:
- `file_load_elapsed = 8000ms`,`mem_load_elapsed = 200ms`
- `file_load_blocks = 95%`,`mem_load_blocks = 5%`
- **优化方向:增加内存缓存,提升缓存命中率**

假设输出显示:
- `composed_blocks = 80%`,`composed_elapsed = 3000ms`
- **优化方向:数据交织严重,需优化写入策略,减少乱序写入**

### 3.3 场景三:分布式查询负载均衡诊断

**业务需求:**
多 VNode 分布式查询性能不稳定,需要判断是否存在慢节点或数据倾斜,以便进行负载均衡优化。

**客户价值:**
- ✅ 快速识别最慢的 VGroup
- ✅ 区分慢节点是数据倾斜还是节点故障
- ✅ 评估集群性能分布均衡性
- ✅ 指导数据重分片或节点扩容

**实现方案:**

```sql
-- 执行分布式查询诊断
EXPLAIN ANALYZE VERBOSE TRUE
SELECT region,
       COUNT(*) AS meter_count,
       AVG(voltage) AS avg_voltage,
       SUM(power) AS total_power
FROM meters
WHERE ts >= '2026-04-01' AND ts < '2026-04-08'
GROUP BY region;

-- 重点分析分布式诊断指标:
-- 1. slowest_vgroup_id:最慢节点 ID
-- 2. slow_deviation_rate:最慢节点相对中位数偏离率
-- 3. cost_ratio:最慢/最快耗时倍数
-- 4. data_deviation_rate:最慢节点数据量偏离率
```

**诊断结论:**

**情况一:数据倾斜**
- `slow_deviation_rate = 150%`
- `data_deviation_rate = 200%`
- **结论:数据倾斜导致性能不均,需要重新分片或调整 hash 策略**

**情况二:节点异常**
- `slow_deviation_rate = 300%`
- `data_deviation_rate = 10%`
- **结论:节点硬件或网络异常,需检查慢节点 (VGroup 3) 的硬件状态**

**情况三:性能均衡**
- `slow_deviation_rate = 15%`
- `cost_ratio = 1.2`
- **结论:集群负载均衡,性能良好**

## 四、运维最佳实践

### 4.1 性能诊断流程

**第一步:日常监控使用普通级别**
```sql
-- 日常查询性能监控
EXPLAIN ANALYZE SELECT ...;
-- 关注 Planning Time 和 Execution Time 即可
```

**第二步:发现慢查询使用 Verbose 级别**
```sql
-- 慢查询深度分析
EXPLAIN ANALYZE VERBOSE TRUE SELECT ...;
-- 查看所有详细指标,定位具体瓶颈
```

**第三步:重点关注指标分析**

**算子层面:**
1. `exec_elapsed`:算子实际计算时间
2. `input_wait_elapsed`:等待下游数据时间
3. `output_wait_elapsed`:等待上游消费时间
4. **诊断方法:**如果 wait 时间远大于 exec 时间,说明瓶颈在上下游算子

**I/O 层面:**
1. `file_load_elapsed`:磁盘 I/O 耗时
2. `mem_load_elapsed`:内存访问耗时
3. `composed_elapsed`:数据交织处理耗时
4. **诊断方法:**对比各项耗时,确定 I/O 瓶颈类型

**分布式层面:**
1. `slowest_vgroup_id`:定位慢节点
2. `slow_deviation_rate`:判断慢节点离群程度
3. `data_deviation_rate`:区分数据倾斜 vs 节点异常
4. **诊断方法:**
   - data_deviation 高 + slow_deviation 高 → 数据倾斜
   - data_deviation 低 + slow_deviation 高 → 节点异常

### 4.2 性能优化建议

**优化算子执行时间:**
- 如果 exec_elapsed 过长,检查 WHERE 条件和索引使用
- 如果 input_wait 过长,优化下游算子
- 如果 output_wait 过长,优化上游算子或增加并发度

**优化 I/O 性能:**
- file_load 耗时长 → 增加内存缓存或升级磁盘
- mem_load 耗时长 → 检查内存压力,考虑扩容
- composed 耗时长 → 优化写入策略,减少乱序写入
- sma_load 占比低 → 调整 SMA 配置,提升预聚合效果

**优化分布式性能:**
- slow_deviation > 100% → 检查慢节点硬件状态
- data_deviation > 50% → 考虑重新分片
- cost_ratio > 5 → 严重不均衡,需紧急处理

### 4.3 常见问题排查

**问题一:查询耗时长但不知道瓶颈在哪**
```sql
-- 使用 VERBOSE TRUE 查看详细指标
EXPLAIN ANALYZE VERBOSE TRUE SELECT ...;

-- 依次检查:
-- 1. Execution Time vs Planning Time → 是优化器慢还是执行慢
-- 2. exec_elapsed vs input_wait → 是计算慢还是等待慢
-- 3. file_load vs mem_load → 是磁盘慢还是内存慢
```

**问题二:分布式查询性能不稳定**
```sql
-- 查看分布式诊断指标
EXPLAIN ANALYZE VERBOSE TRUE SELECT ...;

-- 查看 slowest_vgroup_id,定位慢节点
-- 对比 slow_deviation_rate 和 data_deviation_rate
-- 判断是数据倾斜还是节点异常
```

**问题三:怀疑某个节点有问题**
```sql
-- 使用 VERBOSE TRUE 对比各 VGroup 性能
EXPLAIN ANALYZE VERBOSE TRUE SELECT ...;

-- 查看输出中的平均值和最大值:
-- cost=avg(max) 格式
-- 如果 max >> avg,说明存在慢节点
-- 结合 slowest_vgroup_id 定位具体节点
```

| 网络传输 | fetch_times, fetch_rows, fetch_cost | 分析 RPC 传输性能 |

### 快速上手建议

1. **从普通级别开始** - 日常监控使用 EXPLAIN ANALYZE,关注 Execution Time
2. **慢查询使用 Verbose** - 发现慢查询时使用 VERBOSE TRUE 获取详细指标
3. **掌握关键指标** - 重点关注 exec_elapsed、input_wait、slow_deviation、data_deviation
4. **建立诊断流程** - 算子层面 → I/O 层面 → 分布式层面,逐层分析
5. **数据驱动优化** - 根据指标数据制定优化策略,避免盲目优化
