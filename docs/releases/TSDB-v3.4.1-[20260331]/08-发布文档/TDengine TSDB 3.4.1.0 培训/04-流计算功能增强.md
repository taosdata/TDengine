# 流计算功能增强

## 一、功能背景与问题来源

### 1.1 业务痛点

在实际工业场景中,用户在使用流计算时经常遇到以下挑战:

**窗口触发条件单一:**
- **仅支持时间触发** - TRUE_FOR 只能基于时间长度触发,无法基于数据量触发
- **数据到达率不稳定** - 数据到达速度波动时,窗口内数据量差异很大
- **无法灵活控制** - 缺少 AND/OR 逻辑组合,无法实现复合触发条件
- **批量处理困难** - 需要收集特定数量数据后再处理,现有功能难以实现

**定时触发单位受限:**
- **只支持固定时长** - 只能使用秒、分钟、小时、天等固定时长单位
- **无法对齐日历** - 无法直接实现"每周一"、"每月1日"、"每年1月1日"等业务需求
- **应用层复杂** - 需要在应用层做额外的时间对齐处理
- **周期性报表困难** - 每周汇总、每月报表、年度统计等场景实现复杂

**缺少空闲检测机制:**
- **设备离线无法感知** - 设备停止上报数据时,无法及时发现和告警
- **窗口一直打开** - 分组长时间无数据时,窗口可能一直处于打开状态
- **无法触发告警** - 缺少"长时间无数据"的告警机制
- **恢复无通知** - 设备恢复上报时,无法自动触发恢复事件

### 1.2 典型场景示例

**场景一:批量数据处理**
- 问题:需要收集 100 条设备数据后再进行批量分析,但只能基于时间触发,导致批次大小不稳定
- 影响:数据处理效率低,批量操作难以优化

**场景二:周期性报表生成**
- 问题:需要每周一生成上周的设备运行报表,但只能使用固定时长,需要应用层计算对齐时间
- 影响:实现复杂,容易出错,运维成本高

**场景三:设备离线监控**
- 问题:设备停止上报数据时,无法自动触发告警,需要人工定期检查
- 影响:故障响应不及时,业务连续性差

### 1.3 为什么需要流计算增强?

**流计算是实时数据处理的核心:**
- 灵活的窗口触发机制能提升数据处理效率
- 自然时间单位能简化周期性任务的实现
- 空闲检测能及时发现设备故障和数据链路问题

**TDengine 3.4.1** 通过全面增强流计算功能,提供更灵活的窗口触发、更便捷的周期定时、更完善的状态监控能力。

## 二、功能介绍与核心特性

### 2.1 TRUE_FOR 表达式增强

#### 2.1.1 功能概述

TRUE_FOR 表达式用于 STATE_WINDOW 和 EVENT_WINDOW 窗口类型,原本仅支持基于时间长度的触发。现在新增支持:
- 基于数据行数触发 (COUNT)
- 时间和行数 AND 逻辑组合
- 时间和行数 OR 逻辑组合

适用于流计算查询 (CREATE STREAM) 和普通查询 (SELECT)。

#### 2.1.2 语法格式

**原有语法 (仅基于时间):**
```sql
-- 流计算示例
CREATE STREAM stream_name AS
SELECT _wstart, COUNT(*) FROM source_table
STATE_WINDOW(column_name)
TRUE_FOR(duration);

-- 普通查询示例
SELECT _wstart, COUNT(*) FROM source_table
STATE_WINDOW(column_name)
TRUE_FOR(duration);
```

**新增语法 - COUNT 单独指定:**
```sql
-- 流计算:仅基于行数触发
CREATE STREAM s2 AS
SELECT _wstart, AVG(temperature) FROM sensors
STATE_WINDOW(status)
TRUE_FOR(COUNT 100);
-- 每累积 100 行数据触发一次窗口

-- 普通查询:按行数触发窗口
SELECT _wstart, AVG(temperature) FROM sensors
WHERE ts >= '2024-01-01' AND ts < '2024-01-02'
STATE_WINDOW(status)
TRUE_FOR(COUNT 100);
```

**新增语法 - AND 逻辑:**
```sql
-- 流计算:时间长度和行数都满足才触发
CREATE STREAM s3 AS
SELECT _wstart, MAX(voltage) FROM meters
STATE_WINDOW(status)
TRUE_FOR(10s AND COUNT 5);
-- 必须同时满足:10 秒已过且收到至少 5 行数据

-- 普通查询:应用 AND 逻辑
SELECT _wstart, MAX(voltage) FROM meters
WHERE ts >= '2024-01-01' AND ts < '2024-01-02'
STATE_WINDOW(status)
TRUE_FOR(10s AND COUNT 5);
```

**新增语法 - OR 逻辑:**
```sql
-- 流计算:时间长度或行数任一满足即触发
CREATE STREAM s4 AS
SELECT _wstart, SUM(power) FROM meters
EVENT_WINDOW(START WITH voltage > 220 END WITH voltage < 200)
TRUE_FOR(10s OR COUNT 5);
-- 满足以下任一条件即触发:10 秒已过 或 收到 5 行数据

-- 普通查询:应用 OR 逻辑
SELECT _wstart, SUM(power) FROM meters
WHERE ts >= '2024-01-01' AND ts < '2024-01-02'
EVENT_WINDOW(START WITH voltage > 220 END WITH voltage < 200)
TRUE_FOR(10s OR COUNT 5);
```

#### 2.1.3 核心行为说明

**COUNT 参数:**
- 类型:非负整数
- 有效范围:0 ≤ COUNT ≤ 2,147,483,647 (INT32_MAX)
- COUNT 为 0 表示窗口立即触发 (等价于没有行数限制)

**AND 逻辑行为:**
- 窗口必须等待完整的时间长度,即使行数条件提前满足
- 如果时间长度已到但行数未满足,窗口继续保持打开状态,等待更多数据
- 只有当两个条件都满足时,窗口才会触发并输出结果

**OR 逻辑行为:**
- 哪个条件先满足,窗口就立即触发
- 触发后窗口关闭,开始新的窗口周期

### 2.2 定时触发自然时间单位

#### 2.2.1 功能概述

流计算的定时触发 (PERIOD) 新增支持周 (w)、月 (n)、年 (y) 等自然时间单位,并为所有单位的 offset 参数新增小时 (h) 支持,实现精确的日历周期触发。

#### 2.2.2 新增时间单位

| 单位 | 含义 | 示例 |
| --- | --- | --- |
| w | 周 | PERIOD(1w) — 每周触发一次 |
| n | 月 | PERIOD(1n) — 每月触发一次 |
| y | 年 | PERIOD(1y) — 每年触发一次 |

支持整数倍数,如 PERIOD(2w)、PERIOD(3n)、PERIOD(2y)。

#### 2.2.3 自然时间边界

不同单位的默认触发时刻 (不指定 offset 时):

| 单位 | 默认触发时刻 |
| --- | --- |
| w | 每周一 00:00:00 (服务端时区) |
| n | 每月 1 日 00:00:00 (服务端时区) |
| y | 每年 1 月 1 日 00:00:00 (服务端时区) |

**示例:**
```sql
-- 每周一 00:00:00 触发
CREATE STREAM weekly_summary
TRIGGER PERIOD(1w)
INTO summary_table
AS SELECT AVG(current), MAX(voltage) FROM meters;

-- 每月 1 日 00:00:00 触发
CREATE STREAM monthly_billing
TRIGGER PERIOD(1n)
INTO billing_table
AS SELECT meter_id, SUM(energy) FROM meters GROUP BY meter_id;

-- 每年 1 月 1 日 00:00:00 触发
CREATE STREAM yearly_archive
TRIGGER PERIOD(1y)
INTO archive_table
AS SELECT * FROM meters;
```

#### 2.2.4 offset 参数

offset 表示在自然时间边界基础上的正向偏移,新增支持小时单位 (h)。

**offset 合法单位:** a (毫秒)、s (秒)、m (分钟)、h (小时)、d (天)

**offset 格式:** 单一数值 + 单一单位,不支持多单位组合

**示例:**
```sql
-- 每周二 00:00:00 触发
CREATE STREAM s1 
TRIGGER PERIOD(1w, 1d) 
INTO result_table
AS SELECT * FROM meters;

-- 每月 15 日 00:00:00 触发
CREATE STREAM s3 
TRIGGER PERIOD(1n, 14d) 
INTO result_table
AS SELECT * FROM meters;

-- 每年 2 月 1 日 00:00:00 触发
CREATE STREAM s4 
TRIGGER PERIOD(1y, 31d) 
INTO result_table
AS SELECT * FROM meters;

-- 每天 12:00:00 触发 (新增小时 offset 支持)
CREATE STREAM s5 
TRIGGER PERIOD(1d, 12h) 
INTO result_table
AS SELECT * FROM meters;
```

**约束条件:**
- offset 必须严格小于触发周期 (< ,不含等于)
- 月单位 offset 以 28 天/月为基准静态校验
- 不支持多单位组合 (如 2d12h)

#### 2.2.5 多倍数周期

多倍数周期以服务端时区的 epoch (1970-01-01 00:00:00) 为基准整除对齐,保证所有任务触发时刻全局一致。

**示例:**
```sql
-- 每 3 个月触发一次,对齐 1/4/7/10 月
CREATE STREAM quarterly_stats
TRIGGER PERIOD(3n)
INTO quarterly_table
AS SELECT AVG(current), AVG(voltage) FROM meters;

-- 每 2 周触发一次,对齐双周的周一
CREATE STREAM biweekly_report
TRIGGER PERIOD(2w)
INTO report_table
AS SELECT COUNT(*), SUM(energy) FROM meters;
```

### 2.3 分组空闲检测

#### 2.3.1 功能概述

流计算新增"分组空闲/恢复触发"能力:配置空闲超时阈值,系统按分组跟踪最后一次接收数据的时间,在进入空闲与恢复时触发计算和/或通知。

#### 2.3.2 核心概念

**分组 (Group/Partition):**
- 流任务按 PARTITION BY 指定的键 (如 tbname、tag、列) 划分的独立处理单元
- 若未指定 PARTITION BY,则视为单一分组

**空闲超时 (idle_timeout):**
- 在连续 idle_timeout 时间内未收到该分组的新数据,则该分组进入空闲状态

**空闲事件 (IDLE):**
- 分组从"活跃"转为"空闲"的状态迁移事件,仅在迁移发生时触发一次

**恢复事件 (RESUME):**
- 分组从"空闲"转为"活跃"的状态迁移事件,仅在迁移发生时触发一次

#### 2.3.3 语法格式

在 STREAM_OPTIONS 中新增 IDLE_TIMEOUT 配置项:

```sql
CREATE STREAM stream_name
  STATE_WINDOW(column_name)
  FROM source_table
  PARTITION BY partition_key
  STREAM_OPTIONS(IDLE_TIMEOUT(duration) | EVENT_TYPE(event_types))
  INTO output_table
AS
  SELECT ... FROM %%trows;
```

**参数说明:**

| 参数 | 说明 | 取值范围 |
| --- | --- | --- |
| IDLE_TIMEOUT(duration) | 空闲超时阈值 | 1s 到 10d (包含边界) |
| EVENT_TYPE(...) | 触发计算的事件类型 | IDLE / RESUME / WINDOW_OPEN / WINDOW_CLOSE |

**新增事件类型:**

| 事件类型 | 含义 | 触发时机 |
| --- | --- | --- |
| IDLE | 分组进入空闲 | 分组连续 idle_timeout 未收到新数据时触发一次 |
| RESUME | 分组从空闲恢复 | 已空闲分组收到新数据时触发一次 |

#### 2.3.4 使用示例

**示例一:空闲检测 + 计算触发**

```sql
-- 检测设备空闲并记录空闲事件
CREATE STREAM dev_idle_calc
  STATE_WINDOW(status)
  FROM meters
  PARTITION BY tbname
  STREAM_OPTIONS(IDLE_TIMEOUT(5m) | EVENT_TYPE(IDLE | RESUME))
  INTO dev_event_log
AS
  SELECT
    _tlocaltime    AS event_ts,      -- 事件触发时间
    _tidlestart    AS idle_from,     -- 空闲开始时间
    _tidleend      AS idle_to,       -- 空闲结束时间
    tbname         AS device,        -- 设备标识
    COUNT(*)       AS rows_in_window -- 窗口内数据量
  FROM %%trows;
```

**示例二:空闲检测 + 通知触发**

```sql
-- 设备空闲时发送告警,恢复时发送恢复通知
CREATE STREAM dev_idle_notify
  STATE_WINDOW(status)
  FROM meters
  PARTITION BY tbname
  STREAM_OPTIONS(IDLE_TIMEOUT(5m) | EVENT_TYPE(WINDOW_CLOSE))
  NOTIFY('ws://localhost:12345/dev_idle') ON (IDLE | RESUME)
  NOTIFY_OPTIONS(NOTIFY_HISTORY | ON_FAILURE_PAUSE)
  INTO dev_status_agg
AS
  SELECT _twstart, _twend, tbname, AVG(voltage) AS vavg
  FROM %%trows;
```

**示例三:同时启用窗口事件和空闲事件**

```sql
-- 窗口关闭时计算聚合,空闲/恢复时发送通知
CREATE STREAM comprehensive_monitor
  STATE_WINDOW(status)
  FROM meters
  PARTITION BY tbname
  STREAM_OPTIONS(
    IDLE_TIMEOUT(10m) | 
    EVENT_TYPE(WINDOW_OPEN | WINDOW_CLOSE | IDLE | RESUME)
  )
  NOTIFY('ws://localhost:12345/monitor') ON (IDLE | RESUME)
  INTO meter_stats
AS
  SELECT
    CASE
      WHEN _tevent = 'WINDOW_CLOSE' THEN _twstart
      WHEN _tevent IN ('IDLE', 'RESUME') THEN _tidlestart
    END AS event_start,
    tbname,
    COUNT(*) AS cnt,
    AVG(voltage) AS v_avg
  FROM %%trows;
```

#### 2.3.5 空闲检测行为

**分组状态机:**
- ACTIVE: 分组当前处于活跃状态 (近期收到过数据)
- IDLE: 分组当前处于空闲状态 (已超过 idle_timeout 未收到数据)

**空闲判定:**
1. 分组当前状态为 ACTIVE
2. 连续 idle_timeout 时间内未收到新数据
3. 触发 IDLE 事件,分组状态置为 IDLE

**恢复判定:**
1. 分组当前状态为 IDLE
2. 收到新数据
3. 立即触发 RESUME 事件,分组状态置回 ACTIVE

**时间占位符:**

对于 IDLE/RESUME 事件触发的计算,提供专用的时间占位符:

| 占位符 | 含义 (IDLE 事件) | 含义 (RESUME 事件) |
| --- | --- | --- |
| _tidlestart | 最后一次收到数据的时间 | 最后一次收到数据的时间 |
| _tidleend | IDLE 事件触发时间 | RESUME 事件触发时间 |

**注意事项:**
- IDLE/RESUME 计算不能使用 _twstart/_twend (窗口时间占位符)
- 窗口事件计算不能使用 _tidlestart/_tidleend (空闲时间占位符)
- 如需同时支持两类事件,建议拆分为独立的流

## 三、典型应用场景与价值

### 3.1 场景一:设备数据批量处理

**业务需求:**
工业物联网系统需要对设备数据进行批量分析,每收集 100 条数据执行一次聚合计算,以提升处理效率和批量操作性能。

**客户价值:**
- ✅ 使用 TRUE_FOR(COUNT 100) 精确控制批次大小
- ✅ 批量处理提升计算效率,减少 I/O 次数
- ✅ 数据到达速率波动时仍能保证批次稳定
- ✅ 简化应用层逻辑,降低开发成本

**实现方案:**

```sql
-- 每 100 行数据触发一次批量计算
CREATE STREAM batch_process
STATE_WINDOW(device_type)
FROM sensor_data
PARTITION BY device_id
STREAM_OPTIONS(EVENT_TYPE(WINDOW_CLOSE))
TRUE_FOR(COUNT 100)
INTO batch_results
AS
  SELECT
    _wstart,
    device_id,
    device_type,
    COUNT(*) AS batch_size,
    AVG(temperature) AS avg_temp,
    MAX(pressure) AS max_pressure,
    SUM(power_consumption) AS total_power
  FROM %%trows;
```

**业务价值:**
- 批次大小稳定,便于批量操作优化
- 减少计算频率,降低系统开销
- 数据到达不稳定时仍能保证处理效率

### 3.2 场景二:设备数据质量监控

**业务需求:**
设备必须在 10 秒内上报至少 5 条数据,否则认为采样率不足或设备故障,需要触发告警。

**客户价值:**
- ✅ 使用 TRUE_FOR(10s AND COUNT 5) 实现复合检测
- ✅ 同时检测时间和数据量,确保数据质量
- ✅ 及时发现采样率异常或设备故障
- ✅ 一条 SQL 实现复杂监控逻辑

**实现方案:**

```sql
-- 10 秒内至少 5 条数据才认为正常
CREATE STREAM quality_monitor
STATE_WINDOW(status)
FROM sensor_data
PARTITION BY device_id
STREAM_OPTIONS(EVENT_TYPE(WINDOW_CLOSE))
TRUE_FOR(10s AND COUNT 5)
INTO quality_check
AS
  SELECT
    _wstart,
    _wend,
    device_id,
    COUNT(*) AS data_count,
    CASE
      WHEN COUNT(*) >= 5 THEN 'NORMAL'
      ELSE 'INSUFFICIENT'
    END AS quality_status
  FROM %%trows;

-- 配合空闲检测,检测完全无数据的情况
CREATE STREAM device_offline
STATE_WINDOW(status)
FROM sensor_data
PARTITION BY device_id
STREAM_OPTIONS(IDLE_TIMEOUT(30s) | EVENT_TYPE(IDLE))
NOTIFY('ws://localhost:12345/alert') ON (IDLE)
INTO device_alerts
AS
  SELECT
    _tidlestart AS last_data_time,
    _tidleend AS alert_time,
    device_id,
    'OFFLINE' AS alert_type
  FROM %%trows;
```

### 3.3 场景三:每周业务汇总报表

**业务需求:**
每周一生成上周的设备运行汇总数据,包括总运行时长、平均负载、故障次数等,供管理层查看。

**客户价值:**
- ✅ 使用 PERIOD(1w) 自动对齐每周一
- ✅ 无需应用层计算时间对齐
- ✅ 简化周报生成逻辑
- ✅ 数据窗口完整,统计准确

**实现方案:**

```sql
-- 每周一 00:00:00 触发,统计上周数据
CREATE STREAM weekly_summary
TRIGGER PERIOD(1w)
INTO weekly_report
AS
  SELECT
    PERIOD_START AS week_start,
    PERIOD_END AS week_end,
    device_type,
    COUNT(DISTINCT device_id) AS device_count,
    SUM(running_hours) AS total_running_hours,
    AVG(load_factor) AS avg_load,
    SUM(CASE WHEN status = 'FAULT' THEN 1 ELSE 0 END) AS fault_count
  FROM device_status
  WHERE ts >= PERIOD_START AND ts < PERIOD_END
  GROUP BY device_type;
```

**业务价值:**
- 自动对齐周一,无需人工计算
- 数据窗口完整,覆盖完整一周
- 便于周报自动化生成和分发

### 3.4 场景四:设备离线监控与告警

**业务需求:**
设备 5 分钟内无数据上报,认为设备离线,触发告警通知运维人员;设备恢复上报后,触发恢复通知。

**客户价值:**
- ✅ 使用 IDLE_TIMEOUT(5m) 自动检测离线
- ✅ IDLE 事件触发告警,RESUME 事件触发恢复通知
- ✅ 及时发现设备故障,快速响应
- ✅ 形成完整的告警-恢复闭环

**实现方案:**

```sql
-- 设备离线检测与通知
CREATE STREAM device_offline_monitor
STATE_WINDOW(status)
FROM device_heartbeat
PARTITION BY device_id
STREAM_OPTIONS(
  IDLE_TIMEOUT(5m) | 
  EVENT_TYPE(IDLE | RESUME)
)
NOTIFY('ws://localhost:12345/device_alert') ON (IDLE | RESUME)
INTO device_event_log
AS
  SELECT
    _tlocaltime AS event_time,
    _tidlestart AS last_heartbeat,
    _tidleend AS event_trigger_time,
    device_id,
    device_location,
    CASE
      WHEN _tevent = 'IDLE' THEN 'OFFLINE'
      WHEN _tevent = 'RESUME' THEN 'ONLINE'
    END AS device_status,
    CAST((_tidleend - _tidlestart) / 1000000 AS BIGINT) AS offline_duration_ms
  FROM %%trows;
```

**通知 Payload 示例:**

IDLE 事件通知:
```json
{
  "event": "IDLE",
  "streamName": "device_offline_monitor",
  "deviceId": "device_001",
  "lastHeartbeat": "2026-04-07 10:00:00",
  "idleDurationMs": 300000,
  "message": "设备 device_001 已离线 5 分钟"
}
```

RESUME 事件通知:
```json
{
  "event": "RESUME",
  "streamName": "device_offline_monitor",
  "deviceId": "device_001",
  "offlineDuration": "5 分钟",
  "resumeTime": "2026-04-07 10:05:00",
  "message": "设备 device_001 已恢复在线"
}
```

**业务价值:**
- 自动监控设备状态,无需人工巡检
- 及时发现设备离线,快速响应故障
- 恢复通知形成闭环,故障处理有迹可循

### 3.5 场景五:每季度业绩统计

**业务需求:**
每季度末 (3/6/9/12 月 1 日) 生成上季度的业绩统计报表,供高层决策参考。

**客户价值:**
- ✅ 使用 PERIOD(3n) 自动对齐季度
- ✅ 自动对齐 1/4/7/10 月,覆盖完整季度
- ✅ 简化季度报表生成流程

**实现方案:**

```sql
-- 每季度触发一次,统计上季度数据
CREATE STREAM quarterly_stats
TRIGGER PERIOD(3n)
INTO quarterly_report
AS
  SELECT
    PERIOD_START AS quarter_start,
    PERIOD_END AS quarter_end,
    region,
    SUM(sales_amount) AS total_sales,
    AVG(customer_satisfaction) AS avg_satisfaction,
    COUNT(DISTINCT customer_id) AS active_customers,
    SUM(profit) AS total_profit
  FROM business_data
  WHERE ts >= PERIOD_START AND ts < PERIOD_END
  GROUP BY region;
```

## 四、运维最佳实践

### 4.1 TRUE_FOR 表达式使用建议

**选择合适的触发条件:**
- **仅时间:** 数据到达率稳定,按时间周期处理即可
- **仅行数:** 关注数据量而非时间,如批量处理
- **AND 逻辑:** 既要保证时间周期,又要保证数据量,如数据质量监控
- **OR 逻辑:** 时间或数据量任一满足即可,如快速响应

**COUNT 值设置建议:**
- 批量处理:根据批量操作最优大小设置 (如 100、500、1000)
- 数据质量监控:根据采样率要求设置最小数据量
- 避免设置过大:可能导致窗口长时间不触发
- 避免设置过小:可能导致触发过于频繁

**AND/OR 逻辑选择:**
```sql
-- AND 逻辑:严格要求两个条件都满足
-- 适用场景:数据质量监控、批量处理最小要求
TRUE_FOR(10s AND COUNT 5)

-- OR 逻辑:任一条件满足即可
-- 适用场景:快速响应、灵活处理
TRUE_FOR(10s OR COUNT 100)
```

### 4.2 定时触发最佳实践

**合理选择时间单位:**
- **固定时长 (s/m/h/d):** 简单周期任务,如每小时、每天
- **自然时间 (w/n/y):** 周期性报表,如周报、月报、年报
- **多倍数周期:** 季度、半年等,如 PERIOD(3n)、PERIOD(6n)

**offset 使用建议:**
```sql
-- 错误:offset >= 周期
PERIOD(1w, 7d)  -- 错误:7d = 1w

-- 正确:offset < 周期
PERIOD(1w, 6d)  -- 正确:每周日 00:00:00

-- 月单位注意事项:offset < 28d (单月) 或 < 56d (双月)
PERIOD(1n, 14d)  -- 正确:每月 15 日
PERIOD(1n, 28d)  -- 错误:超过最短月份
```

**首次触发的数据窗口:**
- 任务创建时刻在周期中间时,第一次触发包含历史数据
- 示例:周三创建 PERIOD(1w) 任务,下周一触发时数据窗口为上周一到本周一
- 建议:创建任务时确保历史数据已写入,或接受首次触发可能为空

**时区注意事项:**
- 所有时间边界对齐服务端时区的 00:00:00
- 跨时区部署时,注意服务端时区配置
- 夏令时切换时,以服务端时区的挂钟时间为准

### 4.3 分组空闲检测最佳实践

**合理设置空闲超时:**
- 根据业务 SLA 设置空闲阈值
- 过短:可能频繁误告警
- 过长:故障响应不及时
- 建议:正常上报周期的 2-3 倍

**空闲检测 + 通知:**
```sql
-- 推荐:空闲检测仅用于通知,不触发计算
CREATE STREAM device_monitor
  STATE_WINDOW(status)
  FROM meters
  PARTITION BY tbname
  STREAM_OPTIONS(
    IDLE_TIMEOUT(5m) | 
    EVENT_TYPE(WINDOW_CLOSE)  -- 窗口事件触发计算
  )
  NOTIFY('ws://localhost:12345/alert') ON (IDLE | RESUME)  -- 空闲事件触发通知
  INTO meter_stats
AS
  SELECT _twstart, _twend, tbname, AVG(voltage) 
  FROM %%trows;
```

**避免混用窗口和空闲事件:**
```sql
-- 不推荐:混用窗口时间和空闲时间占位符
CREATE STREAM mixed_event
  STREAM_OPTIONS(EVENT_TYPE(WINDOW_CLOSE | IDLE))
  INTO results
AS
  SELECT 
    _twstart,      -- 窗口时间
    _tidlestart    -- 空闲时间
  FROM %%trows;    -- 错误:两类占位符语义冲突

-- 推荐:拆分为独立的流
CREATE STREAM window_stream
  STREAM_OPTIONS(EVENT_TYPE(WINDOW_CLOSE))
  AS SELECT _twstart, _twend, ... FROM %%trows;

CREATE STREAM idle_stream
  STREAM_OPTIONS(IDLE_TIMEOUT(5m) | EVENT_TYPE(IDLE | RESUME))
  AS SELECT _tidlestart, _tidleend, ... FROM %%trows;
```

**任务重启的影响:**
- 任务重启后清空全部分组的空闲状态
- 重启后分组再次收到数据时才重建状态
- 可能延迟或无法发现重启前已空闲的分组
- 建议:重要监控任务做好高可用部署

### 4.4 常见问题排查

**问题一:TRUE_FOR COUNT 不触发**
```sql
-- 检查窗口是否有足够数据
SELECT COUNT(*) FROM source_table 
WHERE ts >= '2026-04-01' 
GROUP BY partition_key;

-- 检查 COUNT 值是否设置过大
TRUE_FOR(COUNT 10000)  -- 可能数据量不足

-- 调整为合理值
TRUE_FOR(COUNT 100)
```

**问题二:PERIOD 周期不符合预期**
```sql
-- 检查 offset 是否超出周期
PERIOD(1w, 7d)  -- 错误:offset = 周期

-- 检查时区配置
SHOW VARIABLES LIKE 'timezone';

-- 检查首次触发时间
SHOW STREAMS;  -- 查看 next_trigger_time
```

**问题三:空闲检测不触发**
```sql
-- 检查 IDLE_TIMEOUT 配置
SHOW CREATE STREAM stream_name;

-- 检查分组是否有数据
SELECT DISTINCT partition_key FROM source_table;

-- 检查空闲阈值是否合理
STREAM_OPTIONS(IDLE_TIMEOUT(5s))  -- 可能太短,频繁触发
STREAM_OPTIONS(IDLE_TIMEOUT(1h))  -- 可能太长,响应不及时
```
