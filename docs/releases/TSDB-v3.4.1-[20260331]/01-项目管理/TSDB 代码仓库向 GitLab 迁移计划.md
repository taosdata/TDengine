## 2. 计划背景

公司当前研发协作体系中，代码仓库主要托管在 GitHub，研发文档、产品文档等主要存放于飞书文档。随着产品线规模扩大（覆盖 TSDB、IDMP）及合规要求提升，现有分散式管理方式在权限治理、资产沉淀、审计追溯和流程一致性方面存在不足。

为加强管理规范化，统一研发资产管理边界，提升组织级管控能力，决定将代码仓库与文档库统一迁移至公司自建 GitLab 服务，形成“代码、文档、流程、权限、审计”一体化管理体系。

## 2. 核心目标

1. 完成 TSDB、IDMP 全量代码仓库由 GitHub 向公司自建 GitLab 的迁移，保留完整提交历史、分支、标签与权限结构；
2. 完成研发、产品、测试、发布等核心文档资产由飞书文档向 GitLab 文档库（含 Wiki/Docs 仓库）迁移，建立统一目录规范与版本管理机制；
3. 完成 CI/CD 体系在 GitLab 的可用落地（优先保障 MR 测试链路与发布主链路），确保迁移后研发节奏不受影响；
4. 建立统一的组织权限、密钥治理与审计机制（最小权限、分层授权、全链路可追溯）；
5. 在迁移窗口结束前完成“双轨验证-灰度切换-正式收口”，确保业务连续性与可回滚性。

## 3. 范围与原则

### 3.1 迁移范围

1. 产品线范围：TSDB、IDMP；
2. 资产范围：
   - 代码资产：主仓、子仓、工具仓、CI 脚本仓；
   - 文档资产：需求、设计、测试、发布、项目管理、运维制度等文档；
   - 流程资产：MR 流程、分支策略、发版流程、权限审批流；
3. 环境范围：开发、测试、发布相关环境与流水线配置。

### 3.2 迁移原则

1. 业务连续：迁移期间不阻断核心研发与发布；
2. 先通后优：先保障可用，再逐步优化性能与体验；
3. 双轨验证：关键阶段 GitHub/飞书 与 GitLab 并行验证；
4. 最小权限：权限按组织-组-项目分层最小授权；
5. 可回滚：每一阶段具备明确回退触发条件与操作手册。

## 4. 工作阶段与具体任务

### 4.1 阶段一：准备与基线梳理

时间：3.06 - 3.30  
目标：完成迁移前资产盘点、目标架构设计、迁移脚本和规则冻结。

工作项：

1. 完成 TSDB、IDMP 仓库与文档资产清单盘点（含 owner、活跃度、依赖关系）；
2. 设计 GitLab 组织结构（Group/Subgroup/Project）与命名规范；
3. 增加 TSDB 代码仓库设计：采用 monoRepo 方案，将多个 GitHub 代码仓库合并为 GitLab 单一仓库，便于代码统一管理与流水线自动化；
4. 设计分支保护策略、MR 审批规则、Tag 发布规则；
5. 设计文档库目录规范（研发/产品/测试/发布/项目管理）与模板；
6. 完成迁移工具链准备：
   - 代码迁移：仓库镜像迁移、标签分支校验脚本；
   - 文档迁移：批量导出、格式转换、链接修复脚本；
7. 完成密钥治理方案落地：
   - CI 仅保留访问密钥管理系统的最小凭证；
   - 业务 Secret 不落地在代码仓库与普通 CI 变量；
8. 冻结迁移窗口与变更管控机制（冻结期、例外审批、应急响应人）。

### 4.2 阶段二a：代码仓库试运行（TSDB/IDMP）

时间：4.01 - 5.13  
目标：完成代码仓库迁移、核心流程打通，并通过试点团队开展双轨试运行。

工作项：

1. 迁移 TSDB、IDMP 核心仓库与子模块，保留完整历史；
2. 完成 GitLab 仓库权限映射（研发、测试、发布、管理角色）；
3. 完成 GitHub Actions 至 GitLab CI 的 P0 主链路迁移：
   - MR 编译与测试链路；
   - 基础测试报告聚合与失败重试机制；
4. 完成 Runner 池注册与标签路由，建立构建/测试角色分工；
5. 建立制品仓（Nexus/Registry）基础目录与保留策略；
6. 完成 MR 并发隔离、日志与测试报告的可观测性验证；
7. 组织试点团队进行双轨运行（GitHub 与 GitLab 并行），输出差异清单并闭环。

### 4.3 阶段二b：代码仓库正式运行（TSDB/IDMP）

时间：5.18 - 5.29  
目标：完成代码仓库正式切换，保障 GitLab 成为代码协作主入口。

工作项：

1. 完成 GitLab CI 的 P1 主链路迁移：
   - 发布构建；
   - 制品上传；
   - 镜像推送；
2. 完成分支保护、MR 审批、Tag 发布策略正式启用；
3. 按产品线推动 TSDB、IDMP 团队切换至 GitLab 日常开发；
4. 关闭 GitHub 新增开发入口，保留只读镜像与应急回退能力；
5. 完成正式运行阶段问题清单清零，形成稳定运行基线。

### 4.4 阶段三：文档库迁移（研发/产品/测试/发布）

时间：4.08 - 5.20  
目标：与代码仓库迁移并行推进文档库迁移，提前完成核心文档入库与协同流程切换。

工作项：

1. 按文档类型分批迁移：
   - 项目管理文档；
   - 需求/设计文档；
   - 测试/发布文档；
   - 制度与流程文档；
2. 优先迁移高频核心文档，确保与代码试运行阶段同步可用；
3. 完成文档格式标准化（Markdown 优先）与链接修复；
4. 建立文档评审与合入流程（MR + Reviewer + 审批留痕）；
5. 建立文档版本标签策略（季度版本、里程碑版本）；
6. 建立“文档 owner + 维护 SLA”机制，避免迁移后失管；
7. 对高频文档完成可读性优化（目录、索引、交叉引用、变更记录）；
8. 输出飞书到 GitLab 的映射清单与迁移验收报告。

### 4.5 阶段四：切换、收口与治理固化

时间：6.01 - 6.12  
目标：完成正式切换，关闭旧入口，固化组织级管理规范。

工作项：

1. 发布正式切换公告，冻结 GitHub/飞书新增入口（只读）；
2. 启用 GitLab 作为唯一研发资产入口（代码 + 文档）；
3. 执行最终一致性校验：仓库、标签、分支、文档数量与抽样内容；
4. 完成组织培训（研发、产品、测试、项目管理、平台运维）；
5. 完成迁移复盘，沉淀标准作业程序（SOP）与应急预案；
6. 关闭旧平台写入权限，保留必要只读归档周期。

## 5. 角色分工

1. 项目管理（PMO）：总体计划、里程碑跟踪、跨团队协调、风险升级；
2. 平台部：GitLab 平台建设、TSDB/IDMP CI/CD 迁移、版本发布、Runner 运维、权限策略、审计与备份；
3. 研发部（TSDB/IDMP）：代码迁移执行、CI/CD 验证、分支与发布策略落地；
4. 产品与测试团队：文档迁移、模板统一、评审流程执行、验收确认；
5. 安全与合规接口人：密钥治理、权限审计、访问策略检查。

## 6. 里程碑与验收标准

### 6.1 里程碑

1. M1（4.01）：资产盘点完成，目标架构与迁移方案评审通过；
2. M2（5.13）：TSDB/IDMP 代码仓库试运行完成，试点双轨验证通过；
3. M3（5.20）：核心文档迁移完成，文档协同流程跑通；
4. M4（6.01）：TSDB/IDMP 代码仓库正式运行稳定，GitLab 成为代码主入口；
5. M5（6.12）：正式切换完成，旧平台进入只读归档。

### 6.2 验收标准

1. 代码资产验收：
   - 主仓与关键子仓迁移完整率 100%；
   - 分支与标签一致率 100%；
   - MR 流程、代码评审、CI 状态可正常使用；
2. 文档资产验收：
   - 核心文档迁移完整率 100%；
   - 关键链接可用率 >= 99%；
   - 文档评审流程与版本标记流程可执行；
3. 平台治理验收：
   - 权限分层与最小授权策略生效；
   - 审计日志可查询；
   - 备份与恢复演练通过；
4. 业务影响验收：
   - 迁移期间无重大发布中断；
   - 研发主流程中断时间累计不超过 4 小时（含计划窗口）。

## 7. 风险与应对

1. 风险：迁移期间研发效率下降  
   应对：双轨运行 + 关键团队驻场支持 + 问题日清；
2. 风险：CI/CD 链路不稳定  
   应对：分阶段迁移（P0/P1/P2）+ 回归用例 + 灰度启用；
3. 风险：文档迁移后链接失效/格式错乱  
   应对：自动化链接检查 + 抽样人工校验 + 迁移后修复窗口；
4. 风险：权限配置过宽或过紧  
   应对：权限基线模板 + 试点验证 + 周期性审计；
5. 风险：关键 Secret 泄露风险  
   应对：统一密钥管理、短期令牌、定期轮换、禁止明文落库。

## 8. 回滚策略

1. 阶段性回滚：任一阶段出现 P1 级阻塞问题，回退至上一阶段稳定状态；
2. 代码回滚：保留 GitHub 只读镜像与关键分支备份，必要时临时恢复 GitHub 触发链路；
3. 文档回滚：保留飞书原文档只读归档，GitLab 文档按批次回滚；
4. 发布回滚：发布链路保留旧流程应急开关，直至 GitLab 链路稳定满两个迭代周期。
