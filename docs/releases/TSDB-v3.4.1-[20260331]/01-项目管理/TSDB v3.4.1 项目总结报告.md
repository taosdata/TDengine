## 2. 项目概述

### 2.1 **项目名称**

TDengine TSDB v3.4.1.0 版本开发项目

### 2.2 **项目目标**

实现关键功能的安全与高可用加固，显著提升复杂查询与分析能力，大幅优化数据建模与管理的便捷性，拓展生态兼容性与智能化分析边界。

### 2.3 **项目范围**

#### 2.3.1 数据查询

本次版本迭代在查询能力上实现了重大突破，主要围绕以下方向进行建设：
1. 子查询能力：支持 IN + 非相关子查询、ANY/SOME/ALL/EXISTS/NOT EXISTS 运算符与子查询，解决多层级嵌套查询问题。
2. 窗口与插值功能：Interval 窗口支持指定插值时间范围；FILL PREV 支持填充前一个非 NULL 值；External Window 外部窗口功能上线。
3. 查询管理增强：Explain analyze 可读性增强，清晰展示语句执行过程；Show Queries 显示执行进度。
4. 查询性能优化：虚拟超级表窗口查询（Interval/Session/Event/State）性能优化；虚拟表列多、原始表数量多时查询性能优化；虚拟表含 tbname 列查询性能优化；聚合选择函数 + GROUP BY 性能优化。

#### 2.3.2 虚拟表

在虚拟表建模与管理方面进行了深度迭代：
1. 建模增强：虚拟表支持引用虚拟表，实现更灵活的数据建模。
2. 变更管理：虚拟表和源表的引用校验机制，防止误删源表导致虚拟表失效。
3. 订阅支持：数据订阅支持虚拟表的元数据变更（创建、删除、修改）。
4. 性能优化：虚拟超级表批量查询性能显著提升。

#### 2.3.3 流计算

流计算引擎在功能和性能上均取得显著进步：
1. 定时触发：支持按自然周、月、季、年定时触发计算任务。
2. 事件触发增强：TRUE_FOR 条件支持以记录条数和持续时间作为窗口开/关判断条件。
3. 功能改进：流计算支持 IN 子查询、支持 ANY/SOME/ALL/EXISTS 运算符、虚拟超级表触发支持子表增删改和标签值修改。
4. 分组空闲触发：支持在源子表/虚拟子表长时间无新数据写入时发送通知。
5. 性能优化：多分组批量计算性能优化。
6. 平台扩展：流计算支持 Windows 平台。

#### 2.3.4 数据存储

在数据可靠性与管理便捷性方面进行了重点增强：
1. 数据修复工具：开发数据修复工具，最大化恢复数据库可用数据，确保异常状态下数据库可快速恢复并启动。
2. 批量标签修改：支持一次性批量增删改多个子表或虚拟子表的多个标签值。
3. 数据缓存：支持动态调整 LRU 分片数量以提高 Last 查询性能。
4. 敏感数据管理：支持敏感数据删除后的强制覆盖。

#### 2.3.5 安全与可靠

安全加固是本次版本的核心工作之一，覆盖引擎、工具和连接器全链路：
1. 引擎安全：防 SQL 注入防火墙机制、taosc/taosd 防溢出攻击和拒绝服务攻击、审计信息不经过 taoskeeper 直接记录、权限控制完善（列权限、视图与审计权限、密钥过期策略等）。
2. 工具安全：Explorer 登录 CAPTCHA、Explorer SQL 传输层混淆、Explorer 未配置 SSL 时不传输明文密码；taosX 权限管理适配；各连接器密码脱敏和安全加固。
3. 认证增强：Explorer 支持 TOTP 认证和 TOKEN 认证；全部连接器（JDBC/Python/Rust/Node.js/C#/Go）及 taosAdapter 订阅均支持 TOKEN 登录。
4. 供应链安全：各连接器 CI 添加依赖库安全检查、LICENSE 检查和 SBOM 生成；使用 Conan 管理 C 依赖并生成 SBOM；棱镜七彩工具接入 CI。
5. 授权管理：License Center 中心化授权服务完成开发（作为 Demo 推进，待稳定后正式上线）。

#### 2.3.6 工具生态

在工具链和生态兼容性方面进行了广泛建设：
1. taosX 增强：力控 pSpace 实时同步/历史迁移、KingHistorian 查询同步和点位自动更新、Parquet 数据源导入、MQTT 多地址故障转移与用户属性、导出导入顺序一致性优化、Windows 适配。
2. 连接器增强：Node.js 连接器支持负载均衡和 Failover、C# 连接器支持 Failover、Go 连接器 WebSocket 统一连接管理重构。
3. taosdump：支持虚拟表导入导出、支持 DECIMAL 和 BLOB 数据类型、支持 STMT2 写入方式。
4. AI 工具：TDgpt 支持 Windows、IDMP MCP Server、taosgen-config Skill。

### 2.4 项目工期

项目于 2026-01-01 启动，在 2026-03-31 完成开发与测试并成功发布，4 月份进入验证和收尾阶段，于 2026-04-27 完成项目总结归档。

## 3. 项目度量数据分析

### 3.1 进度与工作量评估

项目整体进度按计划推进，最终发布日期与里程碑计划吻合。在开发期间，分别在 2026-02-25、2026-03-18、2026-04-14 三个时间点引入了工作范围变更，可参见[项目变更跟踪表](TSDB%20v3.4.1%20项目变更跟踪表.md)。主要变更来源包括：
1. 第一次变更（2026-02-25）：IDMP 产品新增任务及交付部门客户需求，新增 10 项工作。
2. 第二次变更（2026-03-18）：Windows 平台适配需求，新增 TDgpt、流计算、taosX 的 Windows 支持等 5 项工作。
3. 第三次变更（2026-04-14）：项目收尾阶段同步更新任务最终状态，业务新增 33 项、IDMP 新增 8 项、规划新增 49 项。

项目最终完成任务总计 209 项（业务 64 项、IDMP 29 项、规划 116 项），全部完成，完成率 100%。项目总工作量约为 71 人月，与立项时预估一致。工作量分布上，新特性开发约占 40%，安全加固与工具链建设约占 35%，缺陷修复与测试约占 25%。

### 3.2 缺陷分析

项目周期内通过系统测试共验证了 32 个测试用例、114 个子场景，全部通过。各模块的缺陷分布与典型问题如下表所示：

| 模块名称 | 缺陷数量 | 占比 | 典型问题 |
| --- | --- | --- | --- |
| 查询引擎 | 15 | 25.0% | 子查询在特定场景下结果错误；Explain analyze 输出信息不完整；虚拟表窗口查询性能回归。 |
| 流计算 | 10 | 16.7% | 自然月触发边界条件错误；TRUE_FOR 条数条件与时间条件交叉判断逻辑缺陷；分组批量计算内存占用偏高。 |
| 安全功能 | 12 | 20.0% | SQL 注入防火墙误拦截合法 SQL；密码策略配置项默认值不合理；Token 认证在部分连接器下超时处理异常。 |
| 连接器与工具 | 8 | 13.3% | C# 连接器 Failover 切换延迟；taosdump BLOB 导出编码错误；MQTT 多地址故障转移重连逻辑异常。 |
| 数据存储 | 6 | 10.0% | 数据修复工具在极端损坏场景下恢复率不稳定；批量标签修改在大量子表场景下事务超时。 |
| 其他（taosX、平台等） | 9 | 15.0% | KingHistorian 点位自动更新时间窗口计算偏差；Parquet 数据源特定列类型映射错误；Explorer 登录 CAPTCHA 在高并发下验证码刷新异常。 |

缺陷根本原因分析：
1. **功能复杂性**：查询引擎和安全功能相关的缺陷占比最高（合计 45%），主要源于子查询优化器的逻辑复杂性以及安全防护规则与正常业务逻辑的边界判定。
2. **跨平台适配**：Windows 适配工作引入了部分平台差异导致的兼容性问题，特别是路径处理、进程管理和 Coredump 策略方面。
3. **新组件集成**：License Center、数据修复工具等全新组件的首次集成，在异常路径和边界条件的覆盖上存在不足。

修复效率：缺陷的平均修复时间为 3 人天，严重及以上缺陷的修复周期控制在 5 人天内。缺陷重开率约为 5%，处于可控水平。

### 3.3 成本与预算分析

项目实际总成本与原始预算（71 人月）的偏差较小。成本略超预算的主要原因在于：项目中期因客户需求和 Windows 适配新增了较多工作项（累计新增 90 项），项目团队通过已完成规划任务的同事承接新增工作来消化额外工作量，未大幅增加人力成本。安全加固专项（连接器安全检查、SBOM 生成、SQL Fuzzing Test 等）的投入高于预期，但从安全合规和长期产品可靠性角度看是值得的。

## 4. 项目过程回顾与评估

### 4.1 项目总体表现评估

项目全面达成初始设定目标。成功交付的 TDengine 3.4.1.0 版本包含 209 项工作（业务 64 项、IDMP 29 项、规划 116 项），产品能力在多个维度得到显著提升：
1. 查询能力跨越式增强：IN 子查询、ANY/SOME/ALL/EXISTS 运算符、External Window、Interval 窗口插值等重大功能上线
2. 虚拟表体系日趋完善：虚拟表引用虚拟表、引用校验、元数据变更订阅、全类型窗口查询性能优化
3. 流计算生态扩展：自然时间单位触发、TRUE_FOR 条件增强、Windows 平台支持
4. 安全合规体系化建设：全链路安全加固（引擎→工具→连接器），SBOM 生成、SQL Fuzzing Test、供应链安全检查全面覆盖
5. 数据可靠性显著提升：数据修复工具、敏感数据强制覆盖、批量标签修改
6. 工具生态持续丰富：新增 pSpace/KingHistorian/Parquet 数据源，多连接器 Failover 和 TOKEN 认证

### 4.2 各过程执行情况评价

1. **立项过程**：目标明确，范围清晰，围绕"安全加固、查询增强、虚拟表优化、生态扩展"四大主线展开，与公司产品战略紧密对齐。
2. **开发过程**：采用"特性驱动开发"模式，每个特性/优化项均有明确负责人和验收标准。项目组成员分工明确（引擎部查询组、分析组、存储组、创新机动组，工具部 taosX 组、连接组，测试部），并行开发效率高。
3. **测试过程**：测试策略执行到位。功能测试覆盖 48 项独立功能模块，系统测试 32 个用例 114 个子场景全部通过。新增安全测试、性能测试专项覆盖。
4. **发布过程**：发布流程规范，版本于 2026 年 3 月底按计划发布。发布前完成了培训（8 个专题模块）和考试环节，确保交付团队具备版本支持能力。

### 4.3 风险管理回顾

项目初期识别的核心风险及管控情况如下：

#### 4.3.1 **设计类风险**

1. 漏洞扫描工作量不确定性：立项时识别为主要风险（"漏洞扫描如果过多，需要调整工作范围"）。实际执行中，经评估后调整策略，将安全漏洞修复从集中治理转为持续治理模式，避免了一次性工作量冲击对项目进度的影响，风险已解决。
2. License Center 功能成熟度不足：项目中期评估发现 License Center 对交付和产品稳定性影响较大，决定不在 3.4.1 正式版推送，改为内部验证一个月后再正式上线。此决策有效规避了功能质量风险，体现了风险前置管控的意识。

#### 4.3.2 **管理类风险**

1. 客户需求频繁变更：项目周期内经历 3 次工作范围变更，累计新增 90 项任务。通过已完成规划任务的同事承接新增工作、合理调整优先级等措施，确保关键路径不受影响，项目按计划交付。
2. Windows 平台适配复杂度：第二次变更引入 Windows 适配需求，涉及 TDgpt、流计算、taosX、xnoded 等多个组件。团队制定了专项适配计划（TSDB Windows 适配计划），分模块推进，最终按期完成。

整体来看，项目风险管控成效显著，所有风险均通过精准策略实现闭环管理，为项目按计划高质量交付提供了有力保障。

## 5. 经验教训总结

| 成功经验 | 待改进点 |
| --- | --- |
| **特性驱动与明确责任制**：延续 v3.4.0 的"特性驱动开发"模式，209 项任务每项均有唯一负责人和验收标准。清晰的责任划分保障了大规模并行开发的高效推进，最终实现 100% 完成率。 | **需求变更流程可进一步规范**：项目中期新增 90 项任务（占最终总量的 43%），部分任务在项目后期才被正式纳入跟踪，存在信息不对称风险。**建议**：建立更前置的需求收集窗口期，在每个里程碑前冻结需求变更，紧急需求走快速审批通道并即时更新跟踪表。 |
| **安全体系化建设**：将安全加固从引擎层扩展至工具链和连接器全链路，建立了 SBOM 生成、SQL Fuzzing Test、依赖库安全检查等自动化安全卡点。这些投入不仅解决了当前版本的安全合规要求，更形成了可持续复用的安全基线。 | **Windows 适配测试覆盖可提前规划**：Windows 适配作为第二次变更引入，相应的测试用例和自动化脚本需要额外开发周期。**建议**：后续版本如有跨平台支持计划，应在立项阶段即将测试环境和自动化脚本纳入项目范围。 |
| **风险前置决策**：License Center 功能在评估后决定暂不正式发布，避免了功能不成熟导致的交付风险。这一决策体现了团队"质量优先"的成熟项目管理理念。 | **新组件首次集成的异常路径覆盖不足**：数据修复工具、License Center 等新组件的异常场景和边界条件在测试中发现较晚。**建议**：对全新组件引入专项的"故障注入测试"环节，在功能测试阶段即覆盖异常路径和极端场景。 |
| **变更管理灵活有效**：面对 3 次工作范围变更和 90 项新增任务，项目团队通过资源动态调配和优先级调整，既满足了客户紧急需求，又保证了核心功能的按期交付。 | **安全防护规则的误报率需关注**：SQL 注入防火墙在初期存在误拦截合法 SQL 的情况，说明安全规则的精度有待提升。**建议**：建立安全规则的白名单机制和灰度发布流程，新规则上线前通过生产环境日志回放验证误报率。 |
| **发布前培训考试机制**：新增的 8 个专题培训模块和考试环节，确保了交付团队对新版本特性的深入理解，提升了版本上线后的客户支持质量。 | |
