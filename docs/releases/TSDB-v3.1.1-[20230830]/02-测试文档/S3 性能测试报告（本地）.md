# S3 性能测试报告（本地）

引用： [COS对象存储用户手册](https://taosdata.feishu.cn/wiki/OjmwwCmqdiENPckuo4icjb5fnzc) 

## 一、目的

     S3 存储的优势是空间大，存储成本低，所以我们把 TDengine 多级存储中最后一级存储内的数据存放在 S3 上，可以极大降低用户的存储成本。

## 二、实现原理

    在 TDengine 存储文件中，.data 文件存放时序数据，占用空间最大，所以仅把多级存储中最后一级中的 .data 文件存储在 S3 上，其它小文件仍然原地不动，这样即简化了功能实现，又降低了存储成本。
    当配置了 S3 存储后，多级存储中第二级向第三级迁移时，.data 文件会移动至 S3, 本地存储空间将被释放出来。
    当查询需要获取 S3 上的数据时，会从S3 上下载相应在 DATA 文件到第三级存储配置的本地磁盘上，实现数据查询，如果本地资源不够时，会删除在第三级存储中访问时间离目前最远的 .data 文件来释放空间。下载机制会充分利用第三级存储可用的磁盘空间，如果磁盘空间不足则查询会失败。

## 三、性能测试 

###       1、写入速度

        因为多级存储中咱们约定是不允许在第三级上写入数据的，数据写入只发生在第一级和第二级上，第一级与第二级的写入都是本地磁盘，所以写入性能与原来一样。

### 2、查询速度分类

  1）查询时间范围只在第一级和第二级上的查询速度与原来一致
  2）查询时间范围包括第三级上的数据时，查询时间 = 原来的查询时间 + 下载 DATA 文件所需时间    

###      3、查询测试性能

     使用腾讯云的COS 系统做为 S3 存储服务器，下载速度约为 1M/S
     创建子表数 30W ，每隔 200 ms 生成一条数据，KEEP 配置参数为 1 h, 2h, 365d, DURATION 为 1h 做测试

     **1）整个时间段内 count 有条件聚合查询**
          select count(*) from meters where  ic != 1000;
          第三级上需要下载 data 文件 十几个左右，共计 260 M
          总数据量为: 481W 
          初次查询（需下载260M data 文件）耗时 ： **48 秒**
          再次查询（无需任何下载） 耗时： **7 秒**
    **2）整个时间段内 count 聚合查询**
           select count(*) from meters;
           总数据量为: 481W 
           预期此查询在不超过1秒内返回，这也是设计成只放 DATA 到 S3 上一个亮点
      因为这个聚合查询使用的都是 SMA 中预计算的内容，使用本地 SMA 预计算文件即可完成聚合计算，不需要访问存放具体数据的 data 文件。
          ** 但实际这个需要 50多秒，还是到S3 上下载了一堆文件，这个不符合预期，正在修复跟进中**。
**     3)  只查询历史数据中的一个点**
     select * from d0 where ts='2023-08-23 12:30:00';
     需要下载一个文件 ，约 5M 
     返回数量量： 1 条
     首次查询： 4.75s 
     再次查询：0.02s  
 
## 四、性能总结        

###      1、查询性能由下载文件大小及速度确定

     在使用 S3 做为最后一级存储中，首次查询的性能主要由要下载文件的大小及下载速度两因素决定，下载文件越小，下载速度越快，查询性能越好

###      2、再次查询性能与原来一样

      下载只发生在首次查询中，所以只影响首次查询，再次查询或查询只涉及到前面查询相同的 data 文件时，查询速度与原来一样快。

###      3、规划好 data 文件的大小

       数据库配置参数 DURATION 配置的天数决定了 data 文件的大小，所以项目中要根据应用的读写频率，规划好 data 文件大小，建议控制在 200M 以内比较好，也不建议过小，过于小的话也影响 TDengine 在一级和二级存储上的查询效率。

###      4、S3上的查询不是所有查询都能支持

       最后一级存放到 S3 上，并非除了慢所有查询都能实现，如 S3 上有 100T 数据，本地磁盘只有 100G 空间，如果做全时间段内查询，需要把 100T 都拉下来进行过滤，但本地只有 100G 空间，咱们查询不支持拉一部分过滤一部分，需要全拉下来才能开始过滤，所以这样的查询是无法实现的。解决办法只能把原来的一个查询按时间切分成几个小查询来完成，最后再自己汇总。     

### 5、历史数据尽量点查或分段查

       因为查询需要先下载后查询，下载速度一般都比较慢，所以对于存放到最后一级在S3上的历史数据最好能够指定时间点查或分小时间段来查，查询速度相对来说可接受一些，如果在整个范围内查询，可能会花很长很长的时间。
       同时说明，有需求要存储在 S3 上数据的用户，一般都是数据量非常庞大，但偶尔会有一些历史查询统计场景，可以使用这套系统，如果是频繁在 S3 上查询的需求，查询性能主要依赖下载速度，S3 一般都在公有云上，下载速度不可能很快，所以对于频繁大范围查询历史数据的用户，不适合使用这套 S3 系统。
