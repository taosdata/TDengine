# 统一应用组件日志

## 1. 背景

问题触发点：由于 explorer 没有将日志输出到文件，在2024年8月初，新员工月考过程中上机考试时定位问题无法溯源到 explorer 日志。
在历史建设过程中 TDengine 产品的各个子系统开发语言不同，负责人风格不同，造成日志配置、输出格式等各有差别，造成在一次用户交互过程中，系统的调用链条上各个子系统输出的日志千差万别，不利于技术人员溯源定位问题。
公司对日志有具体的规定[撰写日志的基本要求](https://taosdata.feishu.cn/wiki/XgJDwCEf8iMEW2kA9mMcVqCinke)，已经将系统的可观测性提升到前所未有的高度，而日志是可观测性和问题溯源的根本。关总对日志有了一个框架性的指导并提出明确的规范需求 [需求说明：规范各组件日志](https://taosdata.feishu.cn/wiki/Pdi8w6M4RijsgJkS5wecUG2Inlb)。
本文档基于公司的要求和对日志统一的需求，定义应用侧统一的日志配置和输出规范，并对实现提出明确说明。

## 3. 定义

### 3.1 TOML 配置文件

[TOML](https://toml.io/cn/v1.0.0)：taosAdapter、taosX、Explorer、taosKeeper 均使用 TOML 作为配置文件的格式。在日志文件的标准定义中，我们尽量遵循 TOML 格式的定义，并发挥 TOML 文件的优势。
<quote-container>
TOML 旨在成为一个语义明显且易于阅读的最小化配置文件格式。
TOML 被设计成可以无歧义地映射为哈希表。
TOML 应该能很容易地被解析成各种语言中的数据结构。
</quote-container>

TOML 格式是一个强类型的配置文件格式，支持布尔值、整数、浮点数、字符串、日期、时间、数组、哈希表等类型，使得 TOML 文件有着非常强大的配置文件表达能力，天生适合复杂度较高的文件配置表示。

#### 3.1.1 日志的基本配置

- 日志级别：指日志记录的级别，现代应用系统中多使用 ERROR/WARN/INFO/DEBUG/TRACE 五个级别。日志级别可比较，ERROR < WARN < INFO < DEBUG < TRACE ，更高的日志级别对应更加细节的日志。
  - 不同模块日志级别自定义（功能单一或者模块数量较少的不必要支持）：目前仅 taosd 支持配置不同模块的日志级别，我们希望至少 taosx 也能支持这个功能。
  - 日志级别的运行时调整：这对于服务模式下的问题定位很有帮助，目前也仅 taosd 支持在运行时修改日志级别。
- 日志目录：可指定日志文件所在的目录。
- 滚动生成（Rolling 或者 Rotation）：可通过日志文件大小、时间滚动生成新的日志文件，支持文件压缩，以控制日志文件的磁盘占用。
- 日志限制：除了限制单个文件的大小外，应当可以根据不同的条件限制日志文件的生成，包括：日志目录的剩余空间大小限制、滚动日志的总数量等。
- 日志内容：可以选择性的将有帮助的信息输出到日志中，如文件名和行号、异步任务的 task id、时间、模块名等等。

### 3.2 链路追踪

链路追踪是一种监控和理解软件系统行为的辅助工具，特别是在分布式架构（或应用）中被广泛使用。它通过捕获和分析请求在服务间的传递，提供了一个请求从开始到结束的全局视图。这使得开发者可以理解系统的行为，特别是在处理复杂交互和并发请求时，可以比较便利地定位和分析问题。
日志可以作为链路追踪的一种载体。本文档简要约定各上游应用如何发起和记录请求，以在日志中能够追踪不同应用的请求在各系统中的流转状态和异常行为。

#### 3.2.1 QID 定义

QID 是一个会话调用链跟踪的关键，其作用是对每一条数据或每一个请求都能够从源头追溯到目的地。

#### 3.2.2 QID 生成规则

QID 是一个长度为 8 的 byte array ，总计 64 位 bit（在系统运行中可使用 uint64 存储该值），在日志文件记录中，是一个 **0x 开头的 16 进制小写 **格式字符串，形如 `0x``01``0203040506``0708`。因为一个集群系统中有可能部署多个taosExplorer，多个 taosX，多个 taosAdapter 等应用组件，为保证同一集群系统中各应用组件所生成的 QID 的唯一性，约定其生成方式如下：
1. taosX
taosX 对每一批次 Data In 数据都要生成 QID，它要保证对每一批次数据 QID 的唯一性，保证向下游发送的每一次写入请求的 QID 的唯一性，同时还要保证在多个 taosX 连接同一个 taosd 集群时 QID 的唯一性。在不使用 taosX-Agent 的 Data In 任务中，所有 QID 都由 taosX 生成并向下游传递。它生成的 QID 必须包含以下信息：

| 字节序 | 含义 | 补充说明 |
| --- | --- | --- |
| 0 | 生成 QID 的源头组件当前运行实例的 ID taosX 默认 ID 为 16 ，可通过配置文件修改，限定范围为 [1,255] | 如果集群中有多个 taosX，注意保证其实例 ID 唯一，如果只有一个无需配置 |
| 1~2 | task ID |  |
| 3~6 | 该任务的数据批次 ID，本 ID 需要持久化在任务断点中，在重启后从断点累加；如果超出则重新循环 |  |
| 7 | 该数据批次向下游写入时的子批次 ID，如果只有一个子批次则保持为 0 |  |

1. taosX-Agent
taosX-Agent 生成 QID 的规则与 taosX 完全相同，唯一的区别是其第一个字节组件 ID 不同，其范围为 [1,255]，默认为 48，可通过配置修改。在使用 Agent 的 Data In 任务中，所有 QID 都由 taosX-Agent 生成向下游传递。
1. taosExplorer
taosExplorer 对向下游发出的每个请求都要生成 QID

| 字节序 | 含义 | 补充说明 |
| --- | --- | --- |
| 0 | 生成 QID 的源头组件当前运行实例的 ID taosExplorer 默认 ID 为 1 ，可通过配置文件修改，限定范围为 [1,255] | 如果集群中有多个 taosExplorer，注意保证其实例 ID 唯一，如果只有一个无需配置 |
| 1 ~ 5 | Explorer 当前请求的识别 ID | 运行时全局唯一，每接收到一个浏览器请求后 + 1，重启后重新从零开始 |
| 6 | 如果请求对应多个下游子请求，附加递增 ID 作为下游的请求 ID，不需要持久化，如果 taosExplorer 重启则从零重新开始 | 会话中每次向下游发送请求时 +1，生成新的会话后清零 |
| 7 | taosX 如果需要将上游请求拆分为多个向下游，利用此字节进行扩展；如果不需扩展则为 0 |  |

1. taosAdapter
taosAdapter 仅在上游请求未成生成 QID 的情况下自动生成 QID，用于其上游调用者未设置 QID 的情况 

| 字节序 | 含义 | 补充说明 |
| --- | --- | --- |
| 0 | 当前运行实例的 ID taosAdapter 默认 ID 为 32 ，可通过配置文件修改，限定范围为 [1,255] | 如果集群中有多个 taosAdapter，注意保证其实例 ID 唯一，如果只有一个无需配置 |
| 1 ~ 7 | 简单序列号，表示请求顺序，从零开始递增，不需要持久化，如果 taosAdapter 重启则从零重新开始 |  |
|  |  |  |

1. taosKeeper
taosKeeper 的数据都来自 taosd/taosX 上报，它自己不需要生成 QID。当 taosKeeper 将收到的一批数据拆分为多条写入或查询请求时使用最后一个字节进行编号。InstanceID 默认值为64。
1. 监控数据 (taosX/taosd)
taosd/taosX/taosAdapter 在上报监控数据时需要生成 QID，附加在 HEADER 中：（`X-QID: 0xXXX`）。

| 字节序 | 含义 | 补充说明 |
| --- | --- | --- |
| 0 | dnode ID: taosd Instance ID: taosX Instance ID: taosAdapter |  |
| 1~2 | 必须为 0 ，表示监控数据 | 与 taosX 在 data In 任务中使用这两个字节表示 task_ID 区分 |
| 3~6 | 简单序列号，表示请求顺序，从零开始递增，不需要持久化，如果 taosd/taosX 重启则从零重新开始 |  |
| 7 | 为 taosKeeper 预留：上报时为 0 | 由 taosKeeper 进行扩展 |

### 3.3 SPAN 与 EVENT

在链路追踪（tracing）的上下文中，"SPAN" 和 "EVENT" 是两个专业术语。
- SPAN：译为“跨度”或 “跟踪跨度”，表示一项工作或任务的起始和结束，比如一个函数/方法的调用或一个 HTTP 请求的处理。每个跨度都有一个开始和结束的时间戳，以及许多其他的元数据，如跨度的名称、状态、附加的键值对等。
- EVENT：即“事件”，事件是在跨度生命周期中发生的一个瞬间，比如日志消息的记录、系统错误的发生等。事件通常包含一个时间戳和一些描述事件的元数据。
日志是链路追踪的一种载体，通常情况下，对应的是链路追踪中的“EVENT” 的概念。当然我们也可以选择将 SPAN 信息也记录到日志中，使日志能够承载更多的信息。
后续我们将会在日志中用到 SPAN 或 EVENT 的键值对属性。

## 4. 行为说明

### 4.1 日志公共行为

#### 4.1.1 日志格式

日志格式统一包含以下内容：
1. 时间戳，精确到微秒，不含年份，格式统一为 mm/dd HH:MM:SS.000000
2. 进程或线程 ID
3. 日志级别：分别使用 TRACE/DEBUG/INFO/WARN/ERROR，空格补齐长度为 5 (除 taosd 外)
4. QID:  形如 `QID:0x1234567890123456` 
5. 日志消息体，消息体中如果有 key:value  形式，使用冒号分隔 key:value，使用逗号空格分割 key:value 对，逗号前无空格逗号后一个空格，消息体在 key:value 对之后显示。例如：`task.id:5, job.id:39c0c337`
6. 文件及行号: 文件名和代码行号（由各应用决定）
```bash {wrap}
08/14 15:06:07.561812 00328184 INFO  QID:0x1234567890123456 task.id:5, job.id:39c0c337-2f8c, Committing offsets: Ok(()) kafka.rs:781
08/14 15:06:08.634726 00328184 DEBUG QID:0x1234567890123456 task.id:5, job.id:39c0c337-2f8c, closed file /etc/file/a.toml successfully kafka.rs:256
```

#### 5.0.2 配置文件中的日志配置

taosd/taos shell 使用 taos.cfg 中 `key`` ``value` 的自定义纯文本格式配置。配置 key 值与配置参数一致。
taosAdapter/taosX/Agent/Explorer/taosKeeper 使用 **TOML 格式的配置文件**，统一将日志相关参数设置到 [log] 下，如下所示，此部分在以上各组件的配置文件中相同
```toml
instanceId = 31

[log]
path = "/var/log/taos"
level = "warn"
compress = false   
rotationCount = 30
keepDays = 30
rotationTime = "24h" 
rotationSize = "1GB"
reservedDiskSize = "2GB"

```

#### 5.0.3 日志文件命名

日志文件使用统一命名规则生成：`component_instanceid``_YYYYMMDD.log``[.index]`，每天（本地时区 0 时）生成一个新的日志文件，每天默认生成的第一个日志文件名为 `component``_instanceid``_YYYYMMDD.log`
- `component`：小写的组件名，如果带 taos 字样，应当适配 OEM `CUS_PROPMT` 指定的名称。
  - taosadapter
  - taoskeeper
  - taosx
  - taosexplorer
  - taosxagent
- `instanceid`：instanceid 为组件配置的实例 ID，使用 `component_instanceid_YYYYMMDD.log[.index]`作为日志文件 Pattern。
- `YYYYMMDD` 表示日志创建时间，如 `20240815` 表示 2024 年 08 月 15 日。
- `[.index]`：如果一天当中的日志文件大小超过了 `rotationSize`也会触发日志滚动，新增日志文件名称 `taosx_20240815.log.1` ，以此类推。
滚动日志（即关闭当前日志文件并开始新的日志文件）时：
1. 如果日志数量大于 rotationCount，则删除最早保留的日志文件（对压缩的日志文件同样生效）；如果同一组件的多个实例配置了相同的 path，则它们所产生的日志文件共享 rotationCount 这个上限。
2. 如果 compress 配置为 1/true ，则在滚动创建新的日志文件后，将之前的日志文件压缩（使用 GZIP 压缩算法），并删除原始日志文件；压缩后的文件名添加 `.gz` 后缀，如: 原文件名.gz。
如果配置 reservedDiskSize 大于 0，则在写日志时需要判断当前剩余磁盘空间大小是否小于 reservedDiskSize，如果小于则停止日志写入。

#### 5.0.4 日志压缩

当开启日志压缩时，实例应当对当前实例的所有日志文件均适用压缩。
如果存在同一组件使用同一实例 ID 在同一目录下记录日志，日志压缩应当足够健壮，对非本实例的、正在写入的、正在压缩中的日志不做处理。
压缩后的日志文件名添加 `.gz` 后缀。如果使用文件锁，用 `.lock` 作为后缀。

### 5.1 Explorer 子系统

#### 5.1.1 配置文件

其配置文件名为 `explorer.toml`，使用 TOML 文件格式。其内容与 4.1.4 节完全相同

#### 5.1.2 关键日志

Explorer 的日志主要包含四部分：
- 执行 SQL
- 调用 taosx API 
- 调用其它后端 API

### 5.2 taosx 子系统

taosx 子系统的组件名为 `taosx`，OEM 时，使用 `${CUS_PROMT}x` 作为组件名。

#### 5.2.1 配置文件

配置文件所在路径见 4.1.4 中说明，文件名为 `taosx.toml`，使用 TOML 文件格式。除 4.1.4 中定义的配置参数外，额外还有如下配置参数：
```toml
[log]

## 6. 监听配置文件以实时更新日志配置

watching = true

[log.loggers]

## 7. Tracing 框架支持的模块表达式定义，各依赖模块的自定义日志级别

rdkafka = "trace"
taos_ws = "trace"
```

taosX 支持在配置文件发生变化后（有一定延迟），及时更新日志配置，以此达到类似 taos shell 使用 sql 修改运行时的日志级别的效果。
taosX 支持自定义模块的日志级别：
- `log.loggers` 通用模块表达式配置模块的日志级别。其键值表达式使用 [Tracing Filter Directives](https://docs.rs/tracing-subscriber/0.3.18/tracing_subscriber/filter/struct.EnvFilter.html#directives) 中约定的语法表示：
  ```plaintext
  target[span{field=value}]=level
  ```

  其中：
  - `target`：为模块路径和或板条箱名称，如 `rdkafka` `tokio::net` 等。
  - `span`：tracing 框架的 SPAN 名称，如 `legacy_to_taos` 等。
  - `filed=value`：表示该 `span` 的属性名称和值。
  - `level`: 日志级别。
  示例如下：
   - `tokio::net`` ``=`` ``trace` 表示对 `tokio` 库下的 `net` 模块启用 `trace` 日志级别
   - `rdkafka[span_a]`` ``=`` ``trace` 表示对 `rdkafka` 库的 `span_a` 名称 SPAN 下的所有路径设置 `trace` 级别。
   - `[legacy_to_taos{task.id=1}]`` ``=`` ``trace` 表示对含有 `task.id=1` 属性的 `legacy_to_taos` SPAN 下的任意模块均启用 `trace` 级别日志，用于对指定的任务开启独立日志级别。

#### 7.0.1 关键日志

1. taosx server api 调用日志
在实际系统中，一般由 taosexplorer 发起 API 调用请求，其 QID 通过 HTTP Header 传播：
```plaintext
X-QID: 0x0102030405060708
```

taosX 记录并使用上游 QID 作为每个请求的 QID 写入日志，作为该请求的生命周期起始和结束。
1. 数据源 data in 执行日志，每个批次使用一个 QID 跟踪，从连接器、到IPC、到flat transform，最终写入 tdengine。
  数据源任务创建后，即得到独立的 QID 前缀 `0x{``taosx组件ID``}{任务ID}`，在每一批次添加自增序列号，并在最终写入或进行其他 SQL 查询时附加最后的请求 ID。
1. 特殊地，对于 taosx 发起的使用 Agent 的数据源请求，QID 要附加在请求的元数据中。

### 7.1 taosx-agent 组件日志定义

Taosx-agent 的组件名为 `taosxagent`，配置文件名为 `agent.toml`，示例日志文件名如：`taosx``agent_20240814.log`。

#### 7.1.1 日志配置

详见 4.3.1 ，无额外配置。

#### 7.1.2 关键日志

与 taosx 的日志相比，Agent 有其特殊的 API 与 taosx 连接。连接使用 Arrow Flight RPC 框架，对每一个请求，应当在请求的元数据信息中（ app_metadata ）添加 QID。
包括：
1. 连接心跳日志
   - 由 taosagent 发起的心跳请求，其 QID 形式如下 `0x{Agent 编码}{请求ID}`，且在系统启动后生成 QID 并持续使用这个 QID 发送心跳请求。
   - 心跳连接正常时，仅在 TRACE 级别打印日志，在失去心跳后打印 WARN 级别日志，在彻底断开后打印 ERROR 级别日志。
2. 数据源执行日志，从连接器、IPC 到 arrow flight 发送数据给 taosx，数据源
   - 使用 Agent 的数据源完整执行路径
      - 数据源拉取数据，拼批后生成 QID 
      - Agent 转发数据到 GRPC 接口，元数据附加 QID
      - taosX Server 接收数据，进行数据分析，拆分请求后附加请求 ID，调用 taosc 或 websocket 接口
   - Agent 日志可通过 QID 前 7 位查询到某批次的完整执行日志（TRACE 级别）

### 7.2 taosAdapter 日志定义

taosAdapter 的组件名为 `taosadapter`，配置文件名为 `taosadapter.toml`，示例日志文件名如：`taosadapter_20240814.log`。

#### 7.2.1 配置文件

配置文件名为 `taosadapter.toml` 
日志相关配置如下
```toml
instanceId = 32

[log]
path = "/var/log/taos"
level = "warn"
compress = false   
rotationCount = 30
rotationSize = "1GB"
reservedDiskSize = "2GB"
```

改动如下：
1. `log.path`  `log.rotationCount` `log.rotationSize` 不变，新增 `log.compress` `log.level` `log.reservedDiskSize` `instanceId`
2. `log.level` 与已存在配置 `logLevel` 冲突，将删除之前配置`logLevel` 为保证兼容当 `log.level` 不存在时使用 `logLevel` ，当都存在时使用 `log.level`

#### 7.2.2 关键日志

taosAdapter 关键日志包含
- C 函数调用参数（Trace）
- C 函数调用耗时（Debug）
- 执行 SQL （Debug）
- Websocket 请求（Debug）
- Websocket 返回 （Trace）

#### 7.2.3 动态修改日志级别

taosAdapter 添加 http PUT 请求接口 `/config`，使用与 `rest/sql` 相同的验证方式。body 中传入 json 格式配置项键值对，设置为 debug 的 curl 样例如下
```bash
curl --location --request PUT 'http://127.0.0.1:6041/config' \
-u root:taosdata \
--data '{"log.level": "debug"}'
```

通过接口设置的参数不会持久化，应用重启后无效

## 8. 性能

日志级别越低，对性能影响越大。
性能影响因素与代码中打印日志的详细程度和所在服务器磁盘性能相关。

## 9. 兼容性

各个子系统需要兼容老版本的配置文件，保证使用旧版本的配置文件部分配置项缺失时，能以默认值启动应用。
此部分更新后，taosx Server 不兼容旧版本 Agent。

## 10. 运维

需要掌握 Log 相关的配置参数。
推荐 POC 阶段使用 debug 级别，生产运营阶段使用 info 或者 warn 级别，研发介入定位问题时，可临时调整为 trace 级别，定位完问题后，一定要调整回原生产级别；
compress 推荐打开，设置为 1。
instance id 配置规则：整个 TDengine 系统中各个子系统，根据部署规划区分子系统段，为每一个子系统配置instance id。比如可以规定 taosx占用1~16，taosadapter 占用 128~255。

## 11. 使用场景

### 11.1 Explorer 数据浏览器查询 sql

根据 QID 查看完整调用链路，当执行错误时可以从 explorer server / taos adapter / taosd 根据最源端的 QID，查询链路中每一个系统的执行情况。

### 11.2 taosx data in 问题定位

taosx 数据源任务执行过程内部各调度模块异步并发执行以及外部系统相互协同完成数据的最终写入，需要同一个 QID 串联器所有内部模块和外部子系统，联合定位问题。

## 18. 附录

### 18.1 QID 的实现说明

应用生成 QID 或者从上游应用获取到之后，将 QID 保存在 session 范围内。打印日志时优先从 session 范围内检查有没有 QID，如果有 QID 则应该使用现有的 QID，否则新生成 QID，并保存在 session 范围内。

### 18.2 reservedDiskSize 实现逻辑

考虑到查询剩余磁盘空间代价较高，通常使用单独的线程或异步任务监控系统资源，即便如此，也建议使用其他方式尽量减少查询、比较的代价，比如触发某种条件时再做比较。需要注意的是：“停止日志写入”仅限于一个概念上的意义，在空间受限的情况下，应该首先考虑主动降低日志级别（即：日志**服务降级**），在严重程度达到一定级别后，再考虑完全停止写入，停止写入前应将警告日志写入日志文件。
