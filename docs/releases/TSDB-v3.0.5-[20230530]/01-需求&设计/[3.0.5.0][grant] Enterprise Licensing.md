## Generation

- `taosGrant` is an internal tool to generate the licenses for TDengine, and only the Delivery Team has the authority to generate the licenses.
- Extend the function of `taosGrant` to support the license generation for connectors since version 3.0.5.0
- This chapter below mainly demonstrates the usage of taosGrant with `cluster id`
<callout emoji="bulb" background-color="light-orange" border-color="light-orange">
The usage of taosGrant with `machineCode` is also supported, with the only difference that `machineCode` is specified by the paramter `-k`, e.g. `taosGrant -k ${machineCode} -a ${activeCode}`
</callout>

### 2.2 Method to fetch cluster id/machine code

- The cluster id is specific for each TDengine cluster, and can be fetched by executing the `show cluster` in the taos shell. In the example below, the cluster id is 5681662865067127406.
```sql
taos> show cluster\G;
```

- The `machineCode` is specific for each deployment server, and can be fetched by executing `taosd -k` on each server.

#### 2.3.2 Generate active code for connectors by cluster id

```sql {wrap}
1) Generate a new license for OPC_UA/Kafaka/MQTT, and the apps share the c_number/c_speed/c_expire.
./taosGrant_3.0 -u ${cluster_id} -c_app OPC_UA,Kafka,MQTT -c_number 0 -c_speed 10 -c_expire 2025-12-31
--------------------------------------------------------------------------------
#ServerCode 5491178878311373698

2) Generate a new license for OPC_UA/Kafaka/MQTT, and the apps share -c_speed, but with separated c_number/c_expire.
./taosGrant_3.0 -k ${machine_code} -c_app OPC_UA,Kafka,MQTT -c_number 0,1,3 -c_speed 10 -c_expire 2025-12-31,2025-11-30,2023-12-25

3) Generate license for Pi/Kafka/MQTT, and the apps share -c_number/-c_expire, but with separated c_speed.
./taosGrant_3.0 -u ${cluster_id} -c_app Pi,Kafka,MQTT -c_number 100 -c_speed 10,20,15 -c_expire 2023-12-25

4) Check the license for TDengine/connectors
./taosGrant_3.0 -u ${cluster_id} -a ${activeCode}
./taosGrant_3.0 -k ${machine_code} -a ${activeCode}
```

#### 3.1.2 Reset after drop dnode

- The `activeCode/cActiveCode` entry  is stored in mnode/SDB_DNODE, and should be `reset` after executing the `drop dnode` command.

### 3.2 Activation priority

```cpp {wrap}
P1) If the activation code is set through SQL cmd, it can be displayed with  SQL command 'show dnodes\G;'; and the activation code will be used first when authorizing。
P2) If the activation code is not set through SQL cmd, it cannot be displayed through SQL command 'show dnodes\G;'. At this time, the system will try to obtain the activeCode/cActiveCode configured in taos.cfg for authorization.
P3) If the above two methods are not set, the system will take the default authorization rules(that is, 2 months expire time/unlimited other metrics for TDengine, 2 weeks expire time/1 connection/ulimited speed for connectors).
```

### 3.3 Activation principle

- The mnode licensing module checks the licenses of TDengine and connectors automatically every 60 seconds, which means that there would be a maximum 60s latency to take effect.
- The grants of TDengine/connectors is the `union value` of all dnodes. 
- Increasing the grants takes effect immediately(in 60 seconds), while decreasing the grants takes effect after a delay of 1 hour.

### 3.4 Enterprise Cloud Edition

- The grant of `TDengine` for Enterprise Cloud Edition is not through `activeCode,` but through the configuration file. The rule is that it will never expire and the number of metrics is not limited for ever. Besides, `activeCode` does not take effect even if it is set.
- The grant of `connectors` for Enterprise Cloud Edition is through `cActiveCode`, just like Enterprise Non-Cloud Edition.

## Query

### 4.1 Show grants of TDengine and connectors

- ~~Like ~~`~~show grants~~`~~, ~~~~use ~~`~~show c_grants~~`~~ t~~~~o show the connectors' license of the cluster.~~
- `show grants` is used to get and show the grants information.  
- Extend the system table `information_schema.ins_grants` to add a column for each connector, and the result of `show grants` is the `union value` of all the dnodes in the cluster.

### 4.3 API in taos.h

- Refer to 4.1, the general query API  `taos_query/taos_query_a` can be used to fetch the grants information by executing the statement `select * from information_schema.ins_grants;`.
- Below is the example to fetch grants info of `pi and mqtt`:
