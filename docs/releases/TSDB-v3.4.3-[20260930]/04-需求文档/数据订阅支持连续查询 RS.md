## 2. 引言

## 3. 需求目标

CQ 将数据查询与数据订阅的实时推送机制相结合，实现一个可订阅的、持续生成的数据流
1. **数据流**：将 CQ 定义为一种可订阅的数据流，按固定时间间隔执行查询，并将结果通过数据订阅机制主动推送给消费者
2. **支持乱序数据处理**：通过引入延迟参数，为查询提供一个时间缓冲窗口，以容忍并处理延迟到达的乱序数据
3. **支持可配置的起始点**：允许用户指定查询开始的绝对时间点，便于回溯处理历史数据或从当前时刻开始运行

## 4. 功能要求

### 4.1 语法提案

```sql {wrap}
CREATE TOPIC [IF NOT EXISTS] topic_name 
AS CONTINUOUS QUERY 
WITH (
    INTERVAL = 'interval_time',
    DELAY = 'delay_time'
    [, START_TS = 'start_timestamp']
)
AS 
subquery;
```

### 4.2 参数说明

| 参数名称 | 取值示例 | 功能描述 |
| --- | --- | --- |
| INTERVAL | '10s', '5m', '1h' | 定义查询的执行间隔，即每隔多久触发一次查询 |
| DELAY | '30s', '2m', '10m' | 定义查询的延迟时间，每次查询实际处理的数据时间范围为：
      `[当前时间 - INTERVAL - DELAY, 当前时间 - DELAY)` |
| START_TS | '2025-01-01 00:00:00', Now | 指定连续查询的开始时间点 |

### 4.3 其他说明

对于 CQ，其 Offset 是“每次连续查询的执行时间点”，支持提交到服务器保存，保证在订阅者重启后能基于保存的状态恢复执行。

## 5. 性能需求

CQ 本身的性能开销主要取决于`subquery`的复杂度和执行频率（`INTERVAL`）。其资源消耗与周期性手动执行相同。数据订阅的推送性能与现有 Topic 机制保持一致。

## 6. 安全需求

1. 与现有普通数据订阅（Topic）的权限保持一致，无额外特殊要求
2. 用户必须对`subquery`中涉及的所有数据实体拥有相应的读（SELECT）权限，才能成功创建 CQ Topic

## 7. 兼容性需求

客户端完全兼容并使用现有的**数据订阅 API 接口**进行消费，无需为 CQ Topic 开发新的客户端接口。
