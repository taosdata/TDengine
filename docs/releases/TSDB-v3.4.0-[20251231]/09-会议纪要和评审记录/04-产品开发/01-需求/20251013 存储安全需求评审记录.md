## 2. 评审记录

1. 总体评价
需求文档结构清晰，目标明确。设计采用了分级密钥管理（SVR_KEY -> DB_KEY -> 功能密钥）和透明加密理念，符合常见的数据安全最佳实践
1. 关于密钥管理体系的评审
   - 密钥分层架构（SVR_KEY, DB_KEY, CFG_KEY/META_KEY/DATA_KEY）被认为是合理且安全的，有效隔离了不同层次和范围的风险。
   - 密钥存储安全性​：使用机器码加密 SVR_KEY 的方案，确保了数据文件拷贝到其他机器后，不能被正常使用。
   - 密钥变更与不可变性​：SVR_KEY 和 DB_KEY 支持变更，而 CFG_KEY 等功能密钥不可更改，此设计需在升级或迁移场景下进行充分测试。
   - 密钥分发机制​：依赖 SASL 机制由 mnode 分发。评审指出，​这是一种合理的内部通信机制。
2. 关于透明加密实施的评审​：
   - 对配置文件、元数据文件、数据文件的加密范围定义清晰，具有可操作性。
   - 配置文件规范化​：很多场景下 taos.cfg 不能回写，此处需求调整为仅保留必要的配置参数，且声明 taos.cfg 中的配置仅在系统第一次启动时有效。
   - 数据文件加密​：创建数据库时指定加密算法且后续不可修改的设计是严谨的。
3. 关于非功能性需求的评审​：
   - 性能需求​：文档中设定的性能损耗阈值（写入/查询延迟增加不超过100%）是明确的验收标准。评审建议在后续测试中，需在不同负载和典型数据规模下验证这些指标。
   - 兼容性需求​：向后兼容和版本升级不中断服务是关键要求。​“使用新版本加密数据后，不能退回到旧版本”这一点至关重要，必须在文档和最终用户手册中明确警示。
   - 安全需求​：密钥操作通过 SQL 语句进行，其具体语法和权限控制依赖于后续的“权限管理”功能。评审强调，必须确保密钥管理操作有严格的权限约束，防止未授权访问

## 3. 评审结论

通过
