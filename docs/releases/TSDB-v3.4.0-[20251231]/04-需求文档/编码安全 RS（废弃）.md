## 4. 需求目标

总结整理开发过程中的静态、动态检查机制，系统化运行这类检查。
1. 内存检查
2. 静态扫描
3. 函数返回值扫描
4. 出入参检查
5. 代码规范安全性

## 5. 功能要求

### 5.1 检测方法

1. 内存动态检查： AddressSanitizer
2. 静态扫描检查：选择一种开源或者商用的静态扫描工具，例如 Coverity Scan
3. 函数返回值检查：已有自研工具
4. 出入参检查：选择一种开源或者自研的工具
5. 代码覆盖率检查：现有的 GCOV，参见 [文档](https://taosdata.feishu.cn/wiki/I0tuwHVYWisgkhk8xTNc15mmnzb)
6. 错误码检查：已有自研工具
7. 代码格式化检查：集成现有格式化脚本
8. 漏洞扫描机制：考虑 Trivy、CodeQL 等
9. SQL 注入检测机制：集成一种 SQL 注入检测方法
10. 其他检查：新增或者收集已有的检查工具

### 5.2 检查机制

1. 形成整体设计文档（FS），并形成可运行的工具
2. 该工具可对引擎代码进行全面检查，检查结束后，可自动（半自动）生成检查分析报告
3. 针对检查分析报告，人工分析后，创建相应的修复任务
4. 建立常态化静态扫描机制，由平台部集成到 github actions 或者其他常态化运行方案中

### 5.3 其他组件检查

1. 引擎的编码安全机制完成后，和其他组件负责人一起制定其他组件的规范
2. 产生的新机制，汇总到设计文档中，并集成到同一工具中
