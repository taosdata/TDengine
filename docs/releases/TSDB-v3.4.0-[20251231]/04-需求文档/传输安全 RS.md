## 3. 需求目标

对重要数据的传输过程进行加密。
1. 白名单设计过于简单，需增强功能
2. TLS 外可能还需其他机制
3. 数据包大小无限制
4. 传输层做消息校验，防止恶意消息耗尽内存
5. 防范消息重放攻击
6. 连接管理，登录用户 session 管理
7. 多副本状态切换的消息认证机制
8. 集群状态变换的消息认证机制

## 4. 功能需求

### 4.1 TLS 安全性增强

在  3.3.8 版本已经支持基于 TLS 的证书传输，但其安全性还需要进一步增强，涉及的点有
1. 私钥文件安全存放：使用 “存储安全” 需求中提到的 CFG_KEY 对证书相关的密钥文件进行加密，加密后存储到 dnode/config 文件夹下。加密触发由 taosk 手动进行，记录加密时间。
2. 私钥文件更换时间查看：与[ 存储安全需求文档](https://taosdata.feishu.cn/wiki/UYAqwU3GqiBsjCkT6BccKqLmnGh) 中的 “密钥变更” 节中 “查看SVR_KEY、DB_KEY” 的 SQL 语句一并设计
3. 私钥文件定期更换：与[ 存储安全需求文档](https://taosdata.feishu.cn/wiki/UYAqwU3GqiBsjCkT6BccKqLmnGh) 中的 “密钥变更” 节中 “设置密钥到期时间和到期策略” 的 SQL 语句一并设计

### 4.2 通信安全性增强

当开启 TLS 传输时，所有内部通信，包括多副本状态切换、集群状态变换等消息，均通过 TLS 加密。此外，在传输层，增强如下校验。
1. 为消息增加随机的 SALT 、序列号或者时间戳，避免消息重放攻击
2. 对数据包进行安全性校验，防止恶意消息耗尽内存，即改造现有的消息队列机制
3. 增强数据包的完整性校验，防止消息在传输中被篡改，现有 checksum 机制安全性不够
4. 对数据包大小进行限制，防止恶意传输大数据包

### 4.3 关键信息传输

开发一套 SASL 机制，在 TLS 传输基础上，增强关键信息的传输安全。
1. 在 RPC 层提供单独的传输接口，在业务层可以透明调用
2. 修改“创建用户、修改用户、用户登录、秘钥更改、关键参数”等关键信息的发送过程，使用 SASL 通信
SASL 采用挑战-响应机制，可集成 `libsasl` 库中的 API 来实现。参照的 API 过程如下：

| **阶段** | **主要任务** | **关键 SASL API (示例)** |
| --- | --- | --- |
| 初始化 | 加载库、插件和机制；建立连接上下文；设置安全属性和回调函数。 | sasl_client_init(), sasl_server_init() |
| 机制协商 | 服务端通告支持的机制；客户端选择最合适的机制（通常基于安全强度）。 | sasl_listmech(), sasl_client_start() |
| 认证交互 | 服务端发出挑战（Challenge）；客户端计算并返回响应（Response）；可能多轮往返。 | sasl_server_step(), sasl_client_step() |
| 安全层协商 | 认证成功后，协商后续通信是否启用以及使用何种安全层（完整性、保密性）。 | 自动完成，通过 sasl_getprop()查询 SSF |
| 安全通信 | 若协商了安全层，后续应用数据需通过 sasl_encode()和 sasl_decode()进行加密解密。 | sasl_encode(), sasl_decode() |
| 连接释放 | 认证失败或会话结束后，释放连接上下文和相关资源。 | sasl_dispose(), sasl_done() |

### 4.4 白名单增强

1. 在 [身份鉴别需求文档](https://taosdata.feishu.cn/wiki/GZNPwH62SiiRtQkQHTvcM73YnDh) 中的创建用户语法定义中，增加了 <禁止HOST> 子句，需在白名单中处理此逻辑。
2. 还需和 taosadapter 联调，处理禁止 host 的相关逻辑，因此这个功能还需提早开发，避免阻塞 taosadapter 的开发任务。 

### 4.5 连接管理

在 [身份鉴别需求文档](https://taosdata.feishu.cn/wiki/GZNPwH62SiiRtQkQHTvcM73YnDh) 中的创建用户语法定义中，增加了如下选项
1. SESSION_PER_USER 
2. CONNECT_IDLE_TIME 
3. CONNECT_TIME 
4. CALL_PER_SESSION 
5. VNODE_PER_CALL 
6. <允许时间子句> 
7. <禁止时间子句>
 请处理这些选项的逻辑。此外，还需在系统表中，对 connections 记录更多必要的连接信息，例如
1. connect_idle_time
2. max_call_per_session
3. max_call_per_vnode
4. username
5. token_id

### 4.6 检测暴力破解

1. 详细记录各类通信失败，尤其是登录失败，包括：时间戳、尝试使用的用户名、来源IP地址、失败原因
2. 通信失败应实时写入监控库
3. 出现严重的异常行为时，例如当某用户名或IP的失败次数在设定的时间窗口（如 1 分钟、5 分钟）内超过阈值（如 5 次），即可判定为异常行为。
   - 进行告警（写入监控库、配置告警策略）
   - 暂时锁定该用户账号或来源 IP

## 5. 性能需求

传输安全在保证通信安全性的同时，也会带来一定的性能影响。在测试过程中，对如下指标进行测试，如果性能不达预期，需优化代码。
1. **写入性能**：
   - 加密实现影响数据写入性能，写入延迟增加不得超过 100%。
2. **查询性能**：
   - 加密实现影响数据查询性能，查询延迟增加不得超过 100%。

## 6. 安全需求

1. 连接管理、白名单查看，在“访问控制”实现时，考虑到仅 SYSSSO 具备权限
