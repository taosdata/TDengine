# 4096 改 32767 列性能影响评估

## 1. 第一部分  代码评估

### 1.1 说明

1. LINUX 下 GCC 编译的 TDengine 默认栈大小为 64 M
2. MAX 下 GCC 编译的 TDengine 默认栈大小为 8 M
3. WINDOWS 下 TDengine 编译设置了栈大小为 8 M
```c {wrap}
set(CMAKE_EXE_LINKER_FLAGS "${CMAKE_EXE_LINKER_FLAGS} -Wl,--stack,8388608") 
```

### 1.2 引擎类

1. 宏 TSDB_MAX_COLUMNS 使用
引擎内共 6 处使用，全部为边界检查，评估对性能无影响
1. 宏 TSDB_MAX_SAVED_SQL_LEN 使用 
#define TSDB_MAX_SAVED_SQL_LEN   TSDB_MAX_COLUMNS * 64
用于 TSMA 的 SQL 存放，栈上分配，增大 1.7 M,  建议改为堆上分配
```c {wrap}
char buf[TSDB_MAX_SAVED_SQL_LEN + VARSTR_HEADER_SIZE] = {0};
if (TSDB_CODE_SUCCESS == code) {
  // create sql
  pColInfo = taosArrayGet(pBlock->pDataBlock, cols++);
  len = tsnprintf(buf + VARSTR_HEADER_SIZE, TSDB_MAX_SAVED_SQL_LEN, "%s", pSma->sql);
  varDataSetLen(buf, TMIN(len, TSDB_MAX_SAVED_SQL_LEN));
  code = colDataSetVal(pColInfo, numOfRows, buf, false);
}
```


1. 宏 TSDB_MAX_COL_TAG_NUM 使用
  #define TSDB_MAX_COL_TAG_NUM  (TSDB_MAX_COLUMNS + TSDB_MAX_TAGS)
  仅在复制表 meta 信息中有一个边界检查，评估对性能无影响
1. 宏 TSDB_SHOW_SCHEMA_JSON_LEN  使用
  #define TSDB_SHOW_SCHEMA_JSON_LEN TSDB_MAX_COLUMNS * 256
   - 订阅中把 schema 转为 json 格式，做边界检查，评估对性能无影响
   - 在堆上分配内存增加 6.9 M 内存，评估影响可接受
  ```c {wrap}
  schemaJson = taosMemoryMalloc(TSDB_SHOW_SCHEMA_JSON_LEN + VARSTR_HEADER_SIZE);
  ```

1. 检查源码中直接使用 4096 常量作为列最大值，检查结果为无

## 2. 第二部分 实测性能

### 2.1 测试方案

1. 工具： taosBenchmark 
2. 性能指标：写入/查询
3. 对比：修改分支/3.0 分支
4. 写入类型：拼 SQL 方式批写入
5. 查询类型：投影/聚合查询各一个
6. 全部为 float 列（用户最常用的数据类型）
7. 子表数 100 个
8. 每子表写入 1 万行

### 2.2 场景及预期

1. 常用 256 列场景，预期写入/查询性能无影响
2. 8000 列写入/查询性能摸底

### 2.3 测试结果

测试机器： 192.168.1.43  
       内存： 256M  
       磁盘： SSD 1.8 T 
       CPU:    40 核  Intel(R) Xeon(R) CPU E5-2650 v3 @ 2.30GHz
说明：
- 聚合查询为 select count(*) from super_table
- 投影查询为 select * from super_table

| 场景 | 256 列 （3.0分支） | 256 列 （修改分支） | 8000 列 （修改分支） | 256列 （改版后） | 256列 （merge） |
| --- | --- | --- | --- | --- | --- |
| 写入速度(行/秒) | 42439 | 42290 | 1286 | 42141 | 42858 |
| 聚合查询 QPS(次/秒) | 1.965 （39） | 1.977 | 1.976 | 2.53 | 38 |
| 投影查询 QPS(次/秒) | 0.121 | 0.122 | 0.003 | 0.12 | 0.12 |

     数据解读：
- 256 列 3.0 分支与修改分支比较，写入及聚合/投影查询速度几乎相同，符合预期
- 修改分支上 256 列与 8000 列对比，随列数增加呈线性递减趋势，符合预期
  - 列数增长了 33 倍
  - 写入速度减小了 31 倍
  - 投影查询速度减小了 40 倍
  - 聚合查询变化不大符合预期，列数对 COUNT 查询影响很小。     

## 3. 最终结论

实测性能几乎无影响，与代码层面分析结论一致，但功能上还存在一些问题。

## 4. 存在问题

1. 每行长度限制
目前每行的长度由宏 TSDB_MAX_BYTES_PER_ROW 控制，定义的是 64K， 当列数过多时，会超过这个限制报错，所以上面测试最大只能建到 8000 列个 FLOAT.
1. 栈上分配内存过大
TSDB_MAX_SAVED_SQL_LEN 在栈上分配内存增大 1.7 M，在默认栈较小的平台上存在隐患， 建议改为堆分配为好。
1. SQL 默认最大长度 1 M 限制
目前引擎默认 maxSQLLength 为 1 M, 创建过多列时会超过此值报错，建议增大默认值或在官网文档中说明。
1. taosBenchmark 工具受限
在 taosBenchmark 中定义的 SQL 最大长度为 TSDB_MAX_ALLOWED_SQL_LEN 为 1M,  创建过多列会超过此值报错，建议修改为 4M, 能覆盖大部分情况。
