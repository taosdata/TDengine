## 2. 项目概述

### 2.1 **项目名称**

TDengine TSDB v3.4.0.0 版本开发项目

### 2.2 **项目目标**

全面的安全加固，虚拟表和流计算性能优化，巩固时序数据库领域的领先地位。

### 2.3 **项目范围**

#### 2.3.1 安全功能

本次版本迭代的核心目标之一是全面提升 TDengine 的安全性、可靠性和合规性，主要围绕以下八大安全维度进行建设：
1. 身份鉴别：支持多因子认证，强密码策略，确保用户身份的真实性。
2. 访问控制：实施基于角色的访问控制，实现库、表级别的权限管理。
3. 存储安全：支持配置文件、用户信息、时序数据文件的加密存储，支持国密算法和密钥生命周期管理。
4. 传输安全：对重要数据的传输过程进行加密，防止消息重放攻击，优化白名单，建立消息认证机制。
5. 安全函数：提供一系列内置安全函数，方便开发者处理常见安全需求。
6. 安全审计：建立完整的审计流水线，记录关键操作，满足合规性要求。
7. 加密算法：集成国密等符合行业要求的加密算法套件，提供更多算法选择。
8. 编码安全：优化静态、动态检查机制，降低因编码不当引入的安全漏洞风险。

#### 2.3.2 通用功能

在安全增强的基础上，本次版本迭代将对以下核心通用功能进行迭代和优化，以提升产品性能和用户体验：
1. 虚拟表​：优化虚拟表继承机制，提升其在多场景下的查询性能与稳定性。
2. 流计算：增强流式计算能力，支持按自然月触发计算任务、处理子事件复杂逻辑，并显著提升其性能，缩小与先进计算框架（如 Flink）在特定场景下的差距。
3. TDgpt：引入相关性分析功能，为用户提供更深层次的数据洞察。
4. OAuth 2.0：支持通过 OAuth 2.0 与第三方身份提供商集成，实现单点登录和集中式身份管理。
5. taosX 分布式能力增强：进一步提升 taosX 工具在分布式环境下的数据同步与备份能力。

#### 2.3.3 过程改进

为确保产品高质量交付并提升团队长期研发效能，本项目范围内还包括以下研发过程改进工作，旨在建立更规范、更高效、更质量可控的研发体系
1. 管理体系与流程优化
   - 组织架构与准则​：制定并推行组织级的研发管理准则和过程体系大纲。
   - 项目生命周期管理​：建立覆盖立项、规划、开发、测试、发布、验收、投产的全流程管理规范，并制定明确的变更规则与进度管控机制。
   - 日常运维制度化​：完善缺陷管理、异常告警、客户支持、代码仓库管理、问题复盘及周报、月报等日常运维制度。
2. 质量与安全规范建设
   - 技术基线规则​：统一测试用例编写、编程语言开发、关键字增删及日志撰写的规范与标准。
   - 全面安全管理​：建立贯穿整个开发周期的安全开发管理制度，涵盖安全需求、设计、编码、测试（渗透测试、工具扫描、安全自查）、审计及新技术引入评估等环节。
   - 质量保障体系​：完善风险管理制度、供应商管理、配置管理、变更控制流程、质量保证制度及质量自查体系。
3. 知识沉淀与资产复用
   - 研发文档模板化​：制定并应用统一的需求、设计、测试、验收、评审及会议记录模板，提升文档质量和编写效率。
   - 培训与考核​：建立培训制度与绩效考核制度，确保各项流程规范得以有效贯彻和持续改进。

### 2.4 项目工期

项目于 2025-10-01 启动，在 2026-01-25 完成开发与测试，最终于 2026-01-28 成功发布。

## 3. 项目度量数据分析

### 3.1 进度与工作量评估

项目整体进度按计划推进，最终发布日期与里程碑计划吻合。在开发中期，分别在 2025-09-26、2025-11-20、2025-12-18 三个时间点引入了工作范围变更，可参加[项目变更跟踪表](https://taosdata.feishu.cn/wiki/BTGrwb34eizl3ekaf8scdOaznFb)。项目团队通过临时增加核心开发资源、并调整部分优化项的优先级，确保了关键路径不受影响，最终追回了开发进度。
项目总工作量约为 2000 人天，与立项时的预估基本一致。工作量分布上，新特性开发约占 45%，代码优化与重构约占 30%，缺陷修复与测试约占 25%。

### 3.2 缺陷分析

项目周期内共发现并修复了45个缺陷。各模块的缺陷分布、占比及典型问题如下表所示：

| 模块名称 | 缺陷数量 | 占比 | 典型问题 |
| --- | --- | --- | --- |
| 流计算 | 12 | 26.7% | 触发数据重算时未使用最新WAL版本号导致结果错误；使用FILL_HISTORY计算历史数据失败；事件窗口通知概率性失败[[1]](https%3A%2F%2Fdocs.taosdata.com%2Freleases%2Fnotes%2F3.4.0.0%2F)。 |
| 查询引擎 | 8 | 17.8% | 嵌套查询在逆序排序时结果错误；ORDER BY ABS(col) 在特定场景下报错；虚拟表查询触发“Invalid value in client”错误[[1]](https%3A%2F%2Fdocs.taosdata.com%2Freleases%2Fnotes%2F3.4.0.0%2F)。 |
| 连接器 | 6 | 13.3% | taosAdapter回调函数未调用导致崩溃；C WebSocket `taos_stmt2_get_fields` 接口类型错误[[1]](https%3A%2F%2Fdocs.taosdata.com%2Freleases%2Fnotes%2F3.4.0.0%2F)。 |
| 数据订阅及 taosX | 7 | 15.6% | 与tdb修改操作并发引发的问题；单条消息过大可能导致SQL超长[[1]](https%3A%2F%2Fdocs.taosdata.com%2Freleases%2Fnotes%2F3.4.0.0%2F)。 |
| 企业级功能 | 3 | 6.7% | 修改全局变量时事务无法结束；特定场景下用户登录策略异常。 |
| 其他（存储、OPC-UA采集等） | 9 | 20.0% | OPC-UA点位数多时写入延迟明显；PI/PI Backfill数据源包含句号时任务失败[[1]](https%3A%2F%2Fdocs.taosdata.com%2Freleases%2Fnotes%2F3.4.0.0%2F)。 |

缺陷根本原因分析
1. **逻辑复杂性**：流计算和复杂查询相关的缺陷占比最高（合计超 44%），主要源于时序数据窗口计算、状态维护及嵌套查询优化器的逻辑极其复杂，边界条件容易遗漏。
2. **并发与交互**：数据订阅（taosX）和连接器的缺陷多与高并发场景下的资源竞争、线程同步或跨组件通信相关。
3. **集成与升级**：企业级功能及部分“其他”类缺陷，常出现在新功能与原有系统集成，或特定版本升级路径中。
修复效率
缺陷的平均修复时间为3.5人天，严重及以上缺陷的修复周期控制在 5 人天内。缺陷重开率约为 4%，处于可控水平。

### 3.3 成本与预算分析

项目实际总成本与原始预算的偏差较小。成本略超预算的主要原因在于：为应对流计算等复杂模块的测试挑战，项目中期增加了自动化测试用例和专项测试环境的投入。这部分投入有效降低了后期缺陷修复成本和高优先级线上问题的风险，从整体项目效益看是值得的。

## 4. 项目过程回顾与评估

### 4.1 项目总体表现评估

项目全面达成初始设定目标。成功交付的 TDengine 3.4.0.0 版本包含 21 项新特性、26 项优化和 45 项修复[[1]](https%3A%2F%2Fdocs.taosdata.com%2Freleases%2Fnotes%2F3.4.0.0%2F)[[2]](https%3A%2F%2Fnewreleases.io%2Fproject%2Fgithub%2Ftaosdata%2FTDengine%2Frelease%2Fver-3.4.0.0)。产品能力在多个维度得到显著提升
1. 安全功能全面提升
2. 流计算的事件窗口触发支持子事件窗口
3. 流计算的资源消耗和计算延迟显著降低
4. 虚拟表的查询性能优化
5. 查询性能优化及语法增强

### 4.2 各过程执行情况评价

1. **立项过程**：目标明确，范围清晰，与公司年度“AI First”战略紧密对齐，为项目成功奠定了基础。
2. **开发过程**：采用了“特性驱动开发”模式，每个特性/优化项均有明确负责人和验收标准。特性分支管理策略有效，保证了主线代码的稳定性和并行开发效率。
3. **测试过程**：测试策略执行到位。除了常规功能测试外，重点强化了对流计算引擎、高并发数据订阅、企业级安全功能的专项测试与压力测试。
4. **发布过程**：发布流程规范，所有发布包（各平台安装包、Docker镜像）均经过严格验证。版本发布说明文档[[1]](https%3A%2F%2Fdocs.taosdata.com%2Freleases%2Fnotes%2F3.4.0.0%2F)内容详实，清晰地列出了全部 21 项特性、26 项优化和 45 项修复。

### 4.3 风险管理回顾

项目初期便建立了完善的风险管控机制，系统识别并持续跟踪了 5 项核心风险，涵盖设计与管理两大类别，通过针对性策略落地实现了有效管控，未对项目目标达成造成实质性影响，具体管控情况如下：

#### 4.3.1 **设计类风险**

1. 安全功能开发缺少专业技术支撑：为降低风险影响，项目团队采用风险减轻策略，通过咨询AI工具及专业书籍补充技术储备，目前该风险已顺利解决，保障了安全功能开发的专业性与准确性。
2. 安全功能可能引入性能衰退风险：针对此风险，团队同样采取风险减轻策略，在各安全功能开发过程中同步引入性能测试环节，提前排查性能隐患，目前该风险处于已识别状态，将在后续测试阶段持续跟踪验证，确保性能达标。

#### 4.3.2 **管理类风险**

1. 研发体系建设和过程改进无参考方案：队通过风险减轻策略，参考CMMI3认证体系搭建研发体系、优化过程管理，已形成完善的参考方案，风险已解决。
2. 质量体系建设无参考方案：该为破解无参考依据的难题，团队采取风险减轻策略，引入外部专家提供专业指导，助力质量体系标准化建设，目前风险已解决。
3. 安全体系建设无参考方案：通过引入外部专家参与规划设计，弥补了内部经验短板，顺利搭建起符合项目需求的安全体系，风险已解决。
整体来看，项目风险管控成效显著，除1项设计类风险需持续跟踪外，其余风险均通过精准策略落地实现闭环管理，为项目按计划高质量交付提供了有力保障。

## 5. 经验教训总结

| 成功经验 | 待改进点 |
| --- | --- |
| **特性驱动与明确责任制**：采用"特性驱动开发"模式，为每项新功能、优化或重大修复指定唯一负责人，并制定清晰的验收标准。这极大地提升了开发效率与交付质量的可追溯性。 | **复杂缺陷的早期发现能力不足**：如"数据订阅并发问题"等涉及多线程、分布式状态的缺陷，在测试中后期才被发现，修复成本较高。**建议**：在测试策略中增加"并发与一致性"专项测试轮次，并开发或引入针对性的混沌工程工具，在开发早期模拟异常交互。 |
| **自动化工具链赋能**：项目内生的工具建设（如 Rust 连接器性能测试工具）不仅解决了当前版本的测试难题，更形成了可持续复用的资产，提升了团队长期效能。 | **跨团队接口变更流程有待标准化**：核心引擎与 taosAdapter 等周边组件间的接口变更，有时依赖临时沟通，存在信息不同步的风险。**建议**：建立正式的接口变更通知与兼容性评估流程，所有变更需更新接口文档并通过契约测试验证。 |
| **积极响应社区反馈**：将 GitHub 等高优先级社区 Issue 纳入项目缺陷跟踪系统，并建立快速响应流程。这既修复了用户痛点，也借助真实场景锤炼了产品稳定性。 | **工作量评估精度可提升**：项目中期对部分优化项的工作量评估出现偏差，导致资源需要临时调整。**建议**：推广使用更精细化的任务分解（WBS），并对包含技术不确定性的任务预留合理的缓冲时间。 |
| **风险前置管理**：对 AI 集成等高风险任务进行早期技术预研，避免了项目后期出现不可控的技术障碍。 | |
