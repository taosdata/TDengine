## 3. 需求目标

对于事件窗口和状态窗口，在数据偶尔波动的情况下，往往会生成许多持续时间极短的窗口。从业务角度来看，这些窗口通常会被视为误报。在判断是否构成一个新的窗口时，以往的方法是一旦满足条件即视为窗口开启。而新的方法则要求窗口必须持续一段时间之后，才被认定为真正开启。
为 `STATE_WINDOW`、`EVENT_WINDOW` 窗口新增关键字 `TRUE_FOR`，用于指定窗口的最短持续时间。语法如下
```sql
window_clause: {
  | STATE_WINDOW(col) TRUE_FOR(true_for_duration)
  | EVENT_WINDOW START WITH …… END WITH …… TRUE_FOR(true_for_duration)
}
```

## 4. 功能需求

金清在讨论[功能需求](https://taosdata.feishu.cn/wiki/M0u1wbC7biqIy7kM6yRcTbCDnlC)时提到几个问题：
1. 最短持续时长限制是对 窗口宽度 还是 开窗条件为真的持续时间 的限制 ？(> OR >= true_for)
2. 开窗条件为真的数据必须连续？
3. 如果开窗数据有部分符合关窗条件，如何划分？
4. 如果部分开窗数据在前一个窗口内，如何划分？
我做统一的回答
1. 最短持续时长限制是针对**窗口宽度的**。
2. 开窗条件为真的数据不必须连续。开窗条件为真后，在接收到满足关窗条件的数据之前，窗口的持续时间将不断累加，直至达到预设的 `true_for_duration` 时长。
3. 当接收到任意一条满足关窗条件的数据后，该窗口将被视为未达到 `true_for_duration` 时长的要求。因此，该窗口及其包含的部分数据将被丢弃，随后开始对下一个窗口条件进行判断。
4. 不应出现窗口交错的情况，问题中“部分开窗数据”应属于上一个窗口。
其他说明
Jeff 仅提到在流计算中支持窗口持续时长的功能。但常规批查询也需要支持相同的语法和特性，请综合考虑工作量。
