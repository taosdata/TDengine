# Arbitrator 双副本用户手册

### 1. 部署方式

基于Arbitrator的双副本功能采用双节点（+独立Arbitrator）的部署方式，也就是说只部署3个节点，其中2个节点为正常节点，其中另外一个节点为低配节点。

该部署下，可以在单副本，双副本之间切换。

涉及到的命令如下：
```sql
Create dnode “localhost：6030” as arbitrator; //创建Arbitrator节点

CREATE DATABASE power REPLICA 2 with Arbitrator; //创建2副本的数据库

Alter database db1 replica 2 with arbitrator；//将数据库改为2副本
```


### 2. 复制模式

设置为2副本的db，可以设置复制模式，不同的复制模式决定了2个副本之间的数据复制方式。
用户根据自己的需求选择采用不同的复制模式。不同的复制模式，在一致性和可用性上有不同的表现，用户需要更具自己的业务的一致性和可用性的需求，决定采用不同的复制模式。

#### 2.1 异步

     在数据写入时，投票规则改为，所有节点回复达到2即可

根据异常处理行为分为两种异步模式：
- 自动模式
该模式特性为：
[一致性]:不保证
[可用性]:具有更高的可用性

一致性异常情况：
该模式会出现2个数据节点中，一个数据较新（数据到100），一个数据较旧（数据到98），当较新节点宕机，或者出现网络波动，会导致选举：
1.较旧的节点成为leader，丢失一部分数据（99,100两个数据）
2.旧leader重新启动，成为follower继续运行，rollback部分数据（99,100两个数据）

自动模式的等待时长的设置，在自动模式下，会出现由于网络波动导致的数据丢失情况，为了缓解这种数据丢失，可以将重新选举的时长设置成一个比较长的时间，只有超过这个时间之后，才会重新切主，相当于设置了一个比较难达到的数据丢失条件。

- 手动模式（或者叫固定leader模式，手动切主模式，手动修复模式）（二期）：
与传统的异步主备，基于Arbitrator的异步双副本存在一个问题，由于网络波动，导致选主，从而导致丢失数据，传统的异步主备不存在这个问题，是因为主备2个角色是固定的，不会出现自动的主备切换。将raft中的leader和follower固定，达到与传统的异步主备相同的效果。
该场景的异常情况为：
出现网络波动时，不会发生选举，固因无leader存在，数据将无法继续写入，网络恢复后，写入也自动恢复。
当节点宕机时，因无leader存在，数据无法继续写入，需要人工介入，修复leader节点，或者手工切换leader。
涉及到的命令，暂未设计。

#### 2.2 同步（三期）

在数据写入时，投票规则改为，非arbitrator的回复达到2，即一直等待另外一个有数据的节点的回复
[可用性]:另外一个节点宕机，则这个raft组不可用。
[一致性]:但是可以保证数据的一致性，即数据的可靠性
可用性异常情况：
2个数据节点任意一个节点宕机，如果是leader节点宕机，原来的follower虽然可以被选成leader，但是仍然不能写入数据，必须等宕机节点回复才能继续写入数据

#### 2.3 半同步（三期）

对等半同步，同样，在初始阶段，raft组按照#1中运行进行同步复制。
- 当一段时间没有收到另外一个数据节点的回复时。超过一个设置的时间后，该raft组按照#2中的方式运行，进行异步复制，进入异步状态后，服务恢复可用。
- 当另外一个节点恢复后，即leader节点可以正常收到另外一个follower节点的回复后，该raft恢复回同步模式。
这个半同步模式，相当于是前面同步模式和异步模式的组合，并且根据节点的运行情况自适应切换。
自动适应运行在哪种模式，会具有哪种模式的异常，在同步模式下，任意节点宕机，该raft组不可用，也就是数据不能写入；在异步模式下，会出现丢数据的情况。
