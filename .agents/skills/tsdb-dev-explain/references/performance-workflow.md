# TDengine EXPLAIN 性能诊断流程

当用户正在排查慢查询，或者还不知道该先收集什么证据时，读取此参考文档。

## 总体流程

按照以下顺序进行，一旦下一层瓶颈已经清楚，就可以停止继续展开：

1. 确认 SQL 和现象
2. 索要成本最低的缺失 `EXPLAIN` 证据
3. 按固定顺序阅读执行计划
4. 说明最可能的瓶颈
5. 给出一到两个聚焦的下一步动作

## 第 1 步：确认现象

优先向用户索要最小缺失上下文：

- 是首行返回慢，还是整体结果慢
- 大致涉及哪张表或超级表
- 查询里是否包含过滤、`GROUP BY`、`ORDER BY` 或窗口

除非没有这些信息就无法解释执行计划，否则不要一开始就追问过宽的环境信息。

## 第 2 步：索要成本最低的缺失证据

建议按以下顺序索要：

1. `EXPLAIN <sql>`
2. `EXPLAIN ANALYZE <sql>`
3. `EXPLAIN ANALYZE VERBOSE true <sql>`

优先使用能够回答当前问题、但成本最低的命令。

- 如果用户只想看计划形态，`EXPLAIN` 就够了。
- 如果用户想知道瓶颈在哪，优先用 `EXPLAIN ANALYZE`。
- 如果用户需要看下推、网络或排序细节，再加 `VERBOSE true`。

## 第 3 步：按固定顺序阅读计划

按以下顺序检查：

1. 扫描范围：`Table Scan`、`Tag Scan`、`Table Merge Scan`
2. 裁剪质量：`Primary Filter`、`Tag Index Filter`、`Time Range`
3. 昂贵的结果重整：`Sort`、`Group Sort`、`Merge`
4. 聚合或窗口：`Aggregate`、`GroupAggregate`、`Interval`、`Session`、`StateWindow`、`Event`、`External`
5. 分布式开销：`Data Exchange`、`Network`
6. 运行时证据：`rows=`、`cost=`、`Exec cost`、`I/O cost`

## 第 4 步：谨慎说明瓶颈

使用有证据支撑的表述，例如：

- “主要成本看起来来自大范围表扫描，因为……”
- “最可能的瓶颈是分布式交换，因为……”
- “这条查询在过滤之后又付出了显式排序成本，因为……”

如果执行计划只能部分支持结论，不要下过强判断。

## 第 5 步：给出最小下一步动作

优先给出一到两个动作，例如：

- 收紧时间范围条件
- 检查 tag 条件是否还能更有选择性
- 去掉或减少不必要的排序
- 对比带分组和不带分组的查询变体
- 如果裁剪或网络行为还不清楚，再补跑一次 `VERBOSE true`

## 建议输出结构

面向用户输出性能诊断结论时，建议按以下顺序：

1. 一句话总结诊断结论
2. 列出执行计划里的最强证据
3. 给出一到两个具体下一步动作
4. 只有在确实还缺证据时，再补一条后续命令
