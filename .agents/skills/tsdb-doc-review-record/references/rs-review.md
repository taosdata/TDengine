# 需求评审记录 (RS Review) 格式规范

## 文件命名与存放

- **文件名:** `YYYYMMDD {Feature Name} 需求评审记录.md`
- **目录:** `docs/releases/TSDB-v{version}-[YYYYMMDD]/09-会议纪要和评审记录/04-产品开发/01-需求/`

## 评审目的（固定用语）

```
评估 "{Feature Name}" 需求的完整性、合理性、可行性与安全性
```

## 评审文档链接

链接指向 RS 文档，相对路径示例：
```
[{Feature Name} RS](../../../04-需求文档/Feature%20Name%20RS.md)
```

## 评审记录格式

### 结构

Section 2 包含 **1 个开头段落** + **4 个子标题**（2.1-2.4），每个子标题下使用 **bullet points (`-`)**。

### 开头段落

```markdown
评审团队对需求文档（{Feature Name} 相关）进行了全面审查，认为所有设计合理，具体评审意见如下：
```

### 四个子标题

| 子标题 | 聚焦 | 典型内容 |
|---|---|---|
| **2.1 功能** | 功能完整性 | 痛点是否解决、功能设计清晰度、里程碑/排期合理性 |
| **2.2 性能** | 性能影响 | 资源使用、缓存策略、降级处理 |
| **2.3 安全** | 安全设计 | 认证、加密、访问控制、审计日志 |
| **2.4 兼容性** | 兼容性 | 版本兼容、升级路径、向后兼容 |

### 列表样式

- 使用 bullet points (`-`)
- 每个 bullet 之间空一行
- 每个子标题至少一个 bullet item

### 示例

```markdown
## 2. 评审记录

评审团队对需求文档（XXX 相关）进行了全面审查，认为所有设计合理，具体评审意见如下：

### 2.1 功能

- 需求精准切中{痛点描述}，{功能描述}覆盖{场景描述}

- 功能范围定义清晰，{具体设计决策}

### 2.2 性能

- 性能设计合理，{性能相关描述}

### 2.3 安全

- 安全需求覆盖{安全相关描述}

### 2.4 兼容性

- 兼容性设计稳妥，{兼容性描述}
```

## 评审结论

标准措辞（除非评审未通过才修改）：

```
需求文档整体设计合理、逻辑清晰，可用于指导后续开发工作。
```
