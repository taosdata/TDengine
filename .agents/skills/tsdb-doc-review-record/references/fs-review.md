# 设计评审记录 (FS Review) 格式规范

## 文件命名与存放

- **文件名:** `YYYYMMDD {Feature Name} 设计评审记录.md`
- **目录:** `docs/releases/TSDB-v{version}-[YYYYMMDD]/09-会议纪要和评审记录/04-产品开发/02-设计/`

## 评审目的（固定用语）

```
评估 "{Feature Name} FS" 设计的合理性、安全性、性能、兼容性及可维护性
```

## 评审文档链接

链接指向 FS 文档，相对路径示例：
```
[{Feature Name} FS](../../../05-设计文档/Feature%20Name%20FS.md)
```

## 评审记录格式

### 结构

Section 2 **无子标题**，由 **1 个开头段落** 紧跟 **4 个编号段落** 组成。段落与编号列表之间无空行，编号项之间也无空行。

### 开头段落

```markdown
评审团队对设计文档（{Feature Name} FS）进行了全面审查，认为整体设计{特性相关正面评价}、逻辑严谨、可落地性强，具体评审意见如下：
```

### 四个编号段落

每一项以**短评价短语**开头，逗号或冒号后接详细展开，整段不换行：

| 编号 | 开头短语模式 | 聚焦 |
|---|---|---|
| **1** | 设计目标清晰精准，核心痛点定位明确 | 目标清晰度、痛点、业务场景对齐 |
| **2** | 功能设计全面细致，可落地性强 | 语法/API 设计、功能范围、约束、示例、可测试性 |
| **3** | 设计文档结构规范，版本与修订记录清晰 | 修订记录、术语、引用、模块分层 |
| **4** | 安全性、兼容性与性能考虑周全，风险可控 | 安全、向后兼容、性能影响与优化 |

### 示例

```markdown
## 2. 评审记录

评审团队对设计文档（XXX FS）进行了全面审查，认为整体设计贴合YYY需求、逻辑严谨、可落地性强，具体评审意见如下：
1. 设计目标清晰精准，核心痛点定位明确，紧扣{痛点描述}，明确核心目标为{目标描述}，目标聚焦、指引明确。
2. 功能设计全面细致，可落地性强，覆盖核心业务场景：{功能覆盖描述}，设计闭环完整。
3. 设计文档结构规范，版本与修订记录清晰：{文档结构描述}，逻辑清晰、无歧义，符合 TDengine 设计文档规范要求。
4. 安全性、兼容性与性能考虑周全，风险可控：{安全/兼容/性能描述}。
```

**注意：** 编号项之间**不**留空行。开头段落与第一个编号项之间**不**留空行。

## 评审结论

综合总结，包含特性关键词（非单句固定模板）：

```
设计文档整体设计合理、逻辑清晰，功能覆盖全面，{特性核心设计要素总结}，性能、安全、兼容性设计符合系统规范，精准解决了{核心痛点}。
```

## 后续行动项

默认：`无`。若有行动项，使用编号列表并注明负责人。

## 与需求评审 (RS) 的关键差异

| 方面 | RS 评审 | FS 评审 |
|---|---|---|
| 评审目的 | 完整性、合理性、可行性与安全性 | 合理性、安全性、性能、兼容性及可维护性 |
| 评审记录结构 | 4 个子标题 (2.1-2.4) + bullet points | 无子标题，4 个连续编号段落 |
| 列表间距 | bullet 之间有空行 | 编号项之间无空行 |
| 评审结论 | 固定一句话 | 综合总结含特性关键词 |
