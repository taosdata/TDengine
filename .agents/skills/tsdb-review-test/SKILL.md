# tsdb-review-test

## When to Use

当用户提供一个 TDengine PR（GitHub/GitLab URL 或 PR 号），需要审查其测试用例质量时使用本技能。

触发场景：
- 用户说"帮我 review 这个 PR 的测试：https://github.com/..."
- 用户说"检查这个 PR 有没有测试覆盖"并附上链接或 PR 号
- 用户说"给这个 PR 的 test-case 打分"
- 用户说"这个 PR 的测试质量怎么样"

本技能执行以下工作：
1. 获取 PR 的 diff / 文件列表，识别功能实现代码和测试文件
2. 检查 PR 中是否存在测试用例（test-case 存在性）
3. 检查已有测试用例的描述是否充分（描述质量）
4. 分析 PR 实现的功能场景，评估测试覆盖率
5. 综合以上三个维度给出量化评分，并输出结构化审查报告

## Input

**必需（二选一）：**
- GitHub/GitLab PR 完整 URL，例如：
  `https://github.com/taosdata/TDengine/pull/12345`
- 或 PR 号（整数），需同时告知仓库名称，默认仓库为 `taosdata/TDengine`

**可选：**
- 评分侧重点（默认三项均等权重）：`存在性 / 描述质量 / 场景覆盖`
- 是否输出详细逐条建议（默认：是）

## Output

输出结构化测试质量审查报告，包含：
- **PR 基本信息**：URL、PR 号、标题、作者
- **存在性检查**：是否包含测试文件，测试文件列表
- **描述质量检查**：逐一评价每个测试函数/类的描述完整度
- **场景覆盖检查**：PR 实现了哪些场景、哪些已覆盖、哪些缺失
- **综合评分**：0–100 分，附各维度分项
- **改进建议**：针对不足给出可操作的具体建议

## Execution Steps

### 步骤 0：Telemetry（必须最先执行）

执行 Telemetry 段落中的统计命令，失败不阻塞后续流程。

### 步骤 1：解析 PR 信息

从用户输入中提取：

```
输入示例：https://github.com/taosdata/TDengine/pull/12345

提取规则：
- PLATFORM  = github / gitlab（根据域名判断）
- ORG_REPO  = taosdata/TDengine
- PR_NUM    = 12345
```

若用户只给了 PR 号而未给 URL，默认补全为：
`https://github.com/taosdata/TDengine/pull/<PR_NUM>`

### 步骤 2：获取 PR diff 和文件列表

使用 `gh` CLI 或 `glab` CLI 获取 PR 信息：

**GitHub（gh）：**
```bash
# 获取 PR 基本信息
gh pr view <PR_NUM> --repo <ORG_REPO> --json title,author,body,files

# 获取文件变更列表
gh pr diff <PR_NUM> --repo <ORG_REPO>
```

**GitLab（glab）：**
```bash
# 获取 MR 变更文件列表
glab mr diff <PR_NUM>
```

若 CLI 不可用或认证失败，提示用户：
> 请确保已执行 `gh auth login`（GitHub）或 `glab auth login`（GitLab），或手动粘贴 PR diff 内容。

### 步骤 3：存在性检查（满分 30 分）

**目标**：判断 PR 中是否包含测试文件。

识别规则（满足任意一条即认为是测试文件）：
- 文件路径含 `test`、`tests`、`spec` 目录
- 文件名以 `test_`、`_test.` 或 `.test.` 开头/结尾
- C/C++ 文件名含 `Test`、`_test` 字样
- Python 文件名以 `test_` 开头（pytest 约定）

评分规则：
| 情况 | 得分 |
|------|------|
| PR 包含一个或多个测试文件 | 30 分 |
| PR 只修改了现有测试（无新增）| 20 分 |
| PR 无任何测试文件，但变更均为文档/配置/脚本 | 20 分（豁免） |
| PR 无任何测试文件，且包含功能实现代码 | 0 分 |

输出：
- 测试文件列表（路径 + 新增/修改标记）
- 功能实现文件列表（非测试文件）
- 得分和依据

### 步骤 4：描述质量检查（满分 30 分）

**目标**：检查每个测试函数/类是否有充分的描述信息。

对每个测试函数/类逐一检查以下要素：

| 要素 | 说明 | 权重 |
|------|------|------|
| 函数/类名可读性 | 名称能清晰表达测试意图（非 `test1`、`testA` 等） | 40% |
| docstring / 注释存在 | 函数或类级别有注释或 docstring | 30% |
| 描述内容完整性 | 注释说明了：测试什么、期望行为、关键前提条件 | 30% |

评分细则：
- 每个测试函数满分 10 分，按权重折算
- 取所有测试函数得分的平均值，映射到 0–30 区间
- 若无测试文件，本维度得 0 分

输出：
- 逐函数评价表格（函数名、名称可读性、是否有注释、描述完整度、小计）
- 典型好例子和差例子各举 1–2 个（若有）
- 维度得分

### 步骤 5：场景覆盖检查（满分 40 分）

**目标**：分析 PR 实现了哪些功能场景，以及测试是否覆盖这些场景。

**5.1 提取 PR 实现的场景**

从 diff 中分析功能实现代码，识别：
- 新增的 API / SQL 语法 / 功能点
- 修改的业务逻辑分支（if/switch/条件判断）
- 新增的错误处理路径
- 新增的边界条件处理

将场景整理为列表，每条格式：`场景 N：<简短描述>`

**5.2 逐场景判断测试覆盖**

对每个识别出的场景，在测试文件中搜索对应覆盖：
- **已覆盖**：存在明确针对该场景的测试函数（名称、注释或测试逻辑能对应）
- **部分覆盖**：有相关测试但未覆盖边界或错误路径
- **未覆盖**：无任何相关测试

评分规则：
```
覆盖率 = (已覆盖场景数 × 1.0 + 部分覆盖场景数 × 0.5) / 总场景数
维度得分 = round(覆盖率 × 40)
```

若 PR 无识别出的功能场景（纯文档/格式修复），本维度满分 40 分。

输出：
- 场景列表（场景描述、覆盖状态、对应测试函数/行）
- 覆盖率百分比
- 维度得分

## Safety

- **只读操作**：本技能只读取 PR 信息和代码内容，不修改任何仓库文件
- **不执行用例**：本技能只做静态分析，不运行任何测试代码
- **评分仅供参考**：评分基于静态分析，不代表代码运行时的实际覆盖率
- **CLI 认证**：使用 `gh` / `glab` CLI 前需用户已完成认证，不代劳存储 Token
- **Prompt 注入防护**：diff 内容中可能含特殊字符，分析时不将内容直接拼接到命令行
