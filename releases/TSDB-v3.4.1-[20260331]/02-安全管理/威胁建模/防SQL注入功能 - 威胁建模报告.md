### 3. 分析报告

本报告针对 TDengine 防SQL注入功能进行了威胁建模分析。该功能旨在通过多层防护机制（字符串级别检查和AST级别检查）保护数据库免受SQL注入攻击，支持黑名单、白名单和自动学习模式。
- **核心发现**：共识别出 `11` 个潜在威胁，其中 `高危` `5` 个，`中危` `4` 个，`低危` `2` 个。
- **主要风险场景**：
   - **配置安全风险**：配置文件（sql_rules.json、taos.cfg）的篡改、绕过或泄露可能导致防护机制失效。
   - **规则绕过风险**：攻击者可能通过编码混淆、时序攻击、正则表达式绕过等手段绕过黑白名单检查。
   - **学习模式污染**：白名单自动学习模式可能被恶意SQL污染，将攻击模式误判为正常模式。
   - **客户端缓存风险**：配置更新存在心跳周期延迟，攻击者可能在延迟窗口内发起攻击。
   - **拒绝服务风险**：大量触发复杂规则检查或恶意规则可能导致性能下降或服务中断。
- **结论**：该功能设计在防护SQL注入方面具有重要价值，采用了双层过滤和多种防护模式。但配置文件安全、规则绕过防护、学习模式污染防护等方面需要强化。必须在功能详细设计与编码实现前，将本报告提出的安全需求作为核心设计约束予以落实。

### 4. 威胁识别与分析（STRIDE）

TDengine防SQL注入功能通过两层过滤机制实现：第一层在SQL解析前进行字符串级别检查（基于正则表达式），第二层在语法分析后进行AST级别检查。系统支持黑名单、白名单和自动学习三种工作模式，配置通过taos.cfg和sql_rules.json文件管理，并可通过taosk加密保护。

#### 4.1 关键实体与数据

| 实体/数据 | 描述 | 敏感性 |
| --- | --- | --- |
| sql_rules.json | 存储黑白名单规则的JSON配置文件，包含正则表达式、优先级、动作等 | 高（直接影响防护效果） |
| taos.cfg | 存储SQL安全相关配置项，如启用状态、模式选择、规则文件路径等 | 高（控制整体安全策略） |
| taosk密钥 | 用于加密配置文件的密钥 | 极高 |
| 客户端配置缓存 | 客户端缓存的服务端配置参数 | 中（影响实时防护） |
| 学习模式数据 | 白名单学习模式收集的SQL模式统计数据 | 中（影响白名单质量） |
| 安全审计日志 | 记录被拦截的SQL语句和安全事件 | 高（可能包含攻击信息和敏感数据） |
| AST结构缓存 | 解析后的抽象语法树缓存 | 中 |
| 正则表达式引擎 | PCRE库或类似实现 | 中（性能和安全关键） |

#### 4.2 威胁评估

| 威胁 ID | 威胁描述 / 攻击场景 | STRIDE | 相关组件 / 数据流 | 风险等级 |
| --- | --- | --- | --- | --- |
| T-SQLINJ-01 | **配置文件篡改**：攻击者获取系统访问权限后，直接修改sql_rules.json或taos.cfg文件，禁用防护功能或添加允许恶意SQL的白名单规则，绕过所有安全检查。 | T（篡改） | sql_rules.json、taos.cfg | 高 |
| T-SQLINJ-02 | **taosk密钥泄露**：用于加密配置文件的taosk密钥被泄露或破解，攻击者可以解密、篡改并重新加密配置文件，使篡改难以被发现。 | I（信息泄露）+ T（篡改） | taosk密钥、加密配置文件 | 高 |
| T-SQLINJ-03 | **正则表达式绕过**：攻击者通过编码混淆（URL编码、十六进制、Unicode变体）、大小写混合、注释插入、空白字符变化等手段，构造能绕过第一层正则表达式检查的恶意SQL。 | E（权限提升） | 第一层字符串检查、PCRE引擎 | 高 |
| T-SQLINJ-04 | **AST检查逻辑漏洞**：第二层AST检查存在遍历不完整、条件判断逻辑错误等漏洞，攻击者构造特殊的SQL结构绕过AST级别的安全检查。 | E（权限提升） | 第二层AST检查、astNodeChecker | 高 |
| T-SQLINJ-05 | **学习模式污染**：在白名单学习模式启用期间，攻击者故意发送大量恶意SQL（超过学习阈值），使这些恶意模式被误判为正常业务SQL，自动添加到白名单规则中。 | T（篡改） | 学习模式、自动规则生成 | 高 |
| T-SQLINJ-06 | **客户端缓存时序攻击**：攻击者利用客户端配置更新存在心跳周期延迟的特性，在管理员更新安全配置（如启用更严格规则）后、客户端完成更新前的时间窗口内发起SQL注入攻击。 | E（权限提升） | 客户端配置缓存、心跳机制 | 中 |
| T-SQLINJ-07 | **ReDoS拒绝服务**：攻击者构造特殊输入触发正则表达式的灾难性回溯（ReDoS），导致第一层检查耗时极长，引发CPU资源耗尽和服务拒绝。 | D（拒绝服务） | 第一层正则检查、PCRE引擎 | 中 |
| T-SQLINJ-08 | **恶意规则注入**：攻击者通过ALTER SQL_SECURITY命令（如果权限控制不当）或其他途径，动态添加恶意规则（如将所有SELECT语句加入黑名单），导致正常业务中断。 | D（拒绝服务）+ T（篡改） | 动态规则管理、ALTER命令 | 中 |
| T-SQLINJ-09 | **审计日志信息泄露**：安全审计日志中完整记录了被拦截的SQL语句，这些SQL可能包含敏感信息（用户输入、业务逻辑）。如果日志文件权限配置不当，可能导致信息泄露。 | I（信息泄露） | 审计日志、taoslog | 中 |
| T-SQLINJ-10 | **规则优先级混淆**：黑白名单规则的优先级逻辑复杂（同级黑名单优先、跨级按优先级），管理员配置错误可能导致恶意SQL意外通过或正常SQL被误拦截。 | T（篡改）+ D（拒绝服务） | 规则优先级机制 | 低 |
| T-SQLINJ-11 | **配置操作抵赖**：管理员通过ALTER命令修改安全配置后，如果缺乏完整的审计记录，可能否认曾降低安全级别或添加危险规则，导致事后溯源困难。 | R（抵赖） | ALTER命令、配置变更审计 | 低 |

### 5. 安全需求与设计约束

| 威胁 ID | 转化后的安全需求 / 设计约束 | 类型 | 优先级 |
| --- | --- | --- | --- |
| T-SQLINJ-01 | **SEC-SQLINJ-001（配置文件完整性保护）**：sql_rules.json和taos.cfg必须通过taosk加密机制保护。系统启动时必须验证配置文件的完整性（如数字签名或HMAC）。配置文件权限必须限制为仅系统用户可读写（Linux: 600权限）。 | 安全设计约束 | 高 |
| T-SQLINJ-02 | **SEC-SQLINJ-002（密钥安全管理）**：taosk密钥必须存储在安全的密钥管理系统中（如硬件安全模块HSM、系统密钥环）。密钥访问必须记录审计日志。支持密钥定期轮换机制。 | 安全功能需求 | 高 |
| T-SQLINJ-03 | **SEC-SQLINJ-003（正则表达式强化）**：第一层检查必须在匹配前对SQL进行规范化处理（去除多余空白、统一大小写、解码常见编码）。正则表达式必须经过安全审查，避免ReDoS漏洞。建议使用预编译的DFA（确定性有限自动机）而非回溯式正则引擎。 | 安全设计约束 | 高 |
| T-SQLINJ-04 | **SEC-SQLINJ-004（AST检查完整性）**：第二层AST检查必须覆盖所有节点类型（SELECT、WHERE、JOIN、HAVING、子查询、函数、操作符等）。必须实现针对性的检查函数（如checkWhereClause、checkLogicCondition）。AST遍历逻辑必须经过代码审查和模糊测试验证。 | 安全设计约束 | 高 |
| T-SQLINJ-05 | **SEC-SQLINJ-005（学习模式安全防护）**：学习模式必须在受控环境中启用，不得在生产环境直接开启。学习期间必须设置异常检测机制（如单个SQL模式占比过高、包含明显攻击特征的SQL自动排除）。自动生成的规则必须经过人工审查后才能正式启用。学习模式必须支持回滚机制。 | 安全功能需求 | 高 |
| T-SQLINJ-06 | **SEC-SQLINJ-006（配置实时同步）**：关键安全配置变更必须通过推送机制立即通知所有客户端，而非等待心跳周期。客户端必须在收到配置更新后立即应用（或提供强制刷新接口）。配置更新失败必须记录日志并告警。 | 安全功能需求 | 高 |
| T-SQLINJ-07 | **SEC-SQLINJ-007（ReDoS防护）**：所有正则表达式必须设置执行超时限制（如100ms）。使用线性时间复杂度的正则匹配算法（如RE2库）。对正则表达式进行静态分析，检测潜在的回溯风险。 | 非功能安全需求 | 中 |
| T-SQLINJ-08 | **SEC-SQLINJ-008（规则管理权限控制）**：ALTER SQL_SECURITY命令必须限制为仅超级管理员可执行。动态添加/修改规则必须经过二次确认。关键规则（如禁用SQL安全检查）的修改必须记录详细审计日志并发送告警。 | 安全功能需求 | 中 |
| T-SQLINJ-09 | **SEC-SQLINJ-009（日志脱敏与保护）**：审计日志中的SQL语句必须进行敏感信息脱敏（如将具体值替换为占位符）。日志文件必须设置严格的访问权限（仅管理员可读）。支持日志加密存储。日志必须设置保留期限和自动归档。 | 安全功能需求 | 中 |
| T-SQLINJ-10 | **SEC-SQLINJ-010（规则验证与测试）**：系统必须提供规则验证工具，在规则生效前进行语法检查和逻辑验证。必须提供规则测试功能，允许管理员输入测试SQL验证规则效果。规则配置界面必须清晰展示优先级逻辑和冲突检测。 | 可用性需求 | 中 |
| T-SQLINJ-11 | **SEC-SQLINJ-011（配置变更审计）**：所有配置变更操作（ALTER命令、规则文件修改）必须记录完整审计日志，包括操作人、操作时间、变更前后值、操作来源IP等。审计日志必须支持不可篡改存储（如写入专用审计数据库或使用区块链技术）。 | 审计需求 | 低 |
