## 1. 引言

### 1.1 术语与缩写名词

| 复合主键 | 由多个数据列联合组成主键，也称为联合主键 |

### 1.3 优先级要求

金融行业时间精度是毫秒，一毫秒内往往产生多条交易，无法处理重复时间戳导致 TDengine 在金融行业的成单量很少。因而，在 2024-01-04 的版本规划会议上，提升本需求为最高优先级。
预期在 3.2.4.0 版本发布。

### 1.4 版本要求

在开源版支持。

## 2. 需求目标

通过复合主键实现重复时间戳需求。用户在创建普通表或超级表时，可以通过关键字 PRIMARY KEY 额外指定一列，与时间戳列共同组成复合主键。两行数据在时间戳列取值相同，且 PRIMARY KEY 列取值也相同的时候，被认为是同一行数据，否则为两行数据。建议 SQL 语法如下。
```sql
CREATE TABLE t (
    ts TIMESTAMP, 
    obj_id BINARY(64) PRIMARY KEY,
    data1 FLOAT,
    data2 INT,
    ……
);
```

- 设计时必须说明 PK 列的数据返回顺序与数据写入顺序的关系，须为确定性行为，与数据顺序有关的函数可能无法工作 （2024-01-09 与廖沟通，函数、窗口中涉及的数据顺序，安排 PK 值升序处理）
- 设计时必须说明窗口的时间范围为 0 的场景，与窗口有关的函数、插值、流计算可能无法工作
- 本次需求不对 PK 做索引，其查询性能不会高于普通列，对于卡口场景没有性能优化

## 3. 功能需求

### 3.1 结构定义

| 需求编号 | **需求描述** | 研发确认 |
| --- | --- | --- |
| R101 | 任意时间精度的数据库（毫秒、微秒、纳秒），都支持 PK | 接受 |
| R102 | 普通表和超级表都支持 PK | 接受 |
| R103 | PK 只能设置为表的第二列 | 接受 |
| R104 | 存在 PK 时，表的非标签列数目必须大于等于 3 个 | 接受 |
| R105 | PK 支持 uint64、int64、varchar、nchar 四种类型，不支持其他类型 | 接受 |
| R106 | PK 不允许增加、删除、修改列名 | 接受 |
| R107 | 在显示表创建语句时（show create table），PK 能够显示 primary key 关键字 | 接受 |
| R108 | 在获取表结构信息时（describe tbname），PK 能够显示 primary key 关键字 | 接受 |

### 3.2 数据写入

| 需求编号 | **需求描述** | 研发确认 |
| --- | --- | --- |
| R201 | 在 insert 语句中 PK 的取值不可指定为 NONE 或者 NULL <quote-container> 以如下 schema 为例 create table t (ts timestamp, p int primary key, q int) - 行为正确 insert into t values(now, 0, 0) - 行为错误 insert into t values(now, NULL, 1) - 行为错误 insert into t (ts, p, q) values(now, NULL, 1) - 行为错误 insert into t (ts, q) values(now, 1) </quote-container> | 接受 |
| R202 | 使用 schemaless 写入时，会触发超级表创建、超级表字段增加的操作，这两类操作不支持创建和增加 PK 字段 | 接受 |
| R203 | 时间戳列值相同且 PK 列值相同的时候，更新数据 | 接受 |
| R204 | 时间戳列值相同且 PK 列值不同的时候，写入一行新的数据 | 接受 |
| R205 | 数据删除时，必须指定删除的时间范围，不能指定 PK 的值范围 <quote-container> 支持 delete from t where ts = '2023-12-21 14:57:18.958' 错误 delete from t where ts = '2023-12-21 14:57:18.958' and i = 1; </quote-container> | 接受 |
| R206 | 支持通过 stmt 绑定方式写入 | 接受 |
| R207 | Insert into select 语法中，如果查询结果包含重复时间戳，需要有确定性行为 | 接受 |

### 3.3 数据查询

| 需求编号 | **需求描述** | 研发确认 |
| --- | --- | --- |
| R301 | 投影查询的记录返回不保证任何数序，可通过 order by PK 指定 <quote-container> 以如下 schema 为例 create table t (ts timestamp, p primary key, q int) - insert into t values(13923892332, 0, 0) - insert into t values(13923892332, 2, 0) - insert into t values(13923892332, 1, 0) - insert into t values(13923892332, 3, 0) 执行 select * from t 时返回的记录列表 </quote-container> | 接受 |
| R302 | 投影查询可对 PK 列使用 CASE WHEN THEN 语句 | 接受 |
| R303 | 投影查询可对 PK 列使用 DISTINCT 关键字，也可对重复时间戳的 timestamp 列使用 distinct，返回结果要去除重复值 | 接受 |
| R304 | WHERE 条件可以使用 PK 列进行比较，也可以使用 timestamp 列进行比较（>、>=、=、<=、<），返回同一时间戳的多条 PK 值不同的记录 | 接受 |
| R305 | GROUP BY 子句可以使用 PK 列 | 接受 |
| R306 | PARTITION BY 子句可以使用 PK 列 | 接受 |
| R307 | 在对子表或超级表进行关联查询时，不要求 PK 列有对应的等值关系 当左表和右表的同一时间戳的 PK 列存在多个值时，返回笛卡尔集 | 接受 |
| R308 | 支持通过 UNION ALL 字句把多个有 PK 列的结果集混合在一起，不去重 | 接受 |
| R309 | 嵌套查询可以使用 PK 列，在外层查询中的行为无限制 | 接受 |
| R310 | 函数在有无 PK 列时需保持逻辑上的一致性，例如 count 能够区分重复时间戳但 PK 不同的记录，用户手册中要说明行为，标红色的需重点说明 **数据函数**：ABS、ACOS、ASIN、ATAN、CEIL、COS、FLOOR、LOG、POW、ROUND、SIN、SQRT、TAN **字符串函数**：CHAR_LENGTH、CONCAT、CONCAT_WS、LENGTH、LOWER、LTRIM、RTRIM、SUBSTR、UPPER **转换函数**：CAST、TO_ISO8601、TO_JSON、TO_UNIXTIMESTAMP、TO_CHAR、TO_TIMESTAMP **时间和日期函数**：TIMEDIFF、TIMETRUNCATE **聚合函数**：APERCENTILE、AVG、COUNT、ELAPSED、LEASTSQUARES、SPREAD、STDDEV、SUM、HYPERLOGLOG、HISTOGRAM、PERCENTILE **选择函数**：BOTTOM、FIRST、INTERP、LAST、LAST_ROW、MAX、MIN、MODE、SAMPLE、TAIL、TOP、UNIQUE **时序数据特有函数**：CSUM、DERIVATIVE、DIFF、IRATE、MAVG、STATECOUNT、STATEDURATION、TWA - APERCENTILE：t-digest 算法对于输入数据顺序敏感 - LEASTSQUARES：重复时间戳情况下的拟合结果 - SPREAD：窗口的时间范围为 0 的场景 - STDDEV：窗口的时间范围为 0 的场景 - HYPERLOGLOG：窗口的时间范围为 0 的场景 - HISTOGRAM：窗口时间范围为 0 的场景 - FIRST、LAST、LAST_ROW：与数据顺序有关，尤其是在指定时间范围后的最新数据查询时，不能产生不确定的行为 - INTERP：线性填充策略下，当插值窗口的时间范围为 0 时可能导致分母为 0 - TAIL：offset_rows 与数据顺序有关 - UNIQUE：与数据顺序有关 - CSUM：与数据顺序有关（用户原始需求提到此函数） - DERIVATIVE、DIFF：可能返回时间范围为 0 的窗口，且和数据顺序有关 - IRATE：考虑时间范围时间为 0 的窗口 - MAVG：与数据顺序有关 - STATECOUNT、STATEDURATION：数据顺序与结果关系密切 - TWA ：关注分母为 0 的数据行为（用户原始需求提到此函数） - ELAPSED：将会产生时间范围为 0 的时间窗口 | 接受 |
| R311 | 支持对 PK 列进行 count(distinct ...) 操作 | 测试 |
| R312 | 为 PK 列增加一个伪列名称，例如为 _c1 | 测试 |
| R313 | 可在 PK 列中使用 UDF，尽管从原理上看 UDF 不需要做什么改动，但需设计相关的测试用例 | 测试 |

## 4. 性能需求

为了更好的描述性能需求，用下表描述测试场景

| 类别 | 明细 |
| --- | --- |
| 测试环境 | - 不需特殊的硬件环境，两台普通的 2 核 4GB 内存机器即可 - 操作系统应为常见 Linux，例如 Ubuntu 2004 |
| 数据库参数 | - 纳秒数据库 - vgroups 为 1 - last 内存设置为 16K，表示刚好不用换入换出 - 其他参数默认 - taosd 和 taosc 不打开任何模块的日志 |
| 写入模式 | - native 方式写入 - 写入程序和 taosd 部署在不同机器上 - 线程数目为客户端机器核数的 2 倍 - Interlace 和 batch 模式都需要测试 |
| 查询模式 | - 查询时等待数据写入完成后进行 - 使用多线程查询，线程数目为客户端机器核数的 2 倍，每个线程进行 5 轮查询 - 投影查询读取超级表全部数据，读取结果不写磁盘 - Last 查询采用 group by 读取每个子表的最新数据，读取结果不写磁盘 - 在 flush database 命令前后，分别测试查询性能 |
| 压缩比 | 使用 flush database 命令之后，统计磁盘文件大小 |
| 数据规模 | - 1000 个子表 - 每子表 100,000 条记录 |
| 超级表标签列 | 1 个标签列，类型为 int32，取值递增 |
| 超级表数据列 | 3 个数据列，类型为 timestamp，int64（pk），float - timestamp 列：从 T 开始，每 N 行增加 1 秒作为基准值，当 N = 2 时，分布为 T、T, T+1、T+1、T+2、T+2、…… - int64 列，从 0 开始，取值每行增加 1 - float 列，从 0 开始，取值每行增加 1 |
| 场景定义 | - 场景 A：定义 PK 列， timestmap 列的取值与基准值相同 - 场景 B：未定义 PK 列， timestmap 列的取值在基准值基础上，额外增加 M 纳秒（M 为 int64 列的取去值） |
